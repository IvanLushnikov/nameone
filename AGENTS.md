### Сборка виснет на Node 23, работать надо на Node 22 (01.10.2026)

**Правило:** в nameone `npm run build` и `next dev` **на Node 23 зависают намертво** —
0.1% CPU, лог обрывается на строке «Creating an optimized production build», ни ошибки,
ни таймаута. Ждать бесполезно: проверено дважды, по 90+ секунд без единого записанного файла.

Причина зафиксирована в самом репозитории — `.github/workflows/deploy.yml:24`:
`node-version: 22  # Локально Next 14.2 + Node 23 виснет на M2 Air → собираем в CI`.
То есть это известная проблема, а не регрессия в коде.

**Как чинить (Node 22 установлен в Homebrew рядом с дефолтным):**
```bash
cd /Users/ivanlusnikov/Documents/nameone
export PATH="/opt/homebrew/opt/node@22/bin:$PATH"
export NEXT_TELEMETRY_DISABLED=1
node -v          # должно быть v22.23.3, а не v23.11.0
npm run build
```

**Почему это важно запомнить:** симптом выглядит как «завис мой код» или «перебор
страниц статического экспорта», и легко потратить 20 минут на ложную диагностику
таксономии. Лечится только сменой версии Node. Аналогичная по симптому зависание
`vitest` на этом же проекте (старт > минуты, ноль вывода) лечится флагом
`--environment node` для тестов, которым не нужен DOM.

**Смежное:** дефолтный `node` в этой машине — 23.11.0, поэтому `PATH` надо
переопределять явно в каждой сессии, где запускается build.

### Lock-файл генерировать тем же npm, которым ставит CI (13.10.2026)

**Ситуация (обновление зависимостей в nameone).** Сгенерировал `package-lock.json`
для backend локальным npm 11. Локально `npm ci` проходил, typecheck и все 707 тестов
были зелёные. CI падал:

```
npm error `npm ci` can only install packages when your package.json and
package-lock.json ... are in sync.
npm error Missing: @cloudflare/workers-types@4.20260702.1 from lock file
```

**Причина.** Обе версии пишут `lockfileVersion: 3`, поэтому номер версии
ничего не подсказывает. Расходится само разрешение: npm 10 требует в lock
запись для транзитивного peer-требования, npm 11 её не пишет. CI гоняет
Node 22 → npm 10, разработчик может иметь что угодно.

**Как применять.**

1. Перед тем как доверять локальному `npm ci`, узнать версию npm в CI —
   обычно это `node-version` в `actions/setup-node`. Не угадывать.
2. Генерировать lock ТЕМ ЖЕ npm: `npx npm@<версия-из-CI> install`.
   Для Node 22 это npm 10.
3. Проверять на чистой копии ветки (`git worktree add --detach`), а не в
   рабочей копии: там `node_modules` уже стоят и маскируют расхождение.
   Именно чистая копия воспроизвела падение, рабочая — нет.
4. Отличать две разные ошибки npm: `ERESOLVE` (конфликт peer, нужен
   апгрейд или отказ) и `edgesOut: Cannot read properties of null` (баг npm
   при резолве). Второе лечится сменой версии npm, первое — только правкой
   зависимостей.

### Перед обновлением зависимостей: `npm ci --dry-run`, а не `npm install` (15.10.2026)

**Главное правило.** `npm install` локально **прощает** конфликт пиров (за警告
предупреждением), а `npm ci` в CI его **отвергает**. Поэтому проверять надо так:

```
npm ci --dry-run --no-fund
```

в каждом пакете перед `git push` в `main`. Именно так обнаружилось, что zod 4 в
бэкенде конфликтует с `openai@4.104` (peer `zod@^3.23.8`) — локально стоял
зеленый, а CI упал бы. Поддержка zod 4 появилась только в `openai` 6.x/7.x,
то есть за zod 4 пришлось бы заплатить скачком через три мажора LLM-SDK.

**Считать CI отдельно от локали.** CI собирает `npm ci` на Node 22 (npm
10.9.x), локально Node 23 + npm 10.9.2/11. Расхождение версий npm — источник
граблей, не приговор.

**Грабли, собранные 15.10.2026 (nameone):**

- **npm 10.9.2** падает на пирах vitest 4: `Cannot read properties of null
  (reading 'edgesOut')` в arborist `#loadPeerSet`. Лечится установкой через
  `npx npm@11`. Чистка node_modules и lock не помогает — виноват сам npm.
- **npm 11 блокирует install-скрипты** (`allowScripts`): без одобрения не
  ставятся бинарники `workerd` и `esbuild`, и рантайм Workers не стартует.
  Лечится `npx npm@11 install-scripts approve workerd esbuild` + `rebuild`.
- **jsdom 30 ломает vitest**: «Failed to start forks worker / Timeout waiting
  for worker to respond», не выполняется ни один тест. Проверено изолированно:
  с jsdom 27 тот же файл проходит за 0,6 с. Не обновлять без проверки.
- **vitest 5 → Vite 8 → rolldown/oxc**: опция `esbuild` в конфиге МОЛЧА
  игнорируется, и все `.tsx` падают с «Unexpected JSX expression». Настройка
  переезжает в `oxc: { jsx: { runtime: 'automatic' } }`. Не ошибка, а тишина.
- **vi.fn() без аргументов** в vitest 4 даёт `Mock<Procedure | Constructable>`,
  который TypeScript не считает вызываемым. Тип аргумента задавать руками.

**Порядок работы:** сначала чини проверяющий инструмент, потом обновляй.
Здесь бэкенд-тесты не выполняли НИ ОДНОГО теста (`npm test` падал на старте),
и пока это не починено, принимать любое обновление нельзя — нечем проверять.
Обновление без зелёной проверки = слепое.

**Правило для прогонов:** один показатель за раз. Менять пакеты пачкой и
получать общий отказ бессмысленно: сначала vitest 5, потом jsdom 30 — каждый
раз выяснялось, что виноват второй, а первый наоборот был нормален.

### Окружение УчЛиста без ключей — живые прогоны генерации невозможны (13.10.2026)

В окружении УчЛиста (backend `backend/.dev.vars`) ключи **пустые**: `POLZA_API_KEY`,

Из-за этого локально нельзя выполнить:

- PPTX и ОГЭ/ЕГЭ (тариф «Плюс»).

Проверить при этом МОЖНО и нужно: юнит-тесты промптов и валидаторов, типы,

сгенерированный DOCX (собирается локально без сети), свёрку чисел главной с

**Как применять.** Перед тем как обещать прогон «на живых листах», проверить

записать гейт как `ABANDON` с причиной, чем написать «проверено» без

генерации.

### Стенд на локальном порту может слушать и при этом ничего не отдавать (15.10.2026)

**Правило проверки.** «Порт слушает» ≠ «стенд работает». Всегда проверять
реальным запросом и смотреть на код ответа:

```
curl -s -o /dev/null -w "HTTP %{http_code}\n" http://127.0.0.1:8769/
```

Код `000` при живом `lsof -nP -iTCP:8769 -sTCP:LISTEN` — это тот самый случай.

**Что происходит технически.** macOS TCC закрывает папку в `~/Documents`.
Python-сервер, запущенный из неё, продолжает слушать сокет, но при первом
же запросе падает в обработчике (`PermissionError: [Errno 1] Operation not
permitted` при `os.getcwd()` в `http.server`) и рвёт соединение. Клиент видит
`Connection reset by peer`, в браузере — пустая страница. Снаружи выглядит
как «сервер поднялся».

**Как обнаружить.** Лог сервера: `nohup python3 serve.py --port PORT > /tmp/x.log 2>&1 &`,
потом читать лог, а не только проверять порт.

**Почему это дорого.** Ссылку `http://127.0.0.1:8769/` уже отправили коллегам
как «прототип готов». Она открывается только у того, кто её запустил, —
у всех остальных `127.0.0.1` указывает на их собственный компьютер.
Для раздачи кликабельного прототипа наружу отдавать **архив с инструкцией
запуска**, а не локальную ссылку.

**Правильный порядок.** Копию проекта держать в доступной папке (`~/имя-проекта`),
`serve.py` запускать оттуда, а архив для коллег собирать в `~/workspace/output`.
## Тесты и локальный стенд

### E2E-проверка Next.js через Playwright: ждать `load`, а не `domcontentloaded` (01.10.2026)

**Правило:** при `page.goto(..., { waitUntil: "domcontentloaded" })` Playwright успевает
кликнуть по серверному HTML раньше, чем React подвесит `onClick`. Клик визуально проходит,
обработчик молча не срабатывает — и вывод «фича сломана» ошибочен.

**Как правильно:** `waitUntil: "load"`, плюс у клиентской навигации закладывать таймаут
с запасом (в `next dev` на слабой машине загрузка чанка занимает минуты).

**Проверено 01.10.2026 в nameone:** два прогона подряд давали пустой `localStorage` и H1
страницы логина, хотя обработчик был корректен. Третий прогон с `waitUntil: "load"`
сразу показал запись профиля. Диагностика: логировать `localStorage` сразу после клика
и собирать `pageerror` — они показывают, что JS вообще не падал.

### UI-проверку гонять только в одной команде с dev-сервером (02.10.2026)

**Правило:** `pkill -f "next"` в bash-команде убивает **сам шелл** —
у него в командной строке есть строка `next dev`, и `-f` матчит полную
командную строку. Симптом: команда «успешно» отрабатывает, но вывод
обрывается на середине, следующие шаги не выполняются. Убивать по PID
(`kill $SRV`) или по точным паттернам `next-server` / `next/dist/bin`.

**Почему сервер и проверку надо запускать вместе:** dev-сервер, поднятый
как `nohup … & disown` внутри фоновой задачи, умирает вместе с задачей —
процесс-родитель уносит всю группу. Три попытки подряд давали
`ERR_CONNECTION_REFUSED` на всех страницах при живом на вид логе.

**Рабочий рецепт (проверен, 369 + 57 проверок зелёные):**
```bash
cd /Users/ivanlusnikov/Documents/nameone
export PATH="/opt/homebrew/opt/node@22/bin:$PATH"
export NEXT_TELEMETRY_DISABLED=1
npx next dev -p 3114 > /tmp/dev.log 2>&1 &
SRV=$!
until grep -q "Ready in" /tmp/dev.log; do sleep 5; done
npx tsx scripts/verify-ui-dev.ts        --base=http://127.0.0.1:3114
npx tsx scripts/verify-artifacts-ui.ts  --base=http://127.0.0.1:3114
kill $SRV
```

**Каскад 404 ≠ сломались данные.** Если в UI-проверке первый запрос даёт 500,
а дальше идут подряд 404 — упал dev-сервер. Проверять
`npx tsx scripts/check-taxonomy.ts`: аудит чистый = дело в сервере.
На этом я почти объявил регрессию в английском 10 классе, хотя данные были целы.

**Ещё:** `.next` в состоянии 0 байт (после убитых сборок) вешает dev-сервер
на `✓ Starting...` навсегда. Лечится удалением `.next` — тогда Ready за ~800 мс.
И на загруженной машине (opencode жрёт CPU) `verify-artifacts-ui.ts` не успевает —
есть флаг `--only=N`.

### Не запускать 4+ воркеров, каждый из которых гоняет tsc/vitest одновременно (02.10.2026)

**Правило:** на nameone (MacBook Air M2, троттлит) 4 параллельных воркера,
каждый из которых запускает `tsc --noEmit` и `vitest`, дают load average 15–19
и 40+ процессов. `vitest` виснет на старте (пустой вывод, только `RUN v3.2.7`),
`tsc` идёт 5+ минут. Воркеры тратят по 3–4 попытки на одну проверку и
в итоге не получают результата.

**Как правильно:**
- Воркерам в брифе явно писать: «НЕ запускай vitest / tsc / build.
  Проверки прогоняет оркестратор после завершения всех воркеров».
- Оркестратору — проверять факт через `npx tsx` с одноразовым скриптом в `/tmp`,
  а не через vitest. Это занимает секунды и не требует пула воркеров:
  импорт мока напрямую, проверка инвариантов, `console.log` результата.
- `tsc` и `vitest` — строго последовательно, одно с другим, не параллельно.
- Для тестов, которым не нужен DOM, помогает `--environment node`.
- В tsx-скрипте нельзя top-level `await` — формат cjs, оборачивай в `main().then()`.

**Проверено 02.10.2026 на nameone:** 4 воркера (Карточки, Материалы, Банк
материалов, Фото-по vision) — ни один не смог прогнать тесты; все честно
отчитались «не выполнено». После команды «только код» все закончили за
15 минут. Оркестратор проверил их работу через tsx.

**Побочный урок — про тестовые данные:** проверяя чужой код, сначала
убедись, что слага тем, которые ты передаёшь в мок, реально существуют
в таксономии. В `Grade` поле называется `num`, не `grade`. Прежде чем писать
«у воркера баг, возвращается 0 элементов», проверь на настоящем слаге
из `getGrade(subject, num).topics[].slug`. Мои выдуманные слаги дали ложную
диагностику «моки сломаны», хотя на настоящих слагах всё работает верно.

### Делегация воркерам: файлы, не попавшие ни в чей список, молча остаются без правок (01.10.2026)

Правило (проверено 01.10.2026 на nameone, 6 воркеров, ~40 правок).

При разбиении задачи на N воркеров по непересекающимся файлам обязательно
**сверь список затронутых файлов плана с фактическим `git status` после**:
всё, что есть в плане, но не попало ни в один список воркеров, не будет
сделано вообще — и никто об этом не сообщит, потому что каждый воркер честно
отчитается о СВОИХ пунктах.

**Как поймать:** после волны — `git status --short` + сверка с разделом
«Затронутые файлы» плана. Дешевле, чем отправлять фидбек-цикл заново.

**Почему так выходит:** оркестратор раздаёт работу по «горячим» файлам и
забывает про файлы, которые в плане есть, но не попали ни в один список.
На nameone так потерялась правка `PresetGrid.tsx:319` («домашка» в тексте
пресета) — единственный пункт жалобы, который не закрылся.

**Второй класс пропуска — отклонения «по нельзя трогать»:** воркер честно
пишет «файл принадлежит параллельному агенту, не стал менять». Такие пункты
надо вычитывать отдельно и закрывать самому, когда параллельная работа
успокоится.

### Тест-канарейка на текущий баг надо переводить в тест на исправленное состояние (nameone)

Когда тест вскрывает баг, но сформулирован как «зафиксировать текущее
сломанное поведение» (канарейка), он **упадёт сразу после починки** — и
будет выглядеть как регрессия. Ловит в тупик.

Правильный переход: переписать в форму «проверяю, что поведение ИСПРАВЛЕНО».
Канарейка — не результат, а способ обнаружения; результат — регрессионный
тест на новую правдину.

На nameone так было с тостами: тест утверждал, что `<Toaster />` стоит
соседом с `<main>` (т.е. фиксировал баг). После починки упал — и это был
правильный сигнал, а не сломанный тест.

### Перед тем как отчитаться «всё готово» — сверь критерии плана с кодом сам (02.10.2026)

Даже при зелёных тестах и честных отчётах воркеров остаются пропуски. Проверка
`grep`/`sed` по самому плану ловила: забытое слово «домашка», захардкоженные
цены мимо `plans.ts`, ложные срабатывания при grep по подстрокам
(«постиндустриальное» содержит «триал» — проверять надо по границам слова).

Дешёвые команды, которые стоит прогнать перед «готово»:
`grep -rn` по запрещённым словам из плана, сверка `git status` со списком
затронутых файлов, независимый прогон ключевой логики через `npx tsx` с
однострочным скриптом в `/tmp` (не создавая файлов в репозитории).

**Самое частое место, где правка «уже есть», — а в другом файле та же ошибка
живёт:** проверять только файлы, которые отдавал воркерам, недостаточно.
На nameone критерий «правильные окончания» был закрыт в `Stats.tsx`, а через
два шага верификатор нашёл «21 предметов» в SEO-заголовке и description новой
страницы `/subject` и в `Subjects.tsx`, который вообще никому не достался.
**Ищи по всему `src/`, а не по списку файлов плана.** Особенно:
title/description/OG-строки (в ту самую ошибку уезжает SEO),
страницы, созданные «по пути», и любые файлы вне первоначального разбиения.

И второе: тест, который ищет плохое слово регуляркой по исходнику, сначала
съест **аргументы самого исправляющего вызова** (`plural(21, "предмет",
"предмета", "предметов")` содержит «предметов»). Вырецай вызовы `plural(...)`
целиком перед проверкой, иначе тест валится на правильном коде.

**И третье, самое коварное: `\b` в JavaScript — это ASCII-граница слова.**
`\bДомашка\b` и `/\bтем\b/` **никогда не сматчатся**, потому что кириллица не
входит в `\w`. Тест с таким паттерном всегда зелёный и не защищает ничего,
при этом выглядит строгим. Для русских слов используй явные границы:
`(?<![а-яёa-z])Домашка(?![а-яёa-z])` и `(?![а-яёa-z])` для конца слова.

**Обязательная самопроверка теста-ищейки.** К отрицательным
`expect(...).not.toMatch` добавляй позитивный блок с заведомо плохим кодом и
убеждайся, что паттерн его ловит. Иначе получаешь «вакуумный» тест: 100%
зелёный, нулевой ценности. Так поймали «21 предметов» в SEO-строках и
«Домашка» в DOCX-генераторе.

### Регулярки по русскому тексту в проверках — две ловушки (13.10.2026)

Проверочные скрипты по русским текстам дважды обманули на проекте УчЛист,
и обе ошибки выглядели как «мой контент неправильный», а на самом деле был неправ мой чекер.

**1. `\w` и `\b` в JS не матчат кириллицу.** `\w` = `[A-Za-z0-9_]`. Регулярка
`/коммерческ\w*\s+лицензи/i` не нашла «коммерческую лицензию» в файле, который её
содержит. Нужен явный класс: `[а-яё]*`.

**2. Голое вхождение цифры — не проверка факта.** Проверка «опубликована ли цена
3000 ₽ тарифа Школа» искала просто `3000` и срабатывала на «до 3000 рабочих
листов» — это норма другого тарифа. Нужно привязываться к смыслу: цена = число
рядом со знаком валюты (`/3000\s*(?:₽|руб)/`), а не просто число.

**Как применять.** Пишу проверку по русскому тексту — сперва прогоняю её на
известном подходящем куске текста и убеждаюсь, что она его НАХОДИТ (и на
заведомо неподходящем, что не находит). Иначе «0 найдено» неотличимо от «совпало
не там». Тот же приём, что с негативным контролем гейта: отсутствие сигнала надо
подтверждать положительным примером.

### В пуле vitest-workers нет `process.env` — окружение живёт в биндингах (nameone)

В backend УчЛиста тесты идут под `@cloudflare/vitest-pool-workers`.
**`process.env` там пуст** — не «почти пуст», а именно недоступен: ни
`process.env.POLZA_API_KEY`, ни любой флаг из командной строки.

Это стоило трёх отдельных поломок за один день, и все три выглядели одинаково
молча:

1. Ключ провайдера читался из `process.env` — тест «проходил», но реальной
   генерации не было.
2. Флаг новой стадии `PLAN=1` в командной строке — стадия не включалась, лог
   врал «stage disabled».
3. Фильтр подмножества листов `LIVE_ONLY` — прогонял все шесть листов вместо
   одного, и на почти пустом балансе это съедало деньги до того, как
   становилось заметно.

**Как применять.** Всё, что должно попасть в код под воркером, читать из:

- объекта `env`, который приходит аргументом в `generateWorksheet(args, env, db)`;
- либо `import { env } from "cloudflare:test"` в тестах.

Значение для `.dev.vars` пишем **без кавычек**: `PLAN=1`. С кавычками
приходит строка `"1"` вместо `"1"` — и сравнение молча даёт «выключено».

**Отдельное правило для тестов:** окружение собирать разворотом всего
объекта, а не перечислением полей:

```ts
const FAKE_ENV = { ...(workerEnv as unknown as Record<string, unknown>), /* … */ } as unknown as Env;
```

Перечисление полей — это то место, где забывается ключ, и ошибка выглядит как
«стадия не работает», хотя не работает совсем другое.

**И проверяй, что фильтр сработал, а не что он есть.** Прогон должен
стартовать один тест вместо шести; если стартуют шесть — значение не дошло.

### Проверять деплой по чанку, а не по DOM первого экрана (12.10.2026)

**Ситуация (УчЛист).** Задеплоил переработку флоу фото-проверки,
run зелёный, `Deployment complete! https://efe81516...pages.dev`. Проверил на
проде: новых текстов нет, `data-testid` старые. Четыре раза подряд пришёл к
выводу «код не попал в сборку» — и был неправ.

**Что оказалось:**

1. **Маркеры лежат не в тех чанках, что перечислены в HTML.** Next грузит
   компоненты лениво; список из `<script src>` покрывает только верхний уровень.
   Нужен файл-чанк. Локально: `grep -rl "<уникальный маркер>" out/_next/static/chunks/`
   (рекурсивно! каталог `app/` внутри) → берём ИМЯ файла, и это имя отличается
   между локальной сборкой и продом (хэш отличается из-за `NEXT_PUBLIC_*`).
   Дальше качать чанк с прода по ЭТОМУ имени: `curl https://site/_next/static/chunks/<имя>`.
2. **DOM-проверка смотрела не тот экран.** `/constructor?photo=1` открывает
   PhotoCheckEntry («Сделать лист и проверить фото» / «Взять лист из истории»),
   а не PhotoCheckPanel с полосой шагов. Панель живёт за другим шагом мастера.
   Вывод «старая версия» был следствием открытой не той страницы.

**Как применять.** Прежде чем сказать «не задеплоились»:

1. Взять уникальную строку из своего кода (не из общего UI) и найти чанк
   **локальной** сборки — `grep -rl` по всему `out/_next/static/chunks`,
   с подкаталогами.
2. Вытащить имя файла, скачать этот файл с прода по тому же пути, найти там
   маркер. Если маркер есть — деплой состоялся, дальше проверять поведение.
3. Только если маркера нет в чанке прода — тогда деплой реально старый.
4. DOM-проверять тот экран, куда попадаешь в реальном флоу, а не первый
   рендер страницы; при необходимости пройти кликами до нужного состояния.

### Перед деплоем сливать `origin/main` — в main приходят прод-фиксы (12.10.2026)

**Ситуация (выкатка ТЗ-24).** Ветка
`feature/tz-23-password` копилась неделями, пока `main` ушёл вперёд на пять
коммитов с ПРОД-фиксами: перенос бэка на `api.uchlist.ru`, cookie на
`.uchlist.ru` вместо хоста воркера (иначе Safari/Firefox молча отдавали 401),
серверный выход из аккаунта. При слиянии конфликтовали четыре файла.

**Почему это важно.** Тихой выкатки без слияния не было бы: ветка содержала
код, который затирает прод-фиксы, а фронт собирался бы из main. То есть
деплой прошёл бы успешно, а логин сломался бы у живых учителей.

**Как применять.**

1. Перед деплоем всегда `git fetch origin main` и смотреть
   `git log HEAD..origin/main`. Пустой список — только тогда выкатывать.
2. `git merge-tree --write-tree --name-only origin/main HEAD` проверяет
   конфликты БЕЗ изменения дерева — дешевле, чем `git merge` вслепую.
3. Конфликт в комментарии — обе стороны описывают одно и то же, берётся
   подробная. Конфликт в коде — сначала проверять, не поглощена ли чужая
   логика уже моей (в этом размере общий `setSessionCookie` уже умел
   `SESSION_COOKIE_DOMAIN` + SameSite=Lax, то есть фикс main был не нужен).
4. Если у main вариант без таймаута, а у меня с тайм��утом — оставлять свой:
   перед слиянием прочитать, ЧТО именно чинит чужой коммит.
5. После слияния — обязательно полный прогон тестов обеих сторон. На этот раз
   прошло 684 бэкенда и 1079 фронта.

### Короткий текст в `out/*.html` не доказывает, что страница — заглушка (14.10.2026)

На `/journal` статический экспорт отдавал 17 знаков («Открываем журнал…»). Я назвал это заглушкой, отправил агента переделывать страницу под блог и предложил заменить заглушку редиректом. Агент проверил и остановился: эти символы — fallback внутри клиентской страницы, а сама `/journal` рабочая функция (журнал проверок по фото, ТЗ-19), с бэкендом `backend/src/routes/journal.ts` и шестью входящими ссылками из интерфейса, включая `?check=<id>`. Удаление сломало бы продукт.

**Правило.** Прежде чем назвать страницу заглушкой по объёму текста в собранном HTML: grep по `Suspense`/`loading` в её исходнике и обратные ссылки (`grep -rn "<route>" src/`) плюс маршрут на бэкенде. Три вопроса: есть ли `loading.tsx`/`Suspense`, кто на страницу ссылается, есть ли API за ней. Клиентский рендер на SSR-экспорте почти всегда даёт короткий текст в статике — это артефакт сборки, а не пустая страница.

**Почему важно.** Ошибка в одну сторону: назвать живое пустым и предложить снести работающую функцию. Ошибка в другую: заблокировать готовую работу, потому что «страница пустая». Оба раза цена — сломанный продукт или потерянные часы.

**Как применять.** Оценку «страница пустая» давать только после проверки ссылок и API, и в отчёте писать, чем она проверена. Доверять агенту, который это перепроверил, а не заменять его вывод своим первым впечатлением.

### `wrangler` зависает на этой машине — работать с Cloudflare через REST API (02.10.2026)

Проверено на nameone: `npx wrangler ...` и даже `wrangler --version` висят
120+ секунд без единого вывода, в том числе с `CI=1 WRANGLER_SEND_METRICS=false`.
Проблема именно в CLI, не в сети: `curl https://api.cloudflare.com` отвечает
за 0,3 с.

**Обходной путь — REST API Cloudflare, тот же самый, что использует wrangler:**

```bash
set -a && . ./.env && set +a   # CLOUDFLARE_API_TOKEN, CLOUDFLARE_ACCOUNT_ID

# Список D1-баз
curl -s -H "Authorization: Bearer $CLOUDFLARE_API_TOKEN" \
  "https://api.cloudflare.com/client/v4/accounts/$CLOUDFLARE_ACCOUNT_ID/d1/database"

# Выполнить SQL (миграция)
curl -s -X POST -H "Authorization: Bearer $CLOUDFLARE_API_TOKEN" \
  -H "Content-Type: application/json" \
  "https://api.cloudflare.com/client/v4/accounts/$CLOUDFLARE_ACCOUNT_ID/d1/database/$DB_ID/query" \
  -d '{"sql":"ALTER TABLE payments ADD COLUMN period TEXT NOT NULL DEFAULT '"'"'monthly'"'"'"}'

# Проверить, какие секреты заданы у воркера (только ИМЕНА, значения не читаются)
curl -s -H "Authorization: Bearer $CLOUDFLARE_API_TOKEN" \
  "https://api.cloudflare.com/client/v4/accounts/$CLOUDFLARE_ACCOUNT_ID/workers/scripts/$WORKER/secrets"
```

**Зачем стоит проверять секреты перед любым аудитом прода.** Запрос
`/workers/scripts/<name>/secrets` отдаёт только имена переменных. Эта проверка
за 30 секунд показала, что на проде не заданы `RESEND_API_KEY` и
`YOOKASSA_*` — то есть критическая дыра со входом была активна не
теоретически, а прямо в бою, и её невозможно было увидеть в коде или в
репозитории. Код и git тут ничего не говорят, единственный источник правды —
состояние воркера в Cloudflare.

при load average >20 проваливается по таймауту в 300 с, хотя обычно тот же

### Статус в доке ≠ состояние кода (14.10.2026, УчЛист)

На вопрос «полный список незакрытых задач» я собрал статусы из 32 файлов `docs/tz/` — и они соврали в 8 случаях: ТЗ-11/12/13/15/17 писали «код не написан»/«черновик», а фичи были готовы (`backend/src/routes/f06.ts`, `interactives.ts`, `f07.ts`, промпт `interview-questions`, каталог из 150 материалов). ТЗ-25 писало «🔴 Не начато» — при этом в `main` уже лежал коммит `0c7f85a fix(tz-25)`.

**Как применять.** Строка `> **Статус:**` в доке — это утверждение, а не факт. Прежде чем назвать задачу нереализованной, проверять по коду минимум тремя способами: есть ли маршрут (`src/app/<путь>`, `backend/src/routes/<файл>.ts`), есть ли промпт **и ссылка на него** из реального места (`grep -rn "prompts/<имя>" src` — файл промпта без импорта это мёртвый код), есть ли элемент в интерфейсе (тип в списке конструктора, кнопка). Отдельно: маршрут без подключённого промпта = заглушка; промпт без маршрута = мёртвый код.

**Ищи в коде факт с честным откатом.** Например, `isImageGenAvailable()` жёстко возвращает `false`, а тип помечен в `NOT_YET_IMPLEMENTED_TYPES` — это честный откат, а не баг. Не записывать в список открытых то, что команда осознанно не сделала и показала пользователю.

**Плюс проверка git:** старые ветки с «+N коммитов» часто не содержат незакрытой работы — коммиты уже влиты squash'ом. Прежде чем считать ветку потерянной, проверять конкретный фикс по содержимому в `main`, а не по `git diff main..branch` (он показывает тысячи строк из-за отставания ветки).

### Визуальный аудит: снимай живой прод, а скриншот без прокрутки врёт (02.10.2026)

Правило (выведено на nameone): для аудита дизайна не нужно собирать
проект. Бери URL живого деплоя и снимай Playwright по нему — минуты вместо
сборки. Скрипт держи **внутри репозитория** (например `./.tmp-shoot.mjs`),
иначе ESM-импорт `playwright` из `/tmp` не резолвит node_modules и падает
с `ERR_MODULE_NOT_FOUND`.

**Главная ловушка:** `page.screenshot({fullPage:true})` даёт ложную
дыру в дизайне. Элементы с появлением по скролту (IntersectionObserver,
`whileInView`, `opacity-0` до появления) в момент съёмки ещё скрыты — на
картинке получаются огромные белые провалы между секциями, которых на
сайте нет.

**Как не выдумать баг:** сначала диагностика в DOM, потом выводы. Проверь
`document.body.scrollHeight`, число `<svg>`/`<img>` в каждой `<section>`
и их `getBoundingClientRect().width/height` — если SVG есть и размеры
ненулевые, пустота на скриншоте = артефакт анимации. Затем пересними с
пошаговой прокруткой (`window.scrollTo` + пауза 500–700 мс, скриншот
каждые 800 px) — провалы исчезают.

**Что ловится только так:** обрезанные тексты в карточках сетки, разная
высота карточек, подписи вроде «21 предметов», обрезанные чипы
(«Информат…»), рассинхрон чисел между блоками одной страницы, ошибки
гидратации в `pageerror` (React #418/#423/#425 = mismatch серверного и
клиентского рендера).

**Ещё:** `firecrawl_scrape` со `formats:["screenshot"]` может вернуть
подписанный URL, который не скачивается (403 SignatureDoesNotMatch) — не
трать на него время, если Playwright уже есть. И сначала проверяй, что
домен вообще резолвится: `dig +short <domain> A`. В nameone
`rabochielisty.ru` не резолвился, и это оказалось самой дорогой находкой
ревью — весь SEO-слой вёл на несуществующий хост.

### Защита не должна зависеть от флага, который может быть врён (02.10.2026, nameone)

Главный урок аудита nameone.

умолчанию при отсутствии флага везде одинаково: запрет.

### Проверка шрифтов в статической сборке: ловушка хешированных имён (02.10.2026)

Проверяя, доедут ли шрифты KaTeX в `out/`, легко получить ложный вывод
«шрифты не подключены».

**Симптом.** `grep -oh "KaTeX_[A-Za-z-]*\.woff2" out/_next/static/css/*.css`
возвращает **0 совпадений**, хотя сборка исправна и шрифты на месте.

**Почему.** Webpack хеширует имена файлов при сборке:
`KaTeX_AMS-Regular.a79f1c31.woff2`. Шаблон `[A-Za-z-]*` не покрывает
`a79f1c31` — точка и цифры обрывают совпадение.

**Правильно.** Разбирать сами `url(...)` из собранного CSS и сравнивать с
фактическим содержимым каталога:

```
const urls = [...css.matchAll(/url\(([^)]+)\)/g)].map(m => m[1].replace(/["']/g,"").trim());
const missing = urls.filter(u => !fs.existsSync(path.join(OUT, u.replace(/^\//,""))));
```

**Проверенные числа на nameone (02.10.2026):** 60 ссылок на KaTeX-шрифты в
`out/_next/static/css`, 60 файлов в `out/_next/static/media`, битых 0,
253 КБ woff2. Сборка `npm run build` — 83 секунды, 3 915 HTML-страниц.

**Почему это стоит автоматизировать:** состояние «страница открылась,
математика рисуется системным шрифтом» невозможно заметить глазами, но
реально ломает продукт. Тест `tests/integration/build-assets.test.ts` делает
логику проверки чистой функцией `checkBuild(outDir)` и проверяет её на
синтетически битой и синтетически хорошей фикстуре — иначе тест
неизбежно становится «вакуумным» (всегда зелёным).

### «Зелёно локально, красно в CI» — проверяй в изоляции, а не у себя (02.10.2026, nameone)

**Симптом.** Бэк-джоб CI падал с `Cannot find module 'tailwindcss'`, хотя
локально `npx vitest run` давал 350 зелёных тестов и `tsc` — 0 ошибок.

**Причина.** Джоб делает `cd backend && npm ci` — корневого `node_modules` там
нет. Vite при поиске `postcss.config` идёт ВВЕРХ по дереву и находит корневой
`postcss.config.mjs` от Next.js, а тот требует `tailwindcss`. Локально
tailwindcss резолвится из корневого `node_modules`, поэтому всё зелёное.
Тесты бэка не должны зависеть от того, что установлено в корне репозитория,
но зависели.

**Первый фикс не сработал.** Я поставил `css: { postcss: { plugins: [] } }`
в `vitest.config.ts`. В Vitest 2.1.9 (а в бэке он именно 2.x) опции `postcss`
нет — только `boolean` и `{ include, exclude, modules }`. Поддержка `postcss`
появилась в Vitest 3. Typecheck в CI упал раньше, чем дошли до тестов.
Плюс опция `css` влияет на обработку CSS-файлов, а не на сам поиск конфига —
даже будь она валидна, проблему бы не решила.

**Что сработало.** Свой пустой `backend/postcss.config.mjs` с `plugins: {}`.
Поиск находит его первым и до корневого конфига не доходит.

**Как проверить по-настоящему.** Не «у меня локально зелёное», а воспроизвести
условия CI:
```bash
cd backend && mkdir -p /tmp/ci-sim
tar --exclude=node_modules --exclude=.wrangler -cf - . | (cd /tmp/ci-sim && tar -xf -)
cd /tmp/ci-sim && npm ci --no-fund && npx vitest run && npx tsc --noEmit
```
Копия без родительского `node_modules` — и падение воспроизводится точно.

**Правило.** Джоб CI, который делает `cd <subdir> && npm ci`, надо проверять
в копии подпапки без родительского `node_modules`. Любой конфиг-файл,
который vite/postcss/eslint ищет вверх по дереву, обязан существовать и в
подпапке. Иначе «зелёно дома, красно в CI» будет повторяться.

### iCloud плодит дубли файлов в `.git` и ломает `fetch` (02.10.2026, nameone)

**Симптом.** `git fetch` падает с `fatal: bad object refs/stash 2` и
`did not send all necessary objects`. При этом `git ls-remote origin` работает
нормально — сеть и доступ в порядке, ломается именно локальная часть.

**Причина.** В `.git/refs/` и `.git/logs/refs/` лежали файлы с пробелом и
цифрой в имени: `stash 2`, `stash 3`. Git читает каждое имя в каталоге refs как
ref и падает на пробеле. Это та же болезнь, что уже ловили с `package 3.json`
и `build-manifest 3.json` в рабочем дереве.

**Как распознать быстро.** `git branch -a` печатает
`warning: ignoring ref with broken name refs/stash 2` — эти warnings и есть
диагноз. Команды вроде `git show`/`git diff-tree` по таким объектам виснут
намертво, поэтому «просто посмотреть stash» не получится.

**Как чинить.** Перед удалением сохранить содержимое файлов в ветки, чтобы
работа не пропала: содержимое `refs/stash N` — это sha коммита,
`git branch backup/stash-<дата>-<буква> <sha>`. Сами мусорные файлы — в
корзину (`mavis-trash`), не `rm`. После этого `git fetch` оживает сразу.

**Правило.** Если git ругается на `bad object`/`bad ref`, а `ls-remote` работает —
сначала `git branch -a` и искать warnings про «ignoring ref with broken name».
Это быстрее любых fsck/count-objects, и не нужно ждать полминуты на fsck.

### `dataless` возвращается после каждого `fetch` (машинный уровень, iCloud + `~/Documents`)

## Продуктовые и UI-решения

### Тарифы считаются от реальной нагрузки, а модель — от сложности задачи (02.10.2026)

**Нагрузка учителя — озвучена владельцем продукта, не гипотеза:** домашка
задаётся **на каждый урок** (в РФ 100%), ставка 20-24 урока/нед, 34 учебные
недели. То есть 1 100-1 600 артефактов за учебный год, а не «30 листов/мес»,
на чём был построен первый расчёт юнит-экономики.

**Решения по тарифам (2026-10-02, реализуются волнами):**
1. Цены фронта верны (500/3 800, 1 500/11 000, школа 3 000/класс).
   «Учебный год» = **9 месяцев от даты оплаты**, не календарный. В бэке было
   365 дней и другие суммы — приводим к фронту, бэк не импортирует plans.ts,
   а тестом сверяет файл с диска.
2. **Оплачивается не тарифом, а типом задачи.** Opus → Sonnet 5.5: на polza
   ровно 0,5× цены по обеим позициям при том же prompt caching (проверено
   02.10.2026). Luna — на массовые листы, Sonnet — на ОГЭ/ЕГЭ/КТП.
   Тариф задаёт только норму и право на премиум-типы, не модель.
3. Единица потребления — **взвешенные токены** (`out × цена_out модели /
   цена_out Luna`), показывать пользователю в токенах + подпись «≈ N листов».
4. **Мягкий порог:** норма есть, при исчерпании показываем «докупить» и НЕ
   блокируем; предохранитель — админ-алерт по cost/выручка, не блокировка.
5. Бесплатный: 3 генерации **тотал** (не в сутки), антифрод по IP+UA+отпечатку
   (`request.cf`), подозрительным — невидимый Cloudflare Turnstile. Не блокировать.
6. Ученикам генерацию не даём (роль `student` заводится заранее).

**Главный антипаттерн, найденный в коде nameone:** `plan` приходит из тела
запроса (`routes/worksheets.ts`, `routes/exams.ts`) и имеет приоритет над
сессией — клиент подделывает `plan:"plus"` и получает Opus. Тариф всегда
только из сессии; тест на это обязателен.

### Экономику тарифов в SaaS считать СКРИПТОМ, не в голове (02.10.2026)

**Правило.** Любые числа юнит-экономики (COGS, маржа по сценариям нагрузки,
пороги лимитов) появляются в документе только как вывод скрипта, который лежит
в репозитории рядом. Если цифру не выводит скрипт — она не подтверждена, даже
если выглядит правдоподобно.

**Почему — три реальных случая за один день в nameone:**
1. Колонки в таблице разъехались в 8 раз: при переносе в markdown одну колонку
   посчитали как «Base», а на деле там был Opus-роут.
2. Забыл разделить ГОД на 9 месяцев (период оплаты = 9 мес с даты оплаты) —
   завышение ровно в 9 раз: «14,9 млн токенов» вместо 9,58 млн.
3. Считал цену токена в долларах, а документ в рублях.

Во всех трёх случаях расхождение находил скрипт, а не разум. Ложная правдоподобная
цифра в документе опаснее отсутствующей: на неё опираются решения.

**Практика:** `scripts/unit-economics.py` в nameone — источник всех цифр;
`docs/04-pricing-economics-v2.md` §10 фиксирует это правило явно. Расхождение
текста и скрипта больше 5% — повод обновить раздел «что изменилось», а не руками.

**Смежное:** цены моделей LLM хранятся в коде (`backend/src/llm/config.ts`,
polza.ai) и менялись уже дважды. Скрипт читает их оттуда, документ ссылается на
проверенную дату. Проверять polza.ai нужно ДО планирования экономики, а не после.

### Suspense-заглушка прячет контент конструктора и ОГЭ (02.10.2026)

**Симптом.** `/constructor` и `/oge` показывают «Загрузка…» 3–4 секунды, хотя
весь контент уже есть в статическом HTML. Первый экран продукта — пустота.

**Причина.** `src/app/constructor/page.tsx:2823-2830` оборачивает ВСЮ
страницу в `<Suspense fallback={«Загрузка…»}>`. Обёртка нужна только из-за
`useSearchParams()`: при `output: "export"` Next.js требует для него границу
Suspense, иначе падает сборка. Пока гидратируется JS, fallback заменяет собой
весь контент — то есть то, что уже отрисовано в HTML, прячется наивно.

**Замеры (прод, десктоп 1440, до правки).**
| Страница | готовность | DCL | JS |
|---|---|---|---|
| /constructor | 3782 мс | 1865 мс | 23 файла / 551 КБ |
| /oge | 3455 мс | 2429 мс | 16 файлов / 324 КБ |
| / (лендинг) | 1765 мс | 1741 мс | 4 файла / 28 КБ |
| /pricing | 1952 мс | — | 0 |
| /login | 1612 мс | — | 0 |

Лендинг быстрый именно потому, что он почти статичен (4 JS-файла). Тормозят
только две клиентские страницы.

**Ключевой факт для правки.** В конструкторе ВСЕ 15 обращений к `searchParams`
находятся внутри `React.useEffect` — вне эффектов обращений нет. В `oge` одно,
тоже в эффекте. Значит, `useSearchParams` нужен только для первичной
инициализации состояния из URL, а её делает обычное чтение
`window.location.search` в том же эффекте. Обёртка при этом не нужна.

В остальных файлах (play, preview, form, dashboard/interactives,
auth/callback) `searchParams.get()` читается на верхнем уровне — там обёртку
нельзя просто снять, нужно `useState` + `useEffect`, иначе SSR/hydration
разъедутся.

**Внимание при замере.** «Готовность» мерить через `body.innerText.includes
("Загрузка")` — ловушка: на лендинге есть кнопка «Загрузка PDF…», и страница
показывала 49 секунд. Надо ловить именно заглушку:
`!Array.from(document.querySelectorAll("div")).some(d => d.textContent.trim() === "Загрузка…")`.

**Общий вывод для nameone.** `Suspense` вокруг всей страницы при статическом
экспорте — всегда скрывает уже готовый HTML. Обёртка должна быть минимальной
вокруг той части, где реально нужен `useSearchParams`, а не вокруг страницы.

**Firecrawl для таких задач не нужен.** Он не сработал: в его песочнице нет
Playwright, кредиты кончились, а подписанная ссылка на скриншот бьётся при
передаче. Playwright уже есть в проекте (`npx playwright --version` → 1.63.0),
достаточно запускать скрипт из корня репозитория, иначе Node не видит
`node_modules`. Внешние скриншот-сервисы — лишняя зависимость и трата.

### Метрики по скриншоту графика: восстанавливать числа пикселями, а не на глаз (02.10.2026)

**Правило.** Если Иван просит посчитать среднее/доли по гистограмме или
бар-чарту из картинки — не оценивать высоты столбиков визуально, а извлекать
пиксели и калибровать оси. На глаз ошибка в 1–2 px на столбике = ±0,1 п.п.,
а на итоговом среднем это десятые доли секунды.

**Как это делать (проверено на скрине «Распределение времени до первого
фрагмента», 1920×775, гистограмма «до/после фикса»):**

1. PIL + numpy. Pillow/numpy в системном python3 нет — `python3 -m venv` +
   `pip install pillow numpy` (~15 с).
2. Калибровать Y по тексту подписей оси, а не по сетке: **сетки на скрине
   может не быть вообще** (в этом графике не было ни одной линии). Подписи
   находятся текстовой маской `min(RGB)>85 & (max-min)<25`, дальше кластеры
   строк → центры → линейная регрессия `значение = f(y)`. Здесь 0% = y620,
   19,875 px на 1%.
3. Калибровать X по центрам подписей оси X, регрессия `секунды = f(x)`.
4. Столбики — по цвету (здесь «до фикса» = (225,101,101), «после» =
   (90,191,135)), группировка колонок с зазором ≤3 px, высота = число строк.
5. **Ловушка: первая горизонтальная линия, найденная по всей ширине, — не
   ось 0%, а нижняя граница карточки.** Реальная 0% — по подписи «0 %».
6. Отбрасывать легенду: её маркеры дают «столбики» −1% над осью.
7. Считать среднее по центрам бинов (шаг 0,25 с), а колонку «обрыв»
   (таймаут) — либо как 5,0 с, либо отдельно показать долю обрывов. Обычно
   обрывы — это и есть весь эффект фикса, поэтому среднее по успешным ответам
   надо дать рядом.

## Git и параллельные сессии

### Параллельные сессии в одном репозитории nameone: проверяй чужие отчёты по диску (01–02.10.2026)

**Ситуация.** В репозитории одновременно работают несколько сессий
(`session list` показывает родительские сессии и их воркеров). Все пишут в одно
рабочее дерево без веток. 02.10.2026 на пике было **~10 сессий**,
38 файлов менялись за 10 минут, load average доходил до 13.

**ПЕРВОЕ ПРАВИЛО ДЛЯ АУДИТА: перепроверяй факты перед отчётом.** За один
ревью-проход я нашёл и отрапортовал четыре критичные дыры, которые **за время
проверки починили другие сессии** (`plan` из тела запроса, расхождение цен
фронт/бэк, `PLUS_ONLY_TASKS` без проверки, выбор модели по тарифу). Без
перепроверки отчёт превратился бы в список «уже исправлено, не чини повторно».

> Перед тем как написать «вот эта дыра» — перечитай файл прямо сейчас.
> Между находкой и отчётом проходит 20–40 минут, и другая сессия успевает
> починить. Совпадение по нескольким подряд пунктам = это норма для nameone.

Симптом, что файл уже исчез: `stat` отдаёт `No such file or directory`,
а `git status` показывает `D` или новый файл с другим именем. **Не делай
вывод «я выдумал» — перечитай, файл переименовали.**

**Второе правило: проверяй mtime ПЕРЕД правкой, а не только `read`.**
`stat -f "%Sm" файл` — одна секунда, и видно, правил ли кто-то файл только что.
Свежее 5–10 минут = файл чужой активный, не трогай. Если `edit` падает с
«Could not find the exact text» — файл уже переписали, **перечитай, а не
подгоняй `old_string`**: в 02.10 так ушёл 20-минутный цикл правок теста,
который параллельно починил кто-то ещё.

**Третье: падающие тесты могут быть не твоими.** 02.10.2026 пятнадцать падений
разложились так: 3 — настоящие баги в коде, 5 — устаревшие ожидания в тестах,
7 — незавершённая работа других сессий. Перед починкой смотри `stat` на тест
И на тестируемый код.

**Что из этого следует на практике:**

1. **Отчёт воркера «успешно» ≠ результат.** Два случая за день:
   - субагент TZ-13 отчитался успехом, файл `docs/tz/13-student-interactives.md`
     не создал вовсе (потратил запуск на чтение);
   - субагент TZ-16 написал в отчёте «лейблы в `WorksheetPreview.tsx` добавил
     параллельный воркер», которого на самом деле не было — добавил он сам
     и об этом умолчал.
   **Всегда проверяй `ls` по путям из отчёта и `git diff` по «чужим» правкам.**

2. **`git add` захватывает ЧУЖИЕ файлы, если они уже в индексе.** Две сессии
   держат индекс открытым. Первый мой коммит получился 19 файлов вместо 14:
   в индекс уже лежали `PresetGrid.tsx`, `mock/generator.ts`, `exam-gen.ts`,
   `language-guard.ts`, `docs/tz/10-*`. Вылечило: `git reset --mixed HEAD~1`
   + `git add -- <явный список своих путей>` + `git commit -- <те же пути>`.
   Формула `git commit -m ... -- path1 path2` надёжнее, чем `git commit -m`
   после общего `git add`.

3. **Чужие правки прилетают в твои файлы, и это может быть ПОЛЬЗА.** После моего
   коммита другая сессия дописала в мой `f07.ts` фикс реального бага: интерфейс
   `ResponseView extends ResponseRow` протекал в JSON полями БД в snake_case,
   а фронт читал camelCase → учитель увидел бы `undefined` вместо имени ученика.
   Не откатывай такие правки молча — проверь `git diff` и оставь.

4. **`main` может быть сломан чужим коммитом.** 02.10: `main` лежал с
   `LessonPlanPreview.tsx`, на котором падает webpack. TypeScript этот файл
   читает без ошибок (0 parse errors), то есть похоже на гонку при записи.
   Перед тем как винить свою ветку — проверь `git diff main -- <файл>`.

5. **Машина врёт про «сбой сборки».** Load average доходил до 89 при 4 ядрах.
   Топ потребитель — `opencode` (98% cpu) и `StorageManagement.framework`
   (Spotlight переиндексирует после волны правок). На таком load
   `npm run build` висит на «Linting and checking validity of types» 20+ минут
   и умирает вместе с родительской bash-задачей.
   **Сборку запускать через `nohup bash -c '...' & disown`** — подпроцесс в
   скобках `( ... ) &` умирает вместе с задачей, лог не создаётся.
   И обязательно: `next build` проверяет ТИПЫ ВСЕГО проекта, включая чужой
   незаконченный код. Пока другие сессии пишут — зелёной сборки не будет.

**Рабочий режим:** работать в своей ветке (`feat/tz-competitor-features`),
коммитить строго по списку своих путей, чужие правки в общем дереве не
откатывать и не коммитить, перед отчётом проверять результат по диску.

### Перед тем как сослаться на `file:line` в отчёте — перечитай файл (02.10.2026, nameone)

Репозиторий параллельно правится другими сессиями/агентами прямо во время аудита.
В первый проход я прочитал `backend/src/routes/worksheets.ts` и нашёл уязвимость
«тариф из тела запроса имеет приоритет над сессией» (`bodyPlan ?? user.plan`).
Через 20 минут тот же файл уже содержал `resolvePlan(c)` без body-параметра
и комментарий «Раньше здесь было `bodyPlan ?? user.plan`» — правка уже внесена.

**Правило:** находка, в которой важна точная строка, всегда перепроверяется
повторным чтением файла непосредственно перед тем, как попасть в отчёт.

**Расширение на правку кода (проверено 02.10.2026 на nameone):** это же
относится не только к цитированию, но и к редактированию. Между `read` и
`edit` проходит 5–15 минут, и параллельная сессия успевает переписать файл.
Конкретный случай: я прочитал `src/lib/utils/limit.ts` (там был счётчик
«3 в сутки» в localStorage) — к моменту правки файл уже содержал новую
реализацию с серверным источником правды, `syncFromServer` и `refund()`.

**Симптом:** `edit` возвращает «Could not find the exact text» — это не
баг инструмента, а сигнал «файл уехал из-под тебя».

**Что делать:** перед каждой серией правок в горящем файле — `stat -f "%Sm"`
и повторный `read` нужного диапазона. Если файл менялся в последние
минуты — либо не трогай, либо перечитай и пересобрать план.

**Как описывать в отчёте:** если правка есть в рабочей копии, но не в
коммите (деплой идёт из `main`) — это отдельная находка высокого приоритета
«исправлено локально, но не на сервере», а не «уязвимость закрыта». Проверять
`git status --short` и сопоставлять с веткой деплоя.

**Второй момент:** `git status` показывает огромный незакоммиченный WIP почти
всегда. Отсутствие коммита само по себе — не признак проблемы; проблема
только тогда, когда в коммите/деплое расходится именно строка безопасности.

### НИКОГДА не делай `git reset --hard` в общем рабочем дереве nameone (02.10.2026)

**Что случилось.** Работаем вчетвером одновременно. Одно рабочее дерево,
ветками никто не пользуется — все пишут в `main` или в текущую ветку.

Хотел вынести свой фикс в отдельную ветку, не трогая чужую рабочую копию.
Сделал `git worktree add /tmp/x main`, и **внутри worktree сделал
`git cherry-pick`** — а он передвинул указатель самой `main`. Потом, чиня
это, выполнил `git reset --hard origin/main`, **находясь на чужой ветке
`perf/remove-suspense-gate`**. Это снесло у другой сессии ~8 незакоммиченных
изменённых файлов (README.md, `backend/src/index.ts`, `llm/config.ts`,
`llm/providers/openai.ts`, `db/schema.sql`, миграции, `.dev.vars.example`).
Их содержимое существовало только в рабочем дереве — восстановить нельзя.

**Что удалось:** вернуть ветку на исходный конец (все коммиты целы, untracked
файлы уцелели, `git reflog` показал историю). Что не удалось — содержимое
тех файлов. Та сессия жива и потерянное не заметила.

**Правила, которые из этого следуют:**

1. **`git reset --hard` в этом репозитории запрещён.** Только `git checkout -- <файл>`
   для отката конкретного файла. Никогда не трогать индекс/дерево целиком —
   в дереве чужое.
2. **Перед `git add`/`git commit` всегда смотри индекс,** а не только рабочее
   дерево: `git diff --cached --name-only`. В общем дереве там лежат чужие файлы.
3. **Работай в своей ветке и коммить по явному списку путей:**
   `git add -- p1 p2 p3 && git commit -m ... -- p1 p2 p3`.
4. **Новую ветку из чужой/общей точки создавай БЕЗ переключения.** Способ,
   который сработал: `git worktree add /tmp/fix <база>` → внутри **создать
   отдельную ветку** (`git switch -c fix/name` или `git checkout -b`) →
   cherry-pick → `git branch -f fix/name HEAD` → `git worktree remove --force`.
   **Никогда не cherry-pick поверх checked-out ветки** — это двигает её указатель.
5. **Ветку, на которой стоит рабочее дерево, нельзя двигать:**
   `git branch -f <branch> <sha>` вернёт `fatal: cannot force update the branch
   used by worktree`.
6. **`git reflog show <branch>`** — спасение, когда потерял ветку: показывает
   все её предыдущие концы.

**Правило поведения:** в общем дереве любая операция, затрагивающая чужие
файлы (reset, checkout, stash, restore, clean), требует явного разрешения
Ивана. Мои коммиты делаю только по списку своих путей и только в своей ветке.

### Не stash-ить чужую несохранённую работу без проверки (03.10.2026, nameone)

**Ситуация.** В рабочем дереве шёл чужой ребрендинг (69 файлов, «РабочиеЛисты
AI» → «УчЛист»). Чтобы сделать rebase своей ветки, я спрятал всё в
`git stash push -u`. Rebase прошёл, `git stash pop` применился, и я решил,
что часть вернулась: в дереве осталось 6 файлов, а помнил про 69. Оказалось,
что **ребрендинг был закоммичен в отдельную ветку `brand/uchlist-rename`**
(72 файла, коммит `21e67ac`). Ничего не пропало: `git status` показывал
остатки только потому, что ветка была переключена.

**Вывод, который надо было сделать ДО stash.** Прежде чем прибирать чужие
изменения, спросить `git branch -a` и `git log --all --oneline --grep="<ключевое
слово правки>"`. Незакоммиченное в дереве часто оказывается HEAD другой
ветки.

**Опасность `git stash pop` после rebase на другую базу.** Он применяет
диффы, и конфликтующие файлы молча не применяются (или применяются
частично), а `Dropped refs/stash@{0}` в выводе выглядит как «всё вернулось».
Проверять после pop надо не по отсутствию ошибок, а по дельте:
`git status --porcelain | wc -l` ДО stash и ПОСЛЕ pop должны совпадать
с точностью до своих файлов.

**Force-push запрещён → грязный MR пришлось пересобрать.** Ветка
`perf/remove-suspense-gate` отстала от `main` на 4 коммита, и в неё попали
чужие коммиты (фикс magic-link, фикс QR, строка ребрендинга). Rebase с
force-push нельзя, поэтому сделал новую ветку `perf/remove-suspense-gate-v2`
от актуального `main` + `cherry-pick` нужных коммитов, а старый MR закрыл.
**Вывод: перед первым коммитом в новой ветке делать `git fetch` и проверять,
что ветка от свежего `main`, а не от локального отстающего.**

**Ловушка при работе в залитом дереве.** Пока в рабочем дереве шёл чужой
ребрендинг с расходящимися ключами `localStorage` (`uchlist_gens_v1` в тесте
против `rabochielisty_gens_v1` в коде), полный прогон тестов локально давал
«692 зелёных» — то есть НЕ нашёл реально сломанный `form-runner.test.tsx`
(8 падающих тестов), потому что чужое изменение маскировало моё. Тесты
годится прогонять на чистом дереве, а не на залитом параллельной работой.

### Build-time env теряется в CI — прод молча уходит в мок (03.10.2026, nameone)

**Симптом.** Иван открыл живую страницу входа: «ни ВК, ни Яндекс, ни ТГ не
подключены, зарегистрироваться никак нельзя». Кнопки соцсетей и правда были
захардкожены как `disabled` — но оказалось, что это только верхушка.

**Что было на самом деле.** Переменная `NEXT_PUBLIC_API_URL` читается
next'ом **на этапе сборки** и зашивается в бандл. В CI она не была задана
вообще (только `CLOUDFLARE_API_TOKEN` в secrets, никаких variables), поэтому
на проде `API_URL === ""`, и:
  * `src/lib/auth/api.ts` кидал `NO_API_URL` — форма входа не могла
    отправить ничего;
  * `src/lib/llm/index.ts` уходил в **локальный мок** — учитель получал
    правдоподобный, но выдуманный лист вместо сгенерированного.
Второе опаснее: мок-режим не падает, он «работает».

**Как проверить за 30 секунд, не открывая браузер.** Скачать js-чанки живого
сайта и поискать в них адрес API:
```bash
curl -s https://<host>/<route>/ -o p.html          # сначала со слешем,
                                                     # без слеша бывает 308
grep -o '_next/static/chunks/[^"]*\.js' p.html | sort -u > c.txt
: > all.js; for c in $(cat c.txt); do curl -s "https://<host>/$c" >> all.js; done
grep -o 'https://[a-z0-9.-]*workers\.dev' all.js | sort -u
```
Ноль вхождений = фронт не ходит в бэк вообще. Правило шире любого стека:
**любая `NEXT_PUBLIC_*`/`VITE_*`/`EXPO_PUBLIC_*` переменная проверяется на
живом бандле, а не «вроде задана в .env»** — в рантайме её уже не поменять.

**Что важно для отчёта.** «Кнопки соцсетей не подключены» — это факт, но
пользователю нельзя отвечать только этим: он пришёл с вопросом про вход, и
настоящая причина была в другом слое (письма не уходят из-за неподтверждённого
домена в Resend + фронт без адреса API). Докладывай слоями и называй, какой
слой чинится и что перестанет работать.

**Побочно — ребрендинг как источник поломок.** Тот же день: `main` смержил
ребрендинг, в котором отправитель писем сменился на несуществующий домен
(`noreply@uchlist.ru`). Resend начал отвечать 403 на каждую отправку, бэк
отвечал фронту `{ok:true}` (ошибка доставки глоталась), и страница показывала
«Проверьте почту» — письма не существовало. **Смена бренда обязана трогать всё,
где бренд уходит наружу: FROM письма, домен в Resend, ссылки в письме,
sitemap/canonical.** Проверять это `wrangler tail` на боевом воркере, а не
чтением кода.

### Порядок подключения роутов в Hono — ловушка заглушки-catch-all (03.10.2026, nameone)

**Симптом.** На боевом воркере `GET /api/turnstile/config` и `GET
/api/admin/stats` отдавали `501 {"code":"NOT_IMPLEMENTED","error":"Server-side
tracking ещё не реализован"}`. Роуты выглядели подключёнными, тесты на них
напрямую (через `app.request` с точным путём роутера) проходили.

**Причина.** В `src/routes/track.ts` заглушка объявлена как
`trackRouter.all("*")` и подключена так: `app.route("/api", trackRouter)`.
Любой обработчик с `*`, подключённый на префиксе `/api`, ловит **любой** путь
`/api/*`. Hono отдаёт запрос **первому совпавшему** обработчику и не идёт
дальше — все роуты, подключённые ПОСЛЕ заглушки, мертвы. `/api/llm/models`
работал только потому, что стоял выше.

**Правило.** Заглушки/catch-all/fallback подключать последними, с
комментарием-предупреждением прямо над строкой. Новый роут с префиксом
`/api/*` — всегда выше заглушки. Один и тот же префикс можно подключать
много раз (`/api/worksheets` дважды) — это ок, а вот `all("*")` на общем
префиксе — мина.

**Проверка на живом воркере** (быстрее тестов, ловит и порядок, и несовпадение
задеплоенного кода):
```bash
curl -s -o /dev/null -w "%{http_code}\n" https://<worker>/api/<path>
```
Сравнивать со соседним «заведомо живым» роутом: 501 на одном и 200 на другом
почти всегда = перехват.

**Регресс-тест, который стоит написать.** Не «роут отвечает», а «роут,
подключённый после заглушки, отвечает своим обработчиком» + «заглушка
по-прежнему отвечает на неизвестный путь». И **обязательно проверить, что тест
падает на старом порядке** (вернуть порядок временно, прогнать, убедиться в
падении, восстановить). Тест, который зелен и на сломанном коде, — хуже
отсутствия теста: он закрывает задачу, ни разу не сработав.

**Правило на будущее.** Как только в дереве есть незакоммиченная работа, о
которой ты не знаешь (или в репе параллельно работает кто-то ещё) — **не
переключать ветки и не stash**, а сразу работать в отдельном worktree:
```bash
git worktree add ../<repo>-wt-<задача> -b <branch> origin/main
ln -s <основа>/node_modules ../<repo>-wt-<задача>/node_modules   # для тестов
cd ../<repo>-wt-<задача> && git cherry-pick <старый-коммит>     # вместо rebase
```
Cherry-pick вместо rebase — потому что rebase требует чистого дерева, а оно
не чистое по определению. И отдельная проверка: `**/node_modules/` в
.gitignore со слэшем **не ловит симлинк-файл** — свой `ln -s` на node_modules
попадёт в коммит через `git add -A` (в моём случае так и вышло, поймал на
`git show --stat`). Добавлять `**/node_modules` без слэша.

### Пуш в `main` в nameone: чужие незакоммиченные правки часто уже в `origin/main` (03.10.2026)

**Симптом.** Рабочее дерево `nameone` на 65+ изменённых файлов выглядит как
«чужой ребрендинг в процессе». Прямой `git push origin main` падает:
`Updates were rejected because a pushed branch tip is behind its remote`.
Формулировка вводит в заблуждение — якобы у нас отстающий конец.

**Что на самом деле.** Все эти незакоммиченные правки — уже смержены в
origin/main (в моём случае ребрендинг РабочиеЛисты → УчЛист, коммит
`05a9e76`, плюс #22–#24). Локальная ветка отставала от main на 6 коммитов,
а дерево содержало изменения, которые в main уже есть. Коммитить «чужие
файлы» нельзя — они не чужие, они уже в main; коммит их снова = откат main.

**Правильный путь.**
1. `git fetch origin` и **сначала** сравнить базу:
   `git diff <моя-база> origin/main -- <мои файлы>`. Если main их переписал —
   переносить правки вручную, патч не поможет.
2. `git worktree add ../nameone-wt-<задача> -b feat/<задача> origin/main`
   + `ln -s <основа>/node_modules` для тестов.
3. **`git apply --3way` ненадёжен**: при конфликте в нескольких файлах он
   откатывает применение целиком, а часть файлов трогает без применения.
   Надёжнее копировать файлы целиком (`cp`) и **вручную возвращать правки
   main**, затёртые копированием. Откат заметен по тем же маркерам, что
   использовал раньше (бренд, дефолт домена, флаги фич, правила .gitignore).

**Ловушка при ручном переносе.** `git checkout -- .` в «грязном» worktree
откатывает в том числе только что сделанные правки — я так потерял работу
и переделывал. Перед откатом фиксировать, что уже применено.

**Проверка перед коммитом.** Сверять маркеры main, а не только свой diff:
дефолт `SITE_URL`, строки бренда, `MAGIC_LINK_READY`-подобные флаги,
`no-print` в футере, правила `.gitignore` из main. Затем `git diff --stat`
против HEAD: в индексе должны быть ровно мои файлы.

**Прод-тесты ходят на живой прод** (`E2E_BASE_URL` → pages.dev). Если там
форма ещё не задеплоена, тест красный независимо от локальной правки —
сначала прогонять против `npx serve out` локально, иначе вывод неверный.

### `wrangler deploy` без `--env` — это не «локально», а часто прод (04.10.2026, nameone)

**Симптом.** `wrangler deploy` отрабатывает, версия задеплоена, `healthz` отвечает —
и прод при этом живёт с development-переменными. Ничего не падает, поэтому легко пропустить.

**Почему.** Если в `wrangler.toml` секция `[vars]` и `[env.production]` описывают
ОДИН И ТОТ ЖЕ `name = "..."`, то деплой без `--env` перезаписывает именно
боевой воркер, только переменными из `[vars]`. В nameone так и было:
`ALLOW_DEV_MAGIC_URL=true`, `ALLOW_DEMO_PAYMENTS=true`,
`FRONTEND_URL=http://localhost:3000`. Тот же класс инцидента там же ловили
02.10.2026 — повторяемость и делает его опасным.

**Как правильно (дефолт на будущее).**
1. Перед любым деплоем воркера открыть `wrangler.toml` и посмотреть, **один ли
   `name` у `[vars]` и `[env.production]`**. Один — значит дефолтный деплой бьёт в бой.
2. В `package.json` деплой-прод делать `wrangler deploy --env production`, а
   не-бой назвать явно (`deploy:staging`), чтобы его нельзя было запустить по
   привычке. Второе имя работает лучше первого: ошибка становится видимой
   в команде, а не в проде.
3. После деплоя проверять не только `healthz`, а **сами опасные переменные**:
   `wrangler versions view <ID> --env production` печатает `[vars]` и список
   секретов — этого хватает, чтобы увидеть `APP_ENV=development` или
   `ALLOW_DEMO_PAYMENTS=true`.
4. Проверка CORS origin'ом — тоже рабочий признак: прод-домен есть в
   `access-control-allow-origin`, `localhost` отсутствует.

**Почему не поймали тесты.** Юнит-тесты видят только то, что передали в `env`.
Реальное окружение воркера видно исключительно через API Cloudflare — или через
`wrangler tail`, который ловит собственную проверку конфига воркера при
первом обращении.

### Приём: обещание в тексте проверять grep'ом по коду, а не на глаз

Самый дорогой класс дефектов на nameone — фичи, которые обещаны на странице,
но которых нет в продукте. Найдено 7 штук, каждая видна учителю сразу:

| Обещание в тексте | Что нашлось |
|---|---|
| «материалы проверяет методист, на жалобу ответит» | живого методиста нет вообще, есть только промпт самопроверки модели |
| «вопросы для беседы по фото: 5/50/200 наборов в месяц» | лимит нигде не применяется — ни во фронтенде, ни в бэкенде |
| «контрольные с критериями оценивания» | критерии не генерируются, есть только сам тип `control` |
| «история генераций 30 дней» | история в localStorage, обрезается по количеству записей, срока нет |
| «учеников: 5», «членов семьи: до 5» | таких фич в проекте нет вообще |
| «счётчик сбрасывается в полночь» | `resetUserDailyGenerations` объявлена в `backend/src/db/queries.ts`, но **ни разу не вызывается** |
| «1,44 млн токенов» в прайсе | язык для разработчика на странице с ценами; оставить «до 900 листов» |

**Как искать.** Для каждого глагола обещания из видимых текстов искать
реализацию: `grep -rn "<функция/компонент/поле>" src/ backend/src/`. Функция,
которая объявлена, но не вызывается ни разу, — это обещание без лимита.
Фича, которой нет нигде, — обещание без функции. Удалённый лимит убрали из
тарифа, обещание живой проверки заменили на честное «модель перепроверяет,
нашли ошибку — напишите в поддержку».

**Оставленное честно.** «Админка учителя», «Отчёты по классу», «API для
интеграции» закрыты прочерком во всех действующих тарифах и доступны только
в несуществующем «Школа» (запуск 2027) — такие строки трогать не нужно.

Ключевой дефект качества, который не ловится тестами: задание просит
перечислить, а в ключе 4–7 вариантов. Ученик не может «попасть» в ответ,

### Приём: дубль вопроса между классами — ученик видит одно и то же дважды

### Субагенты на nameone: давать таймер, иначе застревают на разведке

Дважды агент 8–10 минут создавал вспомогательные скрипты и не делал ни одной
правки. Оба раза работа была сделана оркестратором за 5–10 минут, потому что
данные к моменту делегирования уже были собраны. Правило: **сначала собрать
данные скриптом самому** (список файлов, точные строки, количество находок),
и только потом делегировать правку с готовым списком — иначе агент тратит
весь контекст на повторную разведку.

**Ловушка:** агент возвращает `git rm`/удаление временных скриптов, но его
скрипты попадают в коммит на параллельной сессии. Перед каждым коммитом
проверять `git status --porcelain` на `?? scripts/…` и удалять руками.

### Назывные конструкции и IT-жаргон: почему текст «читается не по-русски»

Иван указал на 4 фразы, которые выглядят как калька с англоязычного маркетинга.
Причина не в словах, а в конструкции: **предложение без глагола**.

| Было | Стало |
|---|---|
| «Точно по программе. Быстро. Проверяем ответы — отсеиваем явные ошибки.» | «Листы точно по программе. Делаются за 30 секунд. Проверяем ответы и отсеиваем явные ошибки.» |
| «1 075 тем / растёт» (счётчик, `sub="растёт"`) | «1 075 тем / и добавляются» |
| «Откройте любую — генератор сразу подхватит» | «Выберите тему — конструктор откроется с ней» |
| «УчЛист — узкоспециализированный инструмент для учителей» | «УчЛист сделан специально для учителей» |

Типовые признаки, которые надо искать:
- наречие как отдельное предложение («Быстро.») — в русском так не говорят;
- подпись-приписка без субъекта («растёт» под числом — что растёт?);
- местоимение без существительного («Откройте любую» — любую что?);
- глагол из айти-сленга: «подхватит», «задеплоим», «отрендерится», «сгенерирует»;
- канцелярит: «узкоспециализированный», «осуществлять», «в настоящий момент».

**Искать реже в `out/` по всему статику — слишком медленно** (7781 html, 633 МБ,
регулярки с matchAll не успевают). Быстрее и надёжнее: точечный `grep` по
`src/` + чтение видимого текста 6–8 ключевых страниц из `out/` скриптом,
который снимает теги и `<!-- -->`.

**Ловушка React.** В собранном HTML между текстом и выражением стоит
`<!-- -->`, поэтому наивная склейка даёт мусор: «Это 11 класс , предмет»,
«3 бесплатные генерации , без регистрации», «Актуальные темы по классам на .».
Перед выводом регексп обязательно удаляй `<!-- -->` — иначе половина
находок будет ложными.

### Плейсхолдер в юридическом документе — брак, а не мелочь

В согласии на обработку ПДн печаталось `ИП Лушников Иван (уточняется),
адрес: адрес регистрации (уточняется)` — дефолты из `src/lib/site.ts`.
Согласие с таким текстом неполно, а «(уточняется)» в документе читается как
черновик. Убрал: при незаданной переменной выводится только имя оператора,
без пустого «адрес: .». Полные реквизиты (ИНН, ОГРНИП, адрес) ставятся
через `NEXT_PUBLIC_OPERATOR_NAME` / `NEXT_PUBLIC_OPERATOR_ADDRESS`.

**Общее правило для этого репозитория:** любая строка со словом «уточняется»
в `src/app/legal/**` — это баг. Реквизиты либо проставлены, либо документ
не готов к публикации.

**Ложь о локализации.** В FAQ про фото стояло «Данные хранятся на серверах

### Цифры из брифа проверять по исходному коду продукта до публикации (11.10.2026)

**Публикуемые цифры сверять с исходным кодом, а не с брифом/спецификацией.**
Источник истины — код продукта, а не текст задания.

Проверено 11.10.2026 на интеграции УчЛиста в `ilushnikov.ru`. Бриф содержал формулировку
«тарифы 500 / 990 / 1500 ₽ в месяц или за учебный год (9 мес)» — читается как «год стоит столько
же, сколько месяц». Фактически в `plans.ts` год = 3800 / 7600 / 11000 ₽: **занижение почти в 8 раз**
на публичном сайте. Тариф «Школа» был описан как «3000 ₽ за класс» без единицы измерения, хотя в
самом продукте отдельным комментарием отмечено, что эту формулировку уже уточняли.

Та же ошибка нашлась рядом: в `llms.txt` стояло «0.04% → 50% (50× growth)», тогда как 50/0.04 = 1250
и в двух соседних строках того же файла уже было ×1250.

**Почему так выходит:** бриф пишется из продуктового описания, где «500 / 990 / 1500» — это
помесячные цены, а годовые живут отдельными полями. Склейка «или» даёт правдоподобную, но
кратно заниженную цифру. Ошибку не видно без сверки с кодом.

**Как применять:** перед публикацией любых чисел по продукту (цены, объёмы каталога, метрики)
прогонять сверку с исходником. Отдельный проверяющий агент, которому дан доступ к коду продукта,
ловит это быстрее — он сверял тарифы с `plans.ts`, а числа каталога пересчитывал исполнением
`__count.mts`, а не по комментариям.

Смежное: числа, взятые из **комментария** в коде, тоже не источник истины — там уже лежал
устаревший «1070 тем» при фактических 1075.

### Тест на наличие ссылки не ловит битую ссылку (11.10.2026)

**Проверка «ссылка есть» не проверяет, что ссылка ведёт куда-то.**

Ситуация: задание требовало на страницах экзамена ссылку «Все задания предмета».
Агент её сделал. Оба теста были зелёные, 1010 тестов зелёные. **218 ссылок вели в 404** —
маршрута `/exam/<экзамен>/<предмет>/` просто не существовало, и папка в сборке была
только потому, что внутри лежали пронумерованные подпапки.

Второй дефект того же раунда: критерий «от главной не дальше двух кликов» я зашил
в тест под ОГЭ, поэтому 126 страниц ЕГЭ в четырёх кликах прошли незамеченными.

**Как применять:**
- Тест на ссылку обязан проверять **цель**: взять адрес из разметки и убедиться,
  что соответствующая страница существует в сборке.
- Приёмку «путь от главной ≤ N кликов» считать по фактическим `href` и **для всех
  страниц**, а не для той ветки, на которую смотришь. Не хватает выборки — это провал
  проверки, а не «выглядит нормально».
- Обязательно требовать от исполнителя доказать, что новый тест **падает на старом
  коде**. Тест, который не может упасть, ничего не проверяет.

**Почему это повторяемая ошибка, а не разовая:** агент строит ровно то, что написано
в задании. Если в задании сказано «добавить ссылку», а цели страницы не описано,
агент не додумает — он напишет ссылку на естественный адрес, который может не существовать.

### Диагностировать отправку писем только на реальном адресе (12.10.2026, УчЛист)

**Проверка отправки писем на `@example.com` (и прочих тестовых доменах) даёт ложный диагноз.**

Проверено 12.10.2026 на УчЛисте. `POST /api/auth/magic-link` отдавал 500 на бойе, из
логов воркера уходил текст «Не удалось отправить письмо» — вывод сделали: сломан

Resend — тоже на `example.com`. **Оба вывода оказались неверными.**

Настоящая причина, из логов Resend:
`Invalid 'to' field. Please use our testing email address instead of domains like 'example.com'`
То есть провайдер отклоняет сам домен-заглушку, а не ключ. На настоящий адрес
(`hello@<домен проекта>`) тот же самый запрос вернул `{"ok":true,"sent":true}`.

**Как применять.** Прежде чем говорить «секрет/API-ключ сломан»:
1. Проверь `wrangler secret list` (или аналог) — секрет вообще задан? Здесь он был.
2. Постучи ручкой **на настоящий адрес домена проекта**, а не на `example.com`,
   `test.com`, `mailinator` и прочие заглушки.
3. Прочитай логи воркера (`wrangler tail <name> --format pretty` + повторный вызов),
   а не только HTTP-код ответа. Текст ошибки провайдера стоит всех догадок.
4. Сравни с тем, что агент реально проверил: на каком адресе он стучался.

**Почему это дорого.** Агент не просто ошибся — он из неверного вывода вывел
действие («перезалей секрет») и вписал его в PR и отчёт как требование к владельцу.
Владелец, не проверив, вводит ключ заново — и ничего не меняется, а доверие к
остальным находкам падает. Мой собственный вывод я повторил, не перепроверив.

### Перед слиянием открытого PR — ребейз на `origin/main`, он доказывает дубль (13.10.2026, nameone)

**Ситуация (разбор доски PR).** Иван попросил слить все открытые PR в main.
PR #17 «сбой доставки magic-link» висел с 2 октября, +50/−2, все проверки зелёные —
выглядел как безопасный кандидат на слияние. На деле это был **дубль**: тот же
фикс уже лежал в main как коммит `e0e8773 … (#22)`.

**Как применять.** Перед слиянием открытого PR делать ребейз его ветки на
`origin/main` (в одноразовом worktree, чтобы не трогать чужие ветки):

1. `git worktree add /tmp/prNN <branch>` → `git fetch origin main` →
   `git rebase origin/main`.
2. Git печатает `warning: skipped previously applied commit <sha>` —
   значит содержимое коммита **уже есть в main**, diff PR пустой.
3. Такой PR не сливают, а **закрывают как дубль** со ссылкой на уже
   влитый коммит: `gh pr close N --comment "…уже в main: <sha>"`.
4. Ветку вернуть на исходный коммит (`git branch -f <branch> <sha>`) и
   запушить обратно, иначе PR станет пустым.

**Почему дёшево и надёжно.** Rebase отбрасывает коммит на уровне патча
(cherry-pick), то есть сравнивает содержимое, а не SHA. Поэтому он ловит
и «слитый через другой PR», и «перенесённый руками в main», и ручной
`cherry-pick` — всё, что SHA-compare не видит. Занимает секунды.

**Чего не делать.** Не судить о PR по дате открытия и по зелёным галочкам:
11 дней «висения» в открытом виде — это признак забытого дубля, а не
свежести. Ориентир — содержимое, а не метаданные.

### `git push origin main` из worktree уходит вхолостую (nameone)

**Симптом.** Из worktree (например `/tmp/tz26-fix`, ветка
`fix/tz-26-broken-flows`) выполнено `git push origin main`. Команда вернула
код 0, вывод показал «PUSHED» — и я отчитался, что коммиты в `main`. Через
несколько часов проверка показала: четырёх последних коммитов в `main` нет,
ни как предков, ни как cherry-pick.

**Почему.** Локальная ветка `main` в worktree не обновляется при fetch и
остаётся на старом коммите (81dff79). `git push origin main` пушит ИМЕННО
этот локальный ref. Он либо уже совпадает с удалённым, либо уходит назад — в
обоих случаях код возврата 0. Команда не сравнивает ничего с тем, что я
собирался запушить.

**Как применять.** Пушить **транспортную ветку**, а не `main`:

```
git push -u origin fix/tz-26-broken-flows
gh pr create --base main --head fix/tz-26-broken-flows
gh pr merge <N> --squash
```

И после мержа **обязательно сверять содержимое**, а не код возврата:

```
git fetch origin main
git merge-base --is-ancestor <sha> origin/main   # мимо при squash!
git show origin/main:<path-to-file> | grep -c <признак>
```

`--is-ancestor` врёт на squash-мерже: сквош создаёт НОВЫЙ коммит
(например `305c212` вместо `6f45c9b`), и исходного sha в истории нет, хотя
изменения в main есть. Поэтому главная проверка — **признак в файле**,
например `git show origin/main:src/lib/constructor/quality-notice.ts | grep
-c repeatedSkills`.

**И не путать «пуш прошёл» с «работа в main».** Это разные утверждения, и
второе проверяется содержимым.

**Отдельно:** если main сильно разошёлся, мержить ветку нельзя —
конфликты десятков файлов. Правильный путь: `git checkout -b <имя>
origin/main`, затем `git cherry-pick` только своих последних коммитов. Так
дельта переносится на свежий main без переноса чужих старых версий файлов.

### Ветка «опережает main» после сквош-мерджа — проверять PR и содержимое, а не `git cherry` (nameone)

**Симптом.** Иван просит «залить в main то, что не залито».
`git rev-list --count origin/main..<branch>` показывает 16 коммитов, `git cherry`
помечает их как «+» (нет в main). Вывод кажется очевидным: ветка не влита,
надо мержить.

**Как оказалось.** Из 8 таких веток **семь уже были в main**:
- `fix/tz-26-broken-flows` — PR #48 смержен сквошем, доп. часть приехала через
  PR #50, пост-мержевый фикс линта — отдельным коммитом. Ветка отстаёт на 50
  коммитов, поэтому `merge-tree` показывал 6 «конфликтов», а
  `git diff origin/main..branch` — минус 42 000 строк.
- `brand/uchlist-rename` (PR #21), `perf/remove-suspense-gate-v2` (PR #20) — смержены.
- `ilushnikov-author-link` — ссылка уже была в `main` дословно (patch-id отличался
  из-за контекста, содержимое совпадало).
- `dependabot/.../docx-9.8.1` — версия в `main` уже та же.

**Почему.** Сквош-мерж создаёт новый коммит с новым patch-id. `git cherry` и
счётчик ahead сравнивают историю, а не результат. Ветка, отставшая на 50–169
коммитов, показывает «16 новых коммитов» и «десятки конфликтов», хотя её работа
давно в `main`. **Мержить такую ветку — откатить 169 чужих коммитов.**

**Как применять.** Перед выводом «работа не в main» — четыре проверки, по порядку:

1. `gh pr list --state all --head <branch>` — PR смержен? часто да, даже если ветка «ahead».
2. `git diff --shortstat origin/main..<branch>` — если минус десятки тысяч строк, это отставание,
   а не работа.
3. Точечная сверка: есть ли в `main` конкретный символ/файл из ветки
   (`git show origin/main:<file> | grep -c <признак>`).
4. `git cherry-pick <sha>` в чистую ветку и смотреть, не пустой ли коммит. Часто «новый»
   коммит оказывается пустым — работа уже в main.

**Правило от Ивана (15.10.2026):** «если локально есть что-то, что в main не кинули, или есть
PR/MR — их в main влить». Он хочет, чтобы работа не лежала на ветках неделями. Но вливать
надо **проверенное содержимое**, а не список веток: непрочитанная ветка старше main на 169
коммитов приносит откат, а не пользу.

**Что реально осталось потерянным в nameone 15.10.2026:** `fix/qr-form-review` — 1570 строк,

## Норма, взвешенные токены и подписи тарифа (29.10.2026)

- Единица нормы — **взвешенные токены**: `weighted = tokensOut × price_out(модели) / price_out(Luna)` (`backend/src/services/usage.ts:15`), эталон — выход Luna. Норма «Базового» — `NORM_BASE = 2 400 000` (`src/lib/content/plans.ts:165`).
- `TOKENS_PER_WORKSHEET = 1_600` объявлено **в двух файлах**: `src/lib/content/plans.ts:136` и `backend/src/services/usage.ts:126` — это ОЦЕНКА, измерением пока не подтверждённая (ТЗ-35 требует её измерить и зафиксировать метод в шапке файла).
- **Три разные системы величин — смешивать нельзя** (ошибка поймана владельцем 29.10.2026, коммит `0425e3f`): **взвешенные токены** (1 600; живой замер листа 28.10.2026 — 1 537 **выходных** токенов Luna → ≈1 537, то есть 1 600 правдоподобно, и обещание «до 1 500 листов» в единице нормы **сходится**: 2 400 000 ÷ 1 600 = 1 500) · **сырые токены** (5 911 = 4 374 входных + 1 537 выходных; входные в норму НЕ входят, норма считается по выходу) · **деньги** (0,18 ₽ за лист — фактическое списание; `RUB_PER_WEIGHTED_TOKEN` 2,975e-5 ₽ — модельная оценка по прайсу Luna, а провайдер берёт в 3,8 раза больше, `pricing-cost.ts:1-45`). Поэтому `0,18 ₽ ÷ 2,975e-5 ₽ = 6 050` — это НЕ «взвешенные токены», а денежная оценка с наценкой провайдера внутри.
- **Что реально расходится — денежная сторона:** 1 500 листов × 0,18 ₽ = **270 ₽ фактических денег при выручке 249 ₽/мес**. Это признанный долг (`pricing-cost.ts:1-45`, `plans.ts:155-160`), и в волне 1 он НЕ чинится: потолок тарифа пересчитывается отдельно.
- «Контрольная дороже листа в 54 раза» (деньги) и «~89 листов» (токены) — ответы на разные вопросы; публиковать их рядом нельзя. Исследователь 29.10.2026 поправился в этом месте сам, проектировщик — на следующий день в ТЗ-35, и снова.
- Учёт нормы идёт по сумме **всех** вызовов конвейера (генерация + ретрай + дозапрос + второй вариант) — `backend/src/llm/index.ts:1350-1377`. Ломать нельзя.
- Мягкий порог: превышение нормы НЕ блокирует генерацию, а предлагает докупить (`backend/src/services/usage.ts:285-352`) — осознанное решение владельца, учитель сдаёт урок посреди дня.
- `usage` в ответе API — это кумулятивный счёт в сырых токенах и `null` для анонимов и бесплатного тарифа (`backend/src/services/usage.ts:300-310`); перевода в листы в нём нет.

## Класс дефекта «обещание против реальности» и что ломать нельзя (29.10.2026)

- Три места обязаны совпадать: **обещание в карточке тарифа** (`src/lib/content/plans.ts`) ↔ **данные в ответе API** ↔ **печать**. Расхождение — дефект, даже если каждый кусок по отдельности написан правильно.
- Корневая причина двух находок дня — **один факт в двух местах**: критерии разрешено было принести и в `answer` (промпт, правило 17 — `backend/src/llm/prompts/worksheet-gen.ts:169-175`), и в `criteria` (схема и печать), и эти пути ломали друг друга (фильтр выкидывал задание без пригодного `answer` — `backend/src/llm/validation/quality-filter.ts:482`).
- Правило, живущее только в промпте, не обеспечено: лимиты разнообразия ТЗ-33 считаются в коде (`src/lib/content/task-types.ts:443`) и подставляются в промпт дословно, но проверки после генерации нет, и в сводке `quality` (`backend/src/llm/index.ts:297-346`) полей про типы заданий нет.
- **Ломать нельзя** (проверено и сделано правильно): печать критериев в ключе (`src/lib/utils/docx.ts:636`, `:866`); лимиты разнообразия и блок типов в промпте (`task-types.ts:443`, `worksheet-gen.ts:361`); формула взвешенного токена (`usage.ts:15`); учёт по сумме всех вызовов (`index.ts:1350-1377`).
- **Отдельная шкала, не смешивать**: звёзды интерактивов (`src/lib/interactives/scoring.ts:58`) и оценка по фото (`backend/src/llm/prompts/form-grading.ts`) — это не отметки 5/4/3/2 и не проценты по контрольной.
- Бэк умеет импортировать фронтовые справочники относительным путём (прецедент — `src/lib/content/task-types.ts`), но такой файл не должен тянуть фронтовые типы (`SubjectSlug`), иначе воркер тянет за собой весь `src/lib/types.ts`.
