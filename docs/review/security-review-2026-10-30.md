## 1. Плановая уборка не выполняется никогда

**Уровень: ВЫСОКО. Делать сегодня.**

Воркер задеплоен на Cloudflare с двумя cron-триггерами (`backend/wrangler.toml:130-134`):
ежесуточная уборка в 03:00 UTC и часовой для биллинга. Обработчик написан и выглядит рабочим
(`backend/src/index.ts:284-353`), но воркер его никогда не вызывает.

Причина в способе подключения. Cloudflare зовёт cron только через экспорт `scheduled`
модуля — это требование из документации Workers. В коде обработчик навешан на
`app.fire("scheduled", ...)` (`backend/src/index.ts:284`), а `app.fire` — внутренний диспетчер
Hono для собственных событий; Cloudflare о нём не знает и не зовёт. Модуль отдаёт
`export default app` (`backend/src/index.ts:356`) — объект Hono без метода `scheduled`.

Комментарий в коде (`backend/src/index.ts:278-283`) утверждает обратное: что cron-триггер
«вешается через `app.fire` из обработчика Fetch». Обработчика Fetch, который это делает, нет.

**Что из-за этого не происходит:**

- `purgeExpiredPhotos` — удаление фотографий детских работ через 7 дней. Это персональные
  данные ребёнка, и в `wrangler.toml:126-129` заявлен срок хранения 7 дней.
- `purgeExpiredForms` — удаление ответов учеников через 90 дней.
- `refreshWeeklyTopicState` — ежесуточное обновление темы недели.
- `chargeDueSubscriptions` — ежемесячное списание за подписку.

**Доказательство из боевой базы.** Таблица `weekly_topic_state` по схеме всегда содержит ровно
одну строку (`backend/src/db/schema.sql:860-861`, `id INTEGER PRIMARY KEY CHECK (id = 1)`), и
пишет её только ежесуточный cron (`backend/src/jobs/weeklyTopic.ts:110-120`, upsert). В боевой
базе в ней 0 строк, при том что воркер работает с 02.10.2026. За четыре недели ежесуточного
прогона не было ни одного.

Почему это не заметили: `readWeeklyTopicState` (`backend/src/jobs/weeklyTopic.ts:137-142`)
при отсутствии строки считает тему недели на лету, поэтому главная сайта показывает верную
неделю. Проверку на `rows_written` никто не делал.

**Починка.** Отдавать объект с `fetch` и `scheduled`:

```ts
export default {
  fetch: app.fetch,
  scheduled(event, env, ctx) {
    app.fire("scheduled", event, env, ctx);
  },
};
```

Логика уборки остаётся как есть, меняется только точка входа. После деплоя в логах Cloudflare
должны появиться строки `[cron] purgeExpiredPhotos` — это и есть проверка, что починка сработала.
До первой успешной уборки стоит прогнать скрипты удаления вручную по боевой базе: в R2 уже могут
лежать фотографии старше 7 дней.

**Почему это ВЫСОКО.** Три причины: персональные данные детей не удаляются бессрочно; на
продукте обещано удаление через 7 дней, и обещание не выполняется; в октябрьском ревью это уже
было зафиксировано как открытый вопрос («фактический запуск по расписанию не проверен»,
`docs/SECURITY-REVIEW-2026-10-02.md:702`) — теперь вопрос закрыт ответом «не запускается».

## 2. Соль отпечатка посетителя в проде не задана

**Уровень: ВЫСОКО. Делать сегодня.**

Отпечаток посетителя (IP + User-Agent + страна) считается как SHA-256 с солью
`env.FINGERPRINT_SALT`. По отпечатку живёт счётчик бесплатных генераций и работает антифрод.

Секреты, заданные в боевом воркере (`wrangler secret list`, только имена):

```
ADMIN_EMAILS, JWT_SECRET, POLZA_API_KEY, RESEND_API_KEY, TOTP_ENCRYPTION_KEY
```

`FINGERPRINT_SALT` среди них нет. Во всех семи местах, где считается отпечаток, стоит
запасная константа из исходников `"dev-fingerprint-salt"`:

- `backend/src/routes/llm.ts:76`
- `backend/src/routes/users.ts:266`
- `backend/src/routes/worksheets.ts:179` и `:335`
- `backend/src/routes/exams.ts:80`
- `backend/src/routes/f06.ts:412`
- `backend/src/routes/artifact-generate.ts:219`
- `backend/src/routes/turnstile.ts:143`

`backend/src/env.ts:112-118` объявляет соль обязательной для прода, но проверка прод-конфига
(`backend/src/index.ts:83-89`) её не смотрит — поэтому самопроверка молчит.

**Следствие.** Хэш с публичной солью перебирается за секунды: пространство IPv4 восстанавливается
перебором. В боевой базе уже 107 таких строк. То есть таблица отпечатков фактически стала
справочником по IP, хотя схема обещает обратное («только SHA-256 отпечатка, сырые IP, ASN и
User-Agent в таблицу не попадают»). Для учителя это персональные данные, которые обещали не
хранить.

**Починка.**

```bash
npx wrangler secret put FINGERPRINT_SALT --env production
```

Значение — случайная строка от 32 символов. Дальше убрать fallback в проде (заменять на
`env.FINGERPRINT_SALT` без `??`) и добавить соль в проверку прод-конфига, чтобы в следующий
раз воркер сам на это заорал.

**Что учесть.** После смены соли старые отпечатки перестанут совпадать с новыми — счётчик
бесплатных листов у тех посетителей начнётся заново. Заодно это повод одноразово почистить
старые отпечатки, они больше не привязаны ни к чему полезному.

## 3. Прод можно выкатить с настройками разработки

**Уровень: ВЫСОКО. Делать сегодня.**

В `backend/wrangler.toml` секция `[vars]` (значения по умолчанию) содержит
`ALLOW_DEV_MAGIC_URL = "true"` и `ALLOW_DEMO_PAYMENTS = "true"`. Секция `[env.production.vars]`
переопределяет их в `false` — правильно.

Но скрипт `deploy:staging` (`backend/package.json:10`) — это `wrangler deploy` без
`--env production`, и имя воркера у него то же, `rabochielisty-api`. Запуск этого скрипта
выкатывает на боевой адрес воркер с настройками разработки:

- `ALLOW_DEV_MAGIC_URL=true` — ссылка для входа приходит прямо в ответе на запрос,
- `ALLOW_DEMO_PAYMENTS=true` — подписку можно получить без оплаты.

Самопроверка в `backend/src/index.ts:145-161` в такой конфигурации пишет `console.error` и
**не блокирует запросы**. То есть система замечает опасное состояние и продолжает работать в нём.

Так уже выкатывали дважды — это зафиксировано в `backend/wrangler.toml:7-15` и в части 2
октябрьского ревью («БОЕВОЙ ВОРКЕР ЗАДЕПЛОЕН С НАСТРОЙКАМИ РАЗРАБОТКИ»).

**Починка.** Убрать скрипт `deploy:staging` или дать ему другое имя воркера и отдельный D1.
Второе — в самопроверке: при `ALLOW_DEMO_PAYMENTS` или `ALLOW_DEV_MAGIC_URL` в `true` отдавать
503, а не только писать в лог.

**Проверено вживую:** на боевом `api.uchlist.ru` сейчас `false` в обоих случаях. Ответ на
`POST /api/auth/magic-link` приходит как `{"ok":true,"sent":true}` — без ссылки. То есть прод
сейчас в порядке; риск чисто операционный — он сработает при следующей неудачной раскладке.

## 4. Чужой рабочий лист читается через «избранное»

**Уровень: ВЫСОКО. Делать сегодня.**

`POST /api/users/favorites` (`backend/src/routes/users.ts:146-158`) принимает объект листа
из тела запроса без схемы валидации и без сверки владельца. Внутри
(`backend/src/db/userResources.ts:217-256`) делается только `SELECT id FROM worksheets
WHERE id = ?1` — проверка факта существования. Если лист с таким id уже есть, он не
перезаписывается, но в `favorites` учителя пишется строка со ссылкой на чужой лист.

`GET /api/users/favorites` (`backend/src/db/userResources.ts:152-163`) отдаёт `payload_json`
листа через `LEFT JOIN worksheets w ON w.id = f.worksheet_id WHERE f.user_id = ?1`. Фильтр стоит
на таблице избранного (свои записи), а не на листе. В ответе — полное содержимое чужого листа:
задания, эталоны ответов, критерии оценивания.

Так обходится защита `GET /api/worksheets/:id` (`backend/src/routes/worksheets.ts:415-455`), где
владелец сверяется, а чужой лист отдаётся как 404.

**Как воспроизвести.** Учитель А создаёт лист. Учитель Б отправляет
`POST /api/users/favorites` с `{"worksheet":{"id":"<id листа А>"}}` и читает
`GET /api/users/favorites` — там содержимое листа А.

**Ограничение по эксплуатации.** id листа — это `ws_` + 12 символов из 36-значного алфавита
(`backend/src/lib/shortid.ts:32-34`), около 62 бит. Перебором не берётся: нужен id, который
где-то утёк — ссылка, скриншот, переписка, чужой скан. Случайно встретить почти невозможно,
но в намеренной атаке воспроизводимо.

**Починка.** Проверять владельца перед вставкой в избранное — одна строка по образцу
`backend/src/routes/f07.ts:315-319`, где такой же случай уже закрыт. Плюс заменить
`as { worksheet: Worksheet }` на zod-схему: сейчас тело принимается как есть, и запрос без
`tasks` приводит к 500 вместо 400.

## 5. Антифрод в проде выключен

**Уровень: СРЕДНЕ. На этой неделе.**

Проверено вживую:

```
GET https://api.uchlist.ru/api/turnstile/config
{"ok":true,"enabled":false,"siteKey":null}
```

`TURNSTILE_SECRET_KEY` в боевом воркере не задан, `sitekey` тоже пустой. Капча не требуется
никогда: код её проверяет только если секрет задан (`turnstileConfigured: Boolean(c.env.TURNSTILE_SECRET_KEY)`),
иначе идёт дальше — это осознанное решение «fail-open», чтобы не положить продукт из-за капчи.

Следствие: публичная генерация защищена только квотой по отпечатку и лимитом по IP. Бот с
ротацией IP укладывается в эти лимиты.

**Починка.**

```bash
npx wrangler secret put TURNSTILE_SECRET_KEY --env production
```

и положить sitekey в `[env.production.vars]`. Заодно добавить `TURNSTILE_SECRET_KEY` в проверку
прод-конфига.

**Что уже сделано правильно.** Квота считается по всем отпечаткам пользователя сразу
(`backend/src/services/usage.ts`, `quotaOwnerKeys`), поэтому старый обход «войти-выйти» и смена
браузера закрыты. Лимит на IP и на пару «токен + IP» в публичных формах тоже есть.

## 6. Вебхук оплаты не проверяет подпись

**Уровень: СРЕДНЕ, но латентно. Починить до включения продаж.**

`POST /api/billing/yookassa-webhook` (`backend/src/routes/billing.ts:171-185`) принимает любое
тело и передаёт в `handleWebhook`. Подпись ЮKassa не сверяется нигде в `backend/src`. Защита
построена на трёх проверках: платёж есть в нашей базе, сумма совпадает с серверным прайсом,
живая сверка с API ЮKassa.

Живая сверка — единственное, что держит схему. Она пропускается целиком, если ключи ЮKassa не
заданы (`backend/src/services/billing.ts:624`), и при ответе `unknown` (сеть, 5xx, 401)
подписка всё равно активируется (`backend/src/services/billing.ts:632-640`).

**Проверено вживую сегодня.** Ключей ЮKassa в боевом воркере нет, платежей в базе 0,
`ALLOW_DEMO_PAYMENTS=false`, поэтому создание платежа падает и подделывать нечего: отправка
поддельного вебхука вернула `{"handled":false}`. Эксплуатировать сегодня нельзя.

**Почему всё равно ВЫСОКО к моменту включения продаж.** Как только появятся ключи, схема
станет уязвимой в тот день, когда API ЮKassa недоступен или ключи отозвали и заменили: в этот
момент поддельный `payment.succeeded` активирует подписку бесплатно. Код это прямо
признаёт в комментарии (`backend/src/services/billing.ts:406-411`).

**Починка.** Сверять HMAC-подпись первым фильтром, до остальных проверок. При `unknown` не
активировать подписку, а ставить платёж в очередь на повторную сверку. Плюс allowlist адресов
ЮKassa на уровне Cloudflare.

## 7. CSV в комплекте материалов исполняется как формула

**Уровень: СРЕДНЕ. На этой неделе.**

`csvBytes` (`src/lib/utils/materials-zip.ts:68-71`) пишет содержимое как есть: без кавычек и без
защиты от ячеек, начинающихся с `=`, `+`, `-`, `@`. Excel и LibreOffice выполняют такую ячейку
как формулу.

Сценарий: учитель собирает комплект материалов → отправляет архив коллеге → коллега открывает
CSV из архива, и формула выполняется у него. Содержимое CSV приходит из ответа модели, куда
попадает тема учителя, поэтому подобрать формулу можно темой задания.

Это ещё и обычная поломка: запятая или точка с запятой внутри текста рвут строку таблицы,
потому что кавычек нет.

**Починка.** Оборачивать каждое значение в кавычки, а перед опасным началом ставить апостроф.
Тот же приём применён в `report-xlsx.ts`, там значения экранируются.

## 8. Тип загруженного файла не проверяется

**Уровень: СРЕДНЕ. На этой неделе.**

При загрузке фотографии тип берётся из заголовка, который прислал клиент:
`backend/src/routes/f06.ts:1537-1541` (`uploaded.type` → allowlist `f06.ts:171-176`), и в R2
файл кладётся с этим же contentType (`f06.ts:236-239`). Для ученика по персональной ссылке —
`backend/src/routes/classes.ts:1521-1529`. Байты файла с заголовком не сверяются.

Учитель или ученик может положить HTML или SVG с заголовком `image/jpeg`, и сервер это примет.

**Почему не КРИТИЧНО сегодня.** Бакет `rabochielisty-pdfs` приватный, ни один роут не отдаёт
байты R2 наружу — наружу фото уходит только воркеру для распознавания. Риск проснётся, если
появится ссылка на файл или presigned URL. Пока фото детей лежат в закрытом бакете.

**Починка.** Сверять magic bytes (сигнатуру файла) с заявленным типом. 20 строк.

## 9. Ошибка 502 отдаёт текст модели клиенту

**Уровень: НИЗКО.**

`backend/src/llm/index.ts:3226` и `:3265` кладут в `details` ошибки до 200 символов сырого

сырой вывод модели в браузер незачем: в логи он попасть может, в ответ клиенту — не должен.

Отдельно проверил: в логи уходят id, модель, стоимость и латентность — ответов учеников и
разборов детских рукописей там нет.

## 10. Content-Security-Policy нет

**Уровень: НИЗКО, решение владельца.**

Остальные заголовки на месте, проверил вживую на `uchlist.ru`:

```
strict-transport-security: max-age=31536000; includeSubDomains; preload
x-frame-options: DENY
x-content-type-options: nosniff
referrer-policy: no-referrer
permissions-policy: camera=(), microphone=(), geolocation=(), interest-cohort=()
```

CSP нет — это зафиксированное решение от 02.10 (`public/_headers:9-12`): при строгом CSP
ломаются Яндекс.Метрика и шрифты, а ради отлова одной уязвимости ломать продакшен не стали.

Риск: при уязвимости в HTML-вставке скрипт выполнится без преград. На сегодня вставок
пользовательского HTML в DOM нет — вывод модели рендерится как текст, SVG от модели
проходит серверный санитайзер с allowlist тегов.

**Рекомендация.** Собрать CSP в режиме `report-only`, посмотреть отчёт, и только потом
включать enforce. Отдельная задача, не срочно.

## Что проверили и защита есть

- **SQL-инъекций нет.** Все запросы — через `bind(?1)`, склейки SQL с пользовательскими
  данными нет нигде, `ORDER BY` и `LIMIT` статические или через плейсхолдер.
- **Сессия в HttpOnly-cookie.** Токен не лежит в `localStorage` и не передаётся в
  `Authorization` — только `credentials: "include"`. Cookie: HttpOnly, Secure, SameSite=Lax,
  домен `.uchlist.ru`.
- **CSRF-защита работает.** Проверил вживую: запрос с чужим `Origin` получил 403 с кодом
  `CSRF_ORIGIN_REJECTED`. CORS — явный allowlist, без wildcard.
- **Доступ к чужим данным закрыт.** Листы, формы, работы по фото, классы, журнал — по
  владельцу, с 404 вместо 403, чтобы по коду нельзя было перебирать чужие id.
- **Админские ручки под `requireAdmin`**, права выдаются только из серверного списка
  `ADMIN_EMAILS` при создании аккаунта, из тела запроса права не выдать.
- **Пароли**: argon2 с калибровкой и добивкой по времени; сравнение сессионных токенов за
  постоянное время.
- **SVG от модели** проходит серверный санитайзер с allowlist тегов, в DOM попадает через
  безопасную вставку. Прямых вставок вывода модели в HTML в `src/` нет.
- **Стек-трейсы в проде не утекают**, `/healthz` и `/readyz` не раскрывают окружение.
- **Секретов в репозитории нет**, в CI работает gitleaks по полной истории.
- **Публичные формы** отдают whitelist полей: email учителя и ученика, эталон при
  `show_answers = 0` не отдаются.
- **Обход бесплатной квоты закрыт**: квота считается по всем отпечаткам пользователя.

## Чего не удалось подтвердить

- Публичность бакета `rabochielisty-pdfs` в панели Cloudflare — из репозитория не видно.
  По коду наружу байты не отдаются.
- Настройки TLS, WAF-правила и список тех, у кого есть доступ к панели Cloudflare и к D1.
- Логи Cloudflare за прошлые периоды — не смотрел, есть ли в них персональные данные в тексте.
- `npm audit` показывает 2 критических и 1 high по фронту. `dompurify` — из неиспользуемой
  `jspdf`, снимается удалением зависимости. `next@14.2.35` — решение владельца от 02.10
  не апгрейдить, для статического экспорта advisory неприменимы. `postcss` — только на сборке.
- Работа с `returnUrl` в оплате не сверяется с allowlist доменов
  (`backend/src/routes/billing.ts:118-148`): клиент подставляет свой адрес, и после оплаты
  пользователя уводит на чужой домен. Пока платежи выключены — неактуально.
