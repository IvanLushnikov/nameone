# Аудит информационной безопасности — «РабочиеЛисты AI»

**Дата:** 2 октября 2026
**Объект:** репозиторий `nameone` (Next.js фронт + Cloudflare Worker `backend/` + отдельный воркер `worker-self-verify`)
**Роль:** директор ИБ, полный ревью продукта перед выходом на реальных пользователей
**Метод:** статический разбор кода, конфигурации, CI и зависимостей. Живое тестирование взлома не проводилось.

---

## Короткий итог

Продукт написан аккуратно: секреты не лежат в репозитории, SQL везде параметризован, сессионный токен не хранится в браузере, а данные учеников отдаются по «белому списку» полей. Это выше среднего.

Но есть **три дыры, которые эксплуатируются из интернета без специального доступа** и бьют по деньгам и по аккаунтам:

1. **Вебхук оплаты не проверяет, от кого пришёл запрос** — можно получить подписку, не заплатив.
2. **Если в проде не задан ключ почты — вход ломается полностью**: можно войти в любой аккаунт по чужому email, не получая письмо.
3. **Нет защиты от подделки запросов (CSRF)** — любой сторонний сайт может от имени пользователя отменять подписку и тратить генерации.

Плюс одна находка уже исправлена в коде, но **не закоммичена** — значит, на сервере она, скорее всего, ещё живёт.

**Общая оценка: 6 из 10.** Для внутреннего пилота — приемлемо. Для продажи сотням учителей с реальными платежами и персональными данными учеников — нужно закрыть критическое до запуска.

## 🔴 КРИТИЧЕСКИЕ НАХОДКИ

### К-1. Вебхук оплаты не проверяет отправителя — подписку можно получить бесплатно

**Где:** `backend/src/routes/billing.ts:105-119`, `backend/src/services/billing.ts:240-310`
**Опасность:** критическая, деньги и доступ

Любой человек в интернете может отправить POST-запрос на `/api/billing/yookassa-webhook` с произвольным содержимым. Код не проверяет **ничего**: нет подписи, нет проверки источника, нет сверки с самим платёжным агрегатором. В самом коде это признано как долг:

```
// TODO(security): ЮKassa по умолчанию НЕ подписывает webhooks.
// Сейчас доверяем payload'у (server-to-server + IP allowlist на стороне ЮKassa
// достаточно для маленького продукта).
```

Дополнительно тариф и период берутся **из тела присланного запроса**, а не из базы:

```ts
// services/billing.ts
const plan = body.object.metadata?.plan ?? payment.plan;   // ← из чужого JSON
const period = body.object.metadata?.period ?? "monthly";   // ← из чужого JSON
```

**Как это используется:** злоумышленник узнаёт идентификатор своего платежа (например, из dev-режима или из ссылки на оплату) и отправляет поддельное уведомление `payment.succeeded`, в котором в `metadata` стоит `plan: "plus"`, `period: "yearly"`. Подписка активируется без единого рубля. Сумма платежа при этом не сверяется с прайсом.

**Как чинить (по приоритету):**

1. **Не доверять тарифу из тела.** Брать `plan` и `period` только из своей таблицы `payments` (там они уже сохранены при создании платежа). Удалить чтение `body.object.metadata`.
2. **Сверять сумму.** Перед активацией подписки запрашивать у ЮKassa статус платежа через API (`GET /v3/payments/{id}`) и сверять: статус `succeeded`, `amount.value` совпадает с `PRICES[plan][period]`, `currency === "RUB"`.
3. **Сделать ручку идемпотентной.** Если запись подписки по `yookassa_payment_id` уже есть — не создавать вторую, а просто обновить статус.
4. **Ограничить источник.** Настроить IP-allowlist в личном кабинете ЮKassa и проверять `CF-Connecting-IP` на его стороне — как дополнительный слой, не как основной.
5. На время, пока п.1-3 не сделаны, поставить на ручку явную заглушку, которая логирует и **не активирует подписку**, чтобы не выдавать бесплатный доступ.

### К-2. Если в проде не задан ключ почты — можно войти в любой аккаунт

**Где:** `backend/src/services/email.ts:43-47`, `backend/src/services/auth.ts:131-134`
**Опасность:** критическая, полный захват любого аккаунта

Система входа сделана «с запасом»: если ключа отправки писем нет, ссылка для входа не отправляется, а **возвращается прямо в ответе на запрос**:

```ts
// email.ts — если RESEND_API_KEY не задан
if (!env.RESEND_API_KEY) {
  return { sent: true, url };          // ← url = рабочая ссылка входа
}

// auth.ts — и эта ссылка уходит клиенту
return sendResult.url
  ? { ok: true, sent: true, devMagicUrl: sendResult.url }
  : { ok: true, sent: true };
```

Проверки «а мы точно в проде?» здесь нет. В комментарии написано «в прода не возвращается», но код этого не гарантирует — он полагается на то, что ключ настроен.

**Как это используется:** если `RESEND_API_KEY` не задан или истёк/отозван, любой посетитель отправляет запрос со своим (чужим) email, получает в ответе рабочую ссылку входа и заходит в этот аккаунт. Полный обход входа, письмо не нужно, ждать не нужно. Вся система входа (magic-link) при этом выглядит исправной.

**Как чинить:**

1. Отдавать `devMagicUrl` **только** при `APP_ENV !== "production"`. В проде — никогда.
2. В проде при отсутствии ключа **не создавать** пользователя и не выдавать ссылку, а писать в лог алерт и отдавать 503, чтобы проблема была видна сразу, а не молча.
3. Добавить проверку при старте: воркер не должен подниматься в `production` без `JWT_SECRET` и `RESEND_API_KEY` — падать сразу с внятной ошибкой.
4. Провести ротацию: если есть основания считать, что ключ почты на проде не задан, **сменить ключ** и пересмотреть, не могли ли зайти чужим письмом.

### К-3. Отсутствует защита от подделки запросов (CSRF)

**Где:** `backend/src/middleware/cors.ts:66`, `backend/src/routes/auth.ts:69-75`
**Опасность:** высокая, действия от имени пользователя

Сессионная cookie ставится с `SameSite=None` — браузер отправляет её **на любой** сайт, с которого пришёл запрос. При этом:
- заголовка `X-CSRF-Token` нет нигде в проекте;
- проверки `Origin` / `Sec-Fetch-Site` на бэкенде нет (проверено поиском по всему `backend/src` — совпадений нет, кроме упоминания в комментарии);
- CORS **не защищает от CSRF** — он запрещает только чтение ответа, но сам запрос до сервера доходит и изменение происходит.

**Как это используется:** злоумышленник размещает на любом сайте (соцсеть, блог, письмо) страницу, которая при открытии у пользователя делает `fetch` на `https://rabochielisty-api.../api/billing/cancel` с `credentials: "include"`. У пользователя под руками сессия — подписка отменяется. Тем же способом отправляются генерации за его счёт, создаются формы с его именем, тратятся лимиты.

**Как чинить (выбрать одно, лучше оба):**

1. **Правильный путь — убрать `SameSite=None`.** Как только фронт и бэк живут на одном домене (например `rabochielisty.ru` + `api.rabochielisty.ru`), вернуть `sameSite: "Lax"`. В коде это уже отмечено как план, но не сделано. Пока домены разные — временный вариант ниже.
2. **Проверка Origin на изменяющих ручках.** Middleware, который для `POST/PUT/PATCH/DELETE` сверяет заголовок `Origin` с белым списком и отдаёт 403 при несовпадении. Около 15 строк, закрывает проблему полностью.
3. Отключить передачу cookie на публичные ручки (`/api/public/forms/*`) — им сессия не нужна.

## 🟠 ВЫСОКИЕ НАХОДКИ

### В-1. Найденная и уже исправленная дыра с тарифом — но правка не закоммичена

**Где:** `backend/src/routes/worksheets.ts:44-52`
**Опасность:** была критическая, сейчас закрыта в коде

Это важно именно в статусе «почти». Раньше тариф приходил из тела запроса и имел приоритет над данными сессии:

```ts
// БЫЛО (находилось в рабочей копии до начала аудита):
if (bodyPlan === "plus" || bodyPlan === "base" || bodyPlan === "free") return bodyPlan;
return user.plan;
```

Отправив `{"plan":"plus"}` в теле, клиент снимал с себя все ограничения нагрузки: `LIMITS.plus` в `backend/src/llm/ratelimit.ts:30` равен бесконечности, поэтому лимит не срабатывал **и счётчик вообще не рос**.

Сейчас в коде это исправлено — тариф читается только из сессии, добавлены проверки «тариф включает этот тип артефакта» и запрет генерации ученикам.

**Но:** правка **не закоммичена** (`git status` показывает изменённый `worksheets.ts`), и по истории коммитов деплой идёт из `main`. Значит, **на сервере, скорее всего, всё ещё старая версия**. Коммит `plan` из тела запроса стоит в список «сделать немедленно» — это буквально одна команда.

**Дополнительно (актуально и сейчас):** ручка генерации **не требует входа**. Анонимный посетитель получает 3 генерации в сутки по IP. Для teacher-facing продукта с оплатой это означает бесплатный доступ. Стоит решить, готовы ли мы к этому осознанно.

### В-2. Открытый бесплатный LLM-прокси в `worker-self-verify`

**Где:** `worker-self-verify/src/index.ts:131, 406, 541`
**Опасность:** высокая, прямые расходы

Воркер вызывает LLM по вашему ключу и **не имеет ни аутентификации, ни ограничения частоты запросов**. Поиск по `authorization` / `ratelimit` / `429` в его коде не даёт ни одного совпадения. Заголовок в коде задан как `Access-Control-Allow-Origin: "*"`, хотя в конфиге есть `ALLOWED_ORIGINS` — то есть сужение в проде не работает, оно просто не применяется.

Публичные адреса `*.workers.dev` доступны всем в интернете. То есть любой может положить счёт на Polza от вашего имени.

**Как чинить:**
- Закрыть ручку проверкой секрета: сравнение заголовка `X-Internal-Token` с секретом из переменной окружения; без совпадения — 401.
- Добавить ограничение по IP (rate limit), как уже сделано в основном бэкенде.
- Использовать `ALLOWED_ORIGINS` по назначению, а не литерал `"*"`.
- Если функция нужна только фронту — рассмотреть перенос вызова внутрь основного `backend` (там всё это уже есть).

### В-3. Прод собирается и выкатывается без единой проверки

**Где:** `.github/workflows/deploy.yml`
**Опасность:** высокая, процесс

В пайплайне:
- **нет шагов `npm test`, `typecheck`, `lint`** — в прод уезжает код, который мог даже не компилироваться;
- **нет блока `permissions:`** — `GITHUB_TOKEN` получает права по умолчанию, то есть максимальные, на весь job, который трогает прод;
- стоит `npm ci --no-audit` — проверка зависимостей явно отключена;
- любой коммит в `main` — немедленный деплой, без согласования и без «окружения».

Само по себе это не взлом, это оружие, которое окажется в чужих руках, если взломают репозиторий или зависимость.

**Как чинить (быстро, бесплатно):**
1. Добавить в job блок `permissions: contents: read`.
2. Добавить перед деплоем шаг `npm test` и `npm run typecheck`.
3. Убрать `--no-audit`, добавить отдельный шаг `npm audit --audit-level=high`.
4. Включить защиту ветки `main` в GitHub: запрет прямых пушей, обязательный PR и хотя бы одно подтверждение.

### В-4. Ссылка для входа в проде собрана неправильно

**Где:** `backend/src/services/auth.ts:172-177`, `backend/wrangler.toml:54`
**Опасность:** высокая, вход может не работать вовсе

В проде `FRONTEND_URL` задан **списком через запятую** (чтобы CORS принимал оба домена). Но код отправки письма список не разбирает и подставляет его целиком:

```ts
const base = env.FRONTEND_URL.replace(/\/+$/, "");
return `${base}/auth/callback?token=${token}`;
```

На выходе ссылка вида `https://listai-prototype.pages.dev,https://www.rabochielisty.ru/auth/callback?token=...` — такой URL не открывается. При этом `cors.ts` этот же список разбирает корректно.

**Как чинить:** ввести отдельную переменную `APP_PUBLIC_URL` со значением одного origin для генерации ссылок, а список оставить только для CORS. Или разбирать список и брать первый элемент в `buildMagicLinkUrl` — но отдельная переменная понятнее и безопаснее.

### В-5. Защитных HTTP-заголовков нет нигде

**Где:** `next.config.mjs:2-6`
**Опасность:** высокая, снижает планку атаки

В конфиге Next.js нет функции `headers()`, и на Cloudflare Pages нет файла `public/_headers`. Не выставляются:
- `Strict-Transport-Security` — браузер не запрещает небезопасные подключения;
- `X-Frame-Options` / `frame-ancestors` — сайт можно встроить в чужую страницу (клик-джеккинг);
- `Referrer-Policy` — токены из адресной строки могут утечь в чужие сервисы аналитики;
- `Content-Security-Policy` — нет ограничения источников скриптов;
- `X-Content-Type-Options: nosniff`.

**Как чинить:** добавить `headers()` в `next.config.mjs` (для статического экспорта) и/или `public/_headers` для Pages. Начать с HSTS, `nosniff`, `frame-ancestors 'none'` и `Referrer-Policy: strict-origin-when-cross-origin` — это буквально 20 строк.

## 🟡 СРЕДНИЕ НАХОДКИ

### С-1. Сессионный токен возвращается в теле ответа

**Где:** `backend/src/routes/auth.ts:79`

Помимо cookie, токен возвращается в JSON: `sessionToken: result.sessionToken`. Cookie сделана правильно (HttpOnly), но если в теле ответа его читает скрипт — достаточно любой XSS или вредоносного расширения браузера, чтобы украсть токен. Классическое правило: **токен возвращается только в HttpOnly-cookie**, в теле — никогда.

**Фикс:** удалить поле из ответа. Фронт, судя по проверке, токен из ответа не использует — он работает через cookie.

### С-2. Чтение чужого рабочего листа по ссылке

**Где:** `backend/src/routes/worksheets.ts:168-173`

`GET /api/worksheets/:id` отдаёт лист **без проверки владельца**. Идентификаторы случайные (12 символов), поэтому подобрать их перебором нельзя, но ссылка может утечь через историю браузера, `Referer` или мессенджер.

**Фикс:** если лист принадлежит пользователю — отдавать только владельцу; для общих ссылок завести явный флаг `is_shared` и отдельный токен, как уже сделано для форм (`forms.token`). Плюс закрыть утечку через `Referrer-Policy` из В-5.

### С-3. Ручка эмбеддингов открыта и не ограничена

**Где:** `backend/src/routes/llm.ts:29-44`

`POST /api/llm/embeddings` работает без входа и **без ограничения частоты**, принимает до 100 текстов по 8000 символов за вызов. Это готовая точка расхода вашего бюджета. Ответ дополнительно содержит поле `costUsd` — лишняя деталь для наружу.

**Фикс:** добавить `rateLimitMiddleware` (например 60/час на IP) и убрать `costUsd` из ответа. Если фича не используется фронтом — вернуть 404 до лучшего времени.

### С-4. Зависимости: устаревшая major-версия Next.js

**Где:** `package.json` (`next: 14.2.35`), сборка в CI на Node 22

`npm audit` в корне: **2 critical, 9 high** (23 advisory на пакет `next`).

**Проверено, применима ли хоть одна из них к этому проекту.** Проведён разбор каждой advisory против реальной конфигурации:

| Механизм уязвимости | Есть в проекте | Advisory применима |
|---|---|---|
| RCE на Windows-хосте | Сборка в CI на `ubuntu-latest`, деплой на Cloudflare Pages | ❌ нет |
| RCE в Image Optimization при AVIF | `images: { unoptimized: true }`, AVIF не используется | ❌ нет |
| SSRF/RCE в Server Actions | Директивы `"use server"` в коде отсутствуют | ❌ нет |
| SSRF в `rewrites` | `rewrites` в `next.config.mjs` нет | ❌ нет |
| Обход Middleware в Pages Router с i18n | `src/middleware.ts` отсутствует, i18n нет | ❌ нет |
| DoS через Server Components | Статический экспорт, `src/app/api` — пустая директория, RSC-сервера нет | ❌ нет |
| Утечка эндпоинтов Server Function | Server Actions не используются | ❌ нет |

**Вывод: обе critical и большинство high к этому продукту неприменимы.** Проект собирается как чистый статический экспорт — серверного рантайма Next.js, в котором живут эти уязвимости, у него просто нет. Голый `npm audit` здесь бьёт ложно: он не различает «пакет с advisory» и «код, который этот advisory вызывает».

**Что реально остаётся риском:** не конкретная CVE, а то, что ветка 14.2 — двухлетняя, и advisory продолжают приходить. Пока версия старая, `npm audit --audit-level=high` нельзя сделать блокирующим никогда: он всегда красный, и сигнал перестаёт работать.

**Почему апгрейд не сделан в этом заходе.** Проверено и подтверждено: репозиторий параллельно редактируется другой сессией (в дереве одновременно появляются и исчезают файлы, `main` попал в рассогласованное состояние). Апгрейд major-версии Next.js затрагивает конфиг, сборку и сотни вызовов по всему `src/`, и в таком окружении почти наверняка затерел бы чужую незавершённую работу. Это отдельный заход на чистом дереве.

### Решение владельца: апгрейд не делаем (2 октября 2026)

Вопрос «а не столкнёмся ли мы снова с проблемами сборки» снят проверкой по фактам. Ответ — **нет, при текущей версии не столкнёмся**, потому что обе проблемы уже обойдены в коде.

**Проблема 1 — `next build` зависал на фазе проверки типов/линта.** На M2 Air сборка доходила до конца артефактов, но процесс не завершался. Обход уже стоит в `package.json`:

```json
"build": "tsc --noEmit && next build --no-lint",
"build:full": "next build"
```

Проверка типов не потеряна — она вынесена в `tsc --noEmit` и стала даже жёстче, чем была в CI (там `typecheck` шёл мягко, с `|| echo warning`, а теперь ошибка роняет сборку). Сборка работает: `out/` собран сегодня в 10:52, все 6 заголовков безопасности на месте.

**Проблема 2 — `next dev` зависает на Node 23.** Решается версией Node: в `package.json` нет движка, а `.github/workflows/deploy.yml` и README явно требуют Node 22. В CI это уже закреплено, локально — инструкцией в README.

**Ключевое для будущего решения.** Проблема 1 — не баг этой версии Next.js, а свойство того, что `next build` прогоняет ESLint. По документации Next.js:

- в **15.5** команда `next lint` уже помечена устаревшей, но `next build` **всё ещё** гоняет линтер, если рядом есть ESLint-конфиг;
- автоматический линт при сборке **убрали только в Next.js 16**.

Значит, апгрейд на 15.x проблему не снимет — нужен именно 16. И только тогда флаг `--no-lint` станет не нужен, а `tsc --noEmit` в скрипте можно будет оставить как есть.

**Когда возвращаться к вопросу:** при планировании перехода на Next.js 16+, не раньше. Планировать это стоит в момент, когда в команде нет параллельной работы над репозиторием — на 2 октября 2026 дерево правилось 15 файлами за час, и апгрейд major-версии с высокой вероятностью затёр бы чужую незавершённую работу.

**План апгрейда (когда будет окно):**
1. Дождаться зелёного дерева и закоммитить всё, включая правки безопасности из этого отчёта.

**Защита данных**
- **Все SQL-запросы параметризованы.** Ни одной собранной строкой команды — инъекция невозможна. Явно искал по всему бэкенду.

**Вход в аккаунт**
- Токен сессии **не хранится в браузере** — только HttpOnly + Secure cookie. Это лучше, чем у большинства проектов.
- Ссылка для входа одноразовая и атомарно гаснет при использовании (есть тест на повторное применение).
- Срок жизни ссылки — 15 минут, есть ограничение на частоту запросов.
- **Нет раскрытия, зарегистрирован ли email** — защита от перебора учёток, сделана осознанно.

**Прочее**
- Ввод пользователя проверяется до обращения к платной модели: блокируется мусор, слишком длинный текст и типовые шаблоны prompt-injection.

- Вывод модели экранируется при вставке в SVG и в формулы.

## 🔴🔴 БОЕВОЙ ВОРКЕР ЗАДЕПЛОЕН С НАСТРОЙКАМИ РАЗРАБОТКИ

Самая дорогая находка всего аудита. Обнаружена 2 октября 2026 в 11:15 сверкой **фактического состояния воркера** в Cloudflare, а не чтением кода.

Задеплоенный воркер `rabochielisty-api` имеет:

| Переменная | Значение в проде | Должно быть |
|---|---|---|
| `APP_ENV` | **`development`** | `production` |
| `FRONTEND_URL` | **`http://localhost:3000`** | прод-домены |
| `APP_BASE_URL` | **`http://localhost:8787`** | прод |
| `APP_PUBLIC_URL` | **отсутствует** | прод-домен |

Признак — боевой `/healthz` отдаёт `{"env":"development"}`, и в коде такого поля уже нет (правка убирала его как утечку). То есть **на сервере старая версия кода**.

**Почему это дороже всех остальных находок.** Пока `APP_ENV` равно `development`, работает худший сценарий сразу по трём фронтам:

1. **Вход открыт.** Ссылка для входа возвращается прямо в ответе на запрос. Любой посетитель входит в любой аккаунт, зная чужой email. Дыра К-2 в проде не «теоретическая» — она активна.
2. **Оплата симулируется.** Ключей ЮKassa нет → код уходит в dev-режим, где клиент знает `paymentId` и может дослать поддельное `payment.succeeded`. Подписку можно получить бесплатно.
3. **Письма уходят с адресом localhost.** Даже после задания `RESEND_API_KEY` письмо пришло бы со ссылкой `http://localhost:3000/auth/callback?token=…`, которую открыть негде.

**Это отменяет моё более раннее утверждение.** Я писал: «после выкатки вход будет отдавать ошибку — работать не сможет, но и взломать будет нельзя». **Это было неверно** при данной конфигурации: защита опиралась на `APP_ENV === "production"`, а на проде этот флаг был неверным, и защита выключилась бы молча. Проверить это по коду было невозможно — в коде всё выглядело правильно.

### Что изменено в коде после этого

Защиты переведены с «в проде нельзя» на **явное разрешение**: опасное поведение включается только положительным флагом и по умолчанию запрещено **везде**, включая прод.

| Поведение | Прежде | Теперь |
|---|---|---|
| Ссылка входа в ответе | выдавалась, если `APP_ENV != production` | только при `ALLOW_DEV_MAGIC_URL=true` |
| Симуляция оплаты | работала, если `APP_ENV != production` | только при `ALLOW_DEMO_PAYMENTS=true` |
| Ссылка входа на localhost | уходила в письмо | отвергается с явной ошибкой в лог |

`APP_ENV` больше не влияет ни на одну из этих защит: даже если он врёт, закрыто останется.

Добавлена самопроверка окружения `checkPublishedEnvironment` — она ловит деплой из `[vars]` вместо `[env.production.vars]` и пишет в лог, какие именно значения неверны. Покрыто тремя тестами: вход закрыт при `APP_ENV=development`, оплата не симулируется при `APP_ENV=development`, ссылка на localhost отвергается.

### Источник поломки найден: скрипт деплоя

`backend/scripts/deploy.sh` был написан с комментарием «деплой в production (env.production из wrangler.toml)», но выполнял:

```sh
npx --yes wrangler deploy          # ← без --env production
```

Так работает wrangler: без `--env` публикуется **верхнеуровневая секция** конфига, а `[env.production.vars]` не участвует. То есть скрипт молча выкатывал `[vars]` — то самое окружение разработки — и называл это продом. Аргумент `staging`, описанный в шапке скрипта, в коде нигде не использовался.

Ключевое: автор верил, что деплой идёт в production, и комментарий это подтверждал. В коде и в git всё выглядело правильно — ошибка была в одном аргументе командной строки, который никто не перепроверял.

**Что изменено:**

1. Окружение передаётся явно: `deploy.sh` по умолчанию вызывает `npx wrangler deploy --env production`, а `deploy.sh staging` — без флага.
2. **Деплой теперь проверяет себя.** После публикации скрипт читает фактические vars воркера через Cloudflare API и сверяет: `APP_ENV` должен быть `production`, `FRONTEND_URL` — не локальный, `ALLOW_*` — не включены. При несовпадении скрипт **падает с ненулевым кодом** и печатает, что именно сломано.

Проверка протестирована на шести случаях: текущий прод (находит **оба** дефекта), корректный прод (пропускает), прод с включённой дырой (находит), список доменов через запятую (ложно не срабатывает), прод со врущим `APP_ENV` (находит), пустой `FRONTEND_URL` (находит).

Теперь молчаливый неверный деплой невозможен: он либо не случится, либо упадёт.

### Что нужно сделать владельцу

**Первый приоритет — задеплоить воркер в правильном окружении:**
```bash
cd backend
npx wrangler deploy --env production
```
Без этого остальные меры (ключи, заголовки, тесты) теряют смысл: вход и оплата останутся в небезопасном режиме.

**Второй приоритет — задать секреты** (иначе после правильного деплоя вход и оплата не заработают, и это будет правильно: работать не сможет, но и взломать нельзя):
```bash
npx wrangler secret put RESEND_API_KEY --name rabochielisty-api
npx wrangler secret put YOOKASSA_SHOP_ID --name rabochielisty-api
npx wrangler secret put YOOKASSA_SECRET_KEY --name rabochielisty-api
```

**Третий — проверить, что деплой идёт в правильное окружение в скриптах.** Если деплой запускается без `--env production`, проблема вернётся после следующего раза.

**Проверено, что не так сейчас (11:05).** Р��позиторий по-прежнему активно правится: за час до проверки менялось 15 файлов, включая `backend/src/index.ts`. Дерево почти цельное — 7 ошибок типизации, все в `src/routes/interactives.ts`, который сейчас в работе.

### Почему `main` сломан именно так

`main` попал в состояние «импорт есть, файла нет» не из-за ошибки в правке, а из-за **частичного коммита**: `git add` в тот момент увидел `index.ts` (он уже содержал мой импорт) и не увидел новый файл `origin.ts`. Пока идёт параллельная работа, любой коммит может снять такой снимок снова.

### Как починить за один шаг

Дерево сейчас достаточно цельное, поэтому безопасный вариант — **один коммит на всё дерево**, а не выборочный. Выборочный коммит воспроизведёт ровно ту же поломку: `index.ts` попадёт в коммит, а часть нужных ему файлов — нет.

```bash
cd /Users/ivanlausnikov/Documents/nameone

# 1. Убедиться, что зелёного не ожидаем: показать, что именно изменилось
git status --short

# 2. Один коммит на всё дерево
git add -A && git commit -m "fix(security): закрыть дыры аудита ИБ + текущие правки"

# 3. Проверить, что main снова собирается
git show HEAD:backend/src/middleware/origin.ts > /dev/null && echo "origin.ts в main — порядок"
```

Если незавершённая работа параллельной сессии выкатывать нельзя — тогда `main` придётся починить иначе: убрать из `index.ts` одну строку импорта и регистрацию `originGuard` (три строки) отдельным коммитом, а мои правки довыкатить позже целиком. Это хуже: между коммитами дыры останутся открытыми.

**Что сделать: закоммитить рабочую копию.** Правки безопасности лежат в рабочей копии полностью и проверены. Как только они попадут в коммит, расхождение исчезнет.

**Побочный вывод для процесса.** Пока в репозитории идёт параллельная работа, коммиты снимают снимок дерева в произвольный момент — и могут захватить половину чужой правки. На время такой работы безопаснее вести изменения отдельной веткой.
