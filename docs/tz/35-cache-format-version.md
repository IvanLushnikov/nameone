# ТЗ-35: Версия формата в ключе семантического кэша

> **Статус:** 🔴 Не начато.
> **Приоритет:** 🔴 критичный · **Волна:** 1 · **Трудоёмкость:** 2 дн
> **Закрывает проблемы:** Q-05, M-12, частично Q-12 (версия промпта)
> **Блокирует:** TZ-38 (план листа меняет промпт → версия обязана быть поднята)
> **Источник:** `docs/research/2026-10-29-quality-findings.md` — карточка Q-05;
>   `docs/research/2026-10-29-money-findings.md` — карточка M-12

## 1. Контекст и зачем

Учитель дважды за один вечер делает лист по теме «Обыкновенные дроби», 5 класс,
12 заданий. Первый лист — нормальный: у каждого задания есть метка навыка, ни
одного смешанного числа. Второй лист — другой: метки `skill` пустые у всех
двенадцати заданий, в поле качества нет ни `repeatedSkills`, ни
`tasksWithoutAnswer`, а в задании №5 — «Вычислите и запишите ответ в виде
несократимой дроби **или смешанного числа**: 1 2/9 + 2 4/9». Смешанные числа в
5 классе прямо запрещены правилом 13 промпта (добавлено 13.10.2026).

Один и тот же запрос — два разных материала. Разница только в том, что первый
ушёл в кэш.

Причина в том, что **ключ кэша описывает запрос, но не описывает правила, по
которым ответ был получен**. В ключе есть предмет, класс, тема, сложность,
число заданий, тип и владелец. Версии промпта и схемы ответа в нём нет. TTL
записи — 30 дней.

Учитель при этом не получает никакого предупреждения: на попадании в кэш
`quality` приходит из записи, где этих полей ещё не было, — а условие показа
предупреждения о повторе (`quality.repeatedSkills > 0`) просто не выполняется.

## 3. Технический дизайн

| Файл | Что меняем |
|---|---|
| `backend/src/llm/cache.ts` | Вводится константа версии формата; она входит в канонический ключ; добавляется правило её подъёма |
| `backend/tests/unit/cache-format-version.test.ts` (новый) | Тесты на ключ и на подъём версии |

**Что НЕ меняется:** таблица `semantic_cache` (миграция не нужна), логика
чтения и записи, `backend/src/llm/index.ts`, промпты, фронт.

### Контракты

```ts
// backend/src/llm/cache.ts

/**
 * Версия формата ответа и правил его сборки.
 *
 * Меняется ВСЕГДА, когда меняется:
 *   · системный промпт листа (любое правило, любую формулировку);
 *   · схема ответа (новое поле в `quality`, новый тип задания);
 *   · код, который собирает ответ (правила чистки, фильтрации, нумерации).
 *
 * Старые записи кэша после подъёма просто перестают использоваться: ключ
 * не совпадает, запись не находится, кэш пуст. Миграция не нужна.
 */
export const FORMAT_VERSION = 2;

/** Версия входит в ключ: материал, собранный по другим правилам, не отдаётся. */
export function makeCacheKey(input: CacheKeyInput | GenerationRequest): string;
```

В канонический JSON добавляется одно поле:

```ts
const canonical = JSON.stringify({
  subject, grade, topic, difficulty, count, type, userId,
  formatVersion: FORMAT_VERSION,   // ← новое
});
```

### Правило подъёма версии (обязательно к исполнению)

Поднимать `FORMAT_VERSION` **в том же коммите**, в котором меняется:
- системный промпт любого типа материала (`backend/src/llm/prompts/**`);
- схема ответа (`backend/src/types.ts`, `QualityLossInfo`, `VariantStatusInfo`);
- код сборки ответа (`backend/src/llm/index.ts` — чистка, фильтрация, нумерация).

Чтобы правило не забывалось, в `backend/tests/unit/cache-format-version.test.ts`
добавляется проверка: **хэш системного промпта листа зафиксирован в тесте.**
Если промпт изменился, а версия — нет, тест падает с понятным сообщением.
Хэш считается по содержимому `WORKSHEET_GEN_SYSTEM` и по строке формата ответа.

```ts
// Ожидаемая форма теста
const PROMPT_HASH = "…"; // пересчитывается скриптом, см. §8
expect(hashOf(WORKSHEET_GEN_SYSTEM)).toBe(PROMPT_HASH);
```

Это закрывает половину Q-12: сегодня «версия промпта» — это комментарий в
шапке файла, который человек должен не забыть обновить. После этой задачи
версия — число в коде, за которым следит тест.

## 4. Решения

**AD-1 · Версия в ключе, а не проверка при чтении.**
Ключ включает версию; старые записи просто не находятся.
*Рационал:* вариант «хранить версию в записи и сверять при чтении» требует
правки схемы записи и миграции. Ключевой вариант — одна строка, ноль миграций,
ноль риска.

**AD-2 · Миграции базы не делаем.**
Записи с прежним ключом просто умрут по TTL. Данных в них нет — только
сгенерированный материал, который всё равно устарел.
*Рационал:* миграция `semantic_cache` на проде — это операция с таблицей,
которую никто не чистит, ради экономии места, которое не является проблемой.

**AD-3 · Версия одна на оба вида правил — промпт и схема ответа.**
Не две отдельные версии.
*Рационал:* кэш хранит и правила, и форму ответа. Расходятся они вместе —
промпт изменился, схема обычно тоже.

**AD-4 · TTL не трогаем.**
30 дней остаются. Версия в ключе решает проблему «старый материал», а не
проблему «кэш живёт долго».
*Рационал:* сокращение TTL — это отдельное решение с побочным эффектом: кэш
перестанет работать как ускоритель для повторных открытий одного материала.
Сначала версия, потом (если понадобится) TTL.

**AD-5 · Тест на хэш промпта — в бэке, рядом с кэшем.**
Он падает сам, без чтения ключа.
*Рационал:* правило «поднять версию» невозможно enforce'ить иначе: через
ревью, через комментарий, через память разработчика.

**AD-6 · Название константы — `FORMAT_VERSION`, не `PROMPT_VERSION`.**
Потому что версия покрывает и схему ответа, и код сборки.
*Рационал:* имя, которое шире сути, вводит в заблуждение через полгода.

## 5. Критерии приёмки

Функциональные:
- [ ] `makeCacheKey` для одинакового запроса даёт разные ключи при разной `FORMAT_VERSION` (проверяется подстановкой значения в тесте).
- [ ] Ключ для запроса учителя А не совпадает с ключом для запроса учителя Б (регрессия на `userId` в ключе).
- [ ] Ключ не зависит от регистра темы и от лишних пробелов (регрессия на нормализацию).
- [ ] Запись в кэше, сделанная до подъёма версии, **не отдаётся** после подъёма: интеграционный тест «сохранить → сменить версию → прочитать → промах».

Регрессионные:
- [ ] Обычный повторный запрос по той же тете (без `bypassCache`) по-прежнему попадает в кэш и не тратит деньги — при одной и той же версии.
- [ ] Контрольная с двумя вариантами по-прежнему кэшируется парой, и второй вариант не теряется.
- [ ] Существующие тесты кэша (ТЗ-26, `backend/tests/unit/**cache**`) — зелёные.

Качественные:
- [ ] В шапке `backend/src/llm/prompts/worksheet-gen.ts` вместо ручного «дата — что изменилось» стоит ссылка на `FORMAT_VERSION` и правило подъёма.
- [ ] Тест на хэш промпта падает, если промпт изменён без подъёма версии (проверяется: временно правим промпт в рабочей копии → тест красный → откат → зелёный).
- [ ] НОВЫЕ тесты падают на старом коде: без `FORMAT_VERSION` в ключе тест «разные версии → разные ключи» красный. Результат прикладывается к отчёту.

## 6. Чего не делаем

- **Не удаляем старые записи из базы.** Они умрут сами.
- **Не меняем TTL.**
- **Не расширяем ключ «похожими темами»** — строгий ключ держит кэш полезным.
- **Не переносим версию в `index.ts`.** Она живёт рядом с ключом.
- **Не меняем промпты в этой задаче.** ТЗ-35 ничего не пишет в промпты — оно только вводит дисциплину версий. Правка промпта = подъём версии, и первая такая правка будет в TZ-37/TZ-38, где это осознанно.
- **Не добавляем зависимостей.**

## 7. Риски

| Риск | Вероятность | Цена | Что делаем |
|---|---|---|---|
| Кэш перестанет работать как ускоритель (каждый повтор — реальная генерация) | Средняя | Средняя — деньги на лишние вызовы | Подъём версии — разовое событие; после него кэш работает как раньше |
| Забытый подъём версии → снова отдаётся старый материал | Средняя | Средняя | Тест на хэш промпта падает сам; правило — в шапке промпта и в этом ТЗ |
| Тест на хэш станет «шумным» (падает на любом косметическом изменении промпта) | Средняя | Низкая | Хэшировать только `WORKSHEET_GEN_SYSTEM` и строку формата ответа; правка промпта поднимает версию — это правильно, а не шум |
| Ключ станет длиннее и переполнит индекс D1 | Низкая | Низкая | Ключ — djb2-хеш, длина фиксированная (16 hex-символов) |

## 8. Порядок работ

1. (0,5 дн) `FORMAT_VERSION` в `cache.ts`, поле в канонический JSON, тест «разные версии → разные ключи». **Первая точка приёмки: тест красный на старом коде.**
2. (0,5 дн) Интеграционный тест «запись со старой версией не отдаётся».
3. (0,5 дн) Тест на хэш системного промпта + правило подъёма в шапке промпта.
4. (0,5 дн) Прогон бэкенд-тестов, `npm run typecheck`.

**Как пересчитывать хэш промпта в тесте** (команда для исполнителя, не для
репозитория):

```bash
cd backend && npx tsx -e "import {WORKSHEET_GEN_SYSTEM} from './src/llm/prompts/worksheet-gen';
import {createHash} from 'node:crypto';
console.log(createHash('sha256').update(WORKSHEET_GEN_SYSTEM).digest('hex').slice(0,16));"
```

Хэш вставляется в тест как константа. Тест обязан падать на старом коде и
зелёный после правки.

## 9. Что не удалось подтвердить

- **Сколько записей в `semantic_cache` сейчас на проде.** Снимок D1 от 29.10.2026
  содержит только текст SQL-запросов: все они упали с `/tmp/q.sh: No such file or
  directory`, ни одного числа из базы в файле нет. Реальное число записей
  неизвестно; на оценку усилий это не влияет (миграции нет), но на «сколько
  материала сейчас в кэше» — влияет.
- **Доля попаданий в кэш от всех генераций.** Не измерена по той же причине.
  Из живых прогонов известно: попадание есть (r1, r3, r4, r7 — `latencyMs` 753–778,
  `costUsd: 0`).
- **Есть ли в кэше записи, созданные ещё до появления `skill` и `repeatedSkills`.** Определённо есть: это и есть наблюдаемая проблема. Сколько именно — по базе без доступа не считается.
