## 2. Доказательство закрытия по находкам

### №1. Плановая уборка

**Что было.** Cloudflare вызывает cron только через экспорт `scheduled` модуля воркера. Модуль отдавал `export default app` — объект Hono без такого метода, — а обработчик висел на `app.fire(...)`. В Hono 4.13 `fire` — deprecated-хелпер для Service-Worker-совместимости (`addEventListener("fetch", …)`), а **не** диспетчер событий Cloudflare.

Побочная находка: предложенный в исходном промпте вызов `app.fire("scheduled", event, env, ctx)` несовместим с прежним перекрытием — оно принимало три аргумента `(event, env, ctx)`, и строка `"scheduled"` ушла бы вместо события. Поэтому перекрытие убрано целиком, а cron стал отдельной функцией `handleScheduled`.

**Код сейчас** (`backend/src/index.ts`):
```ts
export default {
  fetch: app.fetch,
  scheduled: handleScheduled,
};
```

**Доказательство 1 — локальный прогон `__scheduled`:**
```

$ curl "http://localhost:8787/__scheduled?cron=0+3+*+*+*"

### №2. Соль отпечатка

**Что было.** `env.FINGERPRINT_SALT ?? "dev-fingerprint-salt"` в восьми местах. Секрета на боевом воркере нет (`wrangler secret list` от 30.10: `ADMIN_EMAILS, JWT_SECRET, POLZA_API_KEY, RESEND_API_KEY, TOTP_ENCRYPTION_KEY`), значит в проде молча считался хэш с публичной константой из исходников.

**Код сейчас** (`backend/src/lib/antifraud.ts`): `fingerprintSalt(env)` — в production без соли бросает `ServiceMisconfiguredError` (503 `SERVICE_MISCONFIGURED`) и пишет причину в лог; локальной разработке и тестам хватает локальной заглушки, которая не похожа на прежнюю публичную константу.

**Проверки:**
```

(пусто)
$ grep -n "FINGERPRINT_SALT" backend/src/index.ts

**Состояние боевой базы:** `SELECT COUNT(*) FROM fraud_signals` → **107**. Это те строки, что посчитаны с публичной солью: они перебираются за секунды, и таблица отпечатков фактически стала справочником по IP. Смена соли их обесценивает — чистить вручную не нужно, но знать про них надо.

### №4. Чужой лист в избранном

**Что было.** `addFavorite` делал только `SELECT id FROM worksheets WHERE id = ?1` — проверку факта существования. Чужой лист не перезаписывался, но в `favorites` учителя писалась ссылка на него, а `GET /api/users/favorites` отдавал `payload_json` листа через JOIN, фильтруя по таблице избранного, а не по листу. Так обходилась защита `GET /api/worksheets/:id`, где владелец сверяется.

**Что сделано:**
- **Запись:** сверка владельца перед вставкой. Тот же policy, что в F-07 (`backend/src/routes/f07.ts`): лист с владельцем, и владелец — не ты, недоступен. Лист без владельца (анонимная генерация) — обычное дело.
- **Чтение:** фильтр `w.user_id IS NULL OR w.user_id = ?1` в `GET /api/users/favorites`. Это закрывает и строки, созданные **до** починки: без фильтра они продолжили бы отдавать чужой payload.
- **Тело:** zod-схема вместо `as { worksheet: Worksheet }`. Раньше запрос без `tasks` давал 500 на `worksheet.tasks.length`, теперь — 400 с кодом `VALIDATION_ERROR`.

**Состояние боевой базы:**
```
$ SELECT COUNT(*) FROM favorites f JOIN worksheets w ON w.id = f.worksheet_id
  WHERE w.user_id IS NOT NULL AND w.user_id <> f.user_id
n: 0
```
Строк, ссылающихся на чужой лист, в проде нет — и `favorites` вообще пуста (0 строк при 184 листах и 41 учителе). То есть находка закрыта в коде, а по живому продукту ещё не успела ударить.

**Регрессия, которую пришлось поймать по ходу.** zod по умолчанию **выбрасывает** неизвестные ключи, а `payload_json` потом читается обратно. Первая версия схемы срезала `text_latex` (дробь печаталась бы в одну строку), `skill` (метка темы для ведомости), `chartSpec` и `isDemo` (водяной знак «заготовка»). Поля перечислены в схеме явно, а на это есть отдельный тест.

### №6. Вебхук ЮKassa

**Сначала — проверка посылки.** Находка требовала «сверять HMAC-подпись ЮKassa». ЮKassa **не подписывает** уведомления — сверять нечем. Официальная документация ЮKassa, раздел «Notification authentication», предлагает ровно два способа проверки подлинности уведомления:

> You can check the authenticity of a notification, for example, by the object status or IP address.
> — **Object status authentication**: check the current status of the object in the API.
> — **IP authentication**: check the IP address that the notification was sent from.

То же самое было написано в коде (`services/billing.ts`: «ЮKassa не подписывает уведомления») — ревью это упустило. Подпись не внедрялась: это была бы проверка, которая всегда отвергает настоящие уведомления.

**Что было опасного на самом деле.** Живая сверка платежа с API — единственная опора схемы (платёж есть в нашей БД + сумма совпадает с прайсом + сверка с API). И при ответе `unknown` (сеть, 5xx, 401) подписка **всё равно активировалась**: сверки не было, а активация проходила по данным БД и сумме из уведомления. Именно в этот день — когда API ЮKassa недоступен или ключи отозвали и заменили — поддельное `payment.succeeded` активировало подписку бесплатно.

**Что стало.** Сверка не удалась → подписка **не** активируется, платёж остаётся `pending`, ручка отвечает **503**. Для ЮKassa ответ с кодом не 2xx означает «не принято», и она повторяет уведомление ещё 24 часа после события — это и есть очередь на повторную сверку.

Путь без ключей ЮKassa (активация по данным БД) сохранён: без ключей платёж нельзя создать, то есть в бою это состояние недостижимо. Но теперь оно пишет ALERT в лог.

**Allowlist IP-адресов** (официальный список из документации) вынесен владельцу — это уровень Cloudflare, не код:
```
185.71.76.0/27   185.71.77.0/27   77.75.153.0/25   77.75.154.128/25
77.75.156.11     77.75.156.35     2a02:5180::/32
```

### №7. CSV как формула

**Что было.** `csvBytes` писал значения как есть: без кавычек и без защиты от ячеек, начинающихся с `=`, `+`, `-`, `@`. Excel и LibreOffice выполняют такую ячейку как формулу. Сценарий: учитель собирает комплект → отправляет архив коллеге → у коллеги при открытии CSV исполняется формула. Содержимое CSV приходит из ответа модели, куда попадает тема учителя, — то есть формулу можно подобрать темой задания.

Там же обычная поломка: запятая или точка с запятой внутри значения рвали строку таблицы.

**Что стало.** Каждое значение обёрнуто в кавычки (внутренние удваиваются — так требует CSV), перед опасным началом ставится апостроф (Excel и LibreOffice показывают его как признак текста и не выполняют ячейку). Числа апострофом не помечаются — иначе столбец температур («-5», «12,5») превратился бы в текст и перестал сортироваться.

### №8. Тип загруженного файла

**Что было.** Тип брался из заголовка, который прислал клиент (`File.type`), и сервер верил ему на слово. Учитель или ученик мог положить HTML или SVG с заголовком `image/jpeg`, и сервер это принимал; в R2 файл ложился с этим же contentType.

**Что стало.** Тип определяется по первым байтам (JPEG `FF D8 FF`, PNG — 8 байт сигнатуры, WebP — `RIFF….WEBP`) и сверяется с заявленным. Несовпадение отклоняется; в R2 кладётся contentType по содержимому. Обе точки входа: фото работы учителя (`routes/f06.ts`) и фото ученика по персональной ссылке (`routes/classes.ts`).

**Почему не КРИТИЧНО.** Бакет приватный, ни один роут не отдаёт байты R2 наружу — наружу фото уходит только воркеру для распознавания. Риск проснётся, если появится ссылка на файл или presigned URL. Проверка добавлена как страховка.

### №9. Текст модели в 502

**Что было.** В двух местах `llm/index.ts` в `details` ошибки 502 клался сырой ответ модели (до 200 символов). Глобальный обработчик отдаёт `details` клиенту — и в проде тоже, в отличие от стектрейсов, которые в проде не утекают.

**Что стало.** В `details` остались только код и модель; текст уходит в лог:

### №10. CSP в режиме report-only

**Что было.** CSP нет — это зафиксированное решение владельца от 02.10 (при строгом CSP ломаются Метрика и шрифты). Ломать решение не стали.

**Что сделано — безопасный следующий шаг:**
- `Content-Security-Policy-Report-Only` в `public/_headers` — **не enforce**: браузер ничего не блокирует, а сообщает о каждом нарушении;
- инвентаризация внешних доменов с объяснением, откуда каждый:

| Домен | Зачем | Директива |
|---|---|---|
| `mc.yandex.ru` | Метрика: скрипт `tag.js`, пиксель `watch/`, beacon-запросы | script-src, img-src, connect-src |
| `challenges.cloudflare.com` | виджет капчи Turnstile: скрипт `api.js` и iframe | script-src, frame-src, connect-src |
| адрес API | фронт ходит в API из браузера | connect-src |
| шрифты KaTeX | **свои, не внешние**: `katex` лежит в `node_modules`, CSS подключается через `@import`, файлы шрифтов попадают в сборку | внешнего домена в `font-src` нет |
| `schema.org`, `t.me`, `obuchai.com`, `neuroom.ru`, `ilushnikov.ru` | не ресурсы: JSON-LD и обычные ссылки — CSP их не ограничивает | — |

- **приём отчётов** воркером: `POST /api/security/csp-report` пишет нарушения в лог (`wrangler tail`). Что в отчёте видно: какая директива сработала, какой адрес заблокирован, какой источник был — то есть ровно то, чего не хватает политике. В лог уходит **только источник документа**: в пути (`/form/<token>`, `/play/<token>`) и в query (`?token=…`) живут токены входа и ссылки учеников. Переводы строк вырезаются, тело отчёта ограничено 8 КБ, поток — rate-limit'ом.

**Что в отчёте НЕ будет видно:** на какой именно странице было нарушение (путь убран ради токенов). Для разбора хватает заблокированного адреса и директивы.

**Включать `enforce` — решение владельца**, и только после того, как отчёт покажет, что политика ничего не ломает. Для `enforce` придётся заменить `'unsafe-inline'` на хэши или nonce (статический экспорт Next.js вставляет инлайновые скрипты и стили).

## 7. Что сломалось по ходу

1. **Предложенный в промпте способ починки №1 не сработал бы как есть.** `app.fire("scheduled", event, env, ctx)` передаёт четыре аргумента, а прежнее перекрытие `app.fire` принимало три `(event, env, ctx)` — строка `"scheduled"` ушла бы на место события, `event.cron` стал бы `undefined`, а `ctx` потерялся бы. Починка сделана без этого перекрытия: cron — отдельная функция `handleScheduled`, а `scheduled` её вызывает.
2. **Первая версия zod-схемы избранного тихо ломала лист.** zod выбрасывает неизвестные ключи, а `payload_json` читается обратно: терялись `text_latex`, `skill`, `chartSpec`, `isDemo`. Поймано до коммита, поля перечислены явно, на это добавлен тест.
3. **Запрет на изменяющие ручки сначала сломал бы половину тестов.** Тесты гоняют воркер на фиктивных хостах (`local.test`, `api.test`), которые для воркера выглядят публичными. Решено явно: тестовой среде задан `ALLOW_INSECURE_MODES=true`, а в «прод-»-окружении теста отмашка выключена.
4. **Тест на вебхук сначала проходил по ложной причине.** 503 на POST давал запрет небезопасной конфигурации, а не логика вебхука. Замечено при проверке «падает ли тест на старом коде» — тест без явного `ALLOW_DEV_MAGIC_URL: "false"` проходил и на старом коде. Исправлено, теперь тест падает там, где надо.
5. **Проверка сигнатуры файла потребовала переписать чужие фикстуры.** `photoStack`, `photoCheckMultiPage` и `student-mobile` подкладывали байты-заглушки (0x01, 0x02 …), и это было законно: сервер верил заголовку клиента. Теперь фейковые фото выглядят как настоящие картинки — иначе тесты проверяли бы не то. Проверки при этом не ослаблены, а усилены: в `photoStack` метка страницы переехала за сигнатуру формата.
6. **Посылка находки №6 оказалась неверной** — ЮKassa не подписывает уведомления. Вместо проверки несуществующей подписи сделано то, что закрывает настоящую дыру (fail-closed при недоступной сверке). Вывод проверен по официальной документации ЮKassa, раздел «Notification authentication».
7. **Свой же тест на отчёты CSP поймал утечку токена.** Изначально в лог писался путь документа без query-строки — но на страницах ученика токен стоит именно В ПУТИ (`/form/<token>`). Теперь в лог уходит только источник документа.
8. **Правило «не смешивать пакеты» и «один коммит на пакет».** Правки по №1 сначала были отдельным коммитом — перед сдачей пакет 1 собран в один коммит `d3ebf64`, чтобы его можно было откатить одним движением.

### Сбой окружения, о котором стоит знать владельцу

31.10.2026, во время перепроверки работы выяснилось: **macOS вытеснил крупные файлы репозитория в облако**, и чтение их стало возвращать 0 байт. Симптомы выглядели как поломка кода: `git show` утверждал «path does not exist in 'HEAD'», `git ls-tree` висел, `vitest` падал на старте с `ERR_INVALID_PACKAGE_CONFIG`, а три фронтовых теста получали вместо исходников пустую строку. При этом `ls` показывал правильный размер файла, а `git status` был чистым.

Причина — файлы в состоянии «dataless»: содержимое вытеснено в iCloud (Optimize Storage), локально его нет. Под каталог попали три pack-файла git и часть loose-объектов — то есть **часть истории репозитория была нечитаема**, и это затронуло не только мою ветку.

Вылечено без потери данных: `brctl download .git/objects` вернул файлы на диск, после чего git и тесты заработали как обычно. Проверено заново: бэкенд 1234 теста, фронт 1429 — зелёные.

**Что делать владельцу:** если после сна или долгого простоя git или тесты начнут «ломаться» без причины — сначала проверить чтение файла (`python3 -c "print(len(open(файл,'rb').read()))"` против `os.path.getsize`), и если размер есть, а чтение пустое — выполнить `brctl download <путь>`. Правкой кода и `git gc`/`repack` в такой ситуации не заниматься: pack может оказаться единственной копией объектов. На время расследования содержимое моей ветки было скопировано и проверено по хэшам в `/tmp/nameone-security-backup/tree`.
