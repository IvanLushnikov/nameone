## 1. Контекст и зачем

Учитель заказывает контрольную работу по математике, 6 класс, «Пропорции»,
6 заданий. Ответ приходит: 12 заданий (два варианта), у каждого — баллы,
ответ, пояснение. **Критериев приёмки нет.** Во всём ответе — ноль вхождений
слов «критери», «оцени», «требован»; из оценочных полей есть только
`points: 1|2|3`, то есть вес задания в баллах.

Учитель платит 8,51 ₽ за контрольную (против 0,19 ₽ за лист — разница в 44
раза) именно потому, что контрольная нужна ему для оценивания. Оценивать
открытые задания по листу, где есть только «правильный ответ», он не может.

Обещание в тарифе есть: «Контрольная **с критериями оценивания** —
расходует тариф быстрее, чем рабочий лист» (`src/lib/content/plans.ts:394`) и
то же в «Плюсе» (`:478`).

Почему обещание не выполнено — не «модель забыла». В схеме ответа
(`backend/src/llm/prompts/worksheet-gen.ts:162-181`) **нет поля для
критериев**: их неоткуда взять даже при полном желании модели. Единственное
место, где «критерии» упоминаются, — правило 17 промпта: у задания типа
`essay` поле `answer` — это критерии приёмки. Но в живой контрольной заданий
типа `essay` не оказалось, и критериев не появилось ни в одном задании.

### Контракты

```ts
// backend/src/types.ts
export interface WorksheetTask {
  // … существующие поля …
  /**
   * Критерии приёмки: что считать правильным ответом на это задание.
   *
   * Заполняется только для контрольной работы. Для рабочих листов поле
   * пустое — там ключ и так однозначен.
   */
  criteria?: string[];
}
```

### Формат (два варианта, выбирает владелец — §7)

**Вариант A — отдельное поле у каждого задания.**

```json
{
  "number": 3,
  "text": "Найдите неизвестный член пропорции 3 : x = 12 : 8",
  "type": "short-answer",
  "answer": "x = 3",
  "criteria": ["верно найдено отношение 3:8", "получено x = 3", "ответ записан в виде x = 3"],
  "points": 2
}
```

**Вариант B — текст критериев в `explanation` для контрольной.**

Плюсы: ноль изменений в схеме и в экспорте (пояснение уже печатается). Минусы:
пояснение перестаёт быть пояснением, смешиваются две разные вещи, и в
«моих листах» это не отличить.

**Рекомендация: A** — с явным полем. Причина: критерии — это то, ради чего
контрольная и покупается, и они должны быть **отличимы** от пояснения. По
исследованию реестра, у живых контрольных в ответе не было ни слова «критери»
— то есть в текущем формате туда просто нечего положить.

### Что должно быть в критериях

Правило промпта (для контрольной):

```
КРИТЕРИИ ПРИЁМКИ (только контрольная):
У КАЖДОГО задания есть поле criteria — список из 1–3 проверяемых признаков
правильной работы. Это НЕ пересказ ответа и НЕ пояснение: это то, по чему
учитель принимает работу ученика.
Пример: задание «найдите x» → ["найдено отношение 3:8", "получено x = 3"].
Для заданий с выбором ответа критерий один: ["выбран верный вариант"].
```

### Проверка в коде

- Для `type === "control"` у каждого задания должен быть `criteria` —
  непустой массив строк. Если нет — задание получает признак в ответе API,
  а учитель видит сообщение «у N заданий нет критериев приёмки».
- Критерии не должны быть пересказом ответа: проверка «текст критерия не
  содержит текст ответа» — грубая, но ловит самый частый мусор.

## 4. Решения

**AD-1 · Отдельное поле `criteria`, а не текст в `explanation`.**
*Рационал:* критерии — самостоятельный артефакт, который учитель ищет
отдельно от пояснения. Смешивать их — значит через год не отличить одно от
другого.

**AD-2 · Критерии только у контрольной.**
*Рационал:* у рабочего листа ключ однозначен, критерии приёмки там не нужны,
а лишние поля раздувают ответ и расход токенов.

**AD-3 · 1–3 критерия на задание, короткими.**
*Рационал:* длинные критерии не читаются и съедают токены. Число ограничено в
промпте — и проверяется в коде (больше трёх — отбрасываем лишние, пишем в
лог).

**AD-4 · Отсутствие критериев — не тишина.**
Задание без критериев получает признак, учитель видит счётчик до печати.
*Рационал:* тот же принцип, что в ТЗ-32 (AD-4: пустой ключ не проходит
молча). Молчаливая пустота — это «учитель узнаёт на печати».

**AD-5 · Тарифное обещание возвращается только вместе с фичей.**
Если критерии не сделаны — текст остаётся как в TZ-37 («с ответами и
баллами»).
*Рационал:* обещание возвращается в том же релизе, в котором появляется
функция. Иначе мы повторяем тот же дефект, который чиним.

**AD-6 · Проверка «критерий ≠ пересказ ответа» — грубая.**
Строка критерия, содержащая текст ответа целиком, отбрасывается.
*Рационал:* полноценная проверка смысла требует ещё одного вызова модели —
это дороже, чем вся контрольная.

## 5. Критерии приёмки

Функциональные:
- [ ] Ответ контрольной содержит непустой `criteria` у каждого задания (живой прогон).
- [ ] В DOCX под ключом задания напечатан блок «Критерии приёмки» с пунктами списка.
- [ ] В превью учитель видит критерии до скачивания файла.
- [ ] Задание без критериев: в ответе API есть признак, на экране — счётчик «у N заданий нет критериев приёмки».
- [ ] Критерий, содержащий текст ответа целиком, не попадает в выдачу (отбрасывается, пишется в лог).
- [ ] У рабочего листа и теста поле `criteria` пустое — лишних токенов нет.
- [ ] В карточке тарифа «Базовый» и «Плюс» снова написано «Контрольная с критериями оценивания».

Регрессионные:
- [ ] Два варианта контрольной по-прежнему едут одним вызовом и одной попыткой.
- [ ] Ответы и пояснения на месте у всех заданий (`tasksWithoutAnswer = 0`).
- [ ] Число заданий контрольной не изменилось (6 на вариант).
- [ ] Существующие тесты ТЗ-25 (два варианта) и ТЗ-32 (ответы) — зелёные.

Качественные:
- [ ] Критерии в живом ответе осмысленны: в 10 заданиях контрольной — 10–30 пунктов, каждый про проверяемое условие, ни один не является пересказом ответа.
- [ ] НОВЫЙ тест падает на старом коде: на старом коде в ответе контрольной нет поля `criteria`. Результат прикладывается к отчёту.

## 6. Чего не делаем

- **Не добавляем критерии к рабочему листу и тесту.**
- **Не делаем отдельный вызов модели для оценки критериев.** Критерии — часть
  ответа контрольной.
- **Не пишем критерии кодом по шаблону.** Тогда они будут одинаковыми и
  бессмысленными.
- **Не переделываем экспорт в PDF.** В репозитории DOCX — рабочий формат.
- **Не меняем маршрутизацию:** контрольная по-прежнему идёт на Sonnet.
