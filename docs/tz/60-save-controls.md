# ТЗ-60: второй вариант контрольной сохраняется в базу

**Дата:** 30.10.2026
**Кто делает:** бэк (+ миграция базы)
**Размер:** S (одна колонка, одна миграция, одно изменение в записи, одно в чтении)
**Источник:** решение владельца 30.10.2026 («контрольные в базу — сохранять; не сохранять — исключено», `docs/research/03-prompt-quality-audit.md:938`), §6.5.1 исследования 03

**Влияет на кэш: НЕТ.** System-промпт, формат ответа генерации и ключ кэша не меняются: поле `secondVariant` в ответе генерации **уже есть** (`backend/src/routes/worksheets.ts:286`). `FORMAT_VERSION` не поднимаем, `PROMPT_HASH` не трогаем.

---

## 1. Контекст и зачем

Учитель сделал контрольную за вчера. Сегодня он открыл личный кабинет, нашёл её в истории — и видит **один вариант**. Второго нет ни в базе, ни где-либо ещё.

Что происходит в коде:

- Воркер отдаёт учителю **оба** варианта: `secondVariant` в ответе API (`backend/src/routes/worksheets.ts:286`), оба в памяти конструктора.
- В базу пишется **только первый**: `await saveWorksheet(c.env.DB, { userId, worksheet })` (`backend/src/routes/worksheets.ts:239`), где `worksheet` — это вариант 1 (`routes/worksheets.ts:233-236`).
- Второй вариант в `saveWorksheet` не попадает никуда. И когда вкладка закрыта — его больше нет нигде: `GET /api/worksheets/:id` читает только `payload_json` (`backend/src/services/worksheet.ts:84`), а в нём — вариант 1.

**Уточнение находки (перепроверено по коду 30.10.2026).** В исследовании написано «контрольных в `worksheets` — 0». Формулировка неточна: **первый** вариант контрольной в базе есть, он лежит обычной строкой. Ноль получается потому, что колонка `type` при сохранении жёстко записана как `"worksheet"` (`backend/src/services/worksheet.ts:34`) — по `type = 'control'` не найдётся ничего; и потому, что `variants` в `payload_json` нет — там лежит только вариант 1. **Теряется второй вариант**, а не вся контрольная. Это уточнение важно для замера: чинить нужно потерю варианта, а не «сохранение контрольных вообще».

**Почему это надо чинить сейчас, а не потом:**

1. **Качество контрольной нечем измерить.** Счётчик дефектов (ТЗ-59) считает то, что есть. Если второго варианта нет в базе — по контрольной нельзя посчитать ни дублей, ни чужого предмета, ни ответа-заглушки. При этом контрольная — самый дорогой материал (8,02 ₽ за вызов против 0,18 ₽ за лист) и самый частый запрос на критерии оценивания.
2. **Жалобы на контрольную нечем разбирать.** Жалобы 6 и 9 учительницы от 08.10 (`docs/30-feedback-cases-2026-10-08.md`) — про контрольную. Их нельзя превратить в счётчик дефектов, если материал не лежит в базе.
3. **Учитель теряет половину работы.** Контрольная без второго варианта — это не контрольная.

## 3. Технический дизайн

### 3.1. Схема

В таблицу `worksheets` добавляется **одна nullable-колонка**:

```sql
ALTER TABLE worksheets ADD COLUMN variants_json TEXT;
```

| Файл | Что меняем |
|---|---|
| `backend/src/db/schema.sql:169-181` | В `CREATE TABLE IF NOT EXISTS worksheets` добавляется строка `variants_json TEXT,` — чтобы свежая база создавалась сразу с колонкой (как в 0009) |
| `backend/src/db/migrations/0010_worksheet_variants.ts` | **новый.** Идемпотентная миграция: `PRAGMA table_info(worksheets)` → если колонки нет, `ALTER TABLE worksheets ADD COLUMN variants_json TEXT`. По образцу `0009_worksheet_cost_link.ts` |
| `backend/src/services/worksheet.ts:13-41` | `saveWorksheet` принимает необязательный `secondVariant` и пишет его в `variants_json`. Формат значения: `{"second": <объект Worksheet>}` |
| `backend/src/services/worksheet.ts` | **новый** `getWorksheetWithVariants(db, id)` → `{ worksheet, secondVariant }`. Существующий `getWorksheetById` не трогаем |
| `backend/src/routes/worksheets.ts:239` | В `saveWorksheet` передаётся `result.secondVariant` |
| `backend/src/routes/worksheets.ts:415-417` | Ответ `GET /api/worksheets/:id` дополняется полем `secondVariant` (когда он есть) |
| `backend/src/db/userResources.ts:228` | **не трогаем** — вставка избранного не знает второго варианта; колонка останется `NULL` |

### 3.2. Формат `variants_json`

```json
{ "second": { "id": "ws_…", "title": "Вариант 2", "subject": "math", "grade": 8, "tasks": [ … ], "createdAt": "…" } }
```

**Почему объект с ключом `second`, а не сам лист и не массив:**

- Сам лист без обёртки — пришлось бы гадать по форме, что это; обёртка `{"second": …}` читается однозначно.
- Массив `[v1, v2]` — пришлось бы дублировать первый вариант, который уже лежит в `payload_json`. Дублирование означает, что при правке одного из них они разойдутся.

Если в будущем появится третий вариант, ключ добавится в тот же объект — **миграция базы не понадобится**.

### 3.3. Что пишется

`saveWorksheet` получает необязательный параметр:

```ts
await saveWorksheet(c.env.DB, { userId, worksheet, secondVariant: result.secondVariant });
```

- `secondVariant` нет (обычный лист) → `variants_json` = `NULL`.
- `secondVariant` есть → `variants_json` = `JSON.stringify({ second: secondVariant })`.

Второй вариант сохраняется **целиком**: `id`, `title`, `subject`, `grade`, `topic`, `difficulty`, `tasks` (вместе с `criteria` и `text_latex`), `createdAt`. Именно целиком: без `criteria` оценить контрольную по критериям нечем, а критерии оценивания — это то, за что в тарифе платят.

### 3.4. Что читается

Новая функция `getWorksheetWithVariants` читает `payload_json` и `variants_json` одной выборкой и возвращает `{ worksheet, secondVariant }`. `secondVariant` — `null`, если колонка пуста.

`GET /api/worksheets/:id` начинает отдавать:

```json
{ "ok": true, "worksheet": { …вариант 1… }, "secondVariant": { …вариант 2… } }
```

Поле `secondVariant` **необязательное**: у обычных листов его нет. Клиенты, которые его не читают, ничего не теряют.

**Существующий `getWorksheetById` не меняется** — он вызывается ещё в трёх местах (`f07.ts`, `f08.ts`, `interactives.ts`), и смена его сигнатуры сломала бы их.

### 3.5. Применение миграции

Миграция **не наезжает на прод сама** — так же, как 0009: в шапке файла пишется команда, владелец выполняет её один раз:

```
cd backend && npx wrangler d1 execute rabochielisty --remote \
  --command="ALTER TABLE worksheets ADD COLUMN variants_json TEXT"
```

и отдельно — программный вызов `migrateWorksheetVariants(db)`. Миграция идемпотентна: повторный прогон ничего не делает.

**Колонка nullable** — старые строки (184 листа) остаются валидными, миграция данных не нужна, ничего не переписывается.

### 3.6. Что НЕ меняется

- Колонка `type` — **не трогаем** (см. AD-3: от неё зависит кнопка «Выдать классу» в истории).
- `getWorksheetById` и его четыре вызывающих места — не трогаем.
- Вставка избранного (`backend/src/db/userResources.ts:228`) — не трогаем.
- Кэш, system-промпт, формат ответа генерации, `FORMAT_VERSION` — не трогаем.
- Печать критериев в ключе, формула взвешенного токена, учёт по сумме всех вызовов, реестр типов задания — не трогаем.

## 4. Решения (AD-N)

**AD-1 · Второй вариант хранится в отдельной колонке, а не внутри `payload_json`.**
`payload_json` читается как `Worksheet` в четырёх местах (`getWorksheetById` и его вызывающие). Если положить туда ещё и второй вариант, тип перестанет соответствовать содержимому, а потребителям придётся разбирать, что за форму пришёл лист. Отдельная колонка: `payload_json` — это по-прежнему «один лист», `variants_json` — «дополнение».
*Рационал:* форма `payload_json` используется как тип `Worksheet` в четырёх местах и в печати. Менять её форму — это правка чужого кода; добавить колонку — не правка чужого кода.

**AD-2 · Контрольная остаётся одной строкой в базе, а не двумя.**
Одна работа — одна строка. Учитель делится одной ссылкой, история показывает один материал, `count` — это число заданий одного варианта.
*Рационал:* две строки означали бы две записи в истории одного материала и потребовали бы колонки-связи между ними. Счётчик и скрининг получают оба варианта из одной строки.

**AD-3 · Колонка `type` остаётся `"worksheet"` для всего, включая контрольные.**
В истории личного кабинета кнопка «Выдать классу» показывается только при `item.type === "worksheet"` (`src/app/dashboard/page.tsx:1159`, `:1176`). Сейчас в колонке у всех «worksheet», и кнопка есть у всех. Если начать писать «control» — кнопка исчезнет у контрольных. Это изменение поведения продукта, а не техника; оно не входит в эту задачу.
*Рационал:* мерить качество контрольной можно и по наличию `variants_json` — скрининг будет `WHERE variants_json IS NOT NULL`. А вот менять то, что видит учитель в кабинете, — отдельное решение владельца (вопрос 4 в пакете вопросов).

**AD-4 · Сохраняется второй вариант целиком, вместе с критериями.**
*Рационал:* контрольная продаётся с критериями оценивания («контрольная с критериями оценивания» — в карточке тарифа). Если сохранить вариант без `criteria`, то качество критериев — то, за что платят, — всё равно нечем мерить.

**AD-5 · Миграция идемпотентная и nullable.**
*Рационал:* прецедент 0009. Старые 184 листа остаются валидными без переписывания; повторный прогон миграции безопасен.

**AD-6 · Чтение расширяется новой функцией, а не изменением старой.**
*Рационал:* `getWorksheetById` вызывается в четырёх местах, и все они ждут `Worksheet | null`. Смена сигнатуры потянула бы правки в чужом коде (формы, интерактивы, доступ к листу).

**AD-7 · Показ второго варианта в интерфейсе — за пределами этой задачи.**
*Рационал:* это правка предпросмотра и печати — отдельный объём работы с отдельными критериями приёмки. Здесь данные сохраняются и **отдаются API**, то есть следующая задача сможет их показать, ничего не переделывая в хранении.

## 6. Чего не делаем

- **Не меняем колонку `type`** (AD-3). Следствие: скрининг по `type = 'control'` по-прежнему ничего не найдёт, и контрольную надо искать по `variants_json IS NOT NULL`. Это надо помнить всем, кто будет считать по базе.
- **Не показываем второй вариант в предпросмотре и в печати.** Данные сохраняются и отдаются API; интерфейс — отдельная задача (вопрос 5 в пакете вопросов).
- **Не пересохраняем старые листы.** У 184 существующих листов второго варианта нет и не будет — их нечего восстанавливать.
- **Не сохраняем другие типы артефактов** (план урока, презентация, КТП): у них нет второго варианта.
- **Не трогаем кэш и формат ответа генерации.**
- **Не меняем `getWorksheetById`** и три его вызывающих места.
- **Не переписываем `db/migrate.ts`**: он применяет `schema.sql` целиком, и этого достаточно для свежих баз.

| Кто-то посчитает `variants_json` обычным SQL-скринингом и не разберётся с форматом | Ошибка в замере | Формат зафиксирован в §3.2 и описан в шапке миграции; счётчик ТЗ-59 читает его через одну функцию |

## 8. Что не удалось подтвердить

- **Не проверено на боевой базе, сколько строк `worksheets` соответствуют контрольным.** Колонка `type` у всех «worksheet», а `variants_json` появится только после деплоя. До деплоя контрольные в базе неотличимы от обычных листов — и это верно и для скрининга, и для счётчика.
- **Не измерено, сколько контрольных было сгенерировано.** В логах 31 вызов `control-gen` (по данным исследования 03) — и это всё, что известно; сколько из них дошло до учителя, неизвестно.
- **Не проверено, что миграция 0010 пройдёт на боевой базе.** Идемпотентность `PRAGMA table_info` + `ALTER TABLE` взята из 0009, но на живой базе не прогонялась (это операция владельца).
- **Не проверено, помещается ли увеличенная строка в лимит D1.** Контрольная с критериями — самая крупная единица, которую мы пишем; фактический размер строки на живых данных не измерялся.
- **Не проверено, как поведёт себя `getWorksheetWithVariants` на строках, где `variants_json` — мусор** (например, после ручной правки базы). Защита — `try/catch` вокруг разбора JSON, как в `getWorksheetById` (`backend/src/services/worksheet.ts:87-92`); поведение при мусоре — вернуть `secondVariant: null`, а не падать.
- **Не измерено, что именно теряет учитель сегодня.** Формально второй вариант теряется после закрытия вкладки; но в конструкторе оба варианта живы до этого момента. Объём реальной потери (сколько раз учитель возвращался за вторым вариантом) неизвестен — обратной связи по этому в `docs/30-feedback-cases-2026-10-08.md` нет.
