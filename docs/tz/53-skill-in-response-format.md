# ТЗ-53: Навык — обязательное поле ответа, детектор дублей не остаётся без сигнала

**Дата:** 30.10.2026
**Кто делает:** бэк
**Размер:** S — 1 правка промпта + 1 константа + 2 тестовых файла
**Источник:** находка Н10 из `docs/research/03-prompt-quality-audit.md` (§6.4, строки 563–587, tip `db0619e`); решение владельца §6.10 (строка 968)
**Волна:** 1.5 — выполняется после волны 1 (ТЗ-50/51/52), отдельным коммитом (решение владельца 30.10.2026)

> **Порядок работ (зафиксирован решением владельца 30.10.2026):** ТЗ-53 выполняется **после ТЗ-50** и едет **отдельным коммитом** — это **волна 1.5**. ТЗ-50/51/52 — волна 1.
>
> Причина именно в порядке, а не в «удобстве»: обе задачи правят один и тот же блок «ФОРМАТ ОТВЕТА» в `backend/src/llm/prompts/worksheet-gen.ts`, одну константу `FORMAT_VERSION` в `backend/src/llm/cache.ts` и одни и те же хэши в `backend/tests/unit/cache-format-version.test.ts`. Параллельно их выполнять нельзя, а в один коммит их сливать **нельзя по решению владельца**: «два отдельных коммита, два сброса кэша» — так каждый шаг виден отдельно и каждый откатывается отдельно. Подробности — в `docs/tz/54-wave1-overview.md`.
>
> Следствие для версий: ТЗ-50 поднимает `FORMAT_VERSION` 2 → 3, **ТЗ-53 поднимает 3 → 4**. Варианта «ТЗ-53 без ТЗ-50» больше не существует.

## 1. Контекст и зачем

В листе два-три задания подряд проверяют **один и тот же навык** — например, четыре задания на определение вида предложения подряд. Учитель это видит и думает, что ему прислали один и тот же текст четыре раза. В продукте для этого есть детектор дублей — он ловит «одно задание дважды» и чинит лист. Но его **главный сигнал — поле `skill`**, а оно не входит в обязательный формат ответа.

Что происходит сегодня:

| Путь, которым пришло задание | Просит ли модель `skill` | Поле в ответе |
|---|---|---|
| Основная генерация листа | Да — в **user-промпте** (`worksheet-gen.ts:494`, «МЕТКА_ТЕМЫ_У_ЗАДАНИЯ») | Почти всегда есть |
| Дозапрос недостающих заданий | Да — в user-промпте (`:614`) | Почти всегда есть |
| **Ретрай контрольной** (второй вариант повторил первый) | **Нет** | **Нет** |
| **Замена задания другого типа** (нарушение разнообразия) | **Нет** | **Нет** |

Формат ответа (`worksheet-gen.ts:228-252`) — это единственное место, где перечислены поля, и там `skill` **нет**. Всё, что в формате не перечислено, модель возвращает по своему усмотрению. Значит: **как только модель решит не писать `skill`, детектор молча потеряет главный сигнал, а починить это без второго вызова нельзя.**

**Что это в бою** (прод-база `rabochielisty`, срез 30.10.2026):

- Поля `skill` нет у **800 из 1 277 заданий (62,6 %)**, и у **127 из 183 листов (69,4 %) — ни одного навыка вообще**. Но: **до 16.10 навыка не было никогда** (0 из 413 заданий), 16.10 — 10 отсутствующих из 27, 19.10 — 40 из 95, 29.10 — 12 из 284, **30.10 — 0 из 133**.

То есть **сегодня это риск, а не наблюдаемый брак**: последние два дня модель пишет навык всегда. Но «всегда» держится на том, что навык просят в user-промпте, а не на контракте формата ответа. Ровно такая конструкция ломается один раз и молча.

Владелец 30.10.2026 решил: **добавить `skill` в обязательный формат ответа**, с подъёмом `FORMAT_VERSION` в том же коммите.

### Уточнение находки (перепроверено по коду 30.10.2026)

Исследователь написал, что «детектор дублей может остаться без сигнала». Точнее:

1. **Три из четырёх проверок детектора от `skill` не зависят** (`backend/src/llm/validation/skill-dupes.ts:641-700`): «точное совпадение», «тот же вопрос» (совпал текст) и «граммы» (общие слова в формулировке) работают и без навыка. От навыка зависит только четвёртая проверка — **«тот же навык»** (`same-skill`, `:684-699`): совпала метка навыка **и** есть общие фразы в формулировке.
2. **Пустые метки в базе — исторические.** Сервер и так проставляет метку заданию, если модель её не прислала: `assignTopicSkills` (`backend/src/llm/validation/skill-labels.ts:67-95`, вызывается в `backend/src/llm/index.ts:1766`) берёт метку из ответа модели → из плана листа по позиции → из темы запроса. Поэтому 62,6 % без навыка — это листы до ТЗ-27 (13.10.2026), а не сегодняшний брак.

Вывод: **дефект Н10 — не «навыка нет», а «навык не в контракте»**. Ценность правки — в том, что после неё четвёртая проверка детектора и разбор «где класс просел» получают сигнал **из всех путей конвейера**, а не только из двух, где навык просят в user-промпте.

### 3.1. Строка в формате ответа

**Было** (`worksheet-gen.ts:239-246`):

```
      "options": ["A","B","C","D"],   // только для multiple-choice и multi-answer, ровно 4 варианта
      "answer": "...",
      "explanation": "...",
      "points": <1|2|3>,
```

**Стало** (добавляется одна строка, текст задан дословно — от него зависит хэш в тесте, см. 3.4):

```
      "answer": "...",
      "explanation": "...",
      "skill": "...",   // ОБЯЗАТЕЛЬНО: короткое название навыка или подтемы, 2–6 слов
      "points": <1|2|3>,
```

(Если ТЗ-50 уже смержен — строки `"points"` в блоке уже нет, добавление `skill` идёт в то же место.)

Формулировка совпадает с той, что уже есть в user-промпте (`worksheet-gen.ts:494-498`: «короткое название проверяемого навыка или подтемы, 2–6 слов, на русском»), — **одна и та же формулировка в двух местах, чтобы они не разошлись**. Расхождение двух копий — это ровно тот класс дефекта, из которого выросли предыдущие находки («один факт в двух местах»).

### 3.2. Что это даёт всем путям

Формат ответа — **общий контракт**: ретрай контрольной (`:773`) и замена типа (`:750`) говорят модели «JSON по схеме из системного промпта». Поэтому одна строка в формате закрывает все четыре пути:

| Путь | Навык в ответе |
|---|---|
| Основная генерация |был (user-промпт) → остаётся + получает статус обязательного |
| Дозапрос | был (user-промпт) → остаётся + получает статус обязательного |
| **Ретрай контрольной** | **появляется** |
| **Замена типа** | **появляется** |

Для ретрая и замены это особенно важно: их задания попадают в лист и участвуют в проверке на дубли (`backend/src/llm/index.ts:1206` — `findSkillDupes([...kept, ...accepted, candidate])`). Кандидат без навыка в этой проверке слеп по четвёртой причине.

Серверная подстановка (`assignTopicSkills`) при этом **не меняется**: пришедший от модели навык остаётся как есть (`skill-labels.ts:82-86`), подстановка работает только там, где навыка нет. То есть ТЗ-53 **не ломает** разбор по темам и **не ломает** правку метки учителем.

### 3.3. Кэш и версия формата

**Влияет на кэш: да — `FORMAT_VERSION` поднимаем в этом же коммите.** Меняется строка формата ответа — прямой пункт правила подъёма (`backend/src/llm/cache.ts:46-55`: «строка формата ответа — новое поле, новый тип задания»).

`backend/src/llm/cache.ts:68` — `FORMAT_VERSION` **3 → 4** (ТЗ-50 уже поднял 2 → 3 — порядок зафиксирован решением владельца 30.10.2026), в историю версий (`:61-67`) добавить:

```
 *   4 — «skill» стал обязательным полем формата ответа (ТЗ-53, 30.10.2026):
 *       детектор дублей и разбор по темам получают сигнал из всех путей
 *       конвейера, а не только из тех, где навык просил user-промпт.
```

`backend/tests/unit/cache-format-version.test.ts` — пересчитать `PROMPT_HASH` и `FORMAT_HASH`.

Посчитаны независимым замером `sha256 → hex → slice(0,16)` — тем же способом, что и в тесте (`cache-format-version.test.ts:80-81`). **Порядок зафиксирован** (ТЗ-53 поверх ТЗ-50), поэтому вариант один:

| Порядок | `PROMPT_HASH` | `FORMAT_HASH` |
|---|---|---|
| ТЗ-53 **поверх ТЗ-50** (зафиксированный порядок) | `ef0c23710c5f1fe7` | `98d56536bbbcf856` |

Если формулировка строки `skill` отличается от ТЗ — пересчитать по подсказке теста (`BUMP_HINT`, `cache-format-version.test.ts:96-98`), тест сам напечатает фактический хэш.

## 4. Решения (AD-N)

**AD-1 · Навык становится полем контракта, а не просьбой в промпте.**
Формат ответа перечисляет поля; всё, чего в нём нет, модель возвращает по своему усмотрению.
*Рационал:* просьба в user-промпте сегодня работает (100 % заполнения), но работает **по расположению текста, а не по контракту**. Ровно это и есть «риск, а не брак»: поломка наступит в тот день, когда модель (или её версия) изменит приоритеты. Формат ответа — единственное место, где перечислено, что модель обязана вернуть.

**AD-2 · Правка идёт в общий формат ответа, а не в каждый промпт по отдельности.**
*Рационал:* ретрай контрольной и замена типа уже ссылаются на формат из system-промпта («JSON по схеме из системного промпта», `worksheet-gen.ts:773`). Одна строка в общем формате закрывает четыре пути; четыре правки в четырёх промптах дали бы четыре расхождения.

**AD-3 · User-промпт с требованием навыка остаётся.**
*Рационал:* он сегодня даёт 100 % заполнения (0 отсутствующих из 133 на 30.10), и его удаление — регрессия без выигрыша: выигрыш даёт именно строка в формате. Формулировка при этом обязана совпадать с форматом — это зафиксировано в критериях приёмки.

**AD-4 · Серверная подстановка навыка не меняется.**
*Рационал:* `assignTopicSkills` — это страховка «навык есть у каждого задания, даже если модель промолчала», и она же уважает ручную правку учителя. ТЗ-53 добавляет **сигнал** (навык от модели), а не заменяет страховку.

**AD-5 · Формат ответа меняется один раз, версия поднимается один раз.**
*Рационал:* правило подъёма (`cache.ts:46-55`) прямо перечисляет строку формата ответа. Поднятие версии без правки формата — пустая трата кэша; правка формата без подъёма — кэш отдаёт материал, собранный по старому контракту (у которого в формате не было `skill`).

## 6. Чего не делаем

- **Не меняем `assignTopicSkills`** (`backend/src/llm/validation/skill-labels.ts`) — серверная страховка и уважение к ручной правке учителя работают правильно.
- **Не меняем логику детектора дублей** (`backend/src/llm/validation/skill-dupes.ts`) — четыре причины и их пороги настроены (ТЗ-33 AD-2); ТЗ-53 даёт детектору сигнал, а не меняет правила.
- **Не убираем просьбу о навыке из user-промпта** (`:494`, `:614`) — см. AD-3.
- **Не делаем `skill` обязательным в схеме сохранения** (`backend/src/routes/worksheets.ts:470` и подобные). Поле `skill` в `WorksheetTask` опциональное намеренно (ТЗ-27): у листов, созданных до ТЗ-27, его нет, и они обязаны вести себя как раньше. Серверная подстановка закрывает новые листы, а жёсткое «обязательно» сломало бы сохранение старых и мок-листов.
- **Не трогаем разбор по темам** (`db/skill-attempts.ts`, `readTaskSkills`) — он работает с тем, что есть.
- **Не переделываем план листа** (ТЗ-26 В-1) — он уже даёт узкие навыки по позиции и остаётся вторым источником.
- **Не откатываем ТЗ-50**, если он смержен: ТЗ-53 в этом ТЗ — **добавление** строки, а не замена блока формата.
- **Не сливаем ТЗ-50 и ТЗ-53 в один коммит.** Решение владельца 30.10.2026: «два отдельных коммита, два сброса кэша». Общий коммит убрал бы отдельный сброс кэша и сделал бы откат невозможным по частям.

## 7. Риски

| Риск | Цена ошибки | Что делаем |
|---|---|---|
| Модель начнёт писать навык «в столбик» (слишком общий) | Средняя: детектор станет шумнее | Уже есть фильтр меток (`cleanSkillLabel`, `skill-labels.ts:51-58`) и порог `same-skill` требует **и** совпадения метки, **и** общих фраз. Критерий приёмки: пара с одинаковым навыком и разными формулировками попадает в `sameSkillPairs`, а не в список на замену |
| Формат ответа стал длиннее → выросло число входных токенов | Низкая: +1 строка на весь промпт (не на задание) | Замер после выката: `llm_logs.tokens_in` по листу до/после |
| Подъём `FORMAT_VERSION` обнулил кэш | Низкая: 122 записи, копейки, материал пересоздаётся | По правилу `cache.ts:41-44` миграция не нужна, старые записи умрут по TTL |
| Формат и user-промпт разойдутся по формулировке | Средняя: модель получит два разных правила | Критерий приёмки: формулировка «2–6 слов» совпадает; обе правки — в одном коммите |
| Параллельное выполнение с ТЗ-50 | Высокая: конфликт в промпте, в `cache.ts` и в тесте | Порядок зафиксирован решением владельца 30.10.2026: ТЗ-53 идёт **после** ТЗ-50, отдельным коммитом (см. шапку файла и `docs/tz/54-wave1-overview.md`) |
| Модель начнёт требовать `skill` там, где его нет, и сломает JSON | Низкая | Формат ответа единый для всех путей; поле опционально на уровне схемы (`skill?: string \| null`) |

## 8. Что не удалось подтвердить

- **Не измерено, сколько именно дублей детектор пропускает из-за отсутствующего `skill`.** Живых замеров детектора нет; в бою зафиксированы 7 групп точных дублей на 21 задание (это ловятся и без навыка — по тексту). Четвёртая причина («тот же навык») в живых данных не измерялась.
- **Не проверено, как модель отреагирует на появление `skill` в формате ответа.** Ожидание: ответы станут чуть длиннее, заполнение — 100 % (сегодня user-промпт даёт 100 %). Проверяется живым прогоном после выката: `SELECT COUNT(*) ... WHERE json_extract(payload_json,'$.tasks').skill IS NULL` по новым листам.
- **Не проверено, сколько токенов стоит добавленная строка.** Оценка — «длина system-промпта», но входные токены считаются по факту вызова; замер после выката.
- **Не проверено поведение ретрая контрольной и замены типа с новым обязательным полем.** Эти пути используют общий формат ответа, но отдельного теста на «модель в ретрае присылает skill» нет — критерий приёмки требует его добавить.
- **Не проверено, что четвёртая причина детектора не станет шумнее после изменения.** Сравнение «до/после» по живым листам не делалось: для этого нужен прогон с включённой записью `sameSkillPairs` в отчёт.
