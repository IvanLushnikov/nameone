## 1. Контекст и зачем

В коде есть готовый механизм, который решает ровно задачу разнообразия.
Отдельный дешёвый вызов разладывает тему на N РАЗНЫХ навыков («Каждый навык
уникален. Если придумать столько разных навыков нельзя — сузь тему до соседних
подтем, но НЕ повторяй навык»), а дорогой вызов затем пишет лист строго по
этому плану.

В проде он **не работает**. Стадия закрыта флагом окружения `PLAN`, который
никто не выставил:

```ts
// backend/src/llm/index.ts:586-587
const planFlag = (env as unknown as Record<string, unknown>).PLAN;
if (String(planFlag) !== PLAN_ENABLED_VALUE) throw new Error("plan stage disabled");
```

В `backend/wrangler.toml` переменной `PLAN` нет ни в `[vars]`, ни в
`[env.production.vars]`; в `.github/workflows/` её тоже нет. Значит, в бою
`sheetPlan` всегда `null`, блок «ПЛАН_ЛИСТА» в user-промпте не собирается, и
навыки в листе придумывает модель по одному правилу промпта.

Почему так: механизм новый, он меняет число вызовов провайдера на каждой
генерации, и его нельзя было включать молча — сначала надо было обкатать на
живых листах. **Обкатать его за полгода не сделали.**

## 3. Технический дизайн

Эта задача — **измерение, а не включение**. Включение — это решение владельца
после цифр.

| Файл | Что меняем |
|---|---|
| `scripts/measure-plan-stage.mjs` (новый) | Скрипт замера: N пар листов с `PLAN=1` и без, сбор разнообразия, стоимости и времени |
| `backend/wrangler.toml` | **Только если** владелец решит включать: `PLAN = "1"` в `[env.production.vars]` |
| `.github/workflows/deploy.yml` | То же — если флаг должен переживать выкатку |
| `backend/src/llm/cache.ts` | Подъём `FORMAT_VERSION` (TZ-35), если включение состоялось: промпт листа меняется |
| `src/app/constructor/page.tsx` | Ожидание по числу заданий пересчитывается (TZ-37), если включение состоялось |

### Что именно измеряем

Для каждой пары (с планом / без плана) на одних и тех же темах, классе, числе
заданий и сложности:

| Что | Как считаем | Зачем |
|---|---|---|
| **Разные конструкции** | число попарно НЕ совпадающих нормализованных текстов заданий | главный вопрос: даёт ли план разнообразие |
| **Разные навыки** | число различных `skill` у заданий | второй вопрос: не маскирует ли разнообразие один навык |
| **Пары-дубли** | `findSkillDupes` на финальном листе | не должно стать хуже |
| **Повтор подряд одного типа** | число соседних заданий одного `type` | контроль Q-09 |
| **Стоимость плана** | `meta.costRub` и `meta.costUsd` в ответе + доля вызова плана | главный вопрос по деньгам |
| **Время** | `meta.latencyMs` и отдельная задержка плана | главный вопрос по скорости |

Минимум — **10 пар** на 3–4 темах (математика 5, русский 8, биология 7,
история 6), `count = 12`. Минимум, потому что разброс числа дублей между
листами большой: в реестре 112 заданий из 10 листов дали 5 пар дублей.

### Ожидаемые числа (оценка, не факт)

Размер промпта плана измерен локально: **system 1 040 символов, user 245
символов** (для сравнения: system промпта листа — 12 641 символ, по счёту
polza — 4 374 входных токена). Ответ плана — 12 позиций с навыком, подтемой и
сложностью, то есть порядка 500–800 выходных токенов.

| Величина | Оценка | Как получено |
|---|---|---|
| Себестоимость вызова плана | **0,03–0,05 ₽** | 400 входных × $0,07/1M + 700 выходных × $0,35/1M ≈ $0,00027 ≈ 0,023 ₽ по нашей модели; с поправкой на реальный счёт polza (M-04, ×1,33–2,10) — 0,03–0,05 ₽ |
| Прирост себестоимости листа (10 заданий, 0,19 ₽) | **+16…26 %** | 0,03–0,05 ÷ 0,19 |
| Прирост времени | **+3–8 с** | один дополнительный последовательный вызов Luna с 700 выходными токенами |
| Прирост расхода нормы | **+700 взвешенных токенов на лист** | выход плана тарифицируется полностью (вход — нет, см. M-03) |
| Что это значит для «до 1 500 листов» | **≈ 1 230 листов** вместо 1 500 | 1 500 × (3 121 ÷ 3 821) |

**Честный вывод по оценке:** стадия плана — не бесплатное улучшение
разнообразия. Она стоит примерно шестую часть листа по деньгам, добавляет
четверть-треть времени генерации и уменьшает число листов в тарифе на 18 %.
При этом **её эффект на разнообразие не измерен ни разу** — это гипотеза
реестра (раздел 9, гипотеза 3), а не факт.

### Как выглядит результат

1. Таблица замеров (таблица выше, заполненная числами) — в отчёте задачи и в
   `docs/backlog.md`, раздел «Требует решения владельца» (заменяет текущую
   оценку).
2. Решение владельца, записанное **в §7 этого файла** (как в ТЗ-32): включать
   / не включать / включать только для контрольной.
3. Если «включать» — правки из §3 и обновление чисел тарифа (TZ-44).

## 4. Решения

**AD-1 · Сначала замер, потом решение.**
Включение флага без замера — это изменение тарифа вслепую.
*Рационал:* эффект на разнообразие не измерен, а цена (деньги, время, число
листов) — посчитана. Менять цену предложения вслепую нельзя.

**AD-2 · Замер идёт по живым листам, а не по мокам.**
Скрипт ходит в боевой API тем же способом, каким ходил исследователь.
*Рационал:* мок промпта не воспроизводит поведение модели. Именно поэтому в
реестре Q-01 и Q-02 и видны: они видны только на живых ответах.

**AD-3 · Замеряем разнообразие, а не «красиоту».**
Метрики — числа: разные конструкции, разные навыки, пары-дубли, соседние
однотипные задания.
*Рационал:* «стало лучше» — не критерий. Критерий приёмки — таблица чисел и
решение владельца по ней.

**AD-4 · Если включаем — версия формата поднимается.**
Промпт листа меняется (добавляется блок плана), значит, кэш старых листов
больше не выдаётся.
*Рационал:* правило из TZ-35. Это не побочный эффект, а требование: иначе
учитель снова получит лист, собранный по другим правилам.

**AD-5 · Стратегия «только для контрольной» — рабочая, но не бесплатная.**
Контрольная стоит 8,51 ₽ и её просят раз в месяц; там цена одного лишнего
вызова незаметна, а выигрыш в разнообразии максимален.
*Рационал:* это компромисс, который стоит проговорить с владельцем, а не
прятать. Вариант «включать только для контрольной» реализуется одной
проверкой типа в `index.ts`.

**AD-6 · Норма тарифа пересчитывается автоматически, обещание — вручную.**
Код учёта уже суммирует все вызовы (`index.ts:1375`), поэтому лишний вызов
вычитается из нормы сам. А вот число «до 1 500 листов» на странице тарифов —
это текст, и его надо пересчитать (TZ-44).
*Рационал:* нельзя оставить обещание, которое после включения перестаёт быть
правдой.

## 5. Критерии приёмки

Функциональные:
- [ ] Скрипт замера лежит в репозитории (`scripts/measure-plan-stage.mjs`), запускается одной командой и печатает таблицу по каждой паре листов.
- [ ] Таблица содержит по каждой паре: число разных конструкций, число разных навыков, пары-дубли, соседние однотипные задания, `meta.costRub`, `meta.latencyMs`.
- [ ] Замер сделано на **не менее 10 парах** листов, минимум на 3 предметах и 2 классах, `count = 12`.
- [ ] В отчёте есть вывод: изменилось ли разнообразие (с числами) и какова цена (деньги и время).

Регрессионные:
- [ ] При `PLAN=1` генерация **не ломается**, если план непригоден: ответ приходит как обычно, в логе — `worksheet-gen: unusable plan, continuing without it`.
- [ ] При `PLAN=1` в `llm_logs` видно **два** вызова на лист (план и лист), и норма посчитана по обоим.
- [ ] Без `PLAN=1` поведение не изменилось: один вызов, лист без блока плана.

Качественные:
- [ ] Решение владельца записано в §7 этого файла — с датой и формулировкой.
- [ ] Если решение «включать»: `PLAN = "1"` присутствует в `[env.production.vars]` **и** в окружении выкатки; `FORMAT_VERSION` поднята; числа «листов» в тарифе пересчитаны; ожидание по времени в конструкторе пересчитано.
- [ ] Если решение «не включать»: в §7 записано, на каких цифрах остановились, и в `docs/backlog.md` Q-04 помечен как «отложено по решению владельца».

## 6. Чего не делаем

- **Не включаем план молча и «на всякий случай».**
- **Не переписываем промпт плана.** Он написан и стрик — «каждый навык
  уникален». Правка промпта = подъём версии (TZ-35) и сброс кэша.
- **Не меняем маршрутизацию моделей.** План идёт на ту же модель, что и лист.
- **Не вводим отдельную модель для плана.** Это отдельное решение с отдельной
  ценой.
- **Не трогаем лимит бесплатной квоты** — план не должен съедать попытку
  отдельно (он внутри того же вызова листа).

1. (1 дн) Скрипт замера `scripts/measure-plan-stage.mjs`: умеет ходить в API с `bypassCache`, печатает таблицу; запускается с ключом в переменной окружения.
2. (1 дн) Прогон: 10+ пар листов. Результат — в отчёт.
3. (0,5 дн) Разбор результата и вывод: разнообразие / деньги / время.

5. (0,5–1 дн) Если «включать»: `PLAN = "1"` в `wrangler.toml` и в workflow, подъём `FORMAT_VERSION`, пересчёт чисел тарифа и ожидания времени.

**Правила репозитория, которые задача не должна нарушать:**

- Скрипт замера — на Node 22, без новых зависимостей: HTTP-запросы делаются

- Коммит строго по списку своих путей: `git add -- scripts/measure-plan-stage.mjs docs/tz/38-*.md` и `git commit -m "..." -- <те же пути>`. **Не `git add -A`.**

## 9. Что не удалось подтвердить

- **Влияние плана на разнообразие.** Не измерено: стадия выключена, живых
  листов с планом в истории нет. Это главный неизвестный задачи и причина
  того, что она начинается с замера.
- **Стоимость вызова плана в рублях.** Оценка получена из длины промпта
  (1 040 + 245 символов) и таблицы цен. Фактические `tokens_in/tokens_out`
  вызова плана в таблице `llm_logs` не измерялись.
- **Доля листов, где разнообразие страдает.** Масштаб дублей известен только
  по 10 живым прогонам реестра: 5 пар дублей в 3 листах из 10. Реальная частота
  по всей базе неизвестна (доступа к D1 у агента нет).
- **Влияет ли план на скорость в худшем случае.** Оценка +3–8 с сделана по
  времени генерации 700 выходных токенов на Luna. Если модель на плане
  «рассуждает» дольше, вызов может занять 15–20 с — это проверяется замером.
