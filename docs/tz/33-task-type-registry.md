# ТЗ-33: Реестр типов заданий вместо пяти

**Дата:** 28 октября 2026
**Кто делает:** бэк (промпт, валидация), фронт (типы, печать, превью)
**Размер:** L. Затрагивает оба конвейера — генерацию и выдачу материала
**Волна:** 1 (В1.1), П0
**Источник:** `docs/tz/25-generation-flow-quality-loss.md` (эталон структуры), промпт владельца «АГЕНТСКИЙ ПРОМПТ: УчЛист», раздел В1.1

---

## 1. Контекст и зачем

Учитель открывает конструктор, просит «рабочий лист по математике, 5 класс, дроби, 5 заданий» — и получает пять арифметик подряд. Не потому, что модель не знает других форм, а потому, что **у формы задания в продукте всего пять**: `computation`, `multiple-choice`, `short-answer`, `essay`, `fill-blank` (`src/lib/types.ts:120`). Остальное школьное разнообразие — «выполните по образцу», «установите соответствие», «расположите в порядке», «найдите ошибку», «разделите на группы», «задание по таблице» — в продукте не смоделировано вообще.

Это не косметика. У школьной практики есть устойчивая форма «по образцу» с образцом **в тексте задания**, и именно этот случай ломался (жалоба №5 из `docs/30-feedback-cases-2026-10-08.md`): модель писала «выполните по образцу», а образца в листе не было. Сейчас это лечится фильтром `hasDanglingPatternRef` (`backend/src/llm/validation/quality-filter.ts:174`) — то есть **выкидыванием** задания. Фильтр убирает симптом; сам формат «по образцу» в системе отсутствует, поэтому правильный ответ на него — отказ, а не материал.

У конкурентов («Обучай» — 70 типов заданий) разнообразие есть. У нас — нет.

**Что делаем:** заводим декларативный **реестр типов заданий** — один файл, из которого собирается и блок промпта, и валидация ответа, и вёрстка, и превью. Не переписываем `worksheet-gen.ts` целиком и не добавляем восемнадцатое «жёсткое правило»: правила добавляются **декларативно**, через реестр.

**Чего не делаем в этом ТЗ:** не меняем тарифы и нормы (В1.6), не трогаем презентации (В1.3), не добавляем критерии оценивания (В1.2). Здесь — только форма задания.

## 3. Технический дизайн

### 3.1. Реестр — новый файл `src/lib/content/task-types.ts`

Единый источник истины. Живёт во фронте (`src/lib/content/`), потому что оттуда его читает и печать (`src/lib/utils/docx.ts`), и превью, и бэк — относительным импортом. Импорт проверен пробой: бэк тянет фронтовый файл и в vitest, и в wrangler (`wrangler deploy --dry-run` собирает такой импорт без ошибок).

```ts
export interface TaskTypeSpec {
  id: string;                 // "pattern"
  name: string;               // «По образцу»
  whatTeacherAsks: string;    // human-readable, как это звучит в учительской формулировке
  answerKind: "exact" | "choice" | "text" | "criteria" | "order";
  needsSample?: boolean;      // требует образец В ТЕКСТЕ задания
  needsOptions?: boolean;
  needsTable?: boolean;
  needsImage?: boolean;
  subjects?: SubjectSlug[];   // где применим; undefined = везде
  grades?: [number, number];  // где применим
  printHints: string[];       // подсказки для верстки (колонки, рамка, чек-лист)
  checkHint: string;          // как проверять, что задание «сделано правильно»
}
```

**Состав реестра — 17 типов:** 5 существующих (обратная совместимость) + 12 новых.

| id | Что это | Где применим | answerKind |
|---|---|---|---|
| `computation` | расчёт | везде | exact |
| `multiple-choice` | выбор из 4 вариантов | везде | choice |
| `short-answer` | краткий ответ | везде | text |
| `essay` | развёрнутый ответ | везде | criteria |
| `fill-blank` | вставь в пропуск | везде | exact |
| **`pattern`** | «Выполните по образцу» — образец в тексте задания | везде | exact |
| **`matching`** | установите соответствие (2 колонки) | lang, bio, social, chem, hist, geo | order |
| **`sequence`** | расположите в порядке | hist, bio, tech, social, lit | order |
| **`classification`** | разделите на группы / по признаку | bio, social, geo, chem | order |
| **`error-fixing`** | найдите и исправьте ошибку | math, rus, phys, chem, inf | text |
| **`table-task`** | задание по таблице или рисунку | math, phys, chem, inf, geo | exact |
| **`multi-answer`** | несколько правильных вариантов | везде | choice |
| **`compare`** | сравните два объекта по признакам | bio, lit, social, geo, phys | text |
| **`open-ended`** | открытый ответ с критериями | везде | criteria |
| **`practical`** | практическая работа: алгоритм + чек-лист | tech, obzh, pe, bio | criteria |
| `word-problem` | текстовая задача с опорой на условие | math, phys | exact |
| `source-analysis` | работа с текстом-источником | rus, lit, social, hist | criteria |

### 3.2. Поля задания

Новые поля **не ломают старые листы**: всё необязательное.

```ts
export interface WorksheetTask {
  // ... существующие поля без изменений
  /** Образец для type="pattern" — реальный разобранный пример. */
  sample?: string | null;
  /** Строки/столбцы для type="table-task" и "matching". */
  table?: { headers: string[]; rows: string[][] } | null;
  /** Элементы для упорядочивания (sequence) / разбиения (classification). */
  items?: string[] | null;
  /** Критерии приёмки для essay / open-ended / practical. */
  criteria?: string[] | null;
  /** Шаги алгоритма для practical. */
  steps?: string[] | null;
}
```

**Обратная совместимость:** `worksheets.payload_json` мигрировать не нужно. Старые листы читаются как раньше: у них нет новых полей, а код трактует отсутствие поля как «обычное задание».

### 3.3. Куда подключается реестр

| Файл | Что делаем |
|---|---|
| `src/lib/content/task-types.ts` | **НОВЫЙ.** Реестр + хелперы: `getTaskTypeSpec`, `taskTypeIds`, `isKnownTaskType`, `typesForSubject(subject, grade)`, `buildTaskTypesPromptBlock(...)` |
| `src/lib/types.ts` | `WorksheetTask.type` → union из реестра (5 старых + 12 новых); новые необязательные поля |
| `backend/src/types.ts` | То же самое: union + поля (бэк и фронт держат копии API-контракта) |
| `backend/src/lib/zod.ts` | `worksheetTaskSchema.type` → `z.enum(taskTypeIds)`; новые поля в схеме |
| `backend/src/llm/prompts/worksheet-gen.ts` | **Блок промпта собирается из реестра**, а не из строки в шаблоне. Типы, неприменимые к предмету/классу, в промпт не попадают |
| `backend/src/llm/validation/quality-filter.ts` | Валидация по реестру: тип из реестра; `pattern` требует `sample`; `matching`/`sequence`/`classification` требуют `items`; `table-task` требует `table` |
| `src/lib/utils/docx.ts` | Печать: образец (`sample`) в рамке, таблица (`table`) таблицей, чек-лист (`steps`) галочками, элементы (`items`) нумерованным списком, критерии (`criteria`) — на странице ответов |
| `src/components/constructor/WorksheetPreview.tsx` | Превью: те же элементы, что и в печати |
| `src/lib/forms/types.ts` | `FormTaskType` остаётся 5-юным **на форме** (ТЗ-16 осознанно сузил); `toFormSourceTask` переводит неизвестный форме тип в `short-answer` |
| `backend/src/services/formGrading.ts` | `switch` по 5 типам: новые типы → `default` → ручная проверка учителем (уже так и сделано в `default`) |

### 3.4. Применимость к предмету и классу

`TaskTypeSpec` применяется не ко всем предметам. Правило из промпта владельца: **если предмет не подходит — не просить модель такое задание, а не «потом отфильтруем»**. Поэтому `typesForSubject(subject, grade)` отсекает типы по `subjects` и `grades` **до** сборки промпта. Модель физически не получает задание, которое ей нельзя делать.

Существующие 5 типов применимы везде (`subjects` не задан) — обратная совместимость не ломается.

## 4. Решения (AD-N)

**AD-1 · Реестр лежит во фронте, бэк импортирует относительным путём.**
Файл `src/lib/content/task-types.ts` — в `src/lib/content/`, рядом с `plans.ts` и `subjects.ts`, потому что это продуктовый справочник, а не API-контракт. Бэк читает его относительным импортом `../../../src/lib/content/task-types`.
*Рационал:* отдельный общий пакет (`packages/shared`) потребовал бы менять и `tsconfig`, и `vitest.config`, и `wrangler`, и деплой — это рефакторинг ради рефакторинга, запрещённый §9 промпта владельца. Импорт проверен пробой: vitest бэка проходит, `wrangler deploy --dry-run` собирает бандл без ошибок. Побочный эффект: типы `SubjectSlug` у фронта и бэка остаются копиями (как сейчас) — реестр их не импортирует, а принимает `string`, чтобы не тянуть фронтовый `types.ts` в бэк.

**AD-2 · Тип задания в листе — строка из реестра, а не закрытый union в типах.**
`WorksheetTask.type` становится `TaskTypeId` (строковый литерал, выведенный из реестра) — 17 значений.
*Рационал:* union из 17 значений в `src/lib/types.ts` пришлось бы дублировать ещё в трёх местах (`backend/src/types.ts`, `backend/src/lib/zod.ts`, `backend/src/routes/worksheets.ts:438`, `backend/src/routes/f07.ts:249`, `backend/src/routes/f08.ts:78`) — и любое расширение реестра требовало бы правки пяти файлов. Реестр даёт `z.enum(taskTypeIds)` одним движением. Zod всё равно не пропустит мусор: значение вне реестра — 400.

**AD-3 · Новые поля необязательные, миграции базы нет.**
`sample`, `table`, `items`, `criteria`, `steps` — все `?` и `| null`.
*Рационал:* промпт владельца прямо требует «миграция `worksheets.payload_json` не нужна (старые листы читаются как раньше)». Необязательные поля дают это бесплатно: у старого листа их нет, код читает `undefined` как «обычное задание».

**AD-4 · `pattern` — это отдельный тип, а не вариант `short-answer`.**
*Рационал:* «по образцу» — самостоятельная школьная форма с проверяемым требованием (образец в тексте). Если оставить её внутри `short-answer`, валидация «есть ли образец» превратится в эвристику по тексту, а в объявленный тип — в правку промпта. Отдельный тип даёт: проверку в коде (`needsSample` → `sample` обязателен), понятную подпись учителю и место в печати (образец в рамке).

**AD-5 · `needsSample` проверяется в коде, а не словами в промпте.**
Задание типа `pattern` без `sample` — дефект: учитель отдаст классу «выполните по образцу» без образца. Такое задание отбрасывается фильтром качества **до** выдачи.
*Рационал:* ровно этот дефект ловил `hasDanglingPatternRef` — но выбрасыванием. С реестром формат можно **выдать**: модель обязана прислать `sample`, код проверяет, печать показывает рамкой. Тот же случай перестаёт быть «невозможным» и становится «сделанным».

**AD-6 · Типы, неприменимые к предмету/классу, не попадают в промпт.**
`typesForSubject(subject, grade)` фильтрует по `subjects` и `grades`; в промпт уходит блок только с применимыми.
*Рационал:* требование владельца — «не просить модель такое задание, а не потом отфильтруем». Просить и отбрасывать — значит платить токены за задания, которые выкинут, и получать листы короче заказанного. Фильтрация до промпта дешевле и честнее.

**AD-7 · `worksheet-gen.ts` не переписывается — блок промпта становится функцией от реестра.**
Строка «Разнообразие типов заданий: computation | multiple-choice | short-answer | essay | fill-blank» в system-промпте заменяется на собранный из реестра блок.
*Рационал:* §9 промпта владельца запрещает переписывать `worksheet-gen.ts` целиком и запрещает добавлять «18-е жёсткое правило». Декларативный блок — ровно то, что требуется: правило появляется не текстом, а записью в реестре. Восемнадцатое правило не понадобится.

**AD-8 · Правка system-промпта сбрасывает prompt cache у «Плюса» — это принято осознанно.**
По шапке `backend/src/llm/prompts/worksheet-gen.ts:37` изменение system-промпта сбрасывает кэш Anthropic. Причина жёсткая: без нового блока модель не знает про новые типы, и весь смысл ТЗ теряется. Сброс — разовая переплата за входные токены, дальше кэш восстанавливается.
*Рационал:* правило владельца — «дальше такие сдвиги только с жёсткой причиной». Причина здесь жёсткая: новая функциональность невозможна без нового текста в промпте. Правка вносится **одним** блоком, а не переписыванием промпта.

**AD-9 · Форма для ученика принимает 5 типов, лист — 17.**
`FormTaskType` не расширяется. При переносе листа в форму (`toFormSourceTask`) тип, которого форма не знает, превращается в `short-answer` — ручная проверка учителем.
*Рационал:* ТЗ-16 осознанно сузил форму до 5 типов, чтобы набор заданий формы не расползся. Автопроверка новых типов — отдельная работа (двухколоночное соответствие и чек-лист проверяются иначе, чем числовой ответ). Сейчас форма не ломается: неизвестный тип уходит учителю, а не ученику.

**AD-11 · Задание без поля `type` — легитимно, его не выкидываем.**
Фильтр проверяет три разных случая и не смешивает их:
1. **типа нет** — задание годное (модель не всегда присылает `type`, и фильтр
   не про форму заданий, а про качество; раньше такие задания проходили);
2. **тип есть, но его нет в реестре** (модель выдумала свой, например
   «diagram») — дефект: такой тип не напечатать и не сохранить, zod на
   клиентском сохранении отвергнет его с 400, и учитель вместо листа получит
   ошибку;
3. **тип из реестра, но не соответствует требованиям** — дефект.
*Рационал:* проверка должна ловить дефект, а не отсутствие необязательного
поля. Отдельный случай «типа нет» сохраняет поведение фильтра прежним и
убирает ложные срабатывания на существующих фикстурах.

**AD-12 · Откат фильтра возвращает только мягкие потери.**
Откат (защита от пустого листа) существует, чтобы учитель получил хоть
какой-то материал. Но жёсткие потери — неизвестный тип и несоответствие типу
— в откат не возвращаются: неизвестный тип сломается на сохранении, а
«по образцу» без образца бессмысленно по смыслу, и откат обнулял бы всю
работу ТЗ-33 ровно тогда, когда модель ошиблась чаще обычного.
*Рационал:* если после жёсткой отсечки не осталось ничего — возвращается
пустой набор, а не исходный. Исходный состоит ровно из тех заданий, которые
мы только что признали непригодными. Пустой лист учитель поймёт (признак
`stillMissing` в ответе API), а бессмысленное задание он унесёт в класс и не
поймёт, почему оно там было.

**AD-13 · Образец типа `pattern` лежит в отдельном поле `sample`, и фильтр это видит.**
Проверка «есть ли образец в тексте» (`hasExampleInText`) такой образец не
видит — он не в тексте, а в своём поле. Без поправки фильтр выкидывал бы
правильные задания типа `pattern`: модель образец прислала, а проверка его не
увидела.
*Рационал:* образец отдельным полом — не только ради печати рамкой ДО текста
задания, но и ради проверки: «есть ли образец» становится вопросом о поле, а
не о разборе текста.

## 5. Критерии приёмки

Реестр:
- [ ] В реестре 17 типов; 5 существующих на месте, их `id` не изменились
- [ ] У каждого типа заполнены `name`, `whatTeacherAsks`, `answerKind`, `printHints`, `checkHint`
- [ ] `typesForSubject("math", 5)` не содержит `practical` (технология, ОБЖ, физкультура, биология)
- [ ] `typesForSubject("pe", 8)` содержит `practical` и не содержит `matching`
- [ ] Тип без `subjects` применим ко всем предметам

Промпт:
- [ ] Блок типов в промпте собран из реестра, а не зашит строкой
- [ ] В промпте для математики 5 класса нет `practical`
- [ ] Модель может вернуть новый тип, и он не отбрасывается валидацией как «неизвестный»

Валидация:
- [ ] Задание типа `pattern` без `sample` → отброшено фильтром качества, лист при этом не пустеет (защита от пустого листа работает)
- [ ] Задание типа `pattern` **с** `sample` → доходит до учителя
- [ ] Тип вне реестра → 400 от API, а не 500
- [ ] `table-task` без `table` → отброшено
- [ ] Старый лист (5 типов, без новых полей) проходит валидацию без изменений

Печать (DOCX):
- [ ] Образец (`pattern`) напечатан в рамке, до задания
- [ ] Таблица (`table-task`) напечатана таблицей, а не строкой текста
- [ ] Чек-лист (`practical`) напечатан галочками
- [ ] Элементы (`sequence`) напечатаны нумерованным списком
- [ ] Старый лист печатается **байт-в-байт** как раньше (регрессии нет)

Превью:
- [ ] Образец, таблица, чек-лист и элементы видны в превью так же, как в печати

Форма для ученика:

## 8. Что не удалось подтвердить по коду

1. **Как именно модель отнесётся к 12 новым типам без «железной» выжимки.** Проверяется только живыми прогонами после выката. Планируемая проверка: 10 листов по разным предметам, счёт типов в каждом.
2. **Печать таблицы в DOCX для `table-task`.** В `docx.ts` уже есть механизм таблицы ответов (`Table`, `WidthType`, `tblLayout fixed` — см. `tests/integration/worksheet-docx.test.ts`), но таблица-задание в теле листа не делалась: переиспользовать надо тот же код сетки, иначе получится «схлопнувшаяся» таблица — ровно тот дефект, что чинили в ТЗ для таблицы ответов.
3. **Совместимость `criteria` с формой.** Если критерии попадут в форму, `formGrading` их не увидит: сейчас у формы 5 типов и `criteria` не в схеме `f07.ts`/`f08.ts`. По AD-9 это не ломается (критерии не теряют смысла — они в листе), но «ключ с критериями» в форме не появится.
4. **`items` для `matching` — две колонки или один список.** В реестре `matching` трактуется как «элементы + соответствие в `answer`». Настоящее «две колонки» (левая и правая) — это уже `table`; для `matching` решено использовать `items` как правую колонку, а соответствие — в `answer`. Если учителю понадобится именно две колонки без ответа, это отдельная правка.
5. **Не проверено, сколько токенов стоит блок типов в промпте.** Реестр на 17 типов добавит к user-промпту примерно 700–1000 токенов. Для «Плюса» — попадание в кэш, для free — рост входа. Замер будет на живых прогонах.
6. **Поведение `polza.ai` при `max_tokens` и новых типах не проверялось.** Ответ модели с новыми полями (`sample`, `table`, `items`) длиннее — при `baseMaxTokens = 4096` лист из 12 новых заданий может обрезаться. Существующий механизм обрыва (`finishReason`) сработает, но порог, возможно, придётся поднять. Не проверено.

## 9. Порядок работ

1. `src/lib/content/task-types.ts` — реестр и хелперы. Тест: реестр полон, 5 старых типов на месте, фильтр по предмету работает.

7. Форма: `toFormSourceTask` — неизвестный форме тип → `short-answer`.
