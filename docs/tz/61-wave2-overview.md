## Почему такой порядок

**Задачи внутри волны независимы** — их можно брать параллельно. Порядок в таблице — **рекомендация**, и он такой: **сначала то, что даёт измерение, потом проверки, потом правки материала.**

```
ТЗ-60 (контрольные в базу)
   └─► ТЗ-59 (измеритель: эталонный набор + счётчик 13 дефектов)
          └─► ТЗ-56 ─► ТЗ-57 ─► ТЗ-55 ─► ТЗ-58
              проверки в коде: сначала те, что не меняют материал,
              потом те, что меняют
```

Обоснование по шагам:

1. **ТЗ-60 — первое, потому что без него нечего мерить.** Второй вариант контрольной сейчас не сохраняется вообще (см. ниже, раздел «Перепроверка»). Пока контрольная не в базе, по ней нельзя посчитать ни один дефект, и половина чек-листа из 13 пунктов останется непроверяемой. Это самая дешёвая задача волны (одна nullable-колонка) — её выгодно сделать первой.
2. **ТЗ-59 — второе, потому что это линейка.** Пока линейки нет, любая правка промпта — выстрел наугад: ни один тест в продукте не проверяет качество материала, все проверяют структуру. Счётчик и эталонный набор дают «до», без них нельзя отличить «стало лучше» от «стало иначе». Офлайн-часть (счётчик + наполнение набора из 184 живых листов) стоит **0 ₽** и делается без ключа провайдера.
3. **ТЗ-56 → ТЗ-57 → ТЗ-55 — порядок по «стоимости последствий».** ТЗ-56 только предупреждает и не меняет system-промпт — самое безопасное первое изменение. ТЗ-57 выкидывает сломанные задания (но чинит их дозапросом). ТЗ-55 меняет system-промпт (убирает рукописный список классов) и поднимает `FORMAT_VERSION` — это самое крупное изменение волны, и к нему лучше подходить, когда линейка уже есть и остальные проверки уже показали, что не врут.
4. **ТЗ-58 — последнее и с жёсткой зависимостью.** Правка меняет USER-промпт, а ключ кэша (`backend/src/llm/cache.ts:114-135`) описывает только параметры запроса. **Без ТЗ-51 (волна 1) правка не вступит в силу для уже закэшированных листов** — кэш до 30 дней будет отдавать лист, собранный по старому порядку типов. Поднимать `FORMAT_VERSION` ради этого не надо: ТЗ-51 делает то же самое и без потери кэша.

**Общая координация — `FORMAT_VERSION`.** Три задачи волны могут поднять версию формата: ТЗ-55 (system-промпт изменился), ТЗ-56 (в ответе новое поле `quality.termConflicts`), ТЗ-57 (в ответе новое поле `quality.droppedAnswerMismatch`). Правило простое: **каждая берёт «текущее значение в `main` на момент мержа + 1»**. Конфликта не будет, потому что мержутся они по очереди. `PROMPT_HASH` в `backend/tests/unit/cache-format-version.test.ts` трогает только ТЗ-55 — он меняет system-промпт.

**Про Node.** На этой машине `node -v` по умолчанию даёт **v23.11.0**, а на Node 23 сборка зависает намертво. Node 22 лежит в `/opt/homebrew/opt/node@22/bin` — для `npx tsx` и `npx vitest` в этой волне используется он.

## Сквозные правила волны

1. **Знание — в данных, проверка — выводится из них.** Каталог ФГОС (`src/lib/content/subjects.ts`) → словарь понятий (`concept-levels.ts`, генерируется) → проверка в коде. Таблица несовместимых терминов (`term-conflicts.ts`) → матчер. Ни одна из трёх новых проверок не содержит «если математика — проверь √».
2. **Два источника правды — источник багов.** Рукописный список классов из промпта уходит (ТЗ-55), потому что он уже разошёлся с каталогом по двум понятиям. Правило 14 в промпте остаётся (ТЗ-56, AD-2) — это подсказка формулировки, а не таблица данных.
3. **Ложное срабатывание дороже пропуска.** Там, где частота ложных срабатываний не измерена (ТЗ-55, ТЗ-56), проверка **предупреждает** и не отнимает у учителя задание. Там, где точность обеспечена структурно (ТЗ-57: оба числа разобрались, ни одно не равно ответу), задание выкидывается, а дозапрос его заменяет.
4. **Пункт, который не посчитан, — не ноль.** Счётчик дефектов печатает «не проверяется автоматически» для непроверяемых пунктов (ТЗ-59, AD-3). Молчаливый ноль хуже отсутствия числа.
5. **Ничего из уже сделанного не переписывается.** Ломать нельзя: печать критериев в ключе (`src/lib/utils/docx.ts:636`, `:866`), формулу взвешенного токена (`backend/src/services/usage.ts:15`), учёт по сумме всех вызовов конвейера (`backend/src/llm/index.ts:1350-1377`), реестр типов задания и лимиты разнообразия (`src/lib/content/task-types.ts:343`, `:477`), блок типов в промпте (`backend/src/llm/prompts/worksheet-gen.ts:412`), кэш контрольной как пара `{worksheet, secondVariant}`.
6. **Каждый новый тест падает на старом коде и зелёный на новом.** Это обязательный пункт в приёмке каждой из шести задач.
7. **Правило кэша — в каждом ТЗ.** ТЗ-55, ТЗ-56, ТЗ-57: `FORMAT_VERSION` +1 («текущее в `main` + 1»). ТЗ-58: версию **не** поднимаем, но требуем ТЗ-51. ТЗ-59, ТЗ-60: на кэш не влияют.
