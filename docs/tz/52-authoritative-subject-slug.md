## 1. Контекст и зачем

В кабинете учителя один и тот же предмет называется **двумя способами**: «Математика» и `math`. Из-за этого в фильтре по предмету появляются **две одинаковые на вид кнопки** («Математика» и «Математика»), а счётчик листов по каждой из них показывает разные числа. Учитель не понимает, куда делись его листы, и думает, что часть материалов потерялась. То же по биологии, физике, истории, окружающему миру.

Причина простая: **название предмета в сохранённом материале берётся не из запроса учителя, а из ответа модели**. Модель отвечает `subject: "Математика"`, сервер это берёт и кладёт в базу. Раньше предмет спрашивали у учителя, а модель отвечала за содержание — из этого выросла привычка отдавать предмет модели.

**Что это в бою** (прод-база `rabochielisty`, срез 30.10.2026, прочитано напрямую):

| Предмет в базе | Листов | | Предмет в базе | Листов |
|---|---|---|---|---|
| Математика | 53 | | algebra | 3 |
| math | 44 | | Физика | 3 |
| Окружающий мир | 31 | | **world** | 2 |
| Русский язык | 13 | | physics | 1 |
| Биология | 9 | | technology | 1 |
| biology | 6 | | **Естествознание** | 1 |
| english | 5 | | Информатика | 1 |
| История | 5 | | **История России** | 1 |
| Технология | 4 | | Обществознание | 1 |

Итого **184 листа, 17 разных значений предмета, из них 120 листов (65 %) записаны по-русски** и не совпадают со своими же слагами. Три значения (`world`, `Естествознание`, `История России`) **не существуют в таксономии вообще** — их придумала модель (`История России` вместо «История»).

Проверено: во всех 184 листах `subject` в `payload_json` совпадает с колонкой `subject` — то есть оба места записаны из одного и того же (модельного) значения. Правка должна чинить оба.

### 3.1. Нормализатор (новый файл)

```ts
// src/lib/content/subject-slug.ts
/**
 * Канонический слаг предмета по любой строке (ТЗ-52).
 *
 * ОБРАТНАЯ сторона `subjectDisplayName`: там slug → «Математика», здесь
 * любая строка → slug. Обе карты строятся из ОДНОГО источника — лёгкой
 * сводки таксономии (`subject-index.ts`), а не из вписанного списка.
 *
 * Учитель в блоке «предмет» прислал «Математика» — мы должны понять, что
 * это тот же предмет, что `math`, иначе в базе появятся два имени одного
 * предмета, а фильтр в кабинете покажет две одинаковые кнопки.
 */
export function subjectSlugFrom(input: string | null | undefined): string | null
```

Правила (по порядку):

1. `null`/`undefined`/пустая строка после `trim()` → `null`.
2. Сравнение без учёта регистра и с обрезкой пробелов: если строка совпала со **слагом** предмета → вернуть канонический слаг (`" MATH "` → `"math"`).
3. Если строка совпала с **названием** предмета (`title`) или с его **коротким названием** (`shortTitle`) → вернуть слаг (`"Математика"` → `"math"`, `"Окр. мир"` → `"okruzhaet"`).
4. Иначе → `null` (значение не опознано).

Источник данных — `subjectIndex` из `src/lib/content/subject-index.ts` (тот же, что использует `subjectDisplayName`). Список предметов и их названия берутся **оттуда**, новый перечисляемый список в коде не заводим — иначе через месяц появятся две разные карты.

**Проверка на коллизии (обязательна):** **ни одно название и ни одно короткое название не должно совпадать с названием ДРУГОГО предмета.** Сейчас не совпадает (проверено по `subject-index.json` 30.10.2026), но это свойство данных, а не кода — его надо зафиксировать тестом (см. 3.6).

⚠️ **Тонкость проверки:** у большинства предметов `title` и `shortTitle` совпадают («Математика» = «Математика»), поэтому «посчитать, сколько раз встречается каждое название» даст **ложные коллизии** (12 предметов «дублируются» сами с собой). Проверять надо **по парам разных предметов**:

```ts
// у 21 предмета title == shortTitle — это не коллизия.
// Коллизия — когда одно название принадлежит ДВУМ РАЗНЫМ предметам.
const seen = new Map<string, string>(); // название → slug
for (const s of subjectIndex) {
  for (const name of [s.title, s.shortTitle]) {
    const key = name.trim().toLowerCase();
    const prev = seen.get(key);
    expect(prev, `название «${name}» принадлежит и «${prev}», и «${s.slug}»`).toBeUndefined();
    seen.set(key, s.slug);
  }
}
```

То же правило держит и сам нормализатор: если название встречается у двух разных предметов, побеждает **первое** попадание (и это ошибка данных, которую ловит тест выше), а не «последний перезаписал».

### 3.2. Схема входа в бэке

В `backend/src/lib/zod.ts` рядом с `subjectSlugSchema` (`:27-49`):

```ts
/**
 * Предмет на входе API: строка → канонический слаг (ТЗ-52).
 *
 * Мягко: неопознанное значение НЕ отклоняется, а остаётся как есть.
 * Причина — предмет приходит из интерфейса, где список предметов может
 * обновиться раньше, чем задеплоится бэк (фронт и бэк катятся отдельно).
 * Отклонение здесь означало бы «учитель нажал «сохранить» и получил ошибку»
 * из-за рассинхронизации выкатки. Неопознанное значение попадает в базу
 * как есть и попадает в лог — его видно и можно починить.
 */
export const subjectInputSchema = z
  .string()
  .min(1)
  .max(64)
  .transform((value) => subjectSlugFrom(value) ?? value);
```

**Влияет на кэш: нет.** Ни один из пунктов правила подъёма версии (`backend/src/llm/cache.ts:46-55`) не выполнен: system-промпт не меняется, строка формата ответа не меняется, схема ответа и код сборки ответа не меняются. `FORMAT_VERSION` **не поднимаем**.

### 3.5. Что это даёт

- **Новые листы** сохраняются со слагом: фронт шлёт в `/save` то, что пришло из ответа API, а ответ теперь содержит `request.subject` — слаг, который пришёл от учителя (а `/save` дополнительно нормализует).
- **Ключ кэша** для «Математика» и `math` совпадает — раньше это были две разные записи кэша на один и тот же материал.
- **Фильтр в кабинете** перестаёт дублировать пункт «Математика» — **для новых листов**. Старые 120 листов останутся в базе как есть (см. 3.7).

## 4. Решения (AD-N)

**AD-1 · Предмет ответа определяет сервер; модель отвечает за содержание, а не за название.**
`subject: request.subject` во всех четырёх местах.
*Рационал:* предмет — это то, что **учитель выбрал**, и по нему потом фильтруют его кабинет, его аналитика и имя файла. Отдавать право переименовать это значение модели — значит закладывать расхождение по умолчанию. Модель при этом ничего не теряет: она по-прежнему пишет содержание заданий по этому предмету.

**AD-2 · Нормализация мягкая: неопознанное значение не отклоняется.**
*Рационал:* фронт и бэк катятся отдельно (Cloudflare Pages и Workers). Если в таксономии добавили предмет, фронт с новым списком может уехать раньше бэка — и учитель получил бы ошибку «предмет не распознан» на кнопке «сохранить», потеряв бы лист. Неопознанное значение сохраняется как есть **и пишется в лог** — его видно. Строгий вариант (400) — отдельное решение, которое стоит принимать владельцу, если он готов на невозможность сохранить лист.

**AD-3 · Нормализатор живёт во фронтовом слое контента, рядом с `subjectDisplayName`, и строится из таксономии.**
*Рационал:* это обратная сторона существующей функции, и обе строятся из одного источника (`subject-index.ts`). Новый перечисляемый список предметов в коде — это «один факт в двух местах», ровно та поломка, из которой уже выросли предыдущие находки. Побочная выгода: `subject-index.json` (17,7 КБ) уже ездит в браузер, в бандл воркера он добавит столько же.

**AD-4 · Промпты не трогаем: поле `"subject"` в формате ответа остаётся, его значение игнорируется.**
*Рационал:* удаление строки из формата ответа означало бы правку system-промпта → по правилу `backend/src/llm/cache.ts:46-55` это **подъём `FORMAT_VERSION`** и сброс prompt cache у тарифа «Плюс» — за то, что и так решается на сервере. В ТЗ-50 та же строка убирается из формата листа, потому что там это часть одного решения (балл).

**AD-5 · Бэкфилл — отдельным шагом, по команде владельца, вне кода.**
*Рационал:* правка данных в проде — решение владельца, а не разработчика. Команда готова и проверена на чтение; 120 строк UPDATE по одному столбцу и одному JSON-пути обратимы (значения известны, до правки сохранён список).

**AD-6 · Предмет в маршруте ОГЭ/ЕГЭ нормализуется мягко, без enum'а.**
*Рационал:* в таксономии экзаменов есть `"math-b"` и `"math-p"`, которых нет в основных 21 предметах. Строгий enum отбил бы эти два — то есть сломал бы генерацию варианта ОГЭ по математике.

## 5. Критерии приёмки

- [ ] `subjectSlugFrom("Математика")` возвращает `"math"`, `subjectSlugFrom(" МАТЕМАТИКА ")` — `"math"`, `subjectSlugFrom("Окр. мир")` — `"okruzhaet"`, `subjectSlugFrom("Естествознание")` — `null`, `subjectSlugFrom("")` — `null`.
- [ ] Ни одно `title` и ни одно `shortTitle` в `subject-index.json` не совпадает с названием другого предмета (тест-страховка; если тест падает — коллизия в данных, разбираются вручную).
- [ ] В ответе API на сгенерированный лист предмет равен предмету запроса, даже если модель в ответе написала «Математика».
- [ ] В ответе API на презентацию, план урока и КТП предмет равен предмету запроса.
- [ ] `POST /api/worksheets/save` с телом `subject: "Математика"` кладёт в колонку `subject` значение `math` и в `payload_json` — тоже `math`.
- [ ] `POST /api/worksheets/save` с телом `subject: "НеизвестныйПредмет"` **не возвращает ошибку** и сохраняет значение как есть.
- [ ] `POST /api/exams/generate` с предметом `"math-b"` **не возвращает ошибку** (мягкая нормализация).
- [ ] `POST /api/worksheets/generate` с предметом «Математика» по-прежнему отклоняется с 400 (строгий enum на входе генерации не тронут).
- [ ] **Каждый новый тест падает на старом коде и зелёный на новом** (кроме двух тестов-страховок, помеченных в разделе 3.5).
- [ ] `npx vitest run tests/subject-slug.test.ts` — зелёный.
- [ ] `npx vitest run backend/tests/unit/tz52-authoritative-subject.test.ts` — зелёный.
- [ ] `npx vitest run backend/tests/unit/` — без новых падений относительно прогона до правки.
- [ ] `git diff --stat` показывает правки только в: `src/lib/content/subject-slug.ts` (новый), `backend/src/lib/zod.ts`, `backend/src/routes/worksheets.ts`, `backend/src/routes/artifact-generate.ts`, `backend/src/routes/exams.ts`, `backend/src/llm/index.ts`, `backend/src/llm/prompts/presentation-gen.ts`, `backend/src/llm/prompts/lesson-plan-gen.ts`, `backend/src/llm/prompts/ktp-gen.ts` и двух тестовых файлах.

## 6. Чего не делаем

- **Не переписываем историю листов в коде** — бэкфилл в разделе 3.6 это разовая команда владельца, а не миграция в приложении.
- **Не переименовываем предмет в таксономии** и не добавляем в неё `world`, `Естествознание`, `История России` — это названия, придуманные моделью, а не предметы школьной программы.
- **Не убираем поле `"subject"` из форматов ответа** — см. AD-4 (это подъём `FORMAT_VERSION` и сброс prompt cache).
- **Не меняем строгий enum на входе генерации листа** (`backend/src/lib/zod.ts:149`) — он работает правильно, это единственная точка, где предмет проверяется жёстко.
- **Не трогаем `subject` в `payload_json` старых листов при чтении** — `GET /api/worksheets/:id` отдаёт то, что лежит в базе; после бэкфилла придёт слаг.
- **Не меняем отображение предмета** (`subjectDisplayName`, `src/app/constructor/page.tsx:225-231`) — для неизвестного значения оно и сейчас возвращает строку как есть, интерфейс не падает.
- **Не переводим `src/lib/lk/history-view.ts:85-87` (`subjectsOf`) на нормализацию.** Двойные пункты в фильтре уйдут сами, когда в базе останется один слаг на предмет; отдельная страховка здесь была бы «одним фактом в двух местах».

## 8. Что не удалось подтвердить

- **Не проверено в браузере, что именно учитель видит в фильтре по предмету.** Дефект выведен из данных (`subjectsOf` собирает уникальные значения из истории, `src/app/dashboard/page.tsx:1031-1040` рисует их как пункты фильтра, а `getSubjectIndex(...)?.shortTitle ?? item.subject` печатает «Математика» для обоих вариантов). Живой прогон в кабинете не делался.
- **Не проверено, что модель ответит «Математика» при заданном предмете `math`** — но сам факт такого ответа подтверждён боевыми данными: 53 листа с русским названием при slug-запросе.
- **Не проверена запись в прод-базу** — команда бэкфилла подготовлена, но не выполнялась: запись в боевую базу решает владелец.
- **Не измерено, сколько листов реально попадает в фильтр учителя с двумя именами.** Считано по всей таблице `worksheets` (184 листа, 3 пользователя — все тестовые). У реального учителя картина может быть другой.
- **Не проверено поведение при предмете из строки с неразрывным пробелом или с кавычками** — сравнение по нижнему регистру и обрезке пробелов такой случай не покрывает; для известных названий это невозможно (они в таксономии написаны без кавычек).
- **Не проверено, что `payload_json` у всех 184 листов имеет одинаковый путь `$.subject`** — проверено на 12 значениях из выборки, для которых выполнялся запрос; остальные не проверялись.
