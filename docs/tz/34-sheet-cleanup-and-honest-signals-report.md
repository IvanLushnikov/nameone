## 1. Что сделано

### 1.1 `backend/src/llm/validation/quality-filter.ts` — откат стал событием

В `QualityFilterReport` добавлено поле `rolledBack: boolean`. Оно выставляется
**в том месте, где откат происходит** — в ветке «осталось меньше трети» (или
не осталось ничего), где фильтр возвращает исходный набор.

Почему это отдельное поле, а не вычисление на стороне конвейера: откат и
«фильтр ничего не отбросил» дают ОДНО И ТО ЖЕ число `before - after == 0`.
Различить их по отчёту было нечем, поэтому конвейер и вычислял признак
неправильно (см. 1.3).

Фильтр в остальном не тронут — добавлено ровно одно поле и одно присваивание.

### 1.2 `backend/src/llm/index.ts` — постусловие чистки

**Новая функция `dropRemainingDupes(tasks)`** (экспортируется, чтобы её можно
было проверить отдельно): по итоговому списку находятся пары-дубли
(`findSkillDupes`) и удаляется **второе** задание каждой пары — так же, как в
`tasksToReplace` (AD-5: первое задание учитель уже видит). Если ничего не
убрано, возвращается тот же массив, а не копия, — вызывающий код сравнивает
списки по ссылке.

**Постусловие применено во всех трёх выходах `dedupeSheet`:**

| Выход | Что было | Что стало |
|---|---|---|
| Замена удалась | `usable[cursor] ?? task` — на слоте без замены оставалось СТАРОЕ задание, то есть сам дубль | `usable[slot] ?? task` + постусловие убирает остаток |
| Замен нет (`accepted` пуст) | возвращался `kept` (в нём могли остаться дубли, если бюджет выброса не дал убрать все пары) | `kept` + постусловие |
| Дозапрос упал (исключение) | возвращался `kept` | `kept` + постусловие |

**Попутно исправлен счётчик слотов замены** (ошибка была в моём файле, её
заметил ТЗ-33, когда чинил фикстуру своего теста):

```ts
// было
let cursor = 0;
return current.map((task, index) => {
  const number = index + 1;
  if (!replaceNumbers.includes(number)) return task;
  return usable[cursor] ?? task;
  cursor += 1;   // ← сюда управление не доходило: return выше
});
```

`return` выполнялся **до** `cursor += 1`, поэтому счётчик не рос НИКОГДА и на
всех заменяемых позициях подставлялось `usable[0]`. При двух заменах лист
получал не две замены, а **две копии одного задания** — и детектор видел в
них новый дубль. Теперь слот замены — это номер позиции в `replaceNumbers`
(`replaceNumbers.indexOf(number)`), а не счётчик.

**Порядок и число проходов.** Было: чистка → добор, проходов 1. Стало: чистка →
добор → проверка → второй проход, `dedupeRounds = 2`. Второй проход нужен не
для надёжности замены (замер 14.10.2026 показал, что дополнительные проходы
не дают её), а чтобы **перед постусловием** попробовать заменить дубль, который
вернул добор: без него постусловие просто выкинуло бы это задание и укоротило
лист — то есть вместо замены мы бы получили нехватку материала.

**Финальное постусловие после цикла проходов** — гарантия, которая не зависит
от того, что сделал добор. После него лист НЕ добирается: чистота важнее
длины (AD-1), учитель получает честное «получено 11 из 12».

**Контрольная** обрабатывается той же функцией: постусловие применено к
каждому варианту, а выравнивание объёмов (AD-8) идёт по кругу
«постусловие → добор → постусловие», максимум два круга.

**`summarizeLoss`**: `filterBackedOff` теперь ставится по `report.rolledBack`,
а не по `before - after == 0`.

**Логи** (только числа и номера, без текстов заданий):

- `logFilterReport` — добавлено поле `rolledBack`;
- «repeated skill inside sheet, replacing» — добавлено `pairCount`;
- новое событие «duplicates dropped after replacement» — `pairCount`,
  `wanted`, `accepted` (сколько замен принято), `removed` (номера удалённых
  позиций), `left` (сколько осталось).

### 1.3 `src/lib/constructor/quality-notice.ts` — текст приведён в соответствие

Строка про откат фильтра вынесена из блока «не хватило заданий» в отдельный
пункт: откат **не уменьшает лист** — он возвращает в него задания, которые
проверка не пропустила, — поэтому учитель должен знать об этом и когда
заданий хватает. Формулировка уточнена: «Фильтр качества откатил свою
проверку: он отсеял слишком много заданий, поэтому часть материала оставлена
без изменений».

Строка про отклонённые задания («N заданий отклонено проверкой качества»)
осталась внутри блока нехватки — это осознанно: фронтовый тест
`tests/quality-notice.test.tsx` («дозапрос, закрывший нехватку, НЕ пугает
учителя») запрещает показывать её, когда добор закрыл нехватку.

## 7. Что сломалось по ходу

### 7.1 Странный `git stash` между worktree — работа агента ТЗ-36 ушла не туда

**Что произошло.** Я спрятал свои правки через `git stash push -- <три файла>`,

своём worktree (`nameone-wt-tz36`). Итог: мы с ним ПОМЕНЯЛИСЯ местами
состояниями:

- мой `git stash pop` применил **их** изменения (`ratelimit.ts`,
  `routes/worksheets.ts`) в мой worktree и удалил их запись из стека;
- их `git stash pop` применил **мои** правки (`index.ts`,
  `quality-filter.ts`, `quality-notice.ts`) в их worktree.

Мои правки в этот момент были потеряны из рабочей копии — я это заметил по
`git status` и восстановил из dangling-коммита stash (мой stash лежал как
`990eb36`, ветка `feat/tz-34-sheet-cleanup`).

**Что я сделал, чтобы никто не потерял работу:**

1. В своём worktree вернул свои три файла из `990eb36`, а чужие два файла
   (которые я применил к себе случайно) — откатил к `HEAD`, предварительно
   сохранив копии.
2. В worktree ТЗ-36 (`/workspace/nameone-wt-tz36`) вернул **их** два файла из

   Итог в их worktree: `git status` показывает ровно то, что было до
   инцидента (4 изменённых файла + 2 новых теста).
3. Больше `git stash` не использовал: «до/после» на старом коде сделано

## 9. Пакет вопросов

1. **Выкатка.** ТЗ-34 меняет смысл `filterBackedOff` в ответе API. Старые
   ответы, сохранённые в кэше (D1, TTL 30 дней), содержат `filterBackedOff:
   true` в старом смысле — фронт покажет по ним «откат», которого не было.
   Варианты: (а) выкатывать вместе с TZ-35 (версия формата, кэш перевыпускается);
   (б) выкатывать сейчас и починить старые записи кэша одноразовой миграцией;
   (в) не трогать — максимум 30 дней «неправды» в старых ответах.
   **Рекомендация: (а)** — иначе получим ровно тот класс дефекта, который
   чиним.
2. **Второй проход чистки и цена.** Второй проход добавляет вызов провайдера,
   когда в первом проходе дубль заменить не удалось. Замер цены контрольной на
   ТЗ-34 не делался (нужен живой прогон, квота закрыта). Считать это приемлемой
   ценой за «лист без дублей» — или ограничить второй проход случаем, когда
   добор реально вернул дубль (тогда вызов будет только в этом узком случае)?
   **Рекомендация: второй вариант** — он не добавляет вызов там, где чинить
   нечего.
3. **`ensureCount` и дубли (находка 3).** Дозапрос не проверяет кандидатов
   детектором, поэтому может вернуть копию имеющегося задания; сейчас её
   снимает постусловие (лист укорачивается). Считать правильным запретить
   `ensureCount` принимать дубль (тогда длина добирается, а лист остаётся
   чистым) — или оставить как есть? **Рекомендация: запретить** — это одна
   проверка на том же детекторе, и она убирает ещё один повод укоротить лист.
   Но это правка `ensureCount`, то есть всех типов работ: нужно ваше решение.
4. **Живая проверка.** Квота анонимных генераций на боевом воркере исчерпана до
   1-го числа. Проверку после выкатки (история 6 класс «Крестовые походы» и
   математика 5 класс, `quality.filterBackedOff`, `quality.repeatedSkills`,
   отсутствие одинаковых заданий) проведёте вы сами по ключу подписки — или
   дать агенту тестовый ключ?
5. **Контрольная: длина вариантов после постусловия.** Если постусловие убрало
   задание из одного варианта, длины вариантов могут разойтись на 1 (AD-8
   «равный объём» vs AD-1 «чистота важнее длины»). Сейчас это редкий исход,
   и он НЕ показывается учителю отдельной строкой. Показывать ли это в
   `quality` (например, отдельным полем)? **Рекомендация: не показывать, но
   зафиксировать в логе** — по оценке, вероятность ничтожна, а лишнее поле в
   ответе — это ТЗ-35.
