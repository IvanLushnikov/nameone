# ТЗ-51: Ключ кэша зависит от реестра типов — правка правил больше не отдаёт старый материал

**Дата:** 30.10.2026
**Кто делает:** бэк
**Размер:** S — 2 файла исходников (реестр типов + кэш) + 1 новый тестовый файл; ~3 правки
**Источник:** находка Н3 из `docs/research/03-prompt-quality-audit.md` (§6.4, строки 388–411)

---

## 1. Контекст и зачем

Учитель повторяет запрос — «математика, 5 класс, дроби, средний уровень» — и получает **не свежий лист, а тот, что был собран до последних изменений правил**: со старым набором типов заданий, со старыми лимитами разнообразия, по старому блоку «ДОСТУПНЫЕ ТИПЫ ЗАДАНИЙ». Он этого не видит: страница выглядит нормально, просто правила в ней другие, а учитель не знает, какие должны быть.

Причина в том, как устроен ключ кэша. Ключ описывает **параметры запроса** (`backend/src/llm/cache.ts:114-148`): предмет, класс, тема, сложность, количество, тип, владелец, версия формата. Правила в ключе нет.

А **правила листа лежат в user-промпте**. Реестр типов задания (`src/lib/content/task-types.ts`) уходит в модель не через system-промпт, а отдельным блоком «ДОСТУПНЫЕ ТИПЫ ЗАДАНИЙ», который собирается в `backend/src/llm/prompts/worksheet-gen.ts:412`. Значит:

- правка реестра **не меняет** system-промпт → хэш-тест `backend/tests/unit/cache-format-version.test.ts` (`:91`) остаётся зелёным и не предупреждает;
- правка реестра **не меняет** `FORMAT_VERSION` → версия формата не поднимается;
- правка реестра **не меняет** ключ кэша → кэш отдаёт материал, собранный по старым правилам.

**Подтверждено боем.** Волна 1 (реестр типов, критерии, версия кэша) влита в `main` 29.10.2026 в 17:49 UTC (`240ad36`). В `llm_logs` есть попадание в кэш **29.10 19:47:30 UTC** — через два часа после мержа, то есть учителю отдан материал, собранный **до** новых правил. Всего записей кэша, созданных до 29.10, с `hit_count > 0` — **15**.

ТЗ-35 ввела `FORMAT_VERSION` в ключ и тест на хэш system-промпта — и закрыла половину проблемы: «правило, живущее только в system-промпте». Реестр в system-промпте не живёт.

## 3. Технический дизайн

| Файл | Что меняем |
|---|---|
| `src/lib/content/task-types.ts:404` | `buildTaskTypesPromptBlock(subject, grade, count, registry = TASK_TYPE_REGISTRY)` — четвёртый необязательный параметр (нужен только для теста, поведение не меняется) |
| `backend/src/llm/cache.ts` | Новая экспортируемая функция `taskTypesRegistryHash(subject, grade, count, registry = TASK_TYPE_REGISTRY): string` + поле `registryHash` в канонический JSON ключа (`:127-141`) |
| `backend/src/llm/cache.ts:114-116` | Третий необязательный параметр `makeCacheKey(input, formatVersion, registryHash?)` — чтобы тест мог подставить произвольный хэш |
| `backend/tests/unit/cache-registry-hash.test.ts` (новый) | Тесты: «правка реестра меняет ключ» и «ключ зависит от хэша реестра» |

### 3.1. Что именно хэшируется

Хэш считается по **двум** кускам данных, оба из реестра:

```ts
// backend/src/llm/cache.ts
import {
  TASK_TYPE_REGISTRY,
  buildTaskTypesPromptBlock,
  type TaskTypeSpec,
} from "../../../src/lib/content/task-types";

/**
 * Отпечаток реестра типов задания для ключа кэша (ТЗ-51).
 *
 * Ключ кэша описывал ПАРАМЕТРЫ запроса, но не ПРАВИЛА, по которым материал
 * собран. Реестр типов уходит в модель в user-промпте (блок «ДОСТУПНЫЕ ТИПЫ
 * ЗАДАНИЙ»), поэтому правка реестра не меняла ни system-промпт (его охраняет
 * тест `cache-format-version.test.ts`), ни `FORMAT_VERSION`, ни ключ кэша —
 * и кэш отдавал материал, собранный по старым правилам.
 *
 * Хэшируем ДВА куска, потому что на промпт влияют оба:
 *   · сам реестр целиком — в нём веса, применимость к предмету и классу и
 *     формулировки «что просим от учителя»;
 *   · готовый блок, который реально уходит в модель, — в нём ещё и лимиты
 *     разнообразия, зависящие от числа заданий (а не от реестра).
 * Изменится любой из них — изменится и ключ.
 */
export function taskTypesRegistryHash(
  subject: string,
  grade: number,
  count: number,
  registry: readonly TaskTypeSpec[] = TASK_TYPE_REGISTRY,
): string {
  return djb2Hex(
    JSON.stringify(registry) + buildTaskTypesPromptBlock(subject, grade, count, registry),
  );
}
```

`djb2Hex` уже есть в этом же файле (`backend/src/llm/cache.ts:150`) — второй хэш не пишем.

### 3.2. Ключ кэша

В канонический JSON (`backend/src/llm/cache.ts:127-141`) добавляется одно поле:

```ts
    // Отпечаток реестра типов задания (ТЗ-51). Правила листа лежат в
    // user-промпте, поэтому system-промпт и FORMAT_VERSION их не видят —
    // без этого поля правка реестра не инвалидировала кэш, и учитель получал
    // материал, собранный по старым правилам.
    registryHash: String(registryHash),
```

`makeCacheKey` получает третий необязательный параметр:

```ts
export function makeCacheKey(
  input: CacheKeyInput | GenerationRequest,
  formatVersion: number = FORMAT_VERSION,
  registryHash: string = taskTypesRegistryHash(
    String(input.subject),
    Number(input.grade),
    Number(input.count),
  ),
): string {
```

Значение по умолчанию считается из того же реестра, что и блок промпта, — поэтому «забыть передать» невозможно: значение по умолчанию всегда правильное.

### 3.3. Влияет на кэш

**Влияет на кэш: да — это и есть правка кэша.** Ключ кэша получает новое поле `registryHash`; материал, собранный по правилам реестра до правки, перестаёт находиться и генерируется заново. **`FORMAT_VERSION` при этом НЕ поднимается** — и вот почему.

`FORMAT_VERSION` по своему контракту (`backend/src/llm/cache.ts:46-55`) охраняет **system-промпт**, строку формата ответа, схему ответа и код сборки ответа. Реестр в system-промпте не входит. Поднимать версию при каждой правке реестра — это дисциплина: «не забудь». Реестр правят часто (ТЗ-33 расширял его с 5 до 17 типов, ТЗ-50 меняет веса), и одна забытая правка версии = 30 дней отдачи материала по старым правилам.

### 3.4. Тесты

Новый файл `backend/tests/unit/cache-registry-hash.test.ts`:

| Тест | Что проверяет | Падает на старом коде? |
|---|---|---|
| `правка реестра меняет отпечаток` | `taskTypesRegistryHash("math", 5, 10)` ≠ `taskTypesRegistryHash("math", 5, 10, изменённыйРеестр)`, где изменённый реестр — копия `TASK_TYPE_REGISTRY` с другим `weight` у одного типа | **Да** — функции не существует, тест не компилируется/не проходит |
| `ключ кэша зависит от отпечатка реестра` | `makeCacheKey(req) !== makeCacheKey(req, FORMAT_VERSION, "другой-хэш")` при одинаковых прочих полях | **Да** — третьего параметра не существует |
| `одинаковый реестр — одинаковый ключ` | `makeCacheKey(req) === makeCacheKey(req)`; `taskTypesRegistryHash(...)` детерминирован | Да (на старом коде первая пара проверок ещё не может быть написана) |
| `предмет и класс входят в отпечаток` | хэш для `("math", 5, 10)` ≠ хэш для `("russian", 5, 10)` — потому что блок типов разный | Нет (проходит и до, и после — это **не** проверка нового поведения, а страховка; в «красный на старом» список не входит) |

**Правило репозитория: каждый новый тест падает на старом коде и зелёный на новом.** Тест «предмет и класс входят в отпечаток» — единственное исключение из перечисленных, и он добавлен как страховка, а не как доказательство правки. В отчёт о выполнении он идёт отдельной строкой с пометкой «проходит и до, и после».

## 4. Решения (AD-N)

**AD-1 · Ключ кэша по построению зависит от реестра, а не по дисциплине.**
Хэш считается внутри `makeCacheKey` из самого реестра, а не передаётся вызывающим кодом.
*Рационал:* находка — это не «забыли поднять версию», а «правило не входит в ключ». Если хэш вычисляется внутри, правило выполняется для всех вызывающих по построению: забыть нечего. Передача хэша аргументом (как `formatVersion`) оставила бы дыру — «а вдруг не передали».

**AD-2 · Хэшируем и реестр, и готовый блок промпта.**
*Рационал:* блок покрывает всё, что видит модель (включая лимиты разнообразия, зависящие от `count`, — их нет в массиве реестра), а массив реестра покрывает то, чего в блоке нет: **веса типов**. После ТЗ-50 вес определяет балл в материале, и его правка тоже должна инвалидировать кэш. Одного блока было бы мало, одного массива — тоже.

**AD-3 · `FORMAT_VERSION` не поднимаем.**
*Рационал:* system-промпт, строка формата ответа, схема ответа и код сборки ответа не меняются — ни один из пунктов контракта версии (`backend/src/llm/cache.ts:46-55`) не выполнен. Поднятие версии без причины сбрасывает кэш целиком (все 122 записи) ради того, что и так чинится точечно. Побочная выгода: ТЗ-51 не конфликтует с ТЗ-50 и ТЗ-53, которые поднимают версию — `cache.ts:68` в этом ТЗ не трогается.

**AD-4 · `buildTaskTypesPromptBlock` получает необязательный четвёртый параметр, а не новую функцию.**
*Рационал:* блок и реестр — одно и то же знание в двух видах. Вторая функция «блок из переданного реестра» через месяц разошлась бы с оригиналом. Необязательный параметр со значением по умолчанию сохраняет один источник и даёт тесту точку подмены.

**AD-5 · Хэш считается по всем вызовам `makeCacheKey`, включая артефакты.**
*Рационал:* артефакты (план урока, презентация, КТП) реестр типов задания не используют, но их ключ строится той же функцией. Отдельная ветка «для листов» — это частное правило; лишняя инвалидация кэша артефактов при правке реестра стоит копейки (одна лишняя запись).

## 6. Чего не делаем

- **Не поднимаем `FORMAT_VERSION`** — обосновано в AD-3.
- **Не меняем сам реестр типов** (`src/lib/content/task-types.ts`): ни весов, ни формулировок, ни лимитов. ТЗ-51 только делает ключ чувствительным к его изменениям. Правки реестра — в ТЗ-50 и в других задачах.
- **Не трогаем лимиты разнообразия и блок типов в промпте** (`src/lib/content/task-types.ts:404-433` и `:435-489`) — только сигнатура.
- **Не пересчитываем и не чистим существующие записи кэша.** Записи, созданные до правки, просто перестанут находиться (ключ не совпадёт) и умрут по TTL (30 дней). Миграция `semantic_cache` не нужна: в записях только устаревший материал.
- **Не добавляем хэш всего user-промпта** в ключ. Он включает тему, план листа, УМК и прочее — это другая история (и partly уже закрыта: УМК входит в ключ через `:492-503`). Здесь — только реестр.
- **Не делаем отдельный ключ для артефактов** — см. AD-5.
- **Не меняем `saveCache`/`lookupCache`** — они работают с готовым ключом и ничего не знают о правилах.

## 8. Что не удалось подтвердить

- **Не измерено, сколько раз за 30 дней отдавался устаревший материал.** В `semantic_cache` есть только счётчик `hit_count`, журнала попаданий по времени нет. Известно: 15 записей, созданных до 29.10, имеют `hit_count > 0`; в `llm_logs` — одно попадание после мержа волны 1 (29.10 19:47 UTC).
- **Не проверено, что новая схема ключа не ломает существующие записи `semantic_cache`.** По коде: `saveCache` пишет через `INSERT OR IGNORE` по уникальному ключу, `lookupCache` ищет по ключу — старые записи просто не находятся. Живой прогон по боевой базе не делался.
- **Не проверено, сколько стоит инвалидация кэша в деньгах.** Оценка «одна лишняя запись — копейки» взята из исследования и не пересчитана: при правке реестра пересоздаются все записи по этому реестру, то есть не одна, а столько, сколько их наберётся за TTL (сейчас 122 записи на все предметы).
- **Не проверено, что блок типов — единственное место, где реестр попадает в промпт.** Проверено чтением `backend/src/llm/prompts/worksheet-gen.ts:412` (единственный вызов `buildTaskTypesPromptBlock`); другие промпты (`exam-gen.ts`, `artifact-gen.ts`, `presentation-gen.ts`) реестр не используют — это видно по отсутствию импорта. Автоматической проверки «реестр не попал в другой промпт» нет.
