## 1. Контекст и зачем

**Часть 1. Дубль доезжает до учителя, и система об этом знает.**

Лист по истории, 6 класс, тема «Крестовые походы», 12 заданий. Задания №6, №9 и
№12 — **байт-в-байт одинаковые**: один и тот же текст, один и тот же ответ, одна
и та же метка «Причины обращения за помощью». В ответе API стоит
`quality.repeatedSkills = 3` — то есть система дубль увидела, честно написала
«заменить не получилось» и всё равно отдала лист.

Учитель печатает такой лист и раздаёт классу. Три ученика получают одно и то же
задание. Три задания из двенадцати — это четверть работы, и она уходит в
брак.

**Часть 2. Фильтр врёт про себя — и враньё идёт учителю в интерфейс.**

Учитель запросил 12 заданий, получил 10. На экране появляется: «Фильтр отсеял
слишком много заданий, поэтому часть материала оставлена без изменений». Это
неправда: фильтр **ничего не отбросил** — `dropped: 0` во всех десяти живых
прогонах. Признак `filterBackedOff` в коде означает не «откат», а «фильтр
ничего не выбросил», а показывается он именно в том случае, когда учителю
не хватило заданий. То есть учителю, которому не хватило материала по другой
причине, говорят про фильтр, который не отбросил ничего.

## 2. Что уже работает (не переписываем)

| Механика | Где | Состояние |
|---|---|---|
| Откат фильтра при слишком агрессивной чистке | `backend/src/llm/validation/quality-filter.ts:367-369` — если осталось меньше трети, возвращается исходный набор | Работает, но следов не оставляет |
| Отчёт фильтра не теряется (ТЗ-25, разрыв 5) | `index.ts:213-225` `filterAndReport` + `logFilterReport` | Работает |
| Кандидат на замену проверяется против принятого, а не только против `kept` | `index.ts:1055-1060` (`[...kept, ...accepted, candidate]`) | Работает. Это была первая половина правки ТЗ-26 |
| Отказ от замены не возвращает дубль: `usable.length === 0` → возвращается `kept` | `index.ts:1094-1100` | Работает для полного отказа |
| Бюджет выбрасывания ограничен половиной листа | `index.ts:1151` `dropBudgetOf(count) = ceil(count / 2)` | Работает осознанно: пустой лист хуже листа с повтором |
| Порядок «сначала чистота, потом длина» | `index.ts:1177-1196` — после чистки вызывается `ensureCount` | Работает |
| Учитель видит предупреждение о неубранном повторе | `src/lib/constructor/quality-notice.ts:99` | Работает |
| Сколько пар-дублей осталось — считается по финальному списку | `index.ts:1157-1158` `countRemainingDupes` → `quality.repeatedSkills` | Работает |

**Где именно ломается (часть 1).** `backend/src/llm/index.ts:1088`:

```ts
return usable[cursor] ?? task;   // ← если замен меньше, чем удалённых позиций,
```

`usable` — это принятые замены. Если модель вернула две замены на три
выкинутых дубля, то на третьей позиции остаётся **старый дубль**: `?? task`
подставляет исходное задание. Длина листа сохраняется, `ensureCount` не
срабатывает, цикл чистки заканчивается (`dedupeRounds = 1`), и дубль уезжает
учителю. **Постусловия «после чистки дублей не осталось» в коде нет.**

**Где именно ломается (часть 2).** `backend/src/llm/index.ts:328-330`:

```ts
if (report.before > 0 && reportDropped === 0) {
  filterBackedOff = true;   // ← это значит «ничего не отбросили», а не «откатились»
}
```

Настоящий откат живёт в `quality-filter.ts:367-369` и в отчёт отчёта не
попадает: `before - after == 0` у отката и у «фильтр ничего не нашёл» — одно
и то же число, разные события.

**Что НЕ меняется:** формат ответа API (поле `quality.filterBackedOff`
остаётся, меняется его смысл), `backend/src/types.ts`, промпты, кэш, тарифы.

### Контракты

```ts
// backend/src/llm/validation/quality-filter.ts
export interface QualityFilterReport {
  droppedPatternRef: number[];
  cleanedAnswer: number[];
  droppedForeignMath: number[];
  droppedNoAnswer: number[];
  before: number;
  after: number;
  /** Фильтр откатил чистку и вернул исходный набор (quality-filter.ts:367).
   *  До этой правки откат был неотличим от «фильтр ничего не отбросил». */
  rolledBack: boolean;
}
```

```ts
// backend/src/llm/index.ts — постусловие чистки
/**
 * Убрать из листа всё, что осталось дублем.
 * Возвращает СПИСОК БЕЗ ДУБЛЕЙ; длина может уменьшиться — это осознанно:
 * лист с дублем хуже короткого листа, а `stillMissing` скажет учителю правду.
 */
function dropRemainingDupes(tasks: CleanTask[]): { tasks: CleanTask[]; removed: number[] };
```

### Порядок внутри `dedupeSheet` (после замены)

1. Собрать итоговый список (как сейчас: `current` с подставленными `usable`).
2. **Вызвать `dropRemainingDupes`** — если после подстановки остались дубли
   (частичная замена, `usable[cursor] ?? task`), убрать второе задание каждой
   пары.
3. Вернуть список **без дублей** и число удалённых позиций.
4. Число удалённых — в лог (`worksheet-gen: duplicates dropped after replacement`).
   Оно же — в `quality` через уже существующий `repeatedSkills` (пары, которые
   остались) — учитель увидит «получено 9 из 12 заданий» вместо листа с тремя
   одинаковыми заданиями.

**Важно:** `ensureCount` вызывается ПОСЛЕ чистки (уже так в коде,
`index.ts:1187`). Если после удаления дублей лист стал короче, `ensureCount`
доберёт длину — и **может вернуть дубль снова** (модель на ту же тему выдаёт
тот же навык). Поэтому порядок такой:

1. чистка → 2. `ensureCount` → 3. **повторная проверка на дубли** →
4. если дубли появились снова — второй проход чистки.

Сегодня `dedupeRounds = 1` (`index.ts:1135`). Ставим **2**: второй проход
нужен именно из-за этого порядка. Каждый проход ограничен бюджетом
`dropBudgetOf(count)` — половина листа, чтобы лист не вычерпали в ноль.

## 4. Решения

**AD-1 · Чистота важнее длины, но не любой ценой.**
Если после чистки лист стал короче — отдаём короткий лист и честный
`stillMissing`, а не полный лист с дублями.
*Рационал:* этот порядок уже записан в коде («сначала чистота, потом длина»,
`index.ts:1183-1185`) — доводим до постусловия. Учитель увидит «9 из 12» и
попросит ещё; дубль он увидит на печати, когда класс уже отвечает.

**AD-2 · Постусловие — отдельный проход, а не проверка «на входе».**
Дубли считаются по ИТОГОВОМУ списку, а не по списку до замены.
*Рационал:* именно в этом разрыв — подстановка `?? task` возвращает старый
дубль в готовый лист. Проверка на входе была бы верной и бесполезной.

**AD-3 · `filterBackedOff` перестаёт означать «ничего не отбросили».**
Признак ставится по факту отката (`report.rolledBack`).
*Рационал:* имя поля уже правильное («откат фильтра»), неверна была формула.
Менять имя поля — значит менять контракт ответа и поднимать версию формата
(TZ-35) без нужды.

**AD-4 · Откат — это событие, а не следствие.**
Откат отмечается в том месте, где он происходит, и передаётся в отчёте.
*Рационал:* «откат не оставляет следов» — это и было причиной смешения двух
разных событий. Отмечать надо там, где событие случилось.

**AD-5 · `dropRemainingDupes` не трогает первое задание пары.**
Заменяется второе — так же, как в `tasksToReplace`.
*Рационал:* первое задание учитель уже видит, замена ломала бы нумерацию
сильнее, чем польза от снятия дубля.

**AD-6 · Число удалённых дублей видно в логе, но не в тексте для учителя.**
Учитель получает «получено 9 из 12 заданий» — этого достаточно. Отдельного
абзаца «мы выкинули 3 задания-дубля» не делаем.
*Рационал:* дубль — это наш брак, а не событие, о котором учитель должен
думать; достаточно факта, что материала меньше.

## 5. Критерии приёмки

Функциональные:
- [ ] Модель вернула лист, где три задания идентичны, и на замену пришло меньше кандидатов, чем нужно: итоговый лист **не содержит** ни одной пары дубликатов (`findSkillDupes` на финальном списке → `hasDupes: false`).
- [ ] В этом случае `quality.repeatedSkills = 0`, а `quality.stillMissing > 0` — то есть учитель получает честное «получено N из 12 заданий».
- [ ] Модель вернула лист с одним дублем и нормальную замену: дубль заменён, длина листа не изменилась, `repeatedSkills = 0`.
- [ ] Фильтр качества откатил чистку (осталось меньше трети): `report.rolledBack === true`, и в `quality.filterBackedOff === true`.
- [ ] Фильтр ничего не отбросил, но заданий не хватило по другой причине: `report.rolledBack === false`, `quality.filterBackedOff === false`, и строка «Фильтр отсеял слишком много заданий…» учителю **не показывается**.
- [ ] Фильтр отбросил часть заданий (без отката): `rolledBack === false`, `dropped > 0`, строка про отклонённые задания показывается.

Регрессионные:
- [ ] Лист без дублей проходит чистку без изменений: количество вызовов провайдера не растёт, длина и состав листа прежние.
- [ ] Контрольная: два варианта обрабатываются той же функцией; дубль в любом из вариантов убирается; `repeatedSkills` считается по обоим вариантам.
- [ ] `ensureCount` по-прежнему добирает длину после чистки, и `stillMissing` считается по факту.
- [ ] Существующие тесты ТЗ-25 и ТЗ-26 (потери, два варианта, кэш) — зелёные.

Качественные:
- [ ] В логе генерации видно: сколько пар-дублей было, сколько замен принято, сколько заданий удалено постусловием, был ли откат фильтра.
- [ ] Логи не содержат текстов заданий — только числа и номера (как сейчас в `logFilterReport`).
- [ ] НОВЫЕ тесты падают на старом коде: `sheet-dedupe-postcondition.test.ts` на коммите до правки показывает, что дубль остаётся в листе; `quality-filter-rollback.test.ts` — что `rolledBack` не существует/не выставлен. Результат прикладывается к отчёту.

## 6. Чего не делаем

- **Не переписываем `dedupeSheet` целиком.** Меняется постусловие и число проходов; вся накопленная логика (бюджет, промпт замены, фильтрация кандидатов) остаётся.
- **Не расширяем промпт замены.** Список занятых навыков в него сознательно не передаётся (замер 14.10.2026: со списком — 1 из 3 успешных замен против 2 из 3 без, и дороже).
- **Не добавляем новые правила в системный промпт.** Правка промпта сбрасывает prompt cache у «Плюса» (шапка `prompts/worksheet-gen.ts`), а гарантию даёт код.
- **Не меняем формат ответа API.** Имя `filterBackedOff` остаётся, меняется только то, когда оно истинно.
- **Не показываем учителю число выкинутых дублей.**
- **Не трогаем `filterTasks` кроме поля `rolledBack`.** Сам фильтр работает правильно — виноват конвейер вокруг него.

## 7. Риски

| Риск | Вероятность | Цена | Что делаем |
|---|---|---|---|
| Листы станут короче, чем просил учитель (чаще, чем раньше) | Средняя | Средняя — учитель увидит «9 из 12» и попросит ещё | `stillMissing` + `ensureCount` добирают; лимит — два прохода и бюджет половины листа |
| Второй проход чистки съест ещё один вызов модели | Средняя | Низкая — вызов на листе, а не на учителе | Бюджет `dropBudgetOf`; лимит проходов = 2 |
| Учитель начнёт чаще видеть «получено N из 12» и жаловаться | Средняя | Низкая | Это правда вместо тихого брака; формулировка предупреждения — в `quality-notice.ts` |
| Признак `filterBackedOff` перестанет показываться вообще, и реальный откат станет невидимым | Низкая | Средняя | Откат теперь виден точно; при откате лист честно укорочен и `stillMissing > 0` |

## 8. Порядок работ

1. (0,5 дн) `rolledBack` в `QualityFilterReport` + тест. Изолированная правка, ничего не ломает.
2. (1 дн) `summarizeLoss` по `report.rolledBack` + тест на «фильтр ничего не отбросил, но не хватило» → предупреждение не показывается.

## 9. Что не удалось подтвердить

- **Точный механизм доставки трёх одинаковых заданий в прогоне по истории.** Реконструкция по коду даёт путь «частичная замена → `?? task` → дубль остался», но промежуточные состояния видны только в логах воркера, а доступа к ним (D1, `wrangler tail`) у агента нет. Гипотеза подтверждается тестом на синтетическом ответе модели, но не на том живом прогоне.
- **Как часто лист не дотягивает до замены.** Не измерено: нужен `wrangler tail` или счётчик в логах. После выкатки это видно по новому полю лога.
- **Влияет ли изменение на кэш.** Не влияет: формат ответа не меняется, версия формата не поднимается (в отличие от TZ-35, где она поднимается осознанно).
