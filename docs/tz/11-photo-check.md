## 1. Контекст и зачем

### 1.1 Что делает фича с точки зрения учителя

Учитель ведёт 25–30 человек в классе. Домашняя работа собрана — 25 тетрадей в стопке. Сегодня вечер уходит на то, чтобы каждую прочитать, примерить и поставить отметку. Реально на это уходит **40–90 минут** на класс.

Фича: учитель фотографирует тетрадь на телефон, загружает стопкой, через минуту видит:
- по каждому заданию — что написал ученик, верно или нет, за что балл;
- итоговый балл и отметку;
- список заданий, где ИИ не уверен — их учитель перепроверяет сам.

**Это не «ещё один генератор контента».** Это вторая точка входа в продукт, которая открывается дважды в день, а не раз в неделю.

### 1.3 Почему мы отстаём и что с этим делать

Мы отстаём не качеством, а **наличием**. В репозитории по фиче есть только:
- фронтовый стаб `src/components/f06/PhotoCheckPanel.tsx` (25 строк, рисует два текстовых поля);
- бэковый стаб `backend/src/routes/f06.ts` (23 строки, отдаёт 501 на любой путь).

При этом **уже есть точка входа в UI** — панель вызывается из конструктора (`src/app/constructor/page.tsx:988`) и уже прокидывает контракт `assignmentId` / `demoTasks` / `onResult`. То есть интерфейсная точка входа согласована, а функциональности за ней нет.

**Стратегическая логика.** Проверка по фото — не «ещё один фичер в копилку», а ответ на вопрос «почему учитель не переходит с Обучай к нам». Их фича держит аудиторию; без неё мы конкурируем только бесплатными листами.

**Плюс — у нас есть козырь, которого у них нет.** Наш ПДн-пайплайн (Jay Guard, столбик **a** в `POSITIONING.md` §3) маскирует данные до отправки провайдеру. Фото чужой тетради — это персональные данные ребёнка, см. §5.2. Мы можем продавать «проверка работ по фото с защитой ПДн» в школы — они такой формулировки дать не могут. **Но это работает только если фича реально есть.**

## 3. Пользовательский сценарий

Описывает **первую полезную версию** (M1, этап 1 из §9). Без стопки, без чтения имён — это этап 2.

### Шаг 1. Учитель открывает проверку

Учитель сгенерировал рабочий лист в конструкторе, нажал кнопку **«Проверить работы по фото»** (сейчас эта кнопка уже рендерит панель — `constructor/page.tsx:988`). Открывается панель `PhotoCheckPanel`.

*Что видит:* короткая инструкция: «Сфотографируйте страницу тетради с ответами. Одна страница — одно фото.»

### Шаг 2. Выбирает файл

Учитель нажимает «Выбрать фото» (на телефоне — сразу камера) или перетаскивает файл. Поддерживаемые форматы: JPEG, PNG, HEIC→JPEG (конвертация на клиенте), WebP. Максимум **1 фото на проверку** в M1.

*Что видит:* превью загруженного снимка + «Удалить».

### Шаг 3. Эталон подставляется автоматически

Эталон берётся из текущего листа — из `demoTasks`, которые уже прокидывает конструктор (`taskText` + `correctAnswer` + `maxPoints`). Учителю **ничего вводить не нужно**.

Если лист сгенерирован локально (есть `localStorage`, ID вида `local-ws_xxx`), эталон всё равно уходит в теле запроса — серверной зависимости от D1 нет.

*Что видит:* сводка «Проверим 8 заданий по математике, 5 класс» + раскрывающийся список «Посмотреть задания и эталоны».

### Шаг 4. Ждёт результат

Учитель жмёт **«Проверить»**. Фото сжимается на телефоне (до 1600 px по длинной стороне, JPEG q0.8 — это важно для стоимости, §5.1), уходит на бэк, бэк отдаёт фото в vision-модель.

*Что видит:* состояние «Распознаём ответы…» с прогресс-индикатором и текстом «обычно 10–30 секунд». Кнопка отмены — **не делаем** в M1 (см. §10).

### Шаг 5. Получает результат

*Что видит:*

| № | Задание (кратко) | Ответ ученика | Верно? | Комментарий ИИ |
|---|---|---|---|---|
| 1 | 3/4 + 1/6 | 11/12 | ✅ | — |
| 2 | Сколько треугольников? | 7 | ❌ | На рисунке 8 |
| 5 | Значение выражения | неразборчиво | ⚠️ | Перепроверьте |

Сверху — итог: **«9 из 12 баллов · 75% · оценка 4»** и кнопки:
- **«Печать / PDF»** — используем уже готовый механизм `window.print()` + CSS `@page A4`, он в проекте есть;
- **«Сохранить проверку»** — пишет результат в D1 и в историю;
- **«Отметки в журнал»** — ⚠️ **не в M1** (в §10, это школьный ЭДЖ, отдельная фича).

Жёлтые строки (⚠️) — это не баг, а честный отказ гадать: если ИИ не уверен, он говорит «не уверен», а не ставит плюс наугад.

### Шаг 6. Проверка нескольких учеников

Учитель повторяет шаги 2–5 для каждого ученика. В M1 — это ручная работа, ровно как сейчас, только вместо чтения тетради — 30 секунд на снимок.

### Шаг 7. Проверка целого класса (этап 2)

Загружает до **10 фото за один раз**, получает один отчёт: 10 учеников, у каждого балл и отметка, сводная таблица, одна кнопка печати на всех. Это и есть «проверка фото стопкой» из §1.2.

## 4. Технический дизайн

### 4.1 D1 — новые таблицы

Все CREATE TABLE добавляются в конец `backend/src/db/schema.sql`. Комментарий-шапка файла обновляется.

```sql
-- ─────────────────────────────────────────────────────────────────────────────
-- Photo-check (F-06): проверка работ по фото
--
-- Хранение фото — в R2 (binding PDFS), здесь только ключ.
-- ПОД ВОПРОСОМ (см. docs/tz/11-photo-check.md §5.2): обработка ПДн детей.
-- ─────────────────────────────────────────────────────────────────────────────

CREATE TABLE IF NOT EXISTS photo_checks (
  id             TEXT PRIMARY KEY,             -- pc_<12> — добавить в lib/shortid.ts
  user_id        TEXT REFERENCES users(id) ON DELETE SET NULL,
  worksheet_id   TEXT,                         -- ws_*; NULL если лист был локальным
  subject        TEXT,
  grade          INTEGER,
  r2_key         TEXT,                         -- ключ исходника в PDFS; NULL после удаления
  source_kind    TEXT NOT NULL DEFAULT 'single', -- 'single' | 'stack' (M2)
  pages          INTEGER NOT NULL DEFAULT 1,
  status         TEXT NOT NULL DEFAULT 'pending', -- 'pending' | 'ok' | 'partial' | 'failed'
  total_points   INTEGER NOT NULL DEFAULT 0,
  earned_points  INTEGER NOT NULL DEFAULT 0,
  percentage     INTEGER,                      -- 0..100, NULL если не посчитан
  grade_mark     TEXT,                         -- '5' | '4' | '3' | '2' | NULL (пороги в §7.3)
  needs_review   INTEGER NOT NULL DEFAULT 0,   -- 1 = есть задания, которые надо перепроверить
  model          TEXT,                         -- vision-модель из MODEL_CATALOG
  provider       TEXT,
  cost_usd       REAL NOT NULL DEFAULT 0,
  latency_ms     INTEGER,
  error_code     TEXT,                         -- 'LOW_CONFIDENCE' | 'LLM_UNAVAILABLE' | 'BAD_IMAGE' | NULL
  deleted_at     INTEGER,                      -- soft-delete: фото удалено из R2, метаданные живы
  created_at     INTEGER NOT NULL,
  completed_at   INTEGER
);

CREATE INDEX IF NOT EXISTS idx_photo_checks_user_created ON photo_checks(user_id, created_at);
CREATE INDEX IF NOT EXISTS idx_photo_checks_worksheet    ON photo_checks(worksheet_id);

CREATE TABLE IF NOT EXISTS photo_check_items (
  id             TEXT PRIMARY KEY,             -- pci_<12>
  check_id       TEXT NOT NULL REFERENCES photo_checks(id) ON DELETE CASCADE,
  task_number    INTEGER NOT NULL,
  task_text      TEXT,
  expected       TEXT,                         -- эталон из тела запроса
  student_answer TEXT,                         -- что распознал ИИ
  correct        INTEGER NOT NULL DEFAULT 0,   -- 0/1, всегда уверенное решение
  confidence     REAL,                         -- 0..1; < порога (§9.1) → needs_review=1
  needs_review   INTEGER NOT NULL DEFAULT 0,
  max_points     INTEGER NOT NULL DEFAULT 1,
  comment        TEXT,                         -- короткое объяснение ИИ, 1 строка
  created_at     INTEGER NOT NULL,
  UNIQUE(check_id, task_number)
);

CREATE INDEX IF NOT EXISTS idx_photo_check_items_check ON photo_check_items(check_id);
```

**Счётчик квоты — отдельная таблица, а не колонка в `users`.** Причина: `ALTER TABLE users ADD COLUMN` в SQLite **не идемпотентен**, а миграция у нас — это повторный прогон всего `schema.sql` (`db:migrate:*`), который запускается повторно. Колонку так не добавить без отдельного одноразового скрипта. Отдельная таблица переживает повторный прогон.

```sql
CREATE TABLE IF NOT EXISTS usage_counters (
  id           TEXT PRIMARY KEY,
  user_id      TEXT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  metric       TEXT NOT NULL,                  -- 'photo_check'
  window_start INTEGER NOT NULL,               -- начало окна (unix seconds)
  count        INTEGER NOT NULL DEFAULT 0,
  updated_at   INTEGER NOT NULL,
  UNIQUE(user_id, metric, window_start)
);

CREATE INDEX IF NOT EXISTS idx_usage_counters_lookup ON usage_counters(user_id, metric, window_start);
```

> **Альтернатива, если команда предпочитает колонки:** `users.photo_checks_month` + `users.photo_checks_reset_at` по образцу `generations_today` / `generations_reset_at`. Тогда миграцию надо делать отдельным одноразовым `ALTER TABLE`-скриптом (`backend/scripts/`), потому что `schema.sql` прогоняется повторно. Выбор — §5, вопрос **В-5**.

**`GET /api/assignments/photo-checks/:id`** — результат проверки (те же поля ответа, без повторного вызова LLM).

**`GET /api/assignments/photo-checks?limit=20&cursor=<ts>`** — история проверок пользователя, только свои (`user_id` из сессии, из query не берётся).

**`DELETE /api/assignments/photo-checks/:id`** — удалить фото: удаляет объект из R2, ставит `deleted_at`, обнуляет `r2_key`. Ответ `200 { ok: true }`. Отдельно — `retention`-скрипт (§5.2).

**`GET /api/assignments/photo-checks/usage`** — остаток квоты, для показа счётчика в UI.

**Авторизация:** `requireAuth(c)` из `backend/src/middleware/auth.ts` — как в `worksheets.ts:294`. Анонимный доступ **запрещён**: без аккаунта нельзя ни получить историю, ни отнести проверку к тарифу.

## 5. Блокеры и открытые вопросы

Блокеры №1 и №2 — блокирующие, без них старт разработки бессмыслен. №3 и №4 требуют юриста/продакта.

### 5.1 В-1. 🛑 Vision-модель: какой моделью распознаём

| Что известно из кода | Что неизвестно |
|---|---|
| `MODEL_CATALOG` (`config.ts:90-114`) содержит 6 моделей, из них 2 — эмбеддинги, 4 — текстовые | Ни одна из 4 текстовых не заявлена как принимающая изображения |
| Провайдер один — polza.ai, ключ `POLZA_API_KEY` покрывает весь каталог | Есть ли на polza vision-модель с `image_url` в OpenAI-совместимом формате |
| `MODEL_COSTS` (`config.ts:179-197`) — прайс в USD/1M токенов | Vision обычно тарифицируется иначе — за изображение или за тайлы; **наша модель учёта стоимости это не умеет** (`cost.ts` считает только текстовые токены) |

**Что нужно решить до старта:**
1. Какая модель распознаёт (кандидаты — vision-модели polza; если на polza нет, обсуждаем второго провайдера).
2. Её цена: за изображение и/или за токены. **Без неё нельзя посчитать юнит-экономику и нельзя выставить лимиты (§7).**
3. Нужен ли `detail: "low"` для черновиков — экономит токены картинки в разы при минимальной потере качества.
4. Проверка на живом ключе: сколько секунд занимает распознавание страницы тетради и какой `%` точности на 20 реальных фото.

**Что делаем в ТЗ до решения:** проектируем так, что выбор модели — это одна строка в `MODEL_CATALOG` + один `case` в `router.ts`. Переключение с дешёвой на дорогую не требует правок фичи.

### 5.2 В-2. 🛑 Персональные данные детей: фото тетради — это ПДн

Это не формальность. Фото страницы школьной тетради может содержать:
- **фамилию и имя ученика**, написанные в шапке работы;
- **рукописный текст**, по которому восстанавливаются личные обстоятельства;
- иногда — фото лица, если ученик вклеил/приклеил фотографию или на фото попал рядом сидящий одноклассник;
- на контрольных — **подписи, иногда с датой рождения**.

По ФЗ-152 персональные данные относятся к специальной категории, обработка требует правового основания и, как правило, **письменного согласия законного представителя**. Согласие ученика 10–14 лет само по себе не является достаточным основанием.

**Что нужно решить и зафиксировать:**

| # | Вопрос | Варианты |
|---|---|---|
| В-2.1 | Кто оператор ПДн и на каком основании обрабатываем фото | Договор с учителем/школой как поручение обработки (п. 3 ст. 6 ФЗ-152) — вероятный путь, требует юриста |
| В-2.2 | Нужно ли согласие законного представителя и в какой форме | Чекбокс согласия на загрузке фото + текст согласия в оферте. **Юридически недостаточно для школы — это осознанный компромисс для B2C-учителя, решает юрист** |
| В-2.3 | Через сколько фото удаляются | Рекомендуем: фото — 7 дней после проверки (нужно на разбор и «учитель увидел не то»); результаты проверок — до удаления аккаунта |
| В-2.4 | Кому утекают данные | Polza — российский провайдер, платёж в ₽, но **фото уходит в чужую инфраструктуру**. Проверить договор/оферту polza на предмет обучения на запросах (Блокер В-3) |
| В-2.5 | Нужно ли маскировать ФИО перед отправкой | Jay Guard маскирует ПДн в тексте. **Распознавание рукописного ФИО из картинки маскировкой не закрывается** — нужна отдельная оценка |
| В-2.6 | ФЗ-152/152-ФЗ уведомление РКН | Нужно ли уведомление об обработке — вопрос юриста, зависит от режима (B2C-учитель vs школа) |

**Минимальное техническое требование по этому блокеру:** фото **не хранится дольше retention-срока**, удаляется по расписанию, учитель может удалить вручную одной кнопкой (`DELETE` эндпоинт), в интерфейсе есть текст согласия на загрузке.

### 5.3 В-3. Условия polza.ai по обработке входных данных

Нужен письменный ответ/выписка из оферты polza: используются ли наши промпты и изображения для обучения, где физически хранятся логи, каков срок хранения. Без этого позиционирование «Jay Guard + ПДн» в `POSITIONING.md` §3 на фото-фиче не распространяется честно.

### 5.4 В-4. Юнит-экономика: сколько стоит одна проверка

Считать нельзя, пока нет В-1. Формула, которую надо будет заполнить:

```
COGS(проверка) = цена_изображения × 1
               + (tokens_in × $input  + tokens_out × $output)
               + фотосжатие/хранение ≈ 0
```

Прикидка для планирования (**не цифра для решения — зависит от В-1**): фото 1600 px ≈ 1.5–3k image-токенов; output ~1k токенов JSON на 12 заданий. Если модель окажется уровня `gpt-6-luna` по тексту ($0.07/$0.35) и тарифицирует картинку по токенам — порядок **$0.01–0.05 за проверку**, это 1–4 ₽. Если тарифицирует за изображение фиксированно (многие так делают) — надо брать цену из прайса напрямую.

**Порог: 500 ₽/мес (тариф Базовый) должен оставаться в зоне маржи ≥ 80%, как зафиксировано в `POSITIONING.md` §4.** Если проверка стоит > 8–10 ₽ — лимиты в §7 надо пересматривать.

### 5.5 В-5. Модель квоты: колонки в `users` или `usage_counters`

Техническая развилка, влияет на трудоёмкость на ±1 день. Рекомендация — `usage_counters` (§4.1), потому что миграция = повторный прогон `schema.sql`.

### 5.6 В-6. Оценка отметки: по пятибалльной шкале или по баллам

Учителя ждут отметку, но «балл → отметка» зависит от предмета и класса (математика 5 класс и русский 8 класс — разные пороги). Варианты: фиксированные пороги в коде (§7.3), пороги настраивает учитель, или показываем только балл и процент. **Решение за продактом, влияет на объём фронта.**

### 5.7 В-7. Синхронный запрос или очередь

Учитель ждёт 10–30 секунд. Синхронный `POST` — просто, но: долгий HTTP-запрос к Worker, нет ретраев и прогресса, при просадке polza пользователь видит ошибку и ждёт заново. Cloudflare Queues требует платного плана. **Рекомендация: M1 — синхронно** (простота важнее), с явным таймаутом и понятной ошибкой; очередь — в M2 вместе со стопкой. Решение за архитектором.

## 7. Схема лимитов и тарификация

### 7.1 Текущая база

| Источник | Что говорит |
|---|---|
| `POSITIONING.md` §4 | free = 3 генерации/день; base 500 ₽ = безлимит; plus 1 500 ₽; школа 3 000 ₽/класс |
| `ratelimit.ts:27-32` | `LIMITS`: anonymous 3/день, free 10/день, base/plus — бесконечность; окно 24 ч, ключ `user:<id>` или `ip:<hash>` |
| `worksheets.ts:400-403` | `generationsLimit` = −1 (безлимит) для base/plus, 3 для free |
| `users` (schema.sql:19-21) | `generations_total`, `generations_today`, `generations_reset_at` |

**Существующий rate-limit — только суточный.** Месячных квот в проекте нет вообще: сделать «N проверок в месяц» на текущем механизме нельзя. Нужна своя таблица (§4.1).

### 7.2 Предлагаемые лимиты

| Тариф | Проверок в месяц | Обоснование |
|---|---|---|
| **Бесплатно** | **10** | Больше, чем у Обучай (3 разово навсегда), но достаточно, чтобы учитель понял ценность. Сознательно меньше, чем 3/день по листам: проверка дороже |
| **Базовый** (500 ₽) | **100** | Реалистичный потолок: учитель с 25 учениками проверяет класс ~4 раза в месяц |
| **Плюс** (1 500 ₽) | **500** | Задел на «два параллельных класса + повторные проверки» |
| **Школа** (3 000 ₽/класс) | **100 на класс** | Вне скоупа M1-M2, зафиксировано на будущее |

**Жёсткий предохранитель на всех тарифах: 1000 проверок/мес** — ровно потолок Обучай, плюс наш абсолютный технический максимум (защита от бесконечного цикла `retry`).

**Как считается:**
- окно — календарный месяц, сброс 1-го числа в 00:00 UTC;
- одна проверка = один принятый вызов vision-модели, **даже если качество плохое** (иначе будут гонять «пока не распознается»);
- лимит списывается **только после успешного вызова LLM** — при 5xx от polza квота не тратится (то же правило, что в `worksheets.ts:140`: если INSERT упал — счётчик не инкрементится);
- проверка ниже порога уверенности **тоже тарифицируется** — это честно: мы всё равно звали модель;
- анонимным пользователям (без сессии) фича **недоступна** — иначе ключ на IP обходится регистрацией.

### 7.3 Пороги отметки (предложение, ждёт В-6)

| % выполнения | Отметка |
|---|---|
| ≥ 85 | «5» |
| 70–84 | «4» |
| 50–69 | «3» |
| < 50 | «2» |

Пороги фиксируем в одном объекте в коде, не размазываем по компонентам. Если учитель не согласен с оценкой — поправить руками нельзя (в M1 это отдельная задача), но оценку всегда видно **вместе с баллом и процентом**, чтобы решение принимал человек, а не алгоритм.

| 2 | **LLM-транспорт**: `image_url` в `LLMMessage`, vision-модель в `MODEL_CATALOG`/`MODEL_COSTS`, `case "photo-check"` в роутере, переписать `polza.ts` под интерфейс `Provider`, починить `calcCost` | 2–3 |
| 3 | **Схема БД**: `photo_checks`, `photo_check_items`, `usage_counters`, `photoCheckId()`/`photoCheckItemId()` | 1 |
| 4 | **Бэкенд-эндпоинты**: POST (загрузка в R2 → LLM → парсинг → запись), GET по id, GET список, GET usage, DELETE | 2–3 |
| 5 | **Фронт**: переписать `PhotoCheckPanel`, `PhotoUpload`, `PhotoCheckResult`, `api.ts`, сжатие фото | 2–3 |
| 6 | **Юр. слой**: текст согласия на загрузке, retention, кнопка удаления | 1–2 |
| 7 | **Тесты + live-verify** | 2–3 |

### M2. «Класс за один раз» — 5–7 дней

Стопка до 10 фото → один отчёт по всем ученикам (таблица «ученик / балл / отметка / ⚠️»), одна печать на весь класс. Плюс ручная правка спорных заданий учителем.

### M3. «Дальше» — по итогам фидбека

Фото условия как эталон, чтение ФИО для разбора стопки, метрики качества распознавания (`photo_check_items.confidence` уже копятся — их можно смотреть в админке).

**Почему M1 первым:** это ровно то, что учитель попробует в первый вечер. Если он не дождётся отметки по одной тетради, стопка из десяти ему не поможет.

## 10. Оценка трудоёмкости

| Этап | Содержание | Человеко-дней |
|---|---|---|
| 0 | Разблокирование В-1 (модель, цена, живой тест) | **1–2** |
| 1 | LLM-транспорт: `image_url`, каталог моделей, роутер, `polza.ts` под интерфейс, `calcCost` | **2–3** |
| 2 | D1: 3 таблицы, ID-генераторы, квотный слой | **1** |
| 3 | Бэкенд-эндпоинты (5 роутов, R2, парсинг, логирование) | **2–3** |
| 4 | Фронт: панель, загрузка, результат, сжатие, печать | **2–3** |
| 5 | Юридический слой: согласие, retention, удаление (с учётом времени юриста на тексты) | **1–2** |
| 6 | Тесты (unit бэка + фронт), live-verify, отладка на реальных фото | **2–3** |
| | **M1 — итого** | **11–17** |
| | M2 (стопка + ручная правка) | 5–7 |
| | **M1 + M2 — итого** | **16–24** |

**Для планирования: закладывать ~3 недели на M1 и ~5–6 недель на M1+M2** (один разработчик, full-time, без учёта ожидания юриста и закупки vision-модели).

**Отдельно за пределами оценки:** работа юриста по В-2 (согласие, основание обработки, уведомление РКН) — календарно дольше, чем разработка, её надо запускать параллельно, а не после.

**Риск перерасхода:** В-1 может не закрыться технически (polza не умеет image-input). Тогда +3–5 дней на второй провайдер и переработку `provider`-слоя. Это главный риск скоупа.
