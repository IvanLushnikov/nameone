# TZ-19: Ручные отметки учителя после проверки по фото

> **Статус:** 🟢 Реализовано (2026-10-03). Журнал проверок сделан здесь же — открытый вопрос №1 закрыт.
> **Не в этой фиче:** синхронизация с внешним классным журналом (открытый вопрос №2) и модель «кто такой учитель» (№3).
> **Приоритет:** 🟠 P1
> **Связано:** `docs/tz/18-money-and-trust.md` блок В, §9 «Новые находки» · `docs/tz/11-photo-check.md`

**Что.** Учитель проверяет 25 тетрадей по фото, видит блок «Проверьте сами» с заданиями, которые модель прочитала неуверенно, и ставит свои отметки вручную. Сейчас эти отметки живут только до закрытия вкладки — сохранять их некуда.

**Почему это важно.** Проверка по фото — второй по частоте сценарий продукта (открывается дважды в день, а не раз в неделю). Если ручная доводка исчезает вместе с вкладкой, фича экономит учителю время только наполовину: он перепроверил сомнительные задания и должен начинать заново.

---

## 1. Что уже есть

- Ответ бэкенда по проверке: `backend/src/routes/f06.ts` — по каждому заданию приходят `confidence`, `verdict`, распознанный ответ, комментарий; итог `gradeMark`/`percentage` в таблице `photo_checks`.
- Эндпоинта **ручных правок нет** — это и есть дырка.
- Фронт уже умеет показать блок проверки и принимает ручные значения (`PhotoCheckPanel.tsx`), но никуда их не отправляет: `onResult` в конструкторе только шлёт аналитику (`src/app/constructor/page.tsx:1775-1780`).

## 2. Что сделать

| # | Что | Где |
|---|---|---|
| 1 | Эндпоинт приёма ручных отметок: `POST /api/assignments/photo-checks/:id/manual-marks`. Принимает `{ taskNumber, accepted: boolean, points?: number }[]`, пишет в таблицу | `backend/src/routes/f06.ts` |
| 2 | Хранение: отдельная таблица под ручные правки, с `updated_at` и `author` | `backend/src/db/schema.sql` |
| 3 | Пересчёт итога: как только учитель подтвердил сомнительные задания, итоговая отметка становится посчитанной **по объединённым данным** (уверенные из разбора + ручные), а не остаётся скрытой | `backend/src/services/photoCheckGrading.ts` |
| 4 | Отправка из панели: кнопка «Сохранить отметки» вместо нынешнего «остаются только на этом экране» | `src/components/f06/PhotoCheckPanel.tsx` |
| 5 | Повторное открытие проверки подтягивает сохранённые ручные отметки — иначе учитель теряет их при перерисовке | там же |

**Обязательно:** не потерять различие «модель не уверена» и «учитель проверил». Отметка учителя — это его решение, оно должно быть помечено как ручное при выгрузке и в будущем журнале.

## 3. Чего не делать

- Не писать ручные отметки в ту же строку, что и результат модели, без разделения: через месяц нельзя будет понять, где кончилась машина и начался человек.
- Не отправлять отметки молча при каждом чекбоксе — только по явной кнопке, иначе учитель уйдёт на середине с половиной правок и не поймёт, что сохранилось.

## 4. Критерии приёмки

- [x] Учитель проставил отметки в блоке «Проверьте сами», нажал «Сохранить» → после перезагрузки страницы отметки на месте
- [x] Итоговая отметка пересчитана и показана, а не скрыта
- [x] В выгрузке видно, какие отметки поставил учитель, а какие — модель
- [x] Тест: две ручные отметки → повторный GET возвращает их и пересчитанный итог

**Где смотреть:** `backend/src/services/photoCheckGrading.ts` (чистое слияние) · `backend/src/db/photoChecks.ts` (хранение) · `backend/src/db/journal.ts` и `backend/src/routes/journal.ts` (журнал) · `src/components/f06/ManualMarksEditor.tsx` (форма) · `src/app/journal/` (журнал и открытая проверка).

**Из решений, принятых при реализации:**
- Отдельные таблицы (`photo_check_manual_marks`, `journal_entries`), а НЕ колонки в существующих. Миграция здесь = повторный прогон `schema.sql`, а `ALTER TABLE ADD COLUMN` в SQLite не идемпотентен: новая колонка ломала бы повторный прогон, а обходной путь через `scripts/migrations/` заставлял бы помнить ручной шаг при каждом деплое. Новые таблицы применяются тем же `npm run db:migrate:prod`, без ручных шагов.
- `accepted: false` ⇒ ровно 0 баллов, даже если учитель прислал `points > 0`. «Не засчитано, но 2 балла» противоречит само себе и в журнале выглядело бы как ошибка.
- Балл без числа = полный балл задания, а не ноль: отсутствие числа означает «учитель не думал о балле», а не «ноль».
- Пока сомнительные задания не закрыты, `gradeMark` и `percentage` = `null`. Молчаливый ноль хуже, чем лишняя перепроверка: в журнале учителя это был бы «двойка», которой никто не ставил.
