## 1. Контекст и зачем

В кабинете учителя есть разбор «кто ошибается два раза подряд по теме». Он
считается по строке `skill_attempts.skill` — то есть по **свободному тексту,
который придумала модель**.

Живые метки показывают, что одна и та же навыковая тема распадается на
несколько строк. В листе по математике 5, «Проценты», два задания одного
упражнения получили метки «Нахождение одного процента» и «Нахождение процента
от числа». Для учителя это **одна и та же тема**, а в разборе — две строки с
разными процентами. То же самое бывает наоборот: метка названа не по навыку, а
по объекту — «Процент в задаче о книгах», «Процент в нескольких наборах». По
таким меткам разбор не отвечает на вопрос «какая тема просела».

Учитель смотрит на этот разбор и не понимает его. Хуже: он принимает решение
«подтянуть проценты» и видит, что по «процентам» в классе всё хорошо, а
проблема — в другом навыке.

### Что такое канонический ключ

```ts
/**
 * Устойчивый ключ навыка для группировки в разборе.
 *
 * Источники (по убыванию качества):
 *   1. навык из ПЛАНА листа — он уникален по построению (prompts/plan-gen.ts,
 *      правило 2: «Каждый навык уникален»);
 *   2. нормализованная метка от модели: нижний регистр, схлопнутые пробелы,
 *      без конечной пунктуации;
 *   3. раздел программы (`fgosRef`) — когда метки нет вовсе.
 *
 * Ключ НЕ показывается учителю: он для группировки. Учитель видит метку.
 */
export function skillKey(args: {
  skill?: string | null;
  planSkill?: string | null;
  fgosRef?: string | null;
}): string | null;
```

### Правила

1. **Ключ не показывается учителю.** Учитель видит метку; ключ — внутренний
   ключ группировки. Иначе в интерфейсе появится «процент в задаче о книгах
   (процент%в%задаче%о%книгах)».
2. **Ручная правка метки учителем пересчитывает ключ.** Учитель написал
   «Проценты» вместо «Процент в задаче о книгах» — ключ должен измениться,
   иначе правка не работает.
3. **Группировка — по ключу, название — по метке.** Если у двух строк ключ
   одинаковый, а метки разные — показывается одна строка с двумя названиями
   (или с самым частым).
4. **Старые строки перезаливаются** нормализованной меткой: они уже записаны,
   и для них другого источника нет.
5. **Пустая метка — это отсутствие метки.** Метка, стёртая учителем, не
   превращается в ключ из названия темы (это уже сделано в `respectBlank`).

## 4. Решения

**AD-1 · Ключ — отдельная колонка, а не перезапись `skill`.**
*Рационал:* `skill` — это то, что видит учитель и что он правит. Ключ —
внутреннее поле группировки. Смешивать их нельзя: правка учителя должна менять
ключ, но не должна ломать историю.

**AD-2 · Источники ключа — по убыванию качества: план → нормализованная
метка → раздел программы.**
*Рационал:* план даёт уникальные навыки по построению — это единственный
источник, который даёт настоящий канон. Нормализация метки — дешёвый
промежуточный вариант, который чинит самый частый случай (регистр, пробелы,
точка в конце). `fgosRef` — последний рубеж.

**AD-3 · Без плана задача всё равно полезна.**
Если план не включён (решение по TZ-38 не принято), ключ = нормализованная
метка + `fgosRef`. Это чинит часть проблемы: «Нахождение одного процента» и
«Нахождение процента от числа» всё равно разойдутся, но разные формулировки
одной строки (регистр, пробелы, точка) — сойдутся.
*Рационал:* задача не должна зависеть от нерешённого вопроса по плану.

**AD-4 · Группировка по ключу, а не по отображаемой метке.**
*Рационал:* иначе разбор продолжит показывать «процент в задаче о книгах» как
отдельную тему — ровно тот дефект, который чиним.

**AD-5 · Слияние «похожих, но разных» меток — не делаем.**
Эвристика слияния (синонимы, морфология) даёт ложные объединения, и это
искажает разбор.
*Рационал:* реестр прямо относит вариант «нормализация + слияние близких» к
рискованным. Канон даёт план, а не эвристика.

**AD-6 · Показываем в разборе, что тема «собрана» из нескольких названий.**
Учитель должен видеть, что «проценты» пришли от трёх разных формулировок
модели, — иначе он не поймёт, почему цифра скачет.
*Рационал:* тихо склеенная строка выглядит как ошибка, когда учитель
откроет отдельную попытку и увидит другое название.

## 5. Критерии приёмки

Функциональные:
- [ ] В `skill_attempts` появилась колонка `skill_key`; у новых попыток она заполнена.
- [ ] Две попытки с метками «Проценты» и «проценты.» получают **один** ключ и попадают в одну строку разбора.
- [ ] Учитель правит метку — ключ пересчитывается, и попытка уезжает в другую группу.
- [ ] Учитель стёр метку — ключ пустой, попытка в разбор не попадает (регрессия на `respectBlank`).
- [ ] Разбор группирует по `skill_key`, а название берёт из метки; при нескольких названиях в одной группе это видно.
- [ ] Старые строки перезалиты: `UPDATE skill_attempts SET skill_key = …` выполнен в миграции, и количество строк с ключом равно количеству строк с непустой меткой.

Регрессионные:
- [ ] Разбор «кто ошибается два раза подряд по теме» работает как раньше по числу строк и по суммам — если метки не менялись.
- [ ] Учительская правка метки в листе по-прежнему сохраняется и отображается.
- [ ] Запись попыток по фото и по QR не сломалась.
- [ ] `npm test --prefix backend` — зелёные.

Качественные:
- [ ] На живом наборе попыток (10+ строк с разными формулировками одного навыка) число строк разбора уменьшилось, а сумма процентов не изменилась.
- [ ] НОВЫЙ тест падает на старом коде: на старом коде колонки `skill_key` нет, группировка идёт по сырой строке. Результат прикладывается к отчёту.

## 6. Чего не делаем

- **Не сливаем похожие метки эвристикой.**
- **Не показываем ключ учителю.**
- **Не меняем приоритет источников метки** (модель → план → тема).
- **Не трогаем механику `respectBlank`** — она работает.
- **Не делаем разбор по разделам программы отдельной страницей** — это был бы
  продуктовый редизайн, а не починка ключа.

## 7. Риски

| Риск | Вероятность | Цена | Что делаем |
|---|---|---|---|
| Ключ не совпадёт с тем, что учитель ожидает увидеть | Средняя | Средняя | Ключ скрыт; название — метка; при нескольких названиях показываем все (AD-6) |
| Перезаливка старых строк склеит разные темы | Низкая | Средняя | Перезаливка = только нормализация (регистр/пробелы/точка) — это не может склеить разные темы |
| План листа не включат (TZ-38) — канона не будет | Средняя | Средняя | AD-3: задача даёт пользу и без плана |
| Учитель правит метку чаще, чем думали | Низкая | Низкая | Ключ пересчитывается при правке — это уже сделано в `routes/f08.ts` |

## 9. Что не удалось подтвердить

- **Сколько именно строк в `skill_attempts` на проде.** Снимок от 29.10.2026
  не отработал SQL-запросы; неизвестно даже, пуста ли разбор. Миграция
  перезаливает существующие строки, поэтому объём данных на оценку усилий не
  влияет, но на объём работы — да.
- **Как часто одна и та же тема называется по-разному в реальных классах.**
  Известны два примера из одного листа («Нахождение одного процента» /
  «Нахождение процента от числа»). Масштаб не измерен: нужен разбор базы.
- **Поможет ли `fgosRef` как последний рубеж.** Зависит от TZ-39: без него
  `fgosRef` в генератор не доходит и в ключ не попадает. Связь задач явная.
- **Не проверено, где именно на экране строится группировка разбора** — файл
  экрана определяется на шаге 3; в реестре указана схема таблицы, а не
  компонент.
