## 1. Контекст и зачем

Учитель покупает «Базовый» за 249 ₽ в месяц. В карточке тарифа написано: «Контрольная с критериями оценивания — расходует тариф быстрее, чем рабочий лист» (`src/lib/content/plans.ts:394`); в «Плюсе» — «Контрольная с критериями оценивания» (`src/lib/content/plans.ts:478`). Он готовит контрольную, скачивает файл, раздаёт классу, а потом вечером садится проверять работы — и обнаруживает, что **критериев оценивания в файле нет вообще**. Есть ключ с голыми ответами: «12», «3/4», «б)». По этой строке отметку не поставить: не сказано, что считается полным ответом, а что — половиной.

Живая проверка 29.10.2026 (один вызов, `bypassCache: true`): в ответе API слово «критери» встречается **0 раз**, поля `criteria` нет ни у одного из восьми заданий. Обещание тарифа не обеспечено.

Почему так вышло. Критерии можно было донести двумя способами, и они ломают друг друга:

1. **Промпт велит класть критерии в `answer`** — правило 17 (`backend/src/llm/prompts/worksheet-gen.ts:169-175`): «Для type = "essay" answer — это КРИТЕРИИ, по которым учитель принимает работу».
2. **Схема и печать ждут отдельного поля `criteria`** — `worksheet-gen.ts:199`, `backend/src/lib/zod.ts:96`, `src/lib/types.ts:168`, печать `src/lib/utils/docx.ts:636`.
3. **Фильтр выкидывает задание, у которого нет пригодного `answer`**, когда ответы обязательны — `backend/src/llm/validation/quality-filter.ts:482`. Задание с критериями в `answer` (то есть по правилу 17) проходит; задание с критериями в `criteria` и пустым `answer` — выкидывается, и его место занимает дозапрос обычного задания (`worksheet-gen.ts:463`).

Печать при этом сделана правильно: `criteriaForTask` (`docx.ts:636`) читает `task.criteria`, а строка «Критерий: …» печатается под ответом в ключе (`docx.ts:866`). Сломаны не данные печати — сломаны данные ответа.

**Вторая половина той же поломки — разнообразие.** ТЗ-33 сделал реестр и превратил правило в числа: `diversityLimits(4)` → `maxSameType = 2` (`src/lib/content/task-types.ts:443`), и числа подставляются в промпт дословно (`worksheet-gen.ts:361`, `:505`, `:593`). Но проверяет правило только модель. В живом ответе вариант 2 контрольной — `short-answer, computation, computation, computation`, то есть **три расчёта из четырёх при лимите «не больше 2 одного типа»**. В блоке `quality` ответа (`backend/src/llm/index.ts:303-346`) про распределение типов нет ни одного поля, `dropped = 0` — нарушение никто не заметил.

Учитель, который заказал два варианта «чтобы сравнить класс», во втором получает три почти одинаковых задания подряд.

**Что делаем:** критерии приезжают в том же ответе модели, что и лист (отдельный вызов запрещён — он удваивает цену контрольной); **баллы и шкалу отметок 5/4/3/2 считает код по явной формуле**, пороги 85/70/50/0 живут в одном месте; от модели — только типичные ошибки по теме и рекомендация учителю; в ответе API — отдельный ключ; в DOCX — отдельная страница «Критерии оценивания» после ключа; критерии работают и для контрольной, и для теста; **разнообразие проверяет код после генерации**.

**Чего не делаем в этом ТЗ:** не трогаем нормы, тарифы и подпись «до 1 500 листов» (это ТЗ-35, и оно идёт ПОСЛЕ этого ТЗ — цена контрольной меняется здесь); не трогаем презентации (Н-5); не строим «конструктор критериев», о котором упоминает `plans.ts:477`; **не трогаем звёзды интерактивов** (`src/lib/interactives/scoring.ts:58`) — это другая шкала оценивания, смешивать её с отметками 5/4/3/2 нельзя.

## 3. Технический дизайн

### 3.1. Формат ответа модели

Один вызов, одна правка промпта. В JSON ответа модели у каждой работы появляется объект `evaluation`:

```jsonc
{
  "title": "...",
  "tasks": [ /* как сейчас */ ],
  "evaluation": {
    // Критерии приёмки ПО ЗАДАНИЯМ. Номера — номера заданий в этой работе.
    "criteria": [
      { "number": 3, "criteria": ["Называет определение и приводит пример", "Связывает с понятием из урока"] }
    ],
    // ТИПИЧНЫЕ ОШИБКИ ПО ТЕМЕ — конкретные, не «бывают ошибки».
    "typicalMistakes": [
      "Путает числитель и знаменатель при сокращении дроби",
      "Приводит неправильную обыкновенную дробь вместо смешанного числа"
    ],
    // РЕКОМЕНДАЦИЯ УЧИТЕЛЮ — что делать с классом.
    "recommendation": "Разобрать на доске перевод смешанного числа в неправильную дробь: в этом классе ошибка в 4 из 8 работ."
  }
}
```

Для контрольной объект `evaluation` лежит **внутри каждого варианта** (вариантов два — критерии у них разные, задания разные):

```jsonc
{
  "variants": [
    { "title": "Вариант 1", "tasks": [ /* … */ ], "evaluation": { /* … */ } },
    { "title": "Вариант 2", "tasks": [ /* … */ ], "evaluation": { /* … */ } }
  ]
}
```

**Что модель НЕ присылает:** веса заданий, пороги отметок, слово «5» как отметку, проценты. Это считает код.

### 3.2. Что считает код: веса и шкала отметок

Новый файл `src/lib/content/grading.ts` — **единственное место**, где живут пороги и формула.

```ts
/** Пороги отметок. Один источник истины: и API, и печать, и тесты. */
export const MARK_THRESHOLDS: readonly { mark: 5 | 4 | 3 | 2; minPercent: number }[] = [
  { mark: 5, minPercent: 85 },
  { mark: 4, minPercent: 70 },
  { mark: 3, minPercent: 50 },
  { mark: 2, minPercent: 0 },
];

/** Отметка по проценту выполнения. Процент вне [0..100] → 2 (нижняя отметка). */
export function markForPercent(percent: number): 5 | 4 | 3 | 2;

/** Полная шкала в процентах — для печати и для API. */
export function marksScale(): { mark: number; fromPercent: number; toPercent: number }[];
```

**Веса заданий** — не от модели, а из реестра: в `src/lib/content/task-types.ts` у `TaskTypeSpec` появляется поле

```ts
/** Максимальный балл за задание этого типа. Считает код, модель вес не присылает. */
weight: number;
```

Значения по типам (основание — трудоёмкость ответа учителя, а не «сколько баллов в школьной системе»):

| answerKind | weight | комментарий |
|---|---|---|
| `exact` (расчёт, вставь в пропуск, по образцу, по таблице) | 2 | есть однозначное число, проверить можно |
| `choice` (выбор из вариантов, несколько вариантов) | 1 | угадал — один балл |
| `text` (краткий ответ, найди ошибку, сравни) | 2 | короткий развёрнутый ответ |
| `criteria` (эссе, открытый ответ, практическая работа, работа с источником) | 3 | оценивается по критериям, это главный вес работы |
| `order` (соответствие, порядок, классификация) | 2 | |

Вес — это `weight` из реестра, то есть **новый тип задания получает вес автоматически**, а не через «ещё одно жёсткое правило». Поле `points`, которое сейчас присылает модель (`worksheet-gen.ts:202`, `"points": <1|2|3>`), в новой схеме **игнорируется**, а в ответе учителю и в API отдаётся кодовый `maxPoints = weight` из реестра. Старые `points` в сохранённых листах не трогаем (см. §6).

Формула отметки (одна на весь продукт):

```
процент выполнения = сумма баллов за верно выполненные задания / сумма maxPoints × 100
отметка = первый порог, у которого процент ≥ minPercent
```

Порядок порогов — от высшей отметки к низшей (`5 → 4 → 3 → 2`), поэтому «отметка = f(процент)» однозначна. `minPercent: 0` у отметки 2 означает «всё, что ниже 50 %».

**Проверять это должна модель?** Нет. Оценку по фото (`backend/src/llm/prompts/form-grading.ts`, `src/lib/interactives/scoring.ts`) **не трогаем**: там своя шкала, там звёзды. Отметка 5/4/3/2 — только для контрольной и теста, и считает её код.

### 3.3. Контракт ответа API

В ответе `POST /api/worksheets/generate` появляется **отдельный ключ** `evaluation` — рядом с `worksheet`, `secondVariant`, `quality`, `variants`, `meta`, `usage` (`backend/src/routes/worksheets.ts:263-269`). Он не внутри текста задания и не внутри `answer`.

Значение — **массив по работам**: один элемент для листа и теста, два для контрольной (по вариантам).

```jsonc
{
  "ok": true,
  "worksheet": { "tasks": [ /* … */ ] },
  "evaluation": [
    {
      "variant": 1,
      "title": "Вариант 1",
      // Критерии по заданиям + кодовый максимальный балл.
      "criteria": [
        { "number": 3, "criteria": ["Называет определение и приводит пример"], "maxPoints": 3 }
      ],
      // Из модели.
      "typicalMistakes": ["Путает числитель и знаменатель при сокращении"],
      "recommendation": "Разобрать перевод в неправильную дробь на доске.",
      // Из кода.
      "totalMaxPoints": 12,
      "marks": [
        { "mark": 5, "fromPercent": 85, "toPercent": 100 },
        { "mark": 4, "fromPercent": 70, "toPercent": 84 },
        { "mark": 3, "fromPercent": 50, "toPercent": 69 },
        { "mark": 2, "fromPercent": 0, "toPercent": 49 }
      ]
    }
  ],
  "quality": { /* … */ },
  "meta": { /* … */ },
  "usage": { /* … */ }
}
```

**Откуда берётся `criteria` в этом ключе.** Модель присылает критерии **внутри задания** — в уже существующем поле `task.criteria` (`worksheet-gen.ts:199`, `backend/src/lib/zod.ts:96`). Бэк **не** заводит второе место для одних и тех же критериев: он **собирает** `evaluation[].criteria` из `tasks[].criteria` и добавляет кодовый `maxPoints`. Поэтому разойтись они не могут: API-ключ — производная, а не второй источник правды.

**Правило «пустые и общие формулировки отбрасываются»** (решение владельца). Проверка конкретности — в бэке, рядом с фильтром:

- критерий отбрасывается, если он короче 15 символов после обрезки;
- критерий отбрасывается, если он совпадает со стоп-листом общих формулировок: «ответ неполный», «ответ неверный», «бывают ошибки», «работа выполнена», «правильно», «развёрнутый ответ», «своими словами», «надо знать тему» и т. п.;
- если после отбрасывания у задания не осталось ни одного критерия — задание не попадает в `evaluation[].criteria` (в печати у него будет пустая строка критериев — как сейчас у листов без критериев);
- типичные ошибки и рекомендация проверяются так же: непустая строка, не совпадает со стоп-листом, длина ≥ 15 символов. Не прошли — поле остаётся пустым массивом / `null`, и на странице не печатается.

Стоп-лист — это **данные** (массив в одном файле), а не ветки в коде: его можно пополнять, не трогая логику.

### 3.5. Проверка разнообразия после генерации (Н-2)

Правило ТЗ-33 живёт в промпте. Теперь оно же проверяется кодом.

1. **Считаем гистограмму** типов по финальному списку заданий работы: `{ computation: 3, short-answer: 1 }`.
2. **Сравниваем** с `diversityLimits(count)` (`src/lib/content/task-types.ts:443`): `maxSameType`, `minOtherTypes`, `minTypes`. Проверка идёт по **каждому варианту отдельно** (у варианта 4 задания, у листа — 4) и по **всей работе суммой** (8 заданий контрольной — это 8, а не 4).
3. **Если нарушено** — берём задание самого частого типа и заменяем его: модель получает точечный запрос «задание №N — тип computation, замени на другой тип из списка, вот какие типы разрешены и вот какой лимит». Это тот же механизм, что уже есть для дублей по навыку (`backend/src/llm/index.ts:982-1100`, `dedupeSheet`), только вместо «тот же навык» — «тот же тип».
4. **Лимит попыток замены** — 2 на работу (как сейчас у дублей: `dedupeRounds = 1`, `index.ts:1135`). Если не помогло — **лист отдаётся как есть**, но в `quality` появляется поле `typeDiversityViolations` со списком нарушений (`{type, actual, limit}`), и это видно в логах и в интерфейсе.
5. **В `quality` добавляется** `typeDiversityViolations: {type, actual, limit}[]` — чтобы нарушение нельзя было скрыть (сегодня в `quality` про типы нет ни одного поля, `index.ts:297-346`).

Проверка **декларативная**: лимиты берутся из `diversityLimits`, а не пишутся заново в валидаторе. Новый тип задания в реестре не требует правок здесь.

### 3.6. Что происходит с критериями в контрольной

- Критерии есть **у каждой работы**, где есть хотя бы одно задание с `answerKind: "criteria"` — то есть у контрольной и теста по правилу «хотя бы одно задание с критериями».
- Если модель не дала ни одного критерия — **дозапрос**: модель получает запрос на критерии к конкретным заданиям (номера и текст). Если и после дозапроса критериев нет — работа отдаётся без блока критериев, а в `quality` появляется `criteriaMissing: true`, и на странице печати пишется честная строка «критерии не удалось сформировать — оценивайте по ключу». Пустая страница «Критерии оценивания» без объяснения — это та же ложь, что мы чиним.
- Задание с `answerKind: "criteria"`, но без `answer`, **не выкидывается** фильтром (см. §3.4): критерий приёмки и есть ключ к такому заданию.

## 4. Решения (AD-N)

**AD-1 · Критерии едут в том же вызове, что и лист.**
*Рационал:* решение владельца от 29.10.2026 — отдельный вызов удваивает цену контрольной (сейчас она и так съедает ~89 листов нормы, см. `plans.ts:392` и ТЗ-35). Второй вызов = второе ожидание учителя = вторая точка отказа. В один вызов помещается всё: модель уже пишет ключ, пусть напишет и критерии по тем же заданиям. Цена: ответ длиннее → риск обрыва по `finish_reason=length`. Поэтому потолок ответа для `control`/`test` (сейчас 8192/4096, `backend/src/llm/index.ts:507`) **поднимается**, а обрыв обрабатывается существующим ретраем с удвоенным потолком (`index.ts:641`).

**AD-2 · Баллы и пороги отметок считает код; модель присылает только типичные ошибки и рекомендацию.**
*Рационал:* шкала 5/4/3/2 — это не мнение модели, а правило, которое должно быть одинаковым у всех контрольных и всех тестов. Если пороги приходят от модели, то у одного учителя будет «5 за 80 %», у другого «5 за 90 %», и через месяц учитель перестанет доверять отметке. Модели оставляем ровно то, где её сила: предметные типичные ошибки и методическая рекомендация — то, что человек написать не сможет.

**AD-3 · Веса заданий лежат в реестре типов, а не приходят от модели.**
*Рационал:* правило владельца — «правила добавляются декларативно». Вес — свойство ФОРМЫ задания, а не конкретного задания; форма уже описана в реестре (`task-types.ts:56`). Новое `weight` в `TaskTypeSpec` автоматически обслуживает печать, API и расчёт `totalMaxPoints`. Модельное поле `points` перестаёт быть источником правды: иначе два разных числа о балле задания в одном файле.

**AD-4 · Один носитель критериев — `task.criteria`; `evaluation` в ответе API — производная.**
*Рационал:* исходная поломка была ровно в том, что критерии жили в двух местах (`answer` и `criteria`) и эти места ломали друг друга. Второе место — та же ошибка. Поэтому модель пишет критерии только в `task.criteria` (поле уже есть в схеме, печать его уже читает), а бэк **собирает** из них отдельный ключ `evaluation` в ответе API. Ключ нужен фронту, чтобы нарисовать страницу, не обходя задания; расходиться они не могут, потому что API-ключ вычисляется из заданий, а не приходит вторым ответом модели.

**AD-5 · Задание с `answerKind: "criteria"` и пустым `answer` не выкидывается.**
*Рационал:* для эссе, открытого ответа, практической работы и работы с источником критерий приёмки и ЕСТЬ ключ — эталонного текста там не существует в принципе. Старое правило (`quality-filter.ts:482`) выкидывало такое задание и ставило на его место обычное расчётное — учитель получал контрольную, где не было ни одного развёрнутого задания. Теперь правило выводится из `answerKind` в реестре: «нужен ответ» = «нужен `answer` ИЛИ, для типа с `answerKind: "criteria"`, непустые конкретные критерии».

**AD-6 · Разнообразие проверяется кодом после генерации, заменой задания, а не только просьбой в промпте.**
*Рационал:* ТЗ-33 сделал правило, но оставил его на честном слове модели — и модель его нарушила в живом ответе. Проверка после генерации — единственный способ дать гарантию. Замена задания (а не выкидывание) выбрана потому, что выкинутое задание уменьшает объём работы, а учитель заказал конкретное число. Лимит попыток (2) и «отдать как есть, но показать нарушение в `quality`» — по той же причине, что и в фильтре качества: лучше честный однообразный вариант с пометкой, чем пустой лист.

**AD-7 · Критерии — для контрольной и теста, но не для обычного рабочего листа.**
*Рационал:* рабочий лист учителю не оценивает, он его раздаёт. Критерии в листе увеличили бы объём ответа модели (цена) и объём печати (файл) без пользы. Контрольная и тест — ровно те, где учитель ставит отметки.

**AD-8 · Звёзды интерактивов не трогаем.**
*Рационал:* в продукте есть вторая шкала оценивания — звёзды за интерактивы (`src/lib/interactives/scoring.ts:58`, пороги 80/50 зафиксированы в самом файле). Это другая сущность с другой ценой и другой валютой; смешивание шкал в одном ответе API запутает и учителя, и будущих разработчиков. Отметки 5/4/3/2 живут только в `grading.ts`.

## 6. Чего не делаем

- **Не строим «конструктор критериев»**, который упоминается в `plans.ts:477`. Это отдельная фича «Плюса» с отдельным интерфейсом; здесь — только то, что приезжает с генерацией.
- **Не трогаем нормы, тарифы и подпись «до 1 500 листов».** Это ТЗ-35, и оно выполняется ПОСЛЕ этого ТЗ: цена контрольной меняется здесь (длиннее ответ → больше выходных токенов → больше взвешенных токенов), и пересчитывать норму надо по фактическому новому расходу.
- **Не трогаем шкалу звёзд интерактивов** (`src/lib/interactives/scoring.ts`) и оценку по фото (`backend/src/llm/prompts/form-grading.ts`). Другая шкала, другие пороги, другая цена.
- **Не меняем формулу взвешивания токенов** (`backend/src/services/usage.ts:15`) и не трогаем `TOKENS_PER_WORKSHEET` (`src/lib/content/plans.ts:136`). Это ТЗ-35.
- **Не убираем строку «Критерий: …» из ключа** (`docx.ts:866`). Она работает и полезна; новая страница её не заменяет, а дополняет.
- **Не переписываем печать листа целиком.** Правка — одна новая секция после блока `withAnswers`.
- **Не меняем реестр типов, кроме добавления поля `weight`.** Лимиты разнообразия (`task-types.ts:443`), блок промпта (`:370`) и проверка соответствия типу (`quality-filter.ts:287`) — трогать нельзя, это сделано правильно.
- **Не просим модель присылать отметки, проценты и веса.** Модель присылает критерии по заданиям, типичные ошибки и рекомендацию — и всё.
- **Не перенумеровываем задания** при замене (учитель сверяет по номерам со своим планом урока — это уже зафиксировано в `quality-filter.ts`).
- **Не храним критерии в базе отдельной таблицей.** Они лежат в `worksheets.payload_json` вместе с заданием — так уже сделано для `criteria` (`src/lib/types.ts:168`), миграция не нужна.
- **Не показываем критерии ученику.** Критерий приёмки нужен учителю; напечатанный на листе, он превращается в подсказку. Это уже зафиксировано в `docx.ts:505-512` — здесь мы это правило соблюдаем, а не меняем.
