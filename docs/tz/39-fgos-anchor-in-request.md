## 1. Контекст и зачем

В репозитории собрана и проверена таксономия ФГОС: 5 658 тем по 141 паре
«предмет × класс», покрытие полное (`node scripts/fgos/verify-reference.mjs
--coverage` → «пар в таксономии: 141, из них с эталоном: 117»,
`build-completion-plan.mjs --write` → «НАДО ДОБАВИТЬ: 0»). У каждой темы есть
`fgosRef` — человекочитаемое название раздела программы — и `examples`:
примеры заданий с ответами, которые уже показываются учителю в интерфейсе.

**Ни одна из этих 5 658 тем не доходит до модели в виде содержания.** В
контракте запроса (`backend/src/types.ts:73-84`) есть только `topic` — строка.
Модель получает название темы и дальше придумывает навыки сама.

Что это значит на практике: качество заданий держится на знаниях модели о
школьной программе, а не на программе, которую продукт собрал и проверил.
Ошибки «не выше своего класса» ловятся постфактум (правило 13 промпта,
эвристики фильтра), а не по данным.

Именно этой нехваткой объясняется, почему модели приходится придумывать
навыки: у неё нет списка подтем, из которых можно выбирать.

### Контракты

```ts
// backend/src/types.ts
export interface GenerationRequestMeta {
  umk?: string | null;
  /** Раздел программы по теме (человекочитаемый, из таксономии ФГОС). */
  fgosRef?: string | null;
  /** ОДИН пример формулировки из этой темы — якорь стиля, не шаблон. */
  fgosExample?: { text: string; answer?: string } | null;
}
```

```ts
// backend/src/llm/prompts/fgos-block.ts
export function buildFgosBlock(meta: GenerationRequestMeta | null | undefined): string;
```

Текст блока (предложение — на утверждение владельцу):

```
ОРИЕНТИР ПО ПРОГРАММЕ. Раздел: «<fgosRef>».
Пример формулировки из этого раздела: «<fgosExample.text>».
Задания должны проверять навыки ИЗ ЭТОГО РАЗДЕЛА. Пример показывает стиль
формулировки и ничего копировать не надо: текст примера не повторяется и не
переписывается дословно.
```

### Правила

1. **Якорь — один пример, не два.** Два примера сужают формулировки сильнее.
2. **Пример — это стиль, а не шаблон.** В промпте это сказано прямо, и это же
   проверяется кодом (см. критерии).
3. **Тема, введённая учителем руками, якоря не получает.** У неё нет раздела
   программы — и выдумывать нечего. Поведение такое же, как сегодня.
4. **Якорь идёт в user-промпт, а не в system.** System-промпт не меняется →
   prompt cache «Плюса» не сбрасывается.
5. **Ключ кэша включает `fgosRef`.** Иначе лист, собранный с якорем, будет
   отдаваться как «тот же запрос» тому, кто якоря не выбирал, и наоборот.
   Механика ровно та же, что с `umk` (`index.ts:392-395`).

## 4. Решения

**AD-1 · Один пример, а не два.**
*Рационал:* два примера превращаются в шаблон — модель начинает повторять их
конструкции, а это ровно тот дефект, который мы чиним (Q-01).

**AD-2 · Якорь в user-промпте.**
*Рационал:* system-промпт листа — 12 641 символ, и любая правка сбрасывает
prompt cache у тарифа «Плюс» (шапка `worksheet-gen.ts:26-63`). Якорь зависит от
темы, а не от правил, — значит, ему место в user-части.

**AD-3 · Только лист. Не все шесть типов.**
*Рационал:* типы материалов используют разные промпты; подключение ко всем —
это отдельная работа и отдельные тесты. Лист — то, где разнообразие болит
сильнее всего.

**AD-4 · Ключ кэша включает `fgosRef`.**
*Рационал:* прецедент `umk` уже есть в коде и уже работает. Нарушение этого
правила — «поставил галочку — никакой разницы», а это ровно тот класс дефектов,
которым посвящён этот заход.

**AD-5 · Код проверяет, что пример не скопирован.**
*Рационал:* правило в промпте — просьба. Если модель скопирует пример в
задание, учитель получит лист с заданием, которое уже видел на странице темы.
Проверка — сравнение нормализованного текста задания с нормализованным
текстом примера.

**AD-6 · Таксономию не трогаем.**
*Рационал:* покрытие полное, добавлять нечего (`build-completion-plan.mjs` →
«НАДО ДОБАВИТЬ: 0»). Работа — connect, а не сбор.

## 5. Критерии приёмки

Функциональные:
- [ ] Запрос, отправленный из конструктора при выборе темы из каталога, содержит `meta.fgosRef` и `meta.fgosExample` (тест на перехваченном теле запроса).
- [ ] Запрос при теме, введённой руками, НЕ содержит `meta.fgosRef` и ведёт себя как раньше.
- [ ] В user-промпте листа при наличии `fgosRef` есть блок-якорь; при отсутствии — блока нет (юнит-тест на `buildFgosBlock` и на `buildWorksheetPrompt`).
- [ ] Ни одно задание в листе не повторяет текст примера дословно: сравнение нормализованных текстов заданий и примера (тест на живом ответе или на синтетическом).
- [ ] Два запроса с одной темой, но разным `fgosRef`, дают **разные** ключи кэша (тест на `makeCacheKey`).

Регрессионные:
- [ ] Лист без якоря генерируется ровно как раньше: тот же промпт (побайтно в user-части), тот же ключ кэша для запроса без `fgosRef`.
- [ ] Учебник (УМК) продолжает работать: блок УМК и блок якоря не конфликтуют, оба попадают в промпт.
- [ ] Существующие тесты промптов (`backend/tests/unit/**prompt**`) — зелёные; новая правка в user-части не ломает хэш prompt cache (см. риск ниже).

Качественные:
- [ ] Замер: 10 листов с якорем и 10 без, на одних темах. Метрики — число разных конструкций, число разных навыков, доля заданий, чей навык соответствует разделу (по совпадению с `fgosRef` в метке или по ручной выборке из 20 заданий).
- [ ] НОВЫЙ тест падает на старом коде: `meta.fgosRef` в теле запроса на старом коде отсутствует. Результат прикладывается к отчёту.

## 6. Чего не делаем

- **Не передаём текст раздела программы целиком.** Он длинный, и это лишние
  токены на каждый вызов. Передаём название раздела и один пример.
- **Не подключаем якорь к остальным пяти типам материалов.** Это отдельная
  задача; здесь — только лист.
- **Не переписываем таксономию и не запускаем сборщики заново.** Данные есть и
  проверены; используем `getTopic` на фронте.
- **Не меняем system-промпт листа.** Значит, prompt cache «Плюса» не сбрасывается.
- **Не делаем якорь обязательным.** Нет якоря — обычная генерация.
- **Не дублируем якорь в кэш-ответ** — только в ключ.

## 7. Риски

| Риск | Вероятность | Цена | Что делаем |
|---|---|---|---|
| Пример сузит разнообразие: модель начнёт повторять его конструкцию | Средняя | Средняя | В промпте сказано прямо, что пример — стиль; код проверяет отсутствие дословного копирования; замер с якорем и без |
| Якорь сместит задания к «скучной» части раздела | Низкая | Низкая | Якорь один, а не список подтем; метрика замера — разные навыки |
| Рост входных токенов на каждый вызов | Низкая | Низкая — пример и название раздела — это десятки токенов | Вход не тарифицируется (это отдельная проблема, M-03) |
| Кэш начнёт отдавать лист, собранный с другим якорем | Низкая | Средняя | `fgosRef` в ключе кэша — тест |
| Входные токены начнут учитываться в норме раньше времени (M-03) — якорь станет дороже | Средняя | Низкая | Следить за порядком: TZ-44 меняет формулу нормы, TZ-39 — до неё |

## 9. Что не удалось подтвердить

- **Даст ли якорь прирост разнообразия.** Не измерено: ни один живой лист в
  истории не собирался с якорем. Замер — обязательный шаг 5.
- **Покрытие `fgosRef` по всем 5 658 темам.** У 4 программ эталон не собран
  (`social ooo/151`, `obzh ooo/164`, `obzh soo/128`, `technology ooo/162`), у
  одной нет источника (`finance`), у 11 разделов нет в программе. Для этих тем
  якорь будет пустым — генерация работает как сегодня. Сколько именно тем без
  `fgosRef` — по данным `verify-reference.mjs` (117 из 141 пар покрыты, но
  потема счёт не снимался).
- **Не измерено, сколько примеров у каждой темы.** У части тем их два-три,
  у части нет ни одного. Якорь берёт первый.
- **Не проверено, что `getTopic` находит тему по всем путям входа** (каталог,
  восстановление из URL, восстановление из истории). Шаг 3 это проверяет.
