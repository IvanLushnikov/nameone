# ТЗ-23: Пароль для учителя — вход без письма

**Дата:** 12 октября 2026
**Решение владельца:** делаем обычный пароль, не PIN. PIN отклонён: перебирается
быстрее, а учителю нужна привычная форма входа.
**Продолжение:** `docs/tz/21-lk-improvements.md` (блок 5 — профиль и устройства).
Пароль живёт в том же месте интерфейса.

---

## 1. Зачем это учителю

Четыре ситуации, где письмо не спасает:

1. **Компьютер в учительской общий.** Учитель вошёл под своей почтой, сессия живёт
   30 дней (`backend/src/services/auth.ts:26`) — после него в кабинете с историей
   работ детей остаётся тот, кто сидел за столом следующим. Это не неудобство, это
   доступ постороннего к персональным данным.
2. **Урок через пять минут, письмо не пришло.** Письмо ушло в корпоративную почту,
   съело фильтр, попало в спам — учитель не понимает почему и не успевает разобраться.
3. **Новое устройство.** Новый ноутбук, новый телефон, а почта доступна не везде.
4. **Ребёнок или родитель** просит «войди в мой кабинет, покажи оценки».

Пароль снимает все четыре. Вход по ссылке из письма при этом остаётся — он нужен
там, где учитель впервые знакомится с сервисом, и там, где он забыл пароль.

## 3. Четыре разрыва

**Разрыв 1. Пароля нет нигде.** В таблице `users` (`backend/src/db/schema.sql:14`)
есть почта, имя, тариф — поля пароля нет. На бэкенде четыре ручки, все про письмо
(`backend/src/routes/auth.ts:6`). Это не «спрятали» — механики нет.

**Разрыв 2. Экран устройств не защищает от главной ситуации.** `SessionsSection`
умеет завершать чужие сессии, но войти по-прежнему можно только через письмо. Если
учитель ушёл с компьютера, не выйдя из кабинета, следующий человек видит его
историю — и остановить это можно только выходом, которого не было.

**Разрыв 3. Тексты говорят учителю «пароля нет».** Девять мест, где это написано
прямым текстом (список в разделе 8). После фичи они становятся неправдой.

**Разрыв 4. Форма входа не знает, задан ли пароль.** Чтобы показать учителю нужное
поле, фронт должен спросить у бэка «у этого email есть пароль?». Такой вопрос
превращает форму входа в способ проверить, зарегистрирован ли конкретный адрес —
ровно то, чего вход по ссылке принципиально не делает
(`backend/src/services/auth.ts:93-95`).

## 4. Решение 1. Пароль включается по желанию, вход по ссылке не ломается

Учитель один раз вошёл по ссылке, зашёл в настройки и задал пароль. Дальше может
входить по паролю. Не задал — всё работает как сегодня, ничего не сломалось и никого
не выкинуло.

Почему не заменяем ссылку паролем: ссылка работает, ею пользуются, ломать её перед
декабрём незачем. Пароль — дополнение, а не замена.

**Миграция базы:**

Пароль хранится **в отдельной таблице**, а не колонкой в `users`. Это конвенция
проекта, а не вкусовое решение: миграция здесь — повторный прогон всего `schema.sql`
(`npm run db:migrate:local`), а `ALTER TABLE ADD COLUMN` в SQLite не идемпотентен —
второй прогон упал бы с ошибкой. Ровно по этой причине роль и счётчик квоты вынесены
в `user_roles` и `usage_counters` (`backend/src/db/schema.sql:32-34`).

```sql
CREATE TABLE IF NOT EXISTS user_passwords (
  user_id    TEXT PRIMARY KEY REFERENCES users(id) ON DELETE CASCADE,
  hash       TEXT NOT NULL,      -- base64, PBKDF2-HMAC-SHA256
  salt       TEXT NOT NULL,      -- base64, 16 случайных байт на пользователя
  iterations INTEGER NOT NULL,   -- сколько итераций посчитано ЭТИМ хешем
  created_at INTEGER NOT NULL,
  updated_at INTEGER NOT NULL
);
```

`user_id` вместо `id` — тот же приём, что в `user_roles`: у пользователя максимум один
пароль, отдельный идентификатор ему не нужен.

Колонка `iterations` обязательна. Если завтра число итераций поднимут, старые хеши
останутся посчитанными по старому правилу — и проверка должна знать своё число, а не
брать константу из кода. Без этой колонки поднятие итераций молча заставит всех
существующих учителей потерять пароль.

Отдельная таблица даёт ещё одно: `ON DELETE CASCADE` при удалении пользователя уносит
пароль автоматически, отдельно чистить не нужно.

## 5. Решение 2. Пароль задаётся в настройках, рядом с устройствами

Отдельная карточка «Вход по паролю» в `src/app/dashboard/settings/page.tsx`,
между `ProfileSection` и `SessionsSection`. Место выбрано по смыслу: учитель пришёл
за «закрыть доступ на чужом компьютере» — он идёт в «Устройства», и пароль должен
быть там же, а не в отдельном разделе «Безопасность».

Три состояния карточки:

| Состояние | Что показываем |
|---|---|
| Пароля нет | «Придумать пароль» — два поля, кнопка |
| Пароль задан | «Пароль задан <дата>» — кнопка «Изменить» и «Убрать пароль» |
| Кабинет без аккаунта (`source === "device"`) | «Пароль появится, когда вы войдёте по почте» + ссылка на `/login` |

Третье состояние обязательно: `TeacherProfileView.source` бывает `"device"` —
данные лежат только в браузере, аккаунта на сервере нет (`src/lib/lk/profile-api.ts:69`).
Пароль без аккаунта задать нельзя, и карточка должна это честно объяснять, а не
показывать форму, которая не сохранится.

При смене пароля требуем старый. Без старого пароля любой, кто открыл вкладку на
чужом компьютере, сменил бы пароль и остался внутри.

## 6. Решение 3. Форма входа: два пути рядом, без предзапроса

На `/login` под основной формой — переключатель из двух пунктов:

- **Получить ссылку на почту** — нынешнее поведение без изменений
- **Войти по паролю** — раскрывает поле пароля под полем почты

Предзапроса «есть ли пароль у этого адреса» не делаем — см. разрыв 4. Правило
жёсткое: если фронт спрашивает про конкретный email до входа, он раскрывает
существование аккаунта, и вся анти-нумерационная политика входа идёт насмарку.

Правило входа по паролю:

1. Валидируем пароль по правилам ниже.
2. Ищем пользователя. Не нашли или пароль не подошёл — **один и тот же ответ**:
   «Не получилось войти. Проверьте почту и пароль». Разные тексты на «нет
   аккаунта» и «неверный пароль» — та же утечка, что и в разделе 3.
3. Пароль сходится — создаём сессию ровно как сейчас: `sessionToken()` →
   `createSession()` → HttpOnly cookie на 30 дней
   (`backend/src/routes/auth.ts:69`). Код сессии не трогаем, он общий с входом по ссылке.

Путь «забыл пароль» не новый: учитель возвращается на «Получить ссылку на почту» и
получает письмо как обычно.

## 7. Безопасность — то, что нельзя упростить

### 7.1. Правила пароля

- Минимум 8 символов, максимум 128.
- Обязательно: буква и цифра. Спецсимволы не требуем — учитель на телефоне с
  русской раскладкой; `!@#$` набирается мучительно, и из-за требования спецсимвола
  люди ставят пароль на копипасте откуда угодно.
- Не проверяем «словарные» пароли и не показываем шкалу надёжности. Оценка
  надёжности для учителя — лишний экран с ответом, который он всё равно проигнорирует.
- Свою же почту паролем разрешаем: человек забывает такой пароль, и это создаёт
  лишний шаг восстановления вместо входа.

### 7.2. Хранение

PBKDF2-HMAC-SHA256 через WebCrypto (`crypto.subtle.deriveBits`) — в Workers нет
нативного bcrypt/argon2, а тянуть WASM-модуль ради одной строки дороже.

- Соль 16 случайных байт на пользователя, хранится рядом с хешем.
- Итерации — по актуальной рекомендации OWASP для PBKDF2-HMAC-SHA256. Конкретное
  число подбирается на этапе реализации замером: **проверить, что Workers успевает
  посчитать хеш в рамках своего CPU-лимита.** При тарифе, где не успевает, снижаем
  итерации и фиксируем решение в коде константой с комментарием. Молча упасть на
  10-мс лимите нельзя — тогда вход по паролю не будет работать вообще, а это
  обнаружится на живом учителе.
- Открытый пароль не хранится, не логируется и не возвращается в ответах ни при
  каких ошибках.

### 7.3. Ограничение попыток

- 5 неудачных попыток на **email** в окне 15 минут.
- Ключ ограничения — по нормализованному email, а не по IP. `rateLimitMiddleware`
  это умеет через `keyFn` (`backend/src/middleware/ratelimit.ts:29`). По IP нельзя:
  вся школа сидит на одном Wi-Fi, и пять попыток одного учителя заблокируют вход
  тридцати другим на уроке.

### 7.4. Письмо со ссылкой при уже установленном пароле

Ссылка продолжает работать всегда — учитель может быть без доступа к почте, ради
такого случая пароль и делается. Но в письмо добавляем одну строку: «Вы вошли без
пароля. Если это были не вы — смените пароль в настройках». Текст в
`backend/src/services/email.ts:112-137`.

Отдельно про строку 148 в политике: сейчас там «Пароли не хранятся — используется
одноразовая ссылка для входа». После фичи это неправда. Заменяем на «хранится
только зашифрованный пароль, открытый пароль мы не видим и не храним». Юридическая

Метаописание и текст «пароль не нужен» на экране входа тоже уходят: теперь пароль
есть, и обещать его отсутствие нельзя.

## 9. Порядок работ

1. **Миграция + модель** — таблица `user_passwords` в `schema.sql`, `setPassword` /
   `verifyPassword` в `backend/src/db/queries.ts`, хеширование в новом
   `backend/src/lib/password.ts`. Проверить, что повторный
   `npm run db:migrate:local` проходит без ошибок.
2. **Бэкенд** — `POST /api/auth/password` (задать/сменить), `POST /api/auth/login`
   (войти по паролю), флаг `hasPassword` в `/api/auth/me`.
3. **Фронт — настройки** — карточка «Вход по паролю», три состояния из раздела 5.
4. **Фронт — вход** — переключатель из раздела 6, отправка формы, тексты ошибок.
5. **Тексты и право** — раздел 8.
6. **Тесты** — пароль есть → вход работает; пароль есть → неверный пароль отклонён;
   пароля нет → вход по паролю отклонён с тем же текстом; чужой пароль отвечает так
   же, как несуществующий аккаунт; 6-я попытка блокируется по email и посторонний
   учитель не страдает; смена пароля требует старый; `source === "device"` —
   карточка показывает честное объяснение.

**Оценка:** 5–8 рабочих дней с тестами и текстами. Точную цифру команда называет
после разбора с frontend и backend.

## 10. Что НЕ делаем

- **PIN-код.** Отклонён владельцем 12.10.2026: перебирается быстрее обычного
  пароля и требует отдельной схемы блокировок.
- **Двухфакторная аутентификация.** Не просил никто из учителей, стоит отдельного
  сценария поддержки. **Уточнение 12.10.2026: решение про учительский вход.**
  В суперадминке код подтверждения делается — решение владельца от 12.10.2026,
  см. `docs/tz/24-superpower-dashboard.md` §8.1. Учителей это не касается.
- **Вход по соцсетям.** Кнопки VK/Яндекс/Telegram уже стоят как витрина
  (`src/app/login/page.tsx:184`), подключение — отдельная задача.
- **Сброс пароля через SMS.** Второй канал восстановления не нужен, пока пароль
  можно снять письмом.
- **Обязательная смена пароля по расписанию.** Пароль живёт вместе с аккаунтом,
  ученик об этом не узнает.

## 12. Live-проверка (как проверять руками)

1. Войти по ссылке → настройки → задать пароль `uchlist2026` → перезагрузить
   страницу: пароль сохранён, вкладка показывает дату установки.
2. Выйти из кабинета → `/login` → «Войти по паролю» → почта и `uchlist2026` →
   кабинет открылся, в «Устройствах» появилась новая сессия.
3. Войти с паролем `uchlist2027` → отказ, текст совпадает с отказом при несуществующем
   адресе `test@example.com`.
4. Шесть неудачных попыток подряд → седьмая отклоняется; с другого email (другой
   учитель) вход в это же время проходит.
5. Сменить пароль без старого → отказ. Со старым → новый работает, старый нет.
6. Удалить пароль → `/login` работает только по ссылке, вкладка в настройках вернулась
   в состояние «пароля нет».
7. Придумать пароль короче 8 символов → поле показывает требование, запрос не уходит.
8. Кабинет в режиме `device` (без аккаунта) → карточка пароля объясняет, что нужен
   вход по почте, и даёт ссылку.
