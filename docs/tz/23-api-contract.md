# ТЗ-23: контракт API и фронта

**Зафиксировано:** 12 октября 2026, до начала реализации.
**Зачем этот файл:** бэкенд и фронт делаются четырьмя разными исполнителями
параллельно. Без общей таблицы имён и полей они разъедутся: фронт напишет
`has_password`, бэк отдаст `hasPassword`, и ошибка увидит учитель.

**Источник истины — ТЗ:** `docs/tz/23-password-auth.md`. Этот файл не принимает
новых решений, он переводит ТЗ в поля и статусы. Если здесь и в ТЗ расхождение —
прав ТЗ.

---

## 1. Общие правила для всех ручек

1. Формат ошибки — как у существующих ручек: JSON `{ error: string }`
   (`backend/src/lib/errors.ts`, фронт читает `res.error` в
   `src/lib/auth/api.ts:246`).
2. Тело запроса — JSON. Нечитаемый JSON → `400`.
3. Невалидная схема (zod) → `400`.
4. **Никогда** не отдавать наружу `hash`, `salt`, `iterations` и сам пароль —
   ни при успехе, ни при ошибке.
5. Email нормализуется существующим `emailSchema`
   (`backend/src/services/auth.ts:49`): trim + lowercase.

## 2. Таблица ручек

| Ручка | Тело | Успех | Ошибки |
|---|---|---|---|
| `POST /api/auth/password` | `{ password, currentPassword? }` | `200 { ok: true, setAt }` | `400` слабый пароль · `401` нет сессии или неверный `currentPassword` · `429` перебор |
| `DELETE /api/auth/password` | — | `200 { ok: true }` | `401` нет сессии |
| `POST /api/auth/login` | `{ email, password }` | `200 { ok: true, user }` + cookie | `400` невалидное тело · `401` ЕДИНЫЙ текст · `429` перебор |
| `GET /api/auth/me` | — | `200 { ok: true, user }` (добавлены 2 поля) | — |

### 2.1 `setAt`

ISO 8601-строка, тот же формат, что уже отдаёт `createdAt` в `/callback`
(`new Date(unixSec * 1000).toISOString()`). На фронте это единственный источник
даты «Пароль задан …».

### 2.2 Единый текст отказа (ТЗ §6, разрыв 4)

Ровно эта строка, символ в символ, на **оба** случая — «нет такого аккаунта»
и «неверный пароль»:

```
Не получилось войти. Проверьте почту и пароль
```

Формулировка дана в ТЗ §6. Проверка verifier'ом: строки совпадают побайтово.

Второй отказ, с кодом `429`, — отдельный и тоже не должен различать причину:

```
Слишком много попыток. Попробуйте через 15 минут
```

### 2.3 Тело `user` в `POST /api/auth/login`

Совпадает с телом `POST /api/auth/callback` (`backend/src/routes/auth.ts:82-92`) —
фронт переиспользует один и тот же тип `AuthUser`:

```json
{
  "id": "usr_…", "email": "…", "name": "…", "plan": "free",
  "generationsTotal": 0, "generationsToday": 0,
  "generationsLimit": 3, "createdAt": "2026-…"
}
```

Cookie ставится **ровно** как в `/callback`: `session`, HttpOnly, Secure,
`SameSite=None`, `path=/`, `maxAge 30 дней`. Код создания сессии
(`sessionToken()` → `createSession()`) общий, не дублируется.

## 3. Что добавляется в `GET /api/auth/me`

К текущему `user` (id, email, name, plan) добавляются два поля:

```json
{ "hasPassword": true, "passwordSetAt": "2026-10-12T12:00:00.000Z" }
```

- `hasPassword: boolean` — есть ли строка в `user_passwords`.
- `passwordSetAt: string | null` — `updated_at` из той же строки, ISO 8601.

**Почему второе поле, хотя его нет в формулировке задания.** ТЗ §12.1 требует:
после перезагрузки страницы «вкладка показывает дату установки». Если отдавать
только `hasPassword`, фронт не сможет показать дату без второго запроса, а
второй запрос — это лишняя ручка и лишняя точка отказа. Оба поля отдаёт одна
ручка, дата берётся из уже существующей колонки `updated_at`.

Когда пароля нет: `hasPassword: false`, `passwordSetAt: null`.
Когда пользователя нет: ответ прежний — `{ ok: true, user: null }`.

## 4. Где фронт берёт `hasPassword` — и почему не из `auth/api.ts`

`hasPassword` читает **Воркер B**, и только он: своей функцией в
`src/lib/lk/profile-api.ts` (там уже есть собственный `request()`-хелпер,
строка 287, который умеет ходить на любой путь).

Причина: `src/lib/auth/api.ts` принадлежит Воркеру C, и если бы оба воркера
правили его одновременно, тип `AuthUser` разъехался бы. Чтение из
`profile-api.ts` оставляет файл C нетронутым со стороны B.

`TeacherProfileView` получает одно новое поле:

```ts
hasPassword: boolean;        // device-режим → всегда false
passwordSetAt: string | null;
```

## 5. Правила пароля (ТЗ §7.1)

| Правило | Значение |
|---|---|
| Длина | 8…128 символов |
| Обязательно | минимум одна буква И минимум одна цифра |
| Спецсимволы | не требуем |
| Шкала надёжности | не показываем |
| Пароль = почта | разрешаем |
| Словарные пароли | не проверяем |

Свою же почту паролем разрешаем — человек такой пароль забывает.

Смена пароля требует `currentPassword`. Текст отказа на неверный
`currentPassword` — тот же, что и на «нет сессии» (`401`), чтобы нельзя было
отличить одно от другого.

## 6. Ограничение попыток (ТЗ §7.3)

- 5 попыток на **email**, окно 15 минут (`windowSec: 900`).
- Ключ — по нормализованному email через `keyFn`
  (`backend/src/middleware/ratelimit.ts:29`). **Не по IP**: вся школа на одном
  Wi-Fi, пять попыток одного учителя заблокируют вход тридцати другим.
- Свой `bucket`, чтобы ручка пароля не делила лимит с `/magic-link`.

**Техническая ловушка, которую надо обойти, а не не заметить.** `keyFn`
выполняется middleware'ом **до** хендлера. Если в нём прочитать тело запроса,
хендлер получит пустое тело — и ручка всегда будет падать. Перед тем как
выбрать способ, это надо проверить на тесте, а не предположить.

**Честное отступление от буквы ТЗ, которое владелец должен знать.**
`rateLimitMiddleware` считает все попытки, а не только неудачные — так устроен
существующий middleware, и ТЗ прямо велит им пользоваться. Значит успешный
вход тоже тратит попытку. Отдельно считать только неудачные — это другой
механизм, не описанный в ТЗ. Реализация идёт по ТЗ (через `keyFn`),
факт вынесен в отчёт.

## 7. Итерации хеширования (ТЗ §7.2)

Не берётся из учебника. Число выбирается замером в этом же репозитории и
фиксируется константой с комментарием, где записано:

1. сколько миллисекунд стоит одна итерация на этой машине,
2. сколько итераций выбрано,
3. сколько это миллисекунд,
4. в какой CPU-лимит это укладывается.

OWASP рекомендует для PBKDF2-HMAC-SHA256 600 000 итераций. Cloudflare по
умолчанию даёт 10 мс CPU на бесплатном тарифе и 30 с на платном; в
`backend/wrangler.toml` лимит не переопределён, значит действует тарифный.
Если 600 000 не укладывается в разумный бюджет — снижаем и **фиксируем это
решение в коде комментарием и в отчёте**, а не молча.

Колонка `iterations` в таблице обязательна: старые хеши помнят своё число.
