## 1. Что сделано

### `backend/src/llm/cache.ts`

- **Введён экспорт `FORMAT_VERSION = 2`** с развёрнутым объяснением: почему это
  число в коде, а не комментарий в промпте; что именно поднимает версию
  (system-промпт, строка формата ответа, схема типов ответа, код сборки ответа);
  почему версия одна, а не две; история версий (1 — неявная, «до 29.10.2026»;
  2 — версия в ключе).
- **`makeCacheKey` теперь принимает необязательный второй аргумент
  `formatVersion` (по умолчанию — текущая `FORMAT_VERSION`) и вписывает версию в
  канонический JSON.** Ключ вырос на одно поле `formatVersion`; длина ключа не
  изменилась (это djb2-хеш, 16 hex-символов).

Зачем второй аргумент: версия обязана быть **проверяемой**, а не декларативной.
Чтобы доказать «запись по старому ключу не отдаётся по новому», нужен способ
посчитать ключ для произвольной версии. Публичная сигнатура ТЗ
(`makeCacheKey(input)`) сохранена — второй параметр необязательный, все
существующие вызовы (`llm/index.ts:391`, `llm/index.ts:1781`,
`llm/interactive-pack.ts`) работают как раньше.

- В шапку файла добавлено объяснение: `saveCache` пишет `INSERT OR IGNORE`,
  первая запись по ключу живёт весь TTL — значит версия в ключе обязательна,
  а не желательна.

### `backend/src/llm/prompts/worksheet-gen.ts`

- В шапку файла и в шапку `WORKSHEET_GEN_SYSTEM` добавлен блок **«ПРАВИЛО ВЕРСИИ
  ФОРМАТА (ТЗ-35)»**: что поднимает `FORMAT_VERSION`, где живёт константа, как

  он переведён под заголовок «ИСТОРИЯ ИЗМЕНЕНИЙ (справочно)» с явной оговоркой,

   `wrangler` без авторизации. Живой прогон локально тоже невозможен.
3. Квота общая для анонимов (ключ кэша для `userId = null` тоже общий).

**Что вместо живой проверки сделано:** тот же путь исполняется локально целиком —
настоящий `generateWorksheet` из `backend/src/llm/index.ts` (сборка ключа,

перегенерация» для контрольной), настоящий `makeCacheKey`/`lookupCache`/
`saveCache`, D1 — заглушка с настоящим `semantic_cache` в памяти, сеть —
заглушка провайдера. Это тесты «повторный запрос попадает в кэш и не зовёт

## 8. Находки вне задачи

1. **Фронтовые тесты не запускаются вообще — 101 файл, 0 тестов.** Причина:
   `vitest.setup.ts:45` → `await import("node:buffer")`, а vite 8.3.4 (версия в
   `package-lock.json`) экстернализует `node:`-модули для браузерного окружения
   и подставляет заглушку, которая падает с «No such built-in module: node:».
   Падает **до** загрузки тестов, то есть тестовый стенд фронта мёртв.
   **Это ломает шаг `npx vitest run` в CI** (`.github/workflows/deploy.yml`,
   шаг «Test» — он блокирующий), то есть деплой из `main` сейчас не проходит.
   Файлы `vitest.setup.ts` / `vitest.config.ts` в мой список не входили, не
   трогал. Возможное лечение — не импортировать `node:buffer` динамически, а
   дописать недостающие методы (`arrayBuffer`, `text`, `stream`) в jsdom-овский
   `Blob`; или вынести подмену `Blob` в отдельный файл с `server.deps.inline`.
   Требует решения владельца/разработчика фронта.
2. **Инвалидации по формату в коде нет вообще.** Проверил сам: `deleteCache`
   вызывается ровно в двух местах — `backend/src/llm/index.ts:424` (контрольная
   без `secondVariant` и без флага результата) и `backend/src/llm/index.ts:428`
   (запись без `worksheet`). Ни формат ответа, ни версия промпта в критерии
   инвалидации не входили и не входят. Поэтому вариант «хранить версию в
   записи и сверять при чтении» потребовал бы правки схемы и миграции — как и
   сказано в AD-1/AD-2. Версия в ключе обходит эту дыру полностью: запись со
   старым ключом просто не находится, и сносить её не нужно.
3. **Ключ кэша — общий для всех анонимов** (`userId = null` → `""`), а квота
   бесплатных анонимных генераций общая (5 в месяц). То есть анонимный
   учитель может получить из кэша материал, за который заплатил другой
   аноним. Для учебного контента это не вредит, но после подъёма версии первый
   анонимный запрос по теме заплатит за материал, который второй получит
   бесплатно. Отдельная тема (TZ-48 «free quota requires account»), здесь не
   трогал.
4. **Админский `invalidateCache(subject, grade, topic)` работает как надо** и
   после подъёма версии: он сносит записи по теме независимо от версии, то
   есть «обновить листы по теме» не сломается. Проверено чтением кода, не
   прогоном.

## 9. Пакет вопросов

1. **Когда выкатывается ветка?** Живая проверка «после» требует деплоя и
   свободной квоты; квота обнулится 1-го числа. Варианты: (а) владелец
   деплоит и я делаю живой прогон 1–2 ноября; (б) считать задачу закрытой по
   локальным доказательствам, живой прогон — отдельной задачей; (в) владелец
   даёт API-ключ для локального прогона.
2. **Что делать с фронтовыми тестами (раздел 8, п. 1)?** Это блокирует деплой
   в CI. Варианты: (а) отдельная задача фронту — починить `vitest.setup.ts`;
   (б) починить мне в этой ветке (выходит за рамки ТЗ-35 и за мои файлы);
   (в) владелец чинит сам.
3. **Нужен ли `FORMAT_VERSION` ещё и для других типов промптов?** Сейчас версия
   одна на весь `backend/src/llm/prompts/**` и на код сборки ответа. Варианты:
   (а) оставить одну (текущий вариант, ТЗ AD-3); (б) завести по версии на тип
   материала — тогда подъём версии листа не сбрасывает кэш карточек.
4. **Поднимать ли версию при смене только user-промпта?** Сейчас да (правило в
   шапке: «правка текста промптов этого файла»). User-промпт листа меняется
   динамически (тема, класс, учебник), и его текст в `makeCacheKey` уже
   отражён параметрами запроса. Варианты: (а) оставить как есть — версия
   поднимается при правке кода шаблона user-промпта; (б) уточнить формулировку
   правила, чтобы случайная правка шаблона не обнуляла кэш целиком.
5. **Нужен ли административный инструмент «показать, какие записи кэша
   протухли по версии»?** Варианты: (а) не делать — записи умрут по TTL;
   (б) сделать позже вместе с чисткой `semantic_cache` (её тоже никто не
   чистит — см. раздел 9 ТЗ-35).
