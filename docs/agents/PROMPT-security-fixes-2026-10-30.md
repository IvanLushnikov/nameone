## 0. Зачем ты нужен

Ревью безопасности от 30.10.2026 нашло 10 проблем. Четыре из них бьют по живому продукту прямо сейчас.

Главная — №1. Воркер задеплоен с cron-триггерами, обработчик написан и выглядит рабочим, но Cloudflare его **не зовёт**: модуль отдаёт `export default app`, а у Hono-объекта нет метода `scheduled`. Итог: за четыре недели (с 02.10) ежесуточная уборка не выполнилась **ни разу**. Фотографии детских работ лежат в бакете бессрочно, хотя обещано удаление через 7 дней; ответы учеников — вместо 90 дней. Страница при этом работает, поэтому поломку никто не заметил.

Доказательство, на которое опирается находка: таблица `weekly_topic_state` в боевой базе (`id INTEGER PRIMARY KEY CHECK (id = 1)`, пишет только cron) пуста.

Остальное: не задана соль отпечатка в проде (база отпечатков обратима в IP), прод можно выкатить с настройками разработки (так уже выкатывали дважды), чужой рабочий лист читается через «избранное».

Твоя работа: **закрыть находки по порядку и доказать, что каждая закрыта.** Не «починил» — а «проверил, что поломки больше нет».

## 2. Пакет 1 — четыре находки, которые делать сегодня

### №1. Плановая уборка не выполняется никогда

**Где:** `backend/src/index.ts:284-356` (подключение обработчика), `backend/wrangler.toml:130-134` (триггеры), `backend/src/jobs/weeklyTopic.ts:110-120` (единственный писатель в `weekly_topic_state`).

**Сейчас:** Cloudflare вызывает cron только через экспорт `scheduled` модуля. Обработчик навешан на `app.fire("scheduled", ...)` — это внутренний диспетчер Hono, Cloudflare о нём не знает. Модуль отдаёт `export default app`, метода `scheduled` у него нет. Комментарий в коде (`backend/src/index.ts:278-283`) утверждает обратное — поправь его, он будет вводить в заблуждение и следующего читателя.

**Что сделать:** отдавать объект с `fetch` и `scheduled`:

```ts
export default {
  fetch: app.fetch,
  scheduled(event, env, ctx) {
    app.fire("scheduled", event, env, ctx);
  },
};
```

Проверь, что `export { app }` (строки 356-357) остаётся, если его кто-то импортирует, и что перекрытие `app.fire` нигде больше не нужно.

**Как проверить локально** (Cloudflare умеет гонять cron локально):

```bash
cd /Users/ivanlusnikov/Documents/nameone/backend
CI=1 npx wrangler dev --test-scheduled --local
# в другом терминале:
curl "http://localhost:8787/__scheduled?cron=0+3+*+*+*"
```

В логах должны появиться строки `[cron] purgeExpiredPhotos` и `[cron] refreshWeeklyTopicState`. Если их нет — правка не сработала.

**Тест:** новый тест падает на старом коде и зелёный на новом. Проверь, что у экспортируемого default есть функция `scheduled`, и что она вызывает `app.fire` с теми же аргументами, что и раньше.

**Критерий приёмки:**
- [ ] локальный прогон `__scheduled` даёт `[cron] purgeExpiredPhotos`
- [ ] после деплоя владельцем в Cloudflare Logs есть строка `[cron] purgeExpiredPhotos` за сегодняшнюю ночь
- [ ] в боевой базе таблица `weekly_topic_state` содержит ровно одну строку:
  ```bash
  cd /Users/ivanlusnikov/Documents/nameone/backend
  CI=1 npx wrangler d1 execute rabochielisty --remote --command "SELECT COUNT(*) AS rows FROM weekly_topic_state"
  ```

**Отдельно — разовая уборка просроченного.** Пока cron не работал, в бакете могли накопиться фотографии старше 7 дней. Скрипт есть (`backend/scripts/purgeExpiredPhotos.ts`), запуск по боевой базе — **с разрешения владельца**. Опиши в отчёте, что запускал и что удалил, либо что не запускал и почему.

### №2. Соль отпечатка посетителя в проде не задана

**Где:** `backend/src/env.ts:112-118` (объявление), fallback в семи местах: `backend/src/routes/llm.ts:76`, `backend/src/routes/users.ts:266`, `backend/src/routes/worksheets.ts:179` и `:335`, `backend/src/routes/exams.ts:80`, `backend/src/routes/f06.ts:412`, `backend/src/routes/artifact-generate.ts:219`, `backend/src/routes/turnstile.ts:143`. Проверка прод-конфига — `backend/src/index.ts:83-89` (соли там нет).

**Сейчас:** в боевом воркере задано пять секретов, `FINGERPRINT_SALT` среди них нет → везде подставляется константа `"dev-fingerprint-salt"` из исходников. Хэш с публичной солью перебирается за секунды, таблица отпечатков становится справочником по IP. Схема обещает обратное — это расхождение обещания и реальности, а не только криптография.

**Что сделать в коде:**
- убрать fallback `?? "dev-fingerprint-salt"` во всех семи местах — в проде соль обязательна;
- добавить `FINGERPRINT_SALT` в проверку прод-конфига, чтобы воркер сам ругался в лог при её отсутствии.

**Команда владельцу** (ты её только готовишь и кладёшь в отчёт, сам не выполняешь — это прод-мутация):

```bash
cd /Users/ivanlusnikov/Documents/nameone/backend
npx wrangler secret put FINGERPRINT_SALT --env production
```

Значение — случайная строка от 32 символов.

**Что учесть и зафиксировать в отчёте:** после смены соли старые отпечатки перестанут совпадать с новыми — счётчик бесплатных листов у тех, кто уже заходил, начнётся заново. Это побочный эффект, а не поломка, но владельцу надо знать. Заодно предложи одноразовую чистку старых отпечатков: после смены соли они больше ни к чему не привязаны.

**Критерий приёмки:**
- [ ] строки `"dev-fingerprint-salt"` в коде нет (проверь `grep -rn "dev-fingerprint-salt" backend/src`)
- [ ] проверка прод-конфига ругается, если секрет не задан
- [ ] после задания секрета новый отпечаток не совпадает со старыми из базы

### №4. Чужой рабочий лист читается через «избранное»

**Где:** `backend/src/routes/users.ts:146-158` (тело без схемы валидации) → `backend/src/db/userResources.ts:217-256` (нет сверки владельца) → `backend/src/db/userResources.ts:152-163` (JOIN отдаёт `payload_json` чужого листа).

**Сейчас:** `POST /api/users/favorites` принимает `worksheet.id` из тела. Внутри делается только `SELECT id FROM worksheets WHERE id = ?1` — проверка факта существования. Если лист существует, он не перезаписывается, но в `favorites` учителя пишется ссылка на чужой лист. `GET /api/users/favorites` отдаёт `payload_json` через JOIN, фильтруя по таблице избранного, а не по листу. Учитель получает задания, эталоны ответов и критерии чужого листа. Так обходится защита `GET /api/worksheets/:id`, где владелец сверяется.

**Что сделать:**
- сверять владельца перед вставкой в избранное — одна проверка по образцу `backend/src/routes/f07.ts:315-319`, где такой же случай уже закрыт;
- заменить `as { worksheet: Worksheet }` на zod-схему: сейчас тело принимается как есть, и запрос без `tasks` даёт 500 вместо 400.

**Тест (обязателен):** два пользователя, лист принадлежит первому. Второй добавляет его в избранное → отказ, и в `GET /api/users/favorites` второго нет содержимого чужого листа.

**Критерий приёмки:**
- [ ] добавление чужого листа в избранное отклоняется
- [ ] в ответе избранного нет `payload_json` чужого листа
- [ ] тело ручки валидируется схемой, некорректное даёт 400, а не 500

### №7. CSV в комплекте материалов исполняется как формула

**Где:** `src/lib/utils/materials-zip.ts:68-71` (`csvBytes`) и `:146` (запись в архив).

Тест: содержимое с `=cmd|'/c calc'!A1` и с запятой внутри значения не исполняется и не рвёт таблицу.

### №8. Тип загруженного файла не проверяется

**Где:** `backend/src/routes/f06.ts:1537-1541` (allowlist по `uploaded.type`), `backend/src/routes/f06.ts:171-176`, `backend/src/routes/f06.ts:236-239` (запись в R2 с этим contentType), `backend/src/routes/classes.ts:1521-1529` (фото ученика).

Сейчас: тип берётся из заголовка, который прислал клиент; байты с заголовком не сверяются. Учитель или ученик может положить HTML или SVG под видом `image/jpeg`. Сейчас не эксплуатируется: бакет приватный, наружу байты не отдаются — но риск проснётся, если появится ссылка на файл.

Сделай: сверяй magic bytes (сигнатуру файла) с заявленным типом, отклоняй несовпадение.

## 4. Пакет 3 — до включения продаж

### №6. Вебхук оплаты не проверяет подпись

**Где:** `backend/src/routes/billing.ts:171-185` (ручка), `backend/src/services/billing.ts:546-641` (`handleWebhook`), `:624` (живая сверка пропускается без ключей), `:632-640` (при `unknown` подписка всё равно активируется).

Сейчас: подпись ЮKassa не сверяется нигде. Схема держится на трёх проверках: платёж есть в базе, сумма совпадает с серверным прайсом, живая сверка с API ЮKassa. Живая сверка — единственная опора, и она пропускается целиком, если ключи не заданы, а при ответе `unknown` (сеть, 5xx, 401) подписка всё равно активируется.

Сегодня эксплуатировать нельзя: ключей ЮKassa в проде нет, платежей в базе 0, `ALLOW_DEMO_PAYMENTS=false`. Проверено вживую 30.10: поддельный вебхук вернул `{"handled":false}`. Но как только появятся ключи, схема станет уязвимой в тот день, когда API ЮKassa недоступен.

Сделай:
- сверять подпись ЮKassa первым фильтром, до остальных проверок;
- при `unknown` не активировать подписку, а ставить платёж в очередь на повторную сверку;
- allowlist адресов ЮKassa на уровне Cloudflare — вынеси владельцу как рекомендацию, не как свою задачу.

Не ломай текущие проверки: сверка с API ЮKassa и сверка суммы с серверным прайсом остаются. Тариф, период и сумма берутся из базы и серверного прайса — поля тела запроса игнорируются, и это правильно, не трогай.

## 6. Что НЕ делать

- **Не деплой.** Публикует владелец. Твоя работа — код, тесты, ветка и отчёт.
- **Не меняй прод-секреты.** `wrangler secret put` — команда для владельца, ты её только готовишь и описываешь в отчёте.
- **Не пушить в `main`.** Коммит — в ветку `fix/security-2026-10-30`. Пуш в `main` = автодеплой.
- **Никогда `git reset --hard` в общем дереве.** Работай в worktree: `git worktree add .worktrees/fix-security -b fix/security-2026-10-30`.
- **Не трогай продукт вне списка находок.** Ни тарифы, ни норму токенов, ни промпты, ни валидацию листов, ни UI. Рефакторинг — отдельная задача.
- **Не меняй публичные обещания.** Тексты про «удаление через 7 дней» и про 152-ФЗ не трогай: их правят после того, как починка заработает.
- **Не трать деньги провайдера.** Баланс polza на 30.10 — 12,14 ₽. Живых вызовов LLM не делай без нужды.
- **Не выдумывай результат.** Если проверку выполнить не удалось — так и напиши «не выполнено, причина».
- **Не считай падение теста своим.** Перед починкой посмотри `stat` на тест и на тестируемый код: за время твоей работы баг могли починить другие сессии. Ветку `research/02-polza-cost-quality` и чужие изменения в дереве не трогай.

5. **Команды и решения, которые остались за владельцем** — точным списком, готовые к копированию: `wrangler secret put FINGERPRINT_SALT --env production`, `wrangler secret put TURNSTILE_SECRET_KEY --env production`, sitekey, решение по `deploy:staging`, решение по блокировке вместо лога, решение по CSP, разовая уборка просроченных фото.
6. **Что не удалось подтвердить** — обязателен и **не может быть пустым**. Например: живая проверка после деплоя не выполнена (деплоит владелец); публичность бакета в панели Cloudflare не проверялась; CSP в report-only не собран.
7. **Что сломалось по ходу** — если что-то сломал и починил.
8. **`git status --short`** — должно быть чисто (или объясни, что это за файлы).

### Выжимка в чат — до 10 строк

Главное: **сколько находок закрыто из десяти**. Потом — что сломано до сих пор и что осталось за владельцем. **Не пересказывай отчёт.**

## 8. Про формат находок

Если по ходу найдёшь дефект, которого не было в списке, оформи его по правилу проекта (`AGENTS.md`, раздел «Как говорим о проблемах»):

```
Как <учитель|админ|разработчик>, я хочу <что>, чтобы <зачем>.
Сейчас: <что происходит — словами этой роли, без терминов>
Цена ошибки: <что будет, если не починить>
Где в коде: <файл:строка>
```

Роли — ровно три: **учитель**, **админ**, **разработчик**.
