## Сборка, зависимости и локальный стенд

### Сборка виснет на Node 23, работать надо на Node 22 (01.10.2026)

**Правило:** в nameone `npm run build` и `next dev` **на Node 23 зависают намертво** —
0.1% CPU, лог обрывается на строке «Creating an optimized production build», ни ошибки,
ни таймаута. Ждать бесполезно: проверено дважды, по 90+ секунд без единого записанного файла.

Причина зафиксирована в самом репозитории — `.github/workflows/deploy.yml:24`:
`node-version: 22  # Локально Next 14.2 + Node 23 виснет на M2 Air → собираем в CI`.
То есть это известная проблема, а не регрессия в коде.

**Как чинить (Node 22 установлен в Homebrew рядом с дефолтным):**
```bash
cd /Users/ivanlusnikov/Documents/nameone
export PATH="/opt/homebrew/opt/node@22/bin:$PATH"
export NEXT_TELEMETRY_DISABLED=1
node -v          # должно быть v22.23.3, а не v23.11.0
npm run build
```

**Почему это важно запомнить:** симптом выглядит как «завис мой код» или «перебор
страниц статического экспорта», и легко потратить 20 минут на ложную диагностику
таксономии. Лечится только сменой версии Node. Аналогичная по симптому зависание
`vitest` на этом же проекте (старт > минуты, ноль вывода) лечится флагом
`--environment node` для тестов, которым не нужен DOM.

**Смежное:** дефолтный `node` в этой машине — 23.11.0, поэтому `PATH` надо
переопределять явно в каждой сессии, где запускается build.

### Lock-файл генерировать тем же npm, которым ставит CI (13.10.2026)

**Ситуация (обновление зависимостей в nameone).** Сгенерировал `package-lock.json`
для backend локальным npm 11. Локально `npm ci` проходил, typecheck и все 707 тестов
были зелёные. CI падал:

```
npm error `npm ci` can only install packages when your package.json and
package-lock.json ... are in sync.
npm error Missing: @cloudflare/workers-types@4.20260702.1 from lock file
```

**Причина.** Обе версии пишут `lockfileVersion: 3`, поэтому номер версии
ничего не подсказывает. Расходится само разрешение: npm 10 требует в lock
запись для транзитивного peer-требования, npm 11 её не пишет. CI гоняет
Node 22 → npm 10, разработчик может иметь что угодно.

**Как применять.**

1. Перед тем как доверять локальному `npm ci`, узнать версию npm в CI —
   обычно это `node-version` в `actions/setup-node`. Не угадывать.
2. Генерировать lock ТЕМ ЖЕ npm: `npx npm@<версия-из-CI> install`.
   Для Node 22 это npm 10.
3. Проверять на чистой копии ветки (`git worktree add --detach`), а не в
   рабочей копии: там `node_modules` уже стоят и маскируют расхождение.
   Именно чистая копия воспроизвела падение, рабочая — нет.
4. Отличать две разные ошибки npm: `ERESOLVE` (конфликт peer, нужен
   апгрейд или отказ) и `edgesOut: Cannot read properties of null` (баг npm
   при резолве). Второе лечится сменой версии npm, первое — только правкой
   зависимостей.

### Перед обновлением зависимостей: `npm ci --dry-run`, а не `npm install` (15.10.2026)

**Главное правило.** `npm install` локально **прощает** конфликт пиров (за警告
предупреждением), а `npm ci` в CI его **отвергает**. Поэтому проверять надо так:

```
npm ci --dry-run --no-fund
```

в каждом пакете перед `git push` в `main`. Именно так обнаружилось, что zod 4 в
бэкенде конфликтует с `openai@4.104` (peer `zod@^3.23.8`) — локально стоял
зеленый, а CI упал бы. Поддержка zod 4 появилась только в `openai` 6.x/7.x,
то есть за zod 4 пришлось бы заплатить скачком через три мажора LLM-SDK.

**Считать CI отдельно от локали.** CI собирает `npm ci` на Node 22 (npm
10.9.x), локально Node 23 + npm 10.9.2/11. Расхождение версий npm — источник
граблей, не приговор.

**Грабли, собранные 15.10.2026 (nameone):**

- **npm 10.9.2** падает на пирах vitest 4: `Cannot read properties of null
  (reading 'edgesOut')` в arborist `#loadPeerSet`. Лечится установкой через
  `npx npm@11`. Чистка node_modules и lock не помогает — виноват сам npm.
- **npm 11 блокирует install-скрипты** (`allowScripts`): без одобрения не
  ставятся бинарники `workerd` и `esbuild`, и рантайм Workers не стартует.
  Лечится `npx npm@11 install-scripts approve workerd esbuild` + `rebuild`.
- **jsdom 30 ломает vitest**: «Failed to start forks worker / Timeout waiting
  for worker to respond», не выполняется ни один тест. Проверено изолированно:
  с jsdom 27 тот же файл проходит за 0,6 с. Не обновлять без проверки.
- **vitest 5 → Vite 8 → rolldown/oxc**: опция `esbuild` в конфиге МОЛЧА
  игнорируется, и все `.tsx` падают с «Unexpected JSX expression». Настройка
  переезжает в `oxc: { jsx: { runtime: 'automatic' } }`. Не ошибка, а тишина.
- **vi.fn() без аргументов** в vitest 4 даёт `Mock<Procedure | Constructable>`,
  который TypeScript не считает вызываемым. Тип аргумента задавать руками.

**Порядок работы:** сначала чини проверяющий инструмент, потом обновляй.
Здесь бэкенд-тесты не выполняли НИ ОДНОГО теста (`npm test` падал на старте),
и пока это не починено, принимать любое обновление нельзя — нечем проверять.
Обновление без зелёной проверки = слепое.

**Правило для прогонов:** один показатель за раз. Менять пакеты пачкой и
получать общий отказ бессмысленно: сначала vitest 5, потом jsdom 30 — каждый
раз выяснялось, что виноват второй, а первый наоборот был нормален.

### Окружение УчЛиста без ключей — живые прогоны генерации невозможны (13.10.2026)

В окружении УчЛиста (backend `backend/.dev.vars`) ключи **пустые**: `POLZA_API_KEY`,
`RESEND_API_KEY`, `YOOKASSA_*`, `ADMIN_EMAIL`. Заполнен только `JWT_SECRET`.
Аккаунта тарифа «Плюс» тоже нет.

Из-за этого локально нельзя выполнить:

- любую генерацию через LLM (листы, карточки, презентации, ОГЭ/ЕГЭ);
- вход по magic-link и любые сценарии с письмами;
- PPTX и ОГЭ/ЕГЭ (тариф «Плюс»).

Проверить при этом МОЖНО и нужно: юнит-тесты промптов и валидаторов, типы,
lint, вёрстку в браузере через `npm run dev`, мобильные замеры `scrollWidth`,
сгенерированный DOCX (собирается локально без сети), свёрку чисел главной с
`scripts/audit-coverage.ts`.

**Как применять.** Перед тем как обещать прогон «на живых листах», проверить
наличие ключа одной командой — и не обещать, если его нет. Лучше честно
записать гейт как `ABANDON` с причиной, чем написать «проверено» без
проверки: дефекты качества материала (смешанные числа в 5 классе,
иррациональная десятичная дробь, дубли навыка) видны только на реальной
генерации.

### Стенд на локальном порту может слушать и при этом ничего не отдавать (15.10.2026)

**Правило проверки.** «Порт слушает» ≠ «стенд работает». Всегда проверять
реальным запросом и смотреть на код ответа:

```
curl -s -o /dev/null -w "HTTP %{http_code}\n" http://127.0.0.1:8769/
```

Код `000` при живом `lsof -nP -iTCP:8769 -sTCP:LISTEN` — это тот самый случай.

**Что происходит технически.** macOS TCC закрывает папку в `~/Documents`.
Python-сервер, запущенный из неё, продолжает слушать сокет, но при первом
же запросе падает в обработчике (`PermissionError: [Errno 1] Operation not
permitted` при `os.getcwd()` в `http.server`) и рвёт соединение. Клиент видит
`Connection reset by peer`, в браузере — пустая страница. Снаружи выглядит
как «сервер поднялся».

**Как обнаружить.** Лог сервера: `nohup python3 serve.py --port PORT > /tmp/x.log 2>&1 &`,
потом читать лог, а не только проверять порт.

**Почему это дорого.** Ссылку `http://127.0.0.1:8769/` уже отправили коллегам
как «прототип готов». Она открывается только у того, кто её запустил, —
у всех остальных `127.0.0.1` указывает на их собственный компьютер.
Для раздачи кликабельного прототипа наружу отдавать **архив с инструкцией
запуска**, а не локальную ссылку.

**Правильный порядок.** Копию проекта держать в доступной папке (`~/имя-проекта`),
`serve.py` запускать оттуда, а архив для коллег собирать в `~/workspace/output`.
