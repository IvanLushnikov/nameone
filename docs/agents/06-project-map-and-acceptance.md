### Цифры из брифа проверять по исходному коду продукта до публикации (11.10.2026)

**Публикуемые цифры сверять с исходным кодом, а не с брифом/спецификацией.**
Источник истины — код продукта, а не текст задания.

Проверено 11.10.2026 на интеграции УчЛиста в `ilushnikov.ru`. Бриф содержал формулировку
«тарифы 500 / 990 / 1500 ₽ в месяц или за учебный год (9 мес)» — читается как «год стоит столько
же, сколько месяц». Фактически в `plans.ts` год = 3800 / 7600 / 11000 ₽: **занижение почти в 8 раз**
на публичном сайте. Тариф «Школа» был описан как «3000 ₽ за класс» без единицы измерения, хотя в
самом продукте отдельным комментарием отмечено, что эту формулировку уже уточняли.

Та же ошибка нашлась рядом: в `llms.txt` стояло «0.04% → 50% (50× growth)», тогда как 50/0.04 = 1250
и в двух соседних строках того же файла уже было ×1250.

**Почему так выходит:** бриф пишется из продуктового описания, где «500 / 990 / 1500» — это
помесячные цены, а годовые живут отдельными полями. Склейка «или» даёт правдоподобную, но
кратно заниженную цифру. Ошибку не видно без сверки с кодом.

**Как применять:** перед публикацией любых чисел по продукту (цены, объёмы каталога, метрики)
прогонять сверку с исходником. Отдельный проверяющий агент, которому дан доступ к коду продукта,
ловит это быстрее — он сверял тарифы с `plans.ts`, а числа каталога пересчитывал исполнением
`__count.mts`, а не по комментариям.

Смежное: числа, взятые из **комментария** в коде, тоже не источник истины — там уже лежал
устаревший «1070 тем» при фактических 1075.

говорить пользователю про это явно: правка может быть нужной, но принимать решение
должен он, а не я.

### Тест на наличие ссылки не ловит битую ссылку (11.10.2026)

**Проверка «ссылка есть» не проверяет, что ссылка ведёт куда-то.**

Ситуация: задание требовало на страницах экзамена ссылку «Все задания предмета».
Агент её сделал. Оба теста были зелёные, 1010 тестов зелёные. **218 ссылок вели в 404** —
маршрута `/exam/<экзамен>/<предмет>/` просто не существовало, и папка в сборке была
только потому, что внутри лежали пронумерованные подпапки.

Второй дефект того же раунда: критерий «от главной не дальше двух кликов» я зашил
в тест под ОГЭ, поэтому 126 страниц ЕГЭ в четырёх кликах прошли незамеченными.

**Как применять:**
- Тест на ссылку обязан проверять **цель**: взять адрес из разметки и убедиться,
  что соответствующая страница существует в сборке.
- Приёмку «путь от главной ≤ N кликов» считать по фактическим `href` и **для всех
  страниц**, а не для той ветки, на которую смотришь. Не хватает выборки — это провал
  проверки, а не «выглядит нормально».
- Обязательно требовать от исполнителя доказать, что новый тест **падает на старом
  коде**. Тест, который не может упасть, ничего не проверяет.

**Почему это повторяемая ошибка, а не разовая:** агент строит ровно то, что написано
в задании. Если в задании сказано «добавить ссылку», а цели страницы не описано,
агент не додумает — он напишет ссылку на естественный адрес, который может не существовать.

### Правки в репозитории с параллельной чужой работой стираются молча (12.10.2026)

Ситуация: в `~/Documents/nameone` (УчЛист) внесена правка в `Footer.tsx`, проверена —
9/9 PASS. Пока шли другие задачи, параллельный заход переписал этот же файл целиком
(другая правка в нём же). Когда пришли финальные проверки, правки в файле уже не было:
`grep` — 0 совпадений.

**Как это пропустили:** контрольный агент проверял по заданию «чужая работа не затронута» —
и прошёл. Проверки «наша правка ещё на месте» в задании не было вообще. Оба предыдущих
проверяющих видели правку, потому что она существовала на момент их запуска.

**Как применять:**
- В репозитории с параллельной работой **сохранять патч своей правки отдельно**
  (например `git diff <файл> > /путь/имя.patch`) сразу после внесения — восстанавливается
  одной командой.
- В финальный контрольный чек-лист включать пункт «наши правки на месте», а не только
  «чужие не тронуты». Проверять не отчёт исполнителя, а факт в файле.
- Не коммитить и не деплоить такой репозиторий, пока в нём чужая незавершённая работа:
  сборка опубликует чужое промежуточное состояние. Здесь было 15+ изменённых файлов
  чужой задачи.

Правило сильнее прошлого («указывай субагенту границы»): даже идеально ограниченный
субагент не защищён от того, что его файл перезапишут. Защита — снапшот патча и проверка
в конце.

### УчЛист (nameone) живёт на GitHub, а не на GitLab (12.10.2026)

`~/Documents/nameone` (УчЛист, uchlist.ru) — репозиторий на **GitHub**:
`origin = https://github.com/IvanLushnikov/nameone.git`. Авторизация через `gh`
уже есть в keyring (аккаунт IvanLushnikov, scope `repo`).

Проверено 12.10.2026, когда ветка `fix/feedback-cases-2026-10-12` уехала пушем и
PR открылся через `gh pr create` → PR #41.

**Почему это важно помнить:** из правил проекта «GitLab-токен не спрашивать, он
в keychain, дефолт — коммит → push → MR через API» следует, что не нужно
переспрашивать пользователя про доступ. Но этот дефолт написан для другого
репозитория (Jay Agents, `gitlab.just-ai.com`). Для nameone применять его нельзя:
проверять платформу через `git remote -v` ДО того, как доставать токен, иначе
несколько минут уходит на бесполезный curl в GitLab API.

**Как применять:** перед коммитом в любом новом для меня репозитории —
`git remote -v` + `gh auth status`. GitHub → `gh`. GitLab → токен из keychain.

### Диагностировать отправку писем только на реальном адресе (12.10.2026, УчЛист)

**Проверка отправки писем на `@example.com` (и прочих тестовых доменах) даёт ложный диагноз.**

Проверено 12.10.2026 на УчЛисте. `POST /api/auth/magic-link` отдавал 500 на бойе, из
логов воркера уходил текст «Не удалось отправить письмо» — вывод сделали: сломан
`RESEND_API_KEY`, владельцу сказали перезалить секрет. Агент это подтвердил «проверкой»
Resend — тоже на `example.com`. **Оба вывода оказались неверными.**

Настоящая причина, из логов Resend:
`Invalid 'to' field. Please use our testing email address instead of domains like 'example.com'`
То есть провайдер отклоняет сам домен-заглушку, а не ключ. На настоящий адрес
(`hello@<домен проекта>`) тот же самый запрос вернул `{"ok":true,"sent":true}`.

**Как применять.** Прежде чем говорить «секрет/API-ключ сломан»:
1. Проверь `wrangler secret list` (или аналог) — секрет вообще задан? Здесь он был.
2. Постучи ручкой **на настоящий адрес домена проекта**, а не на `example.com`,
   `test.com`, `mailinator` и прочие заглушки.
3. Прочитай логи воркера (`wrangler tail <name> --format pretty` + повторный вызов),
   а не только HTTP-код ответа. Текст ошибки провайдера стоит всех догадок.
4. Сравни с тем, что агент реально проверил: на каком адресе он стучался.

**Почему это дорого.** Агент не просто ошибся — он из неверного вывода вывел
действие («перезалей секрет») и вписал его в PR и отчёт как требование к владельцу.
Владелец, не проверив, вводит ключ заново — и ничего не меняется, а доверие к
остальным находкам падает. Мой собственный вывод я повторил, не перепроверив.

### Отчёт субагента не равен результату — сверять дифом (12.10.2026, nameone)

**Субагент-воркер отработал `succeeded` и не сделал ничего из задачи.** Задача
«снизить цены по плану» в `nameone`: агент получил точный план с файлами и значениями,
потратил весь бюджет на чтение и вернул отчёт по baseline-проверкам. `git diff` по
объявленным файлам — пусто.

При этом в рабочем дереве шли изменения **чужой задачи** (ТЗ-23, пароль и авторизация),
попавшие в то же окно времени. Их легко принять за работу агента.

**Как применять.**

1. После `task` проверять результат `git diff --stat -- <файлы из OWNS>`, а не читать отчёт.
   Пустой диф при `succeeded` — работа не сделана, переделать самому или перезапустить.
2. Отчёт агента («я проверил baseline, всё понятно») — это описание подготовки, а не результат.
3. Статус `succeeded` означает, что сессия завершилась без ошибки, а не то, что файлы изменены.
4. Перед тем как отчитаться пользователю, прогнать собственные гейты (`GATES.md`) — они
   не зависят от того, кто правил файлы.

### Диагностика прода без входа — удалённая D1 + кука на домене API

**Воспроизводить прод-флоу без логина по email.** На nameone вход только по magic-link,
поэтому живого прогона через браузер не получить. Рабочий путь:

1. `cd backend && npx wrangler d1 execute <db> --remote --command "SELECT ..."` — читает боевую базу, авторизация через OAuth wrangler уже есть.
2. Вставить тестового пользователя + строку в `sessions` (таблица: `token`, `user_id`, `expires_at`, `created_at`).
3. API принимает `Authorization: Bearer <session-token>` — через curl можно создать форму, интерактив и т.д. без браузера.

**Критично: домен куки — это домен API, а не сайта.** Фронт на `uchlist.ru`, API на `rabochielisty-api.<acct>.workers.dev`. Куку надо добавлять в браузер для `workers.dev` с `sameSite: 'None'`. Поставленная на `uchlist.ru` — молча даёт 401 на всех запросах кабинета, и страница честно показывает «Данные из аккаунта не загрузились». Я так сделал и чуть не записал это как продуктовый баг; перед выводом проверять, чей это домен.

**Зачем это нужно.** Продуктовые баги часто видны только по данным прода: у nameone в проде было `0` строк в `forms` при 28 пользователях и 72 листах — это и указало, что фичей «выдать лист по QR» никто в бою не пользовался.

**Гигиена.** Тестовые строки (пользователь, сессия, форма, ответы) удалить сразу после проверки и перепроверить counts. Писать в боевую базу — только ради воспроизведения бага по прямой просьбе владельца.

### Деплой бэка — только из чистого worktree от `main` (12.10.2026, УчЛист)

**Ситуация.** В рабочем дереве висела чужая незавершённая
работа: 76 изменённых файлов на ветке `feature/tz-23-password` (вход по паролю,
ТЗ-24 супер-админ). Эта ветка **не собирается**: `tsc` даёт ошибки
(`isTotpEnabled`, `createPendingToken`, `Env`, `secret_enc/secretEnc`).

Я задеплоил бэк командой `npm run deploy` прямо из этого дерева — то есть на прод
попал недоделанный ТЗ-23/24. Wrangler собирает esbuild и **не проверяет типы**,
поэтому прод при этом «работал» и тихо отдавал код, который не собирается в CI.

**Как применять.**

1. Перед любым деплоем бэка: `git branch --show-current` + `git status --short`.
   Если ветка не `main` или есть чужие изменения — **не деплоить из этого дерева**.
2. Деплоить из отдельного worktree: `git worktree add /tmp/hotfix main`,
   внести правки, задеплоить оттуда. `node_modules` прилинковать:
   `ln -sfn <репозиторий>/backend/node_modules backend/node_modules`.
   Слинковать корневой `node_modules` (фронтовый) в `backend/` нельзя — tsc/vitest
   молча дают чужие ошибки, и это выглядит как «ветка сломана».
3. `wrangler deploy` не ловит типы. Прогонять `npx tsc --noEmit` и `npm test`
   ДО деплоя, иначе на прод уедут недоделанные куски.
4. Если правки должны попасть и в чужую ветку — сказать об этом явно: при мержа
   будут конфликты, версию брать из `main`.

### Перед «это дыра» — прочитать комментарии в коде (12.10.2026, УчЛист)

**Случай.** Увидел, что 2291 страница (`/ktp/*`, `/lesson-plan/*`, `/presentation/*`)
собрана, отдаёт 200, но **нет в sitemap.xml** и на них нет внутренних ссылок.
Решил: «SEO-дыра, срочно вернуть в карту» и внёс это в список срочного к владельцу
продукта.

Читал `src/app/sitemap.ts` — и там стоял комментарий: страницы сняты из карты
**намеренно**, потому что текст шаблонный, а 2140 однотипных URL рискуют уронить
индексацию всего каталога предмета. Это защитное решение автора, а не дефект.

Проверил цифрами: страницы `/lesson-plan/*` совпадают на **97–98 %** слов между
собой — решение обосновано. А страницы `/subject/*` в карте уникальны, идентичных
ноль — с картой всё в порядке.

**Как применять.** Прежде чем назвать что-то дырой/мусором/недоработкой:

1. Прочитать комментарии рядом с местом, где это «должно» быть
   (`sitemap.ts`, `robots.ts`, код выдачи страницы). Решения об индексации и
   показах обычно задокументированы.
2. Подтвердить внешними признаками **цифрой**, а не на глаз: для тонкого контента
   это доля совпадающих слов между страницами (сравнивать текст внутри `<body>`
   без `nav`/`header`/`footer`), для дублей — группировка по хэшу нормализованного
   текста.
3. Только после этого ставить в список срочного — иначе владельцу уходит совет,
   который ухудшит проект.

**Леджер в `.unlazy/<scope>/` запускать с `--root . --cwd .` (12.10.2026, УчЛист, скоуп teacher-path)**

Корень репозитория уже держал чужой `GATES.md` с неоткрытыми гейтами (задача
про цены). Свой леджер завёл в `.unlazy/teacher-path/GATES.md`, чтобы его не затереть.

1. **Корневой `GATES.md` — общая очередь.** Если он не пустой и не твой, свой
   скоуп живёт в `.unlazy/<scope>/GATES.md` + `PLAN.md`. Один файл на две
   задачи = тихая порча чужой работы.
2. **`gate-check.mjs` требует явных `--root` и `--cwd`,** когда леджер лежит
   внутри `.unlazy/`:

   ```
   node ~/.minimax/skills/unlazy/scripts/gate-check.mjs --root . --cwd . .unlazy/<scope>/GATES.md
   ```

   Без `--cwd` рабочим каталогом становится папка леджера, и все
   repo-relative `CHECK:` падают с `Cannot find module …/.unlazy/<scope>/.unlazy/…`.
   С `--root .` без `--cwd` — та же ошибка. Ошибка выглядит как «скрипт сломан»,
   а не как «неверный cwd».
3. **Правка `CHECK:` требует нового `--approve`.** Аппрув привязан к точному
   тексту команды, cwd, shell, PATH. Меняешь строку — переутверждай, иначе гейт
   молча останется unmet.
4. **Ручной гейт всё равно надо закрыть по существу:** записать в `EVIDENCE:`
   конкретный просмотр (сколько пунктов, какие цифры, чем проверял), а не слово
   «посмотрел». Потом `--reverify`, чтобы прогнать и автоматические заново.
5. **Дешёвая проверка «а скрипт вообще умеет падать?»:** скопировать документ в
   `/tmp`, убрать одну ссылку, убедиться, что скрипт дал `exit=1`. Без этого
   зелёный прогон не значит ничего — он может быть зелёным всегда.
6. **В N1 ветки нельзя перечислять её СОБСТВЕННЫЙ леджер.** Шаблон показывает
   `… leaf-<a>.md node-<b>.md`, и это читается как «лист + узел». На деле
   `node-<b>` — леджер ДРУГОЙ ветки. Свой леджер в списке = бесконечная
   рекурсия: вложенный `--reverify` перезапускает N1, тот запускает себя снова.
   Проверено 14.10.2026 (УчЛист, скоуп geo-2026-10-13): развернулось в **2332
   процесса** `gate-check.mjs`, пришлось убивать `pkill -9` руками. В списке
   N1 — только прямые листья.
7. **Таймаут тоже входит в привязку аппрува, и вложенный прогон ломает её.**
   Листья подтверждены при `--timeout 900`, N1 вкладывает `--timeout 1200` —
   вложенная проверка падает с `APPROVAL REQUIRED` по КАЖДОМУ гейту листа.

### Общий headless-браузер перехватывают другие сессии (12.10.2026, УчЛист)

### Ревьюиду стоит просить проверять честность тестов, а самому — сверять находки (12.10.2026)

### Перед слиянием открытого PR — ребейз на `origin/main`, он доказывает дубль (13.10.2026, nameone)

**Ситуация (разбор доски PR).** Иван попросил слить все открытые PR в main.
PR #17 «сбой доставки magic-link» висел с 2 октября, +50/−2, все проверки зелёные —
выглядел как безопасный кандидат на слияние. На деле это был **дубль**: тот же
фикс уже лежал в main как коммит `e0e8773 … (#22)`.

**Как применять.** Перед слиянием открытого PR делать ребейз его ветки на
`origin/main` (в одноразовом worktree, чтобы не трогать чужие ветки):

1. `git worktree add /tmp/prNN <branch>` → `git fetch origin main` →
   `git rebase origin/main`.
2. Git печатает `warning: skipped previously applied commit <sha>` —
   значит содержимое коммита **уже есть в main**, diff PR пустой.
3. Такой PR не сливают, а **закрывают как дубль** со ссылкой на уже
   влитый коммит: `gh pr close N --comment "…уже в main: <sha>"`.
4. Ветку вернуть на исходный коммит (`git branch -f <branch> <sha>`) и
   запушить обратно, иначе PR станет пустым.

**Почему дёшево и надёжно.** Rebase отбрасывает коммит на уровне патча
(cherry-pick), то есть сравнивает содержимое, а не SHA. Поэтому он ловит
и «слитый через другой PR», и «перенесённый руками в main», и ручной
`cherry-pick` — всё, что SHA-compare не видит. Занимает секунды.

**Чего не делать.** Не судить о PR по дате открытия и по зелёным галочкам:
11 дней «висения» в открытом виде — это признак забытого дубля, а не
свежести. Ориентир — содержимое, а не метаданные.

### `git push origin main` из worktree уходит вхолостую (nameone)

**Симптом.** Из worktree (например `/tmp/tz26-fix`, ветка
`fix/tz-26-broken-flows`) выполнено `git push origin main`. Команда вернула
код 0, вывод показал «PUSHED» — и я отчитался, что коммиты в `main`. Через
несколько часов проверка показала: четырёх последних коммитов в `main` нет,
ни как предков, ни как cherry-pick.

**Почему.** Локальная ветка `main` в worktree не обновляется при fetch и
остаётся на старом коммите (81dff79). `git push origin main` пушит ИМЕННО
этот локальный ref. Он либо уже совпадает с удалённым, либо уходит назад — в
обоих случаях код возврата 0. Команда не сравнивает ничего с тем, что я
собирался запушить.

**Как применять.** Пушить **транспортную ветку**, а не `main`:

```
git push -u origin fix/tz-26-broken-flows
gh pr create --base main --head fix/tz-26-broken-flows
gh pr merge <N> --squash
```

И после мержа **обязательно сверять содержимое**, а не код возврата:

```
git fetch origin main
git merge-base --is-ancestor <sha> origin/main   # мимо при squash!
git show origin/main:<path-to-file> | grep -c <признак>
```

`--is-ancestor` врёт на squash-мерже: сквош создаёт НОВЫЙ коммит
(например `305c212` вместо `6f45c9b`), и исходного sha в истории нет, хотя
изменения в main есть. Поэтому главная проверка — **признак в файле**,
например `git show origin/main:src/lib/constructor/quality-notice.ts | grep
-c repeatedSkills`.

**И не путать «пуш прошёл» с «работа в main».** Это разные утверждения, и
второе проверяется содержимым.

**Отдельно:** если main сильно разошёлся, мержить ветку нельзя —
конфликты десятков файлов. Правильный путь: `git checkout -b <имя>
origin/main`, затем `git cherry-pick` только своих последних коммитов. Так
дельта переносится на свежий main без переноса чужих старых версий файлов.

### Ветка «опережает main» после сквош-мерджа — проверять PR и содержимое, а не `git cherry` (nameone)

**Симптом.** Иван просит «залить в main то, что не залито».
`git rev-list --count origin/main..<branch>` показывает 16 коммитов, `git cherry`
помечает их как «+» (нет в main). Вывод кажется очевидным: ветка не влита,
надо мержить.

**Как оказалось.** Из 8 таких веток **семь уже были в main**:
- `fix/tz-26-broken-flows` — PR #48 смержен сквошем, доп. часть приехала через
  PR #50, пост-мержевый фикс линта — отдельным коммитом. Ветка отстаёт на 50
  коммитов, поэтому `merge-tree` показывал 6 «конфликтов», а
  `git diff origin/main..branch` — минус 42 000 строк.
- `brand/uchlist-rename` (PR #21), `perf/remove-suspense-gate-v2` (PR #20) — смержены.
- `ilushnikov-author-link` — ссылка уже была в `main` дословно (patch-id отличался
  из-за контекста, содержимое совпадало).
- `dependabot/.../docx-9.8.1` — версия в `main` уже та же.

**Почему.** Сквош-мерж создаёт новый коммит с новым patch-id. `git cherry` и
счётчик ahead сравнивают историю, а не результат. Ветка, отставшая на 50–169
коммитов, показывает «16 новых коммитов» и «десятки конфликтов», хотя её работа
давно в `main`. **Мержить такую ветку — откатить 169 чужих коммитов.**

**Как применять.** Перед выводом «работа не в main» — четыре проверки, по порядку:

1. `gh pr list --state all --head <branch>` — PR смержен? часто да, даже если ветка «ahead».
2. `git diff --shortstat origin/main..<branch>` — если минус десятки тысяч строк, это отставание,
   а не работа.
3. Точечная сверка: есть ли в `main` конкретный символ/файл из ветки
   (`git show origin/main:<file> | grep -c <признак>`).
4. `git cherry-pick <sha>` в чистую ветку и смотреть, не пустой ли коммит. Часто «новый»
   коммит оказывается пустым — работа уже в main.

**Правило от Ивана (15.10.2026):** «если локально есть что-то, что в main не кинули, или есть
PR/MR — их в main влить». Он хочет, чтобы работа не лежала на ветках неделями. Но вливать
надо **проверенное содержимое**, а не список веток: непрочитанная ветка старше main на 169
коммитов приносит откат, а не пользу.

**Что реально осталось потерянным в nameone 15.10.2026:** `fix/qr-form-review` — 1570 строк,
жила в ворктере `/Users/ivanlusnikov/Documents/nameone-qr-fix` неделю, ни одного PR.
Остальное — WIP-ветка `feat/tz-21-marketing-seo` (по собственному коммиту не готова),
