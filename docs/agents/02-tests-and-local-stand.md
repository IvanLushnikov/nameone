## Тесты и локальный стенд

### E2E-проверка Next.js через Playwright: ждать `load`, а не `domcontentloaded` (01.10.2026)

**Правило:** при `page.goto(..., { waitUntil: "domcontentloaded" })` Playwright успевает
кликнуть по серверному HTML раньше, чем React подвесит `onClick`. Клик визуально проходит,
обработчик молча не срабатывает — и вывод «фича сломана» ошибочен.

**Как правильно:** `waitUntil: "load"`, плюс у клиентской навигации закладывать таймаут
с запасом (в `next dev` на слабой машине загрузка чанка занимает минуты).

**Проверено 01.10.2026 в nameone:** два прогона подряд давали пустой `localStorage` и H1
страницы логина, хотя обработчик был корректен. Третий прогон с `waitUntil: "load"`
сразу показал запись профиля. Диагностика: логировать `localStorage` сразу после клика
и собирать `pageerror` — они показывают, что JS вообще не падал.

### vitest на nameone: 123 с против 1.19 с из-за одного флага окружения (02.10.2026)

Измерено 02.10.2026 на тесте из 5 кейсов, которые не трогают DOM
(читают файлы сборки):

| Запуск | Время |
|---|---|
| `npx vitest run tests/.../build-assets.test.ts` | **123.41 с** |
| `npx vitest run --environment node tests/.../build-assets.test.ts` | **1.19 с** |

Разница целиком в строке `setup`: 120.73 с против 297 мс. Тесты при этом
идентичны, файлы те же.

**Как распознать, что флаг забыт:** смотри строку `setup N ms` в выводе vitest.
Если она больше суммарной длительности самих тестов — окружение тяжелее работы
и почти наверняка можно переключиться на `node`.

Применять только к тестам, которым не нужен DOM (файлы, строки, парсеры,
проверка артефактов сборки). Тесты с рендером компонентов оставляем на jsdom.

### UI-проверку гонять только в одной команде с dev-сервером (02.10.2026)

**Правило:** `pkill -f "next"` в bash-команде убивает **сам шелл** —
у него в командной строке есть строка `next dev`, и `-f` матчит полную
командную строку. Симптом: команда «успешно» отрабатывает, но вывод
обрывается на середине, следующие шаги не выполняются. Убивать по PID
(`kill $SRV`) или по точным паттернам `next-server` / `next/dist/bin`.

**Почему сервер и проверку надо запускать вместе:** dev-сервер, поднятый
как `nohup … & disown` внутри фоновой задачи, умирает вместе с задачей —
процесс-родитель уносит всю группу. Три попытки подряд давали
`ERR_CONNECTION_REFUSED` на всех страницах при живом на вид логе.

**Рабочий рецепт (проверен, 369 + 57 проверок зелёные):**
```bash
cd /Users/ivanlusnikov/Documents/nameone
export PATH="/opt/homebrew/opt/node@22/bin:$PATH"
export NEXT_TELEMETRY_DISABLED=1
npx next dev -p 3114 > /tmp/dev.log 2>&1 &
SRV=$!
until grep -q "Ready in" /tmp/dev.log; do sleep 5; done
npx tsx scripts/verify-ui-dev.ts        --base=http://127.0.0.1:3114
npx tsx scripts/verify-artifacts-ui.ts  --base=http://127.0.0.1:3114
kill $SRV
```

**Каскад 404 ≠ сломались данные.** Если в UI-проверке первый запрос даёт 500,
а дальше идут подряд 404 — упал dev-сервер. Проверять
`npx tsx scripts/check-taxonomy.ts`: аудит чистый = дело в сервере.
На этом я почти объявил регрессию в английском 10 классе, хотя данные были целы.

**Ещё:** `.next` в состоянии 0 байт (после убитых сборок) вешает dev-сервер
на `✓ Starting...` навсегда. Лечится удалением `.next` — тогда Ready за ~800 мс.
И на загруженной машине (opencode жрёт CPU) `verify-artifacts-ui.ts` не успевает —
есть флаг `--only=N`.

### Не запускать 4+ воркеров, каждый из которых гоняет tsc/vitest одновременно (02.10.2026)

**Правило:** на nameone (MacBook Air M2, троттлит) 4 параллельных воркера,
каждый из которых запускает `tsc --noEmit` и `vitest`, дают load average 15–19
и 40+ процессов. `vitest` виснет на старте (пустой вывод, только `RUN v3.2.7`),
`tsc` идёт 5+ минут. Воркеры тратят по 3–4 попытки на одну проверку и
в итоге не получают результата.

**Как правильно:**
- Воркерам в брифе явно писать: «НЕ запускай vitest / tsc / build.
  Проверки прогоняет оркестратор после завершения всех воркеров».
- Оркестратору — проверять факт через `npx tsx` с одноразовым скриптом в `/tmp`,
  а не через vitest. Это занимает секунды и не требует пула воркеров:
  импорт мока напрямую, проверка инвариантов, `console.log` результата.
- `tsc` и `vitest` — строго последовательно, одно с другим, не параллельно.
- Для тестов, которым не нужен DOM, помогает `--environment node`.
- В tsx-скрипте нельзя top-level `await` — формат cjs, оборачивай в `main().then()`.

**Проверено 02.10.2026 на nameone:** 4 воркера (Карточки, Материалы, Банк
материалов, Фото-по vision) — ни один не смог прогнать тесты; все честно
отчитались «не выполнено». После команды «только код» все закончили за
15 минут. Оркестратор проверил их работу через tsx.

**Побочный урок — про тестовые данные:** проверяя чужой код, сначала
убедись, что слага тем, которые ты передаёшь в мок, реально существуют
в таксономии. В `Grade` поле называется `num`, не `grade`. Прежде чем писать
«у воркера баг, возвращается 0 элементов», проверь на настоящем слаге
из `getGrade(subject, num).topics[].slug`. Мои выдуманные слаги дали ложную
диагностику «моки сломаны», хотя на настоящих слагах всё работает верно.

### Делегация воркерам: файлы, не попавшие ни в чей список, молча остаются без правок (01.10.2026)

Правило (проверено 01.10.2026 на nameone, 6 воркеров, ~40 правок).

При разбиении задачи на N воркеров по непересекающимся файлам обязательно
**сверь список затронутых файлов плана с фактическим `git status` после**:
всё, что есть в плане, но не попало ни в один список воркеров, не будет
сделано вообще — и никто об этом не сообщит, потому что каждый воркер честно
отчитается о СВОИХ пунктах.

**Как поймать:** после волны — `git status --short` + сверка с разделом
«Затронутые файлы» плана. Дешевле, чем отправлять фидбек-цикл заново.

**Почему так выходит:** оркестратор раздаёт работу по «горячим» файлам и
забывает про файлы, которые в плане есть, но не попали ни в один список.
На nameone так потерялась правка `PresetGrid.tsx:319` («домашка» в тексте
пресета) — единственный пункт жалобы, который не закрылся.

**Второй класс пропуска — отклонения «по нельзя трогать»:** воркер честно
пишет «файл принадлежит параллельному агенту, не стал менять». Такие пункты
надо вычитывать отдельно и закрывать самому, когда параллельная работа
успокоится.

### Тест-канарейка на текущий баг надо переводить в тест на исправленное состояние (nameone)

Когда тест вскрывает баг, но сформулирован как «зафиксировать текущее
сломанное поведение» (канарейка), он **упадёт сразу после починки** — и
будет выглядеть как регрессия. Ловит в тупик.

Правильный переход: переписать в форму «проверяю, что поведение ИСПРАВЛЕНО».
Канарейка — не результат, а способ обнаружения; результат — регрессионный
тест на новую правдину.

На nameone так было с тостами: тест утверждал, что `<Toaster />` стоит
соседом с `<main>` (т.е. фиксировал баг). После починки упал — и это был
правильный сигнал, а не сломанный тест.

### Перед тем как отчитаться «всё готово» — сверь критерии плана с кодом сам (02.10.2026)

Даже при зелёных тестах и честных отчётах воркеров остаются пропуски. Проверка
`grep`/`sed` по самому плану ловила: забытое слово «домашка», захардкоженные
цены мимо `plans.ts`, ложные срабатывания при grep по подстрокам
(«постиндустриальное» содержит «триал» — проверять надо по границам слова).

Дешёвые команды, которые стоит прогнать перед «готово»:
`grep -rn` по запрещённым словам из плана, сверка `git status` со списком
затронутых файлов, независимый прогон ключевой логики через `npx tsx` с
однострочным скриптом в `/tmp` (не создавая файлов в репозитории).

**Самое частое место, где правка «уже есть», — а в другом файле та же ошибка
живёт:** проверять только файлы, которые отдавал воркерам, недостаточно.
На nameone критерий «правильные окончания» был закрыт в `Stats.tsx`, а через
два шага верификатор нашёл «21 предметов» в SEO-заголовке и description новой
страницы `/subject` и в `Subjects.tsx`, который вообще никому не достался.
**Ищи по всему `src/`, а не по списку файлов плана.** Особенно:
title/description/OG-строки (в ту самую ошибку уезжает SEO),
страницы, созданные «по пути», и любые файлы вне первоначального разбиения.

И второе: тест, который ищет плохое слово регуляркой по исходнику, сначала
съест **аргументы самого исправляющего вызова** (`plural(21, "предмет",
"предмета", "предметов")` содержит «предметов»). Вырецай вызовы `plural(...)`
целиком перед проверкой, иначе тест валится на правильном коде.

**И третье, самое коварное: `\b` в JavaScript — это ASCII-граница слова.**
`\bДомашка\b` и `/\bтем\b/` **никогда не сматчатся**, потому что кириллица не
входит в `\w`. Тест с таким паттерном всегда зелёный и не защищает ничего,
при этом выглядит строгим. Для русских слов используй явные границы:
`(?<![а-яёa-z])Домашка(?![а-яёa-z])` и `(?![а-яёa-z])` для конца слова.

**Обязательная самопроверка теста-ищейки.** К отрицательным
`expect(...).not.toMatch` добавляй позитивный блок с заведомо плохим кодом и
убеждайся, что паттерн его ловит. Иначе получаешь «вакуумный» тест: 100%
зелёный, нулевой ценности. Так поймали «21 предметов» в SEO-строках и
«Домашка» в DOCX-генераторе.

### Регулярки по русскому тексту в проверках — две ловушки (13.10.2026)

Проверочные скрипты по русским текстам дважды обманули на проекте УчЛист,
и обе ошибки выглядели как «мой контент неправильный», а на самом деле был неправ мой чекер.

**1. `\w` и `\b` в JS не матчат кириллицу.** `\w` = `[A-Za-z0-9_]`. Регулярка
`/коммерческ\w*\s+лицензи/i` не нашла «коммерческую лицензию» в файле, который её
содержит. Нужен явный класс: `[а-яё]*`.

**2. Голое вхождение цифры — не проверка факта.** Проверка «опубликована ли цена
3000 ₽ тарифа Школа» искала просто `3000` и срабатывала на «до 3000 рабочих
листов» — это норма другого тарифа. Нужно привязываться к смыслу: цена = число
рядом со знаком валюты (`/3000\s*(?:₽|руб)/`), а не просто число.

**Как применять.** Пишу проверку по русскому тексту — сперва прогоняю её на
известном подходящем куске текста и убеждаюсь, что она его НАХОДИТ (и на
заведомо неподходящем, что не находит). Иначе «0 найдено» неотличимо от «совпало
не там». Тот же приём, что с негативным контролем гейта: отсутствие сигнала надо
подтверждать положительным примером.

### В пуле vitest-workers нет `process.env` — окружение живёт в биндингах (nameone)

В backend УчЛиста тесты идут под `@cloudflare/vitest-pool-workers`.
**`process.env` там пуст** — не «почти пуст», а именно недоступен: ни
`process.env.POLZA_API_KEY`, ни любой флаг из командной строки.

Это стоило трёх отдельных поломок за один день, и все три выглядели одинаково
молча:

1. Ключ провайдера читался из `process.env` — тест «проходил», но реальной
   генерации не было.
2. Флаг новой стадии `PLAN=1` в командной строке — стадия не включалась, лог
   врал «stage disabled».
3. Фильтр подмножества листов `LIVE_ONLY` — прогонял все шесть листов вместо
   одного, и на почти пустом балансе это съедало деньги до того, как
   становилось заметно.

**Как применять.** Всё, что должно попасть в код под воркером, читать из:

- объекта `env`, который приходит аргументом в `generateWorksheet(args, env, db)`;
- либо `import { env } from "cloudflare:test"` в тестах.

Значение для `.dev.vars` пишем **без кавычек**: `PLAN=1`. С кавычками
приходит строка `"1"` вместо `"1"` — и сравнение молча даёт «выключено».

**Отдельное правило для тестов:** окружение собирать разворотом всего
объекта, а не перечислением полей:

```ts
const FAKE_ENV = { ...(workerEnv as unknown as Record<string, unknown>), /* … */ } as unknown as Env;
```

Перечисление полей — это то место, где забывается ключ, и ошибка выглядит как
«стадия не работает», хотя не работает совсем другое.

**И проверяй, что фильтр сработал, а не что он есть.** Прогон должен
стартовать один тест вместо шести; если стартуют шесть — значение не дошло.

### Бэкенд-тесты УчЛиста падают с EADDRNOTAVAIL при многих параллельных сессиях (14.10.2026)

`npm test` в `backend` (пул `@cloudflare/vitest-pool-workers`) может падать с:

```
TypeError: fetch failed
Caused by: Error: connect EADDRNOTAVAIL 127.0.0.1:64212 - Local (0.0.0.0:0)
error during close MiniflareCoreError [ERR_RUNTIME_FAILURE]: The Workers runtime failed to start
```

Прогон обрывается после ~25 файлов из 49. **Проваленных утверждений при этом
ноль** — падает запуск рантайма, а не тесты.

Это происходит при нескольких параллельных агентских сессиях в одной
рабочей папке: каждая держит `next dev` и фоновые задачи. 14.10.2026
диагностика показала 16 258 сокетов в TIME_WAIT и несколько `next dev`
(`--port 4317`, `-p 3123`, `-p 8799`) от разных сессий.

**Как отличить «сломал я» от «сломалась среда»:** прогнать ТОТ ЖЕ пайплайн
на чистом `main`. Если падает так же — среда, а не код.

**Что НЕ помогает:** чистка `node_modules/.mf` и `.vite`, убийство
`workerd`/`miniflare`. Дренирование TIME_WAIT (16 258 → 445 за 2 минуты)
тоже не вернуло сокет.

**Что применять:** не чинить код по этому симптому и не объявлять «у меня всё
зелёное». Запускать таргетные тесты по своим файлам (они проходят) и писать
в отчёте ровно: полный бэкенд-прогон в этой среде не завершается, падает
рантайм, на чистом main — так же.

**Не убивать чужие процессы.** `next dev` и фоновые задачи других сессий —
их работа; `pkill -f next` здесь ломает чужое.
