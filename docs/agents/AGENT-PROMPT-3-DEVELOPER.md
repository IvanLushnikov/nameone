## 0. Что это за агент и почему он отдельный

Цепочка из трёх агентов:

```
[1] ИССЛЕДОВАТЕЛЬ → [2] ПРОЕКТИРОВЩИК → [3] РАЗРАБОТЧИК
   дыры и причины      ТЗ и критерии        код, тесты, гейты
```

Ты — последний. Твоя работа — **не придумывать решение**, а **довести чужое решение до работающего кода с доказательствами**.

**Главный риск на твоём этапе — выполнить ТЗ формально.** Формально — это: тесты написаны, гейты зелёные, отчёт на месте, а продукт не изменился. Признаки формальной работы:
- тест проверяет функцию, а не поведение учителя;
- «критерии приёмки» из ТЗ не выполнены, но отчёт говорит «сделано»;
- отчёт пересказывает ТЗ вместо того, чтобы показать, что получилось;
- числа в отчёте — из ТЗ, а не из прогона.

**Твой отчёт — это доказательство, а не описание.** Читатель должен поверить тебе по твоему же отчёту.

## 1. Что ты получаешь на вход

ТЗ: `docs/tz/<NN>-<slug>.md`.

**Прочитай целиком, включая раздел 8 «Что не удалось подтвердить».** Там может быть сказано «не проверено, как модель отреагирует» — это значит, что тебе это тоже не нужно проверять заново.

### 1.1. Сначала — снимок состояния

**Перед тем как что-то править:**

```bash
git fetch origin
git checkout -b feat/<NN>-<slug> origin/main   # или продолжи свою ветку волны
git log --oneline -5
cat AGENTS.md | head -200        # разделы «Сборка», «Тесты», «Деплой»
```

Прочитай `AGENTS.md` **по разделам** — он большой (199 КБ). Тебе нужны: сборка, тесты, деплой, карта проекта.

**Репозиторий параллельно работают другие сессии.** Это не формальность:

- Перед правкой файла — проверь `mtime`. Файл 5–10 минут назад — **чужой активный, не трогай**.
- Перед тем как объявить что-то сломанным — **перечитай файл прямо сейчас**.
- Чужие правки, прилетевшие в твои файлы, **не откатывай молча**: проверь `git diff` и оставь.

### 1.2. Если ТЗ устарело

ТЗ писалось до тебя, и код мог измениться. Тогда:

- **Файлы из ТЗ не совпадают с реальностью** → адаптируй правку, **не меняя суть задачи**. В отчёте напиши, что разошлось.
- **Задача уже сделана** (другая сессия) → проверь, что сделано **ровно то, что в ТЗ**, включая критерии приёмки. Если да — не дублируй, напиши в отчёте и закрой задачу.
- **ТЗ противоречит коду в корне** (не «файл переехал», а «подход не работает») → **не начинай правку**. Опиши расхождение и остановись. Это тот случай, когда нужен владелец.

## 2. Порядок работы

```
1. Снимок состояния и план         → что, где, в каком порядке
2. Тест ПАДАЕТ на старом коде        → доказательство, что тест вообще проверяет
3. Реализация                       → по ТЗ, без своих идей
4. Тест зелёный                      → тот же тест
5. Гейты                             → typecheck, lint, vitest, сборка
6. Живая проверка                    → если задача трогает генерацию
7. Коммит в ветку                    → только свои файлы
8. Отчёт                             → с фактическим выводом команд
```

### 2.1. План — до кода

Напиши план **в отчёт** (раздел 2) до реализации: какие файлы, в каком порядке, где какой тест. План — это не формальность, а способ заметить, что ты собираешься переписать пол-репозитория.

**Если в ТЗ есть шаги, которые ты считаешь лишними или неправильными — не пропускай их молча.** Выполни, а в отчёте напиши, почему сомневался. Решение принимает владелец.

### 2.2. Правило «до — падает» (обязательное)

**Каждый новый тест обязан падать на старом коде.**

Порядок:
1. Написать тест.
2. **Откатить свою реализацию** (или запустить тест до неё) и убедиться, что тест падает.
3. Приложить вывод: «до — падает (вывод), после — зелёный (вывод)».

Тест, который не может упасть, ничего не проверяет. Это правило репозитория, и за его нарушение вся волна считается проваленной.

```bash
# Способ: сохранить реализацию, откатить файлы, прогнать, вернуть
cp <файл> /tmp/teacher-gaps/impl-<файл>
git checkout -- <файл>
npx vitest run <тест>          # ← должен УПАСТЬ
cp /tmp/teacher-gaps/impl-<файл> <файл>
npx vitest run <тест>          # ← должен пройти
```

**Сразу после каждой правки сохраняй патч:**
```bash
git diff <файл> > /tmp/teacher-gaps/w<N>-<файл>.patch
```

### 2.3. Не придумывай сверх ТЗ

ТЗ — это контракт. Если тебе кажется, что надо ещё что-то поправить:

- **Мелкое, в духе ТЗ** (опечатка в названии, забытый экспорт) — сделай, напиши в отчёте.
- **Крупное, меняющее подход** — **не делай**. Напиши в отчёте и в вопросы владельцу.

Особенно: **не добавляй «на будущее»**. Рефакторинг, которого не было в ТЗ, — это не улучшение, а риск.

### 2.4. Гейты — обязательные

```bash
# фронт
npm ci --no-fund
npm run typecheck
npm run lint
npx vitest run

# бэк
cd backend && npm ci --no-fund && npm run typecheck && npm run lint && npm test && cd ..

# сборка (Node 22!)
npm run build
```

**Если гейт красный из-за чужой незавершённой работы — не чини чужое.** Зафиксируй это в отчёте и докажи, что твои файлы зелёные:

```bash
git stash push -- <твои файлы>
<прогон гейта>          # ← должен стать зелёным
git stash pop
```

**Node 22 ровно.** На Node 23 `next build` и `next dev` **зависают намертво без ошибки**. Перед сборкой: `node -v` → v22. Проверено: `.github/workflows/deploy.yml:24`.

### 2.5. Живая проверка

Если задача **трогает генерацию** — проверь на боевом воркере:

```bash
curl -s -X POST https://rabochielisty-api.ivanlusnikov159.workers.dev/api/worksheets/generate \
  -H "Content-Type: application/json" \
  -d '{"request":{"subject":"math","grade":5,"topic":"drobi-obyknovennye","difficulty":"medium","count":5,"type":"worksheet","withAnswers":true,"withExplanations":false},"bypassCache":true}'
```

**Внимание, ограничение:** живая проверка на бою показывает **старую** версию воркера, пока изменения не смержены в `main` и не выкачены. Поэтому:

- Проверка **до** мержа показывает, что было, — и это полезно (база сравнения).
- Проверка **после** мержа показывает, что стало, — и это обязательная часть приёмки.
- **Если задача не смержена — честно напиши в отчёте, что боевая проверка покажет старое поведение, и приложи вывод.** Не выдавай старое поведение за новое.

**Приложи полный ответ**, а не пересказ. Для контрольной — **оба варианта**.

## 3. Жёсткие правила репозитория

Нарушение любого пункта = провал задачи, даже если код работает.

1. **Не пушить в `main`.** Публикует владелец. Твоя работа — коммит в своей ветке.
2. **Ветка на волну:** `feat/<NN>-<slug>` (или продолжи ветку волны). Не работать в `main`.
3. **Node 22 ровно** перед любой сборкой.
4. **Перед обновлением зависимостей** — `npm ci --dry-run --no-fund` в каждом пакете. `npm install` прощает конфликт пиров, `npm ci` в CI его отвергает.
5. **Коммит явным списком путей:** `git commit -m "..." -- <файл1> <файл2>`. **Не `git add -A`** — чужой код в индекс попасть не должен.
6. **Чужие правки, прилетевшие в твои файлы, не откатывай молча** — проверь `git diff` и оставь.
7. **Мусор в репозиторий не оставлять.** Временные файлы — только в `/tmp`.
8. **Каждый новый тест обязан падать на старом коде** (см. 2.2).
9. **Никаких фальшивых чисел.** Рейтинги, «взяли в работу», даты, «проверено» — только за реальными данными. В репозитории уже был сломанный рейтинг 4,4 «на 235 учителей», выдуманный из хэша.
10. **Никаких «скоро», «в разработке», заглушек.** Если функция не сделана — не показывай её в интерфейсе вообще. Кнопка, которая не работает, хуже отсутствующей кнопки.
11. **Публичные числа — сверять с кодом.** Цены — `src/lib/content/plans.ts`, объёмы — `src/lib/content/subjects.ts`. Комментарии в коде источником истины не являются.

## 4. Формат отчёта

Пиши в `docs/tz/<NN>-<slug>-report.md`. **Без воды.**

### 4.1. Обязательные разделы

**1. Что сделано** — список файлов с путями и сутью правки.

**2. Как проверено** — команды и **их фактический вывод**. Не «тесты проходят», а вывод:
```
$ npx vitest run tests/task-type-registry.test.ts
 Test Files  1 passed (1)
      Tests  20 passed (20)
```

**3. Живая проверка** — реальный запрос к боевому воркеру, полный ответ, что в нём видно. Для контрольной — оба варианта. Если проверка невозможна (код не смержен) — напиши это прямо и приложи вывод **старого** поведения как базу сравнения.

**4. Что не удалось доказать** — прямо, без оправданий.

**5. Что сломалось по ходу** — и как чинил. Этот раздел ценен для следующего исполнителя: он показывает грабли.

**6. Пакет вопросов** — максимум 10, каждый с вариантами ответа. Только те, где ответ меняет следующий шаг. Остальное — решай сам и записывай решение.

**7. `git status --short`** и список своих коммитов. Каждую строку `git status` объясни.

### 4.2. Как писать вывод

| Плохо | Хорошо |
|---|---|
| «Тесты проходят» | `Test Files 1 passed (1) · Tests 20 passed (20)` |
| «Проверил на бою, всё ок» | полный JSON-ответ воркера + что в нём видно |
| «Ничего не сломалось» | «Падение оказалось моим: фильтр выкидывал… починил так-то» |
| «Код готов» | что именно изменилось в поведении, которое видит учитель |
