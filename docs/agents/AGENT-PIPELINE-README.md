# Три агента для УчЛиста: исследователь → проектировщик → разработчик

**Дата:** 29 октября 2026
**Зачем:** один большой агент-промт («сделай волну 1») даёт две беды — либо агент расползается по всем задачам сразу, либо делает формально. Разделение на три роли с разными артефактами на выходе убирает обе.

---

## Файлы

| Файл | Роль | Что сдаёт | Что НЕ делает |
|---|---|---|---|
| `AGENT-PROMPT-1-RESEARCHER.md` | Исследователь | `docs/research/<NN>-<slug>.md` — дыры, причины, способы правки | Не пишет код, не проектирует |
| `AGENT-PROMPT-2-DESIGNER.md` | Проектировщик | `docs/tz/<NN>-<slug>.md` + `<NN>-<wave>-overview.md` | Не пишет код, не исследует заново |
| `AGENT-PROMPT-3-DEVELOPER.md` | Разработчик | Код + `docs/tz/<NN>-<slug>-report.md` | Не исследует, не проектирует |

---

## Как запускать

### Шаг 1. Исследователь

Скопируй `AGENT-PROMPT-1-RESEARCHER.md` в агента с правом на файлы и Bash. Дай ему тему:

```
Исследуй: <что именно>. Область — то, что учитель видит и чем пользуется
каждый день. Найди дыры, причины и способы правки.
```

**Ждёшь:** файл в `docs/research/` и выжимку в чат.

### Шаг 2. Проектировщик

Скопируй `AGENT-PROMPT-2-DESIGNER.md` в **свежую** сессию (важно: чистый контекст — проектировщик не должен тащить догадки исследователя, он должен проверять по коду сам).

```
Спроектируй задачи по исследованию docs/research/<NN>-<slug>.md.
```

**Ждёшь:** файлы ТЗ + обзорный файл волны.

### Шаг 3. Разработчик

Скопируй `AGENT-PROMPT-3-DEVELOPER.md` в **свежую** сессию на каждую задачу.

```
Выполни задачу из docs/tz/<NN>-<slug>.md.
```

**Ждёшь:** коммит в ветку + отчёт + выжимку.

**Одна сессия = одна задача.** Не три задачи в одну сессию: контекст забивается, гейты начинают падать по таймауту, качество падает на третьей задаче.

---

## Контракт между агентами

Это то, что держит цепочку. Нарушение контракта ломает связку тихо — не сразу.

```
ИССЛЕДОВАТЕЛЬ                    ПРОЕКТИРОВЩИК                  РАЗРАБОТЧИК
docs/research/<NN>-<slug>.md  →  docs/tz/<NN>-<slug>.md      →  код + отчёт
                                 docs/tz/<NN>-<wave>-overview.md
```

**Что обещает каждый на выходе:**

| Артефакт | Обязательные поля | Что проверяет получатель |
|---|---|---|
| Исследование | «Что уже работает», находки (причина с `файл:строка`, способ правки, цена ошибки), улучшения, «что осталось неясным» | Воспроизводимость и причину |
| ТЗ | Контекст, «что уже работает», техдизайн (список файлов), решения AD-N с рационализацией, критерии приёмки, «чего не делаем», риски, «что не удалось подтвердить» | Полноту и выполнимость |
| Отчёт | Файлы, **фактический вывод команд**, живая проверка, «что не удалось доказать», «что сломалось по ходу», вопросы, `git status` | Достоверность |

**Три правила, которые нельзя нарушать:**

1. **Исследование → ТЗ:** проектировщик **перепроверяет** находку по коду. Находка может быть уже исправлена другой сессией — это нормальный исход, а не ошибка.
2. **ТЗ → код:** разработчик **не придумывает сверх ТЗ**. Крупное расхождение — остановиться и спросить, а не додумать.
3. **Код → отчёт:** отчёт — **доказательство**. Читатель должен поверить по отчёту, а не по словам.

---

## Почему так, а не иначе

**Почему не один агент на всё.** В ТЗ-33 (первая волна) один агент работал над тремя слоями сразу — исследование, проектирование и реализация — и результат оказался таким: часть задач сделана формально, а часть выводов в отчёте не подтверждалась кодом. Разделение заставляет каждую находку пройти через три фильтра: воспроизведение → техническое решение → доказательство.

**Почему исследователь не пишет код.** У агента, который правит, появляется соблазн чинить то, что он уже видит, вместо того чтобы искать остальное. Исследователь без права редактировать читает код иначе.

**Почему проектировщик не пишет код.** ТЗ — единственное место, где формулируется «как именно». Если решение пишет тот же агент, что и код, ТЗ превращается в пересказ сделанного, а не в контракт.

**Почему каждая задача — отдельная сессия.** Контекст — расходуемый ресурс. К третьей задаче в той же сессии агент уже держит в голове две чужих архитектуры, начинает «проводить рефакторинг на будущее» и гейты падают по таймауту.

## Что менять под себя

| Место | Что там | Как менять |
|---|---|---|
| Раздел «Памятка о продукте» в каждом промте | Факты о продукте (числа, модели, тарифы) | **Обновляй после каждой волны** — иначе агенты опираются на устаревшее. Это единственная часть, которая протухает |
| Раздел 9 «Известные незакрытые обещания» | Что обещано, но не сделано | Убирай закрытое, добавляй новое |
| Раздел «Что делать нельзя» (разработчик) | Запреты подхода | Добавляй запреты, когда агент нарушил что-то и это было дорого |
| «Что сдаёшь» | Формат выжимки | Подстрой под себя — но **длина выжимки** должна остаться маленькой. Выжимка, которая пересказывает отчёт, не нужна: отчёт и так в репозитории |

**Чего менять не стоит:** правила репозитория (не пушить в `main`, Node 22, явные пути в коммите, «до — падает»), формат ТЗ и отчёта, запреты на подход. Они проверены на реальной ошибке — их ломали, и это стоило денег.

## Известные ограничения связки

1. **Исследователь не видит прода.** Он смотрит в код и в прод-базу, но не знает, что учитель на самом деле открывает второй раз. Это ограничение лечится данными, а не агентом: нужна статистика повторных открытий.
2. **Три агента — три контекста.** Если второй агент не перепроверяет находку, ошибка исследователя проходит дальше как аксиома. Поэтому в промте проектировщика перепроверка — обязательный шаг, а не рекомендация.
3. **Живая проверка требует мержа.** Разработчик не может проверить на бою то, что ещё не выкачено. ТЗ-33 это ограничение проявило: гейт «живая проверка» выполнить в рамках сессии нельзя, и в отчёте это зафиксировано честно.
4. **Цепочка не заменяет решение владельца.** Разработчик получает «а или б» там, где цена ошибки высока. Это не дефект промта, а задуманное поведение.
