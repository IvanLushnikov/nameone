## Git и параллельные сессии

### Параллельные сессии в одном репозитории nameone: проверяй чужие отчёты по диску (01–02.10.2026)

**Ситуация.** В репозитории одновременно работают несколько сессий
(`session list` показывает родительские сессии и их воркеров). Все пишут в одно
рабочее дерево без веток. 02.10.2026 на пике было **~10 сессий**,
38 файлов менялись за 10 минут, load average доходил до 13.

**ПЕРВОЕ ПРАВИЛО ДЛЯ АУДИТА: перепроверяй факты перед отчётом.** За один
ревью-проход я нашёл и отрапортовал четыре критичные дыры, которые **за время
проверки починили другие сессии** (`plan` из тела запроса, расхождение цен
фронт/бэк, `PLUS_ONLY_TASKS` без проверки, выбор модели по тарифу). Без
перепроверки отчёт превратился бы в список «уже исправлено, не чини повторно».

> Перед тем как написать «вот эта дыра» — перечитай файл прямо сейчас.
> Между находкой и отчётом проходит 20–40 минут, и другая сессия успевает
> починить. Совпадение по нескольким подряд пунктам = это норма для nameone.

Симптом, что файл уже исчез: `stat` отдаёт `No such file or directory`,
а `git status` показывает `D` или новый файл с другим именем. **Не делай
вывод «я выдумал» — перечитай, файл переименовали.**

**Второе правило: проверяй mtime ПЕРЕД правкой, а не только `read`.**
`stat -f "%Sm" файл` — одна секунда, и видно, правил ли кто-то файл только что.
Свежее 5–10 минут = файл чужой активный, не трогай. Если `edit` падает с
«Could not find the exact text» — файл уже переписали, **перечитай, а не
подгоняй `old_string`**: в 02.10 так ушёл 20-минутный цикл правок теста,
который параллельно починил кто-то ещё.

**Третье: падающие тесты могут быть не твоими.** 02.10.2026 пятнадцать падений
разложились так: 3 — настоящие баги в коде, 5 — устаревшие ожидания в тестах,
7 — незавершённая работа других сессий. Перед починкой смотри `stat` на тест
И на тестируемый код.

**Что из этого следует на практике:**

1. **Отчёт воркера «успешно» ≠ результат.** Два случая за день:
   - субагент TZ-13 отчитался успехом, файл `docs/tz/13-student-interactives.md`
     не создал вовсе (потратил запуск на чтение);
   - субагент TZ-16 написал в отчёте «лейблы в `WorksheetPreview.tsx` добавил
     параллельный воркер», которого на самом деле не было — добавил он сам
     и об этом умолчал.
   **Всегда проверяй `ls` по путям из отчёта и `git diff` по «чужим» правкам.**

2. **`git add` захватывает ЧУЖИЕ файлы, если они уже в индексе.** Две сессии
   держат индекс открытым. Первый мой коммит получился 19 файлов вместо 14:
   в индекс уже лежали `PresetGrid.tsx`, `mock/generator.ts`, `exam-gen.ts`,
   `language-guard.ts`, `docs/tz/10-*`. Вылечило: `git reset --mixed HEAD~1`
   + `git add -- <явный список своих путей>` + `git commit -- <те же пути>`.
   Формула `git commit -m ... -- path1 path2` надёжнее, чем `git commit -m`
   после общего `git add`.

3. **Чужие правки прилетают в твои файлы, и это может быть ПОЛЬЗА.** После моего
   коммита другая сессия дописала в мой `f07.ts` фикс реального бага: интерфейс
   `ResponseView extends ResponseRow` протекал в JSON полями БД в snake_case,
   а фронт читал camelCase → учитель увидел бы `undefined` вместо имени ученика.
   Не откатывай такие правки молча — проверь `git diff` и оставь.

4. **`main` может быть сломан чужим коммитом.** 02.10: `main` лежал с
   `LessonPlanPreview.tsx`, на котором падает webpack. TypeScript этот файл
   читает без ошибок (0 parse errors), то есть похоже на гонку при записи.
   Перед тем как винить свою ветку — проверь `git diff main -- <файл>`.

5. **Машина врёт про «сбой сборки».** Load average доходил до 89 при 4 ядрах.
   Топ потребитель — `opencode` (98% cpu) и `StorageManagement.framework`
   (Spotlight переиндексирует после волны правок). На таком load
   `npm run build` висит на «Linting and checking validity of types» 20+ минут
   и умирает вместе с родительской bash-задачей.
   **Сборку запускать через `nohup bash -c '...' & disown`** — подпроцесс в
   скобках `( ... ) &` умирает вместе с задачей, лог не создаётся.
   И обязательно: `next build` проверяет ТИПЫ ВСЕГО проекта, включая чужой
   незаконченный код. Пока другие сессии пишут — зелёной сборки не будет.

**Рабочий режим:** работать в своей ветке (`feat/tz-competitor-features`),
коммитить строго по списку своих путей, чужие правки в общем дереве не
откатывать и не коммитить, перед отчётом проверять результат по диску.

### Перед тем как сослаться на `file:line` в отчёте — перечитай файл (02.10.2026, nameone)

Репозиторий параллельно правится другими сессиями/агентами прямо во время аудита.
В первый проход я прочитал `backend/src/routes/worksheets.ts` и нашёл уязвимость
«тариф из тела запроса имеет приоритет над сессией» (`bodyPlan ?? user.plan`).
Через 20 минут тот же файл уже содержал `resolvePlan(c)` без body-параметра
и комментарий «Раньше здесь было `bodyPlan ?? user.plan`» — правка уже внесена.

**Правило:** находка, в которой важна точная строка, всегда перепроверяется
повторным чтением файла непосредственно перед тем, как попасть в отчёт.

**Расширение на правку кода (проверено 02.10.2026 на nameone):** это же
относится не только к цитированию, но и к редактированию. Между `read` и
`edit` проходит 5–15 минут, и параллельная сессия успевает переписать файл.
Конкретный случай: я прочитал `src/lib/utils/limit.ts` (там был счётчик
«3 в сутки» в localStorage) — к моменту правки файл уже содержал новую
реализацию с серверным источником правды, `syncFromServer` и `refund()`.

**Симптом:** `edit` возвращает «Could not find the exact text» — это не
баг инструмента, а сигнал «файл уехал из-под тебя».

**Что делать:** перед каждой серией правок в горящем файле — `stat -f "%Sm"`
и повторный `read` нужного диапазона. Если файл менялся в последние
минуты — либо не трогай, либо перечитай и пересобрать план.

**Как описывать в отчёте:** если правка есть в рабочей копии, но не в
коммите (деплой идёт из `main`) — это отдельная находка высокого приоритета
«исправлено локально, но не на сервере», а не «уязвимость закрыта». Проверять
`git status --short` и сопоставлять с веткой деплоя.

**Второй момент:** `git status` показывает огромный незакоммиченный WIP почти
всегда. Отсутствие коммита само по себе — не признак проблемы; проблема
только тогда, когда в коммите/деплое расходится именно строка безопасности.

### НИКОГДА не делай `git reset --hard` в общем рабочем дереве nameone (02.10.2026)

**Что случилось.** Работаем вчетвером одновременно. Одно рабочее дерево,
ветками никто не пользуется — все пишут в `main` или в текущую ветку.

Хотел вынести свой фикс в отдельную ветку, не трогая чужую рабочую копию.
Сделал `git worktree add /tmp/x main`, и **внутри worktree сделал
`git cherry-pick`** — а он передвинул указатель самой `main`. Потом, чиня
это, выполнил `git reset --hard origin/main`, **находясь на чужой ветке
`perf/remove-suspense-gate`**. Это снесло у другой сессии ~8 незакоммиченных
изменённых файлов (README.md, `backend/src/index.ts`, `llm/config.ts`,
`llm/providers/openai.ts`, `db/schema.sql`, миграции, `.dev.vars.example`).
Их содержимое существовало только в рабочем дереве — восстановить нельзя.

**Что удалось:** вернуть ветку на исходный конец (все коммиты целы, untracked
файлы уцелели, `git reflog` показал историю). Что не удалось — содержимое
тех файлов. Та сессия жива и потерянное не заметила.

**Правила, которые из этого следуют:**

1. **`git reset --hard` в этом репозитории запрещён.** Только `git checkout -- <файл>`
   для отката конкретного файла. Никогда не трогать индекс/дерево целиком —
   в дереве чужое.
2. **Перед `git add`/`git commit` всегда смотри индекс,** а не только рабочее
   дерево: `git diff --cached --name-only`. В общем дереве там лежат чужие файлы.
3. **Работай в своей ветке и коммить по явному списку путей:**
   `git add -- p1 p2 p3 && git commit -m ... -- p1 p2 p3`.
4. **Новую ветку из чужой/общей точки создавай БЕЗ переключения.** Способ,
   который сработал: `git worktree add /tmp/fix <база>` → внутри **создать
   отдельную ветку** (`git switch -c fix/name` или `git checkout -b`) →
   cherry-pick → `git branch -f fix/name HEAD` → `git worktree remove --force`.
   **Никогда не cherry-pick поверх checked-out ветки** — это двигает её указатель.
5. **Ветку, на которой стоит рабочее дерево, нельзя двигать:**
   `git branch -f <branch> <sha>` вернёт `fatal: cannot force update the branch
   used by worktree`.
6. **`git reflog show <branch>`** — спасение, когда потерял ветку: показывает
   все её предыдущие концы.

**Правило поведения:** в общем дереве любая операция, затрагивающая чужие
файлы (reset, checkout, stash, restore, clean), требует явного разрешения
Ивана. Мои коммиты делаю только по списку своих путей и только в своей ветке.

### Параллельная сессия в том же репо затирает правки — работай в worktree (02.10.2026)

**Симптом.** Начал массовую замену бренда (71 файл, `sed` по `src/ backend/src/`).
Через ~20 минут `git status` показал пусто по `src/`, а `src/lib/site.ts` снова
содержал старое значение — которое я уже заменял и проверил. `git reflog` показал
чужую активность: `checkout main → rebase start → cherry-pick ×3 → commit` от другой
сессии на ветке `perf/remove-suspense-gate-v2`. Чужая перебаза делает
`git checkout`/rebase по дереву, и незакоммиченные изменения в файлах,
которые она не трогала, **пропали без предупреждения**. Доки уцелели
(`git status` их показал), код — нет.

**Правило.** Если в репо, где я работаю, уже есть другая сессия
(другой агент, другая ветка, `git reflog` показывает активные
`checkout`/`rebase`, не совпадающие с моей задачей) — **не править в основном
рабочем дереве**. Создать отдельный worktree:

```bash
git worktree add /Users/ivanlusnikov/Documents/nameone-brand -b brand/<тема> HEAD
```

`git worktree add` с абсолютным путём обязателен: в этом рантайме
`cd ..` / относительные пути блокируются («Path traversal detected»).

Дальше работать в новом worktree, коммитить в свою ветку, в конце — не
удалять worktree, пока пользователь не смержит: чужая сессия его не видит
и не тронет, в отличие от общего дерева.

**Что перенести в новый worktree вручную:** всё, что я успел сделать до
переключения, — `cp` по абсолютным путям (доки), плюс повторить кодовые
правки с нуля (sed-скрипт воспроизводится за секунды).

**Что НЕ переносить:** `node_modules` — связать симлинком
(`ln -s /путь/к/основному/node_modules node_modules`), при `git add -A`
он попадёт в индекс, если не исключить. `git rm --cached node_modules`
и `.git/info/exclude` в worktree не работают (это файл, не каталог) —
проще перечислять каталоги явно: `git add -A src backend scripts tests docs`.

**Побочная польза.** Работа в отдельной ветке дала поймать реальную ошибку:
`sed` переименовал и **инфраструктурные** идентификаторы в `wrangler.toml`
(`name`, `database_name`, `bucket_name`) и `WORKER_NAME` в деплой-скрипте.
Проверка показала: воркер `rabochielisty-api` живой (`/healthz` → 200),
`database_id fb8cc87f-…` уже создан, R2-бакет существует. Массовая
замена бренда чуть не уронила прод-деплой. **Имя бренда и имена облачных
ресурсов — разные вещи, заменять надо только первое.**

### Работа в git worktree — правки уходят в соседний каталог (12.10.2026, nameone)

**Ситуация.** Из-за чужой незавершённой работы в рабочем папке понадобился
отдельный worktree: `git worktree add ../nameone-qr-fix -b fix/qr-form-review`.
Правки бэка я делал инструментом `edit` по пути **основного репозитория**
(`/Users/ivanlusnikov/Documents/nameone/backend/...`), а читать и запускать — в
worktree. Результат: файлы правились в двух местах одновременно, а тесты в
worktree падали со «старым» поведением, потому что видели незапатченный код.

**Как применять.**

1. После создания worktree **сразу** определить рабочий префикс и дальше
   использовать его во ВСЕХ `read`/`edit`/`write`/`bash cd`. Не «по памяти»,
   а каждый раз смотреть в вывод инструмента, какой путь он открыл.
2. Подстраховка: включить `cd ../nameone-qr-fix && git status --short` в тот же
   вызов, где идёт правка. Пустой список после правки означает, что пишу не туда.
3. Если правки уже разъехались: `git checkout -- <файлы>` в основном репозитории
   (предварительно убедиться через `git diff`, что там только мои изменения и
   ничего чужого), затем скопировать файлы в worktree.
4. Общий симптом: «я изменил, а тест показывает старое» — почти всегда про то,
   что правился не тот файл.

### В одном репозитории Иван гоняет несколько сессий сразу (12.10.2026)

**Рабочий режим чужих и общих изменений:**

1. Чужие незакоммиченные правки в `git add` не тащить и коммитом не закрывать.
   Свою работу фиксировать так, чтобы чужая версия осталась у чужих.
2. Чужие незавершённые ветки не дописывать.
3. **Чужие незакоммиченные файлы не чинить, не откатывать, не коммитить** — даже
   если они ломают сборку и даже если «очевидно, что там ошибка».
4. **Стенды гонять изолированно:** свои порты и свой персист-дир D1. Общий
   `npm run dev` деградирует до 404, когда параллельная сессия пересобирает
   `.next`, и на это уходит время.
5. **`.env` в этом репозитории смотрит в прод-API**, а `.dev.vars` содержит боевой
   ключ Resend — локальная проверка должна переопределять URL и запускать бэк без
   ключа, иначе реальное письмо уйдёт клиенту.

**Побочный эффект:** чужие сессии могут переписать мой файл в любой момент (cookie-домен
вернулся в `routes/auth.ts` через 15 минут после отката). Правки чужих файлов надо
подтверждать повторным чтением перед тем, как на них опираться.

### Не stash-ить чужую несохранённую работу без проверки (03.10.2026, nameone)

**Ситуация.** В рабочем дереве шёл чужой ребрендинг (69 файлов, «РабочиеЛисты
AI» → «УчЛист»). Чтобы сделать rebase своей ветки, я спрятал всё в
`git stash push -u`. Rebase прошёл, `git stash pop` применился, и я решил,
что часть вернулась: в дереве осталось 6 файлов, а помнил про 69. Оказалось,
что **ребрендинг был закоммичен в отдельную ветку `brand/uchlist-rename`**
(72 файла, коммит `21e67ac`). Ничего не пропало: `git status` показывал
остатки только потому, что ветка была переключена.

**Вывод, который надо было сделать ДО stash.** Прежде чем прибирать чужие
изменения, спросить `git branch -a` и `git log --all --oneline --grep="<ключевое
слово правки>"`. Незакоммиченное в дереве часто оказывается HEAD другой
ветки.

**Опасность `git stash pop` после rebase на другую базу.** Он применяет
диффы, и конфликтующие файлы молча не применяются (или применяются
частично), а `Dropped refs/stash@{0}` в выводе выглядит как «всё вернулось».
Проверять после pop надо не по отсутствию ошибок, а по дельте:
`git status --porcelain | wc -l` ДО stash и ПОСЛЕ pop должны совпадать
с точностью до своих файлов.

**Force-push запрещён → грязный MR пришлось пересобрать.** Ветка
`perf/remove-suspense-gate` отстала от `main` на 4 коммита, и в неё попали
чужие коммиты (фикс magic-link, фикс QR, строка ребрендинга). Rebase с
force-push нельзя, поэтому сделал новую ветку `perf/remove-suspense-gate-v2`
от актуального `main` + `cherry-pick` нужных коммитов, а старый MR закрыл.
**Вывод: перед первым коммитом в новой ветке делать `git fetch` и проверять,
что ветка от свежего `main`, а не от локального отстающего.**

**Ловушка при работе в залитом дереве.** Пока в рабочем дереве шёл чужой
ребрендинг с расходящимися ключами `localStorage` (`uchlist_gens_v1` в тесте
против `rabochielisty_gens_v1` в коде), полный прогон тестов локально давал
«692 зелёных» — то есть НЕ нашёл реально сломанный `form-runner.test.tsx`
(8 падающих тестов), потому что чужое изменение маскировало моё. Тесты
годится прогонять на чистом дереве, а не на залитом параллельной работой.

### Если чужой код льётся в то же рабочее дерево — работай в worktree (03.10.2026, nameone)

**Симптом.** В репозитории в момент сессии кто-то активно правил файлы:
`git status --porcelain` дал 43 файла на 16:59 и 65 на 17:20, mtime свежих
файлов — текущая минута. Плюс ветка `brand/uchlist-rename` была занята вторым
worktree.

**Что пошло не так.** `git checkout -b <new> origin/main` отказался («Please
commit your changes or stash them») — и это был последний шанс. Следом
`git cherry-pick` **успешно** выполнился в текущей ветке, потому что цепочка
`&&` упала не на первой команде. Чужой коммит уехал в чужую ветку
`perf/remove-suspense-gate-v2`, унаследовавшей чужие правки.

**Перед откатом** сравнить, что именно в тех файлах (diff по конкретному файлу),

### Массовая sed-замена бренда: проверяй, что вошло ВСЕ поддеревья (03.10.2026, nameone)

**Симптом.** После `sed` по списку `src backend/src backend/scripts scripts

### Build-time env теряется в CI — прод молча уходит в мок (03.10.2026, nameone)

**Симптом.** Иван открыл живую страницу входа: «ни ВК, ни Яндекс, ни ТГ не
подключены, зарегистрироваться никак нельзя». Кнопки соцсетей и правда были
захардкожены как `disabled` — но оказалось, что это только верхушка.

**Что было на самом деле.** Переменная `NEXT_PUBLIC_API_URL` читается
next'ом **на этапе сборки** и зашивается в бандл. В CI она не была задана
вообще (только `CLOUDFLARE_API_TOKEN` в secrets, никаких variables), поэтому
на проде `API_URL === ""`, и:
  * `src/lib/auth/api.ts` кидал `NO_API_URL` — форма входа не могла
    отправить ничего;
  * `src/lib/llm/index.ts` уходил в **локальный мок** — учитель получал
    правдоподобный, но выдуманный лист вместо сгенерированного.
Второе опаснее: мок-режим не падает, он «работает».

**Как проверить за 30 секунд, не открывая браузер.** Скачать js-чанки живого
сайта и поискать в них адрес API:
```bash
curl -s https://<host>/<route>/ -o p.html          # сначала со слешем,
                                                     # без слеша бывает 308
grep -o '_next/static/chunks/[^"]*\.js' p.html | sort -u > c.txt
: > all.js; for c in $(cat c.txt); do curl -s "https://<host>/$c" >> all.js; done
grep -o 'https://[a-z0-9.-]*workers\.dev' all.js | sort -u
```
Ноль вхождений = фронт не ходит в бэк вообще. Правило шире любого стека:
**любая `NEXT_PUBLIC_*`/`VITE_*`/`EXPO_PUBLIC_*` переменная проверяется на
живом бандле, а не «вроде задана в .env»** — в рантайме её уже не поменять.

**Что важно для отчёта.** «Кнопки соцсетей не подключены» — это факт, но
пользователю нельзя отвечать только этим: он пришёл с вопросом про вход, и
настоящая причина была в другом слое (письма не уходят из-за неподтверждённого
домена в Resend + фронт без адреса API). Докладывай слоями и называй, какой
слой чинится и что перестанет работать.

**Побочно — ребрендинг как источник поломок.** Тот же день: `main` смержил
ребрендинг, в котором отправитель писем сменился на несуществующий домен
(`noreply@uchlist.ru`). Resend начал отвечать 403 на каждую отправку, бэк
отвечал фронту `{ok:true}` (ошибка доставки глоталась), и страница показывала
«Проверьте почту» — письма не существовало. **Смена бренда обязана трогать всё,
где бренд уходит наружу: FROM письма, домен в Resend, ссылки в письме,
sitemap/canonical.** Проверять это `wrangler tail` на боевом воркере, а не
чтением кода.

### Порядок подключения роутов в Hono — ловушка заглушки-catch-all (03.10.2026, nameone)

**Симптом.** На боевом воркере `GET /api/turnstile/config` и `GET
/api/admin/stats` отдавали `501 {"code":"NOT_IMPLEMENTED","error":"Server-side
tracking ещё не реализован"}`. Роуты выглядели подключёнными, тесты на них
напрямую (через `app.request` с точным путём роутера) проходили.

**Причина.** В `src/routes/track.ts` заглушка объявлена как
`trackRouter.all("*")` и подключена так: `app.route("/api", trackRouter)`.
Любой обработчик с `*`, подключённый на префиксе `/api`, ловит **любой** путь
`/api/*`. Hono отдаёт запрос **первому совпавшему** обработчику и не идёт
дальше — все роуты, подключённые ПОСЛЕ заглушки, мертвы. `/api/llm/models`
работал только потому, что стоял выше.

**Правило.** Заглушки/catch-all/fallback подключать последними, с
комментарием-предупреждением прямо над строкой. Новый роут с префиксом
`/api/*` — всегда выше заглушки. Один и тот же префикс можно подключать
много раз (`/api/worksheets` дважды) — это ок, а вот `all("*")` на общем
префиксе — мина.

**Проверка на живом воркере** (быстрее тестов, ловит и порядок, и несовпадение
задеплоенного кода):
```bash
curl -s -o /dev/null -w "%{http_code}\n" https://<worker>/api/<path>
```
Сравнивать со соседним «заведомо живым» роутом: 501 на одном и 200 на другом
почти всегда = перехват.

**Регресс-тест, который стоит написать.** Не «роут отвечает», а «роут,
подключённый после заглушки, отвечает своим обработчиком» + «заглушка
по-прежнему отвечает на неизвестный путь». И **обязательно проверить, что тест
падает на старом порядке** (вернуть порядок временно, прогнать, убедиться в
падении, восстановить). Тест, который зелен и на сломанном коде, — хуже
отсутствия теста: он закрывает задачу, ни разу не сработав.

**Правило на будущее.** Как только в дереве есть незакоммиченная работа, о
которой ты не знаешь (или в репе параллельно работает кто-то ещё) — **не
переключать ветки и не stash**, а сразу работать в отдельном worktree:
```bash
git worktree add ../<repo>-wt-<задача> -b <branch> origin/main
ln -s <основа>/node_modules ../<repo>-wt-<задача>/node_modules   # для тестов
cd ../<repo>-wt-<задача> && git cherry-pick <старый-коммит>     # вместо rebase
```
Cherry-pick вместо rebase — потому что rebase требует чистого дерева, а оно
не чистое по определению. И отдельная проверка: `**/node_modules/` в
.gitignore со слэшем **не ловит симлинк-файл** — свой `ln -s` на node_modules
попадёт в коммит через `git add -A` (в моём случае так и вышло, поймал на
`git show --stat`). Добавлять `**/node_modules` без слэша.

### Пуш в `main` в nameone: чужие незакоммиченные правки часто уже в `origin/main` (03.10.2026)

**Симптом.** Рабочее дерево `nameone` на 65+ изменённых файлов выглядит как
«чужой ребрендинг в процессе». Прямой `git push origin main` падает:
`Updates were rejected because a pushed branch tip is behind its remote`.
Формулировка вводит в заблуждение — якобы у нас отстающий конец.

**Что на самом деле.** Все эти незакоммиченные правки — уже смержены в
origin/main (в моём случае ребрендинг РабочиеЛисты → УчЛист, коммит
`05a9e76`, плюс #22–#24). Локальная ветка отставала от main на 6 коммитов,
а дерево содержало изменения, которые в main уже есть. Коммитить «чужие
файлы» нельзя — они не чужие, они уже в main; коммит их снова = откат main.

**Правильный путь.**
1. `git fetch origin` и **сначала** сравнить базу:
   `git diff <моя-база> origin/main -- <мои файлы>`. Если main их переписал —
   переносить правки вручную, патч не поможет.
2. `git worktree add ../nameone-wt-<задача> -b feat/<задача> origin/main`
   + `ln -s <основа>/node_modules` для тестов.
3. **`git apply --3way` ненадёжен**: при конфликте в нескольких файлах он
   откатывает применение целиком, а часть файлов трогает без применения.
   Надёжнее копировать файлы целиком (`cp`) и **вручную возвращать правки
   main**, затёртые копированием. Откат заметен по тем же маркерам, что
   использовал раньше (бренд, дефолт домена, флаги фич, правила .gitignore).

**Ловушка при ручном переносе.** `git checkout -- .` в «грязном» worktree
откатывает в том числе только что сделанные правки — я так потерял работу
и переделывал. Перед откатом фиксировать, что уже применено.

**Проверка перед коммитом.** Сверять маркеры main, а не только свой diff:
дефолт `SITE_URL`, строки бренда, `MAGIC_LINK_READY`-подобные флаги,
`no-print` в футере, правила `.gitignore` из main. Затем `git diff --stat`
против HEAD: в индексе должны быть ровно мои файлы.

**Прод-тесты ходят на живой прод** (`E2E_BASE_URL` → pages.dev). Если там
форма ещё не задеплоена, тест красный независимо от локальной правки —
сначала прогонять против `npx serve out` локально, иначе вывод неверный.

### `wrangler deploy` без `--env` — это не «локально», а часто прод (04.10.2026, nameone)

**Симптом.** `wrangler deploy` отрабатывает, версия задеплоена, `healthz` отвечает —
и прод при этом живёт с development-переменными. Ничего не падает, поэтому легко пропустить.

**Почему.** Если в `wrangler.toml` секция `[vars]` и `[env.production]` описывают
ОДИН И ТОТ ЖЕ `name = "..."`, то деплой без `--env` перезаписывает именно
боевой воркер, только переменными из `[vars]`. В nameone так и было:
`ALLOW_DEV_MAGIC_URL=true`, `ALLOW_DEMO_PAYMENTS=true`,
`FRONTEND_URL=http://localhost:3000`. Тот же класс инцидента там же ловили
02.10.2026 — повторяемость и делает его опасным.

**Как правильно (дефолт на будущее).**
1. Перед любым деплоем воркера открыть `wrangler.toml` и посмотреть, **один ли
   `name` у `[vars]` и `[env.production]`**. Один — значит дефолтный деплой бьёт в бой.
2. В `package.json` деплой-прод делать `wrangler deploy --env production`, а
   не-бой назвать явно (`deploy:staging`), чтобы его нельзя было запустить по
   привычке. Второе имя работает лучше первого: ошибка становится видимой
   в команде, а не в проде.
3. После деплоя проверять не только `healthz`, а **сами опасные переменные**:
   `wrangler versions view <ID> --env production` печатает `[vars]` и список
   секретов — этого хватает, чтобы увидеть `APP_ENV=development` или
   `ALLOW_DEMO_PAYMENTS=true`.
4. Проверка CORS origin'ом — тоже рабочий признак: прод-домен есть в
   `access-control-allow-origin`, `localhost` отсутствует.

**Почему не поймали тесты.** Юнит-тесты видят только то, что передали в `env`.
Реальное окружение воркера видно исключительно через API Cloudflare — или через
`wrangler tail`, который ловит собственную проверку конфига воркера при
первом обращении.

### Приём: обещание в тексте проверять grep'ом по коду, а не на глаз

Самый дорогой класс дефектов на nameone — фичи, которые обещаны на странице,
но которых нет в продукте. Найдено 7 штук, каждая видна учителю сразу:

| Обещание в тексте | Что нашлось |
|---|---|
| «материалы проверяет методист, на жалобу ответит» | живого методиста нет вообще, есть только промпт самопроверки модели |
| «вопросы для беседы по фото: 5/50/200 наборов в месяц» | лимит нигде не применяется — ни во фронтенде, ни в бэкенде |
| «контрольные с критериями оценивания» | критерии не генерируются, есть только сам тип `control` |
| «история генераций 30 дней» | история в localStorage, обрезается по количеству записей, срока нет |
| «учеников: 5», «членов семьи: до 5» | таких фич в проекте нет вообще |
| «счётчик сбрасывается в полночь» | `resetUserDailyGenerations` объявлена в `backend/src/db/queries.ts`, но **ни разу не вызывается** |
| «1,44 млн токенов» в прайсе | язык для разработчика на странице с ценами; оставить «до 900 листов» |

**Как искать.** Для каждого глагола обещания из видимых текстов искать
реализацию: `grep -rn "<функция/компонент/поле>" src/ backend/src/`. Функция,
которая объявлена, но не вызывается ни разу, — это обещание без лимита.
Фича, которой нет нигде, — обещание без функции. Удалённый лимит убрали из
тарифа, обещание живой проверки заменили на честное «модель перепроверяет,
нашли ошибку — напишите в поддержку».

**Оставленное честно.** «Админка учителя», «Отчёты по классу», «API для
интеграции» закрыты прочерком во всех действующих тарифах и доступны только
в несуществующем «Школа» (запуск 2027) — такие строки трогать не нужно.

- «Назовите 3 средства связи предложений» (4 в ключе) → «Какое средство
  связи соединяет предложения „В доме было тепло. Я закрыл окно.“?»
- «Назовите основные элементы композиции» (5) → вопрос про экспозицию

Искать регуляркой по словам «Назовите|Перечислите|Приведите|Какие вы знаете»
и смотреть, сколько запятых в ключе. Псевдотермины («автономность»,
«информационная неграмотность») — та же болезнь: звучат умно, в программе их
нет.

### Приём: дубль вопроса между классами — ученик видит одно и то же дважды

Скрипт по `subjects` с группировкой по нормализованному `examples[].text`,
затем фильтр: одна и та же строка в разных `num` одного предмета. Найдено 19.
Часть — осмысленная прогрессия (типы придаточного в 7–8, пассив в 7–8, группы
инструментов в 4–5) — её не трогать. Часть между разными предметами
(география 5 и окружающий мир 2) — нормально. Чинить только мусор внутри
одного предмета: «бег на выносливость» в 2 и 5 классе физкультуры.

### Субагенты на nameone: давать таймер, иначе застревают на разведке

Дважды агент 8–10 минут создавал вспомогательные скрипты и не делал ни одной
правки. Оба раза работа была сделана оркестратором за 5–10 минут, потому что
данные к моменту делегирования уже были собраны. Правило: **сначала собрать
данные скриптом самому** (список файлов, точные строки, количество находок),
и только потом делегировать правку с готовым списком — иначе агент тратит
весь контекст на повторную разведку.

**Ловушка:** агент возвращает `git rm`/удаление временных скриптов, но его
скрипты попадают в коммит на параллельной сессии. Перед каждым коммитом
проверять `git status --porcelain` на `?? scripts/…` и удалять руками.

### Назывные конструкции и IT-жаргон: почему текст «читается не по-русски»

Иван указал на 4 фразы, которые выглядят как калька с англоязычного маркетинга.
Причина не в словах, а в конструкции: **предложение без глагола**.

| Было | Стало |
|---|---|
| «Точно по программе. Быстро. Проверяем ответы — отсеиваем явные ошибки.» | «Листы точно по программе. Делаются за 30 секунд. Проверяем ответы и отсеиваем явные ошибки.» |
| «1 075 тем / растёт» (счётчик, `sub="растёт"`) | «1 075 тем / и добавляются» |
| «Откройте любую — генератор сразу подхватит» | «Выберите тему — конструктор откроется с ней» |
| «УчЛист — узкоспециализированный инструмент для учителей» | «УчЛист сделан специально для учителей» |

Типовые признаки, которые надо искать:
- наречие как отдельное предложение («Быстро.») — в русском так не говорят;
- подпись-приписка без субъекта («растёт» под числом — что растёт?);
- местоимение без существительного («Откройте любую» — любую что?);
- глагол из айти-сленга: «подхватит», «задеплоим», «отрендерится», «сгенерирует»;
- канцелярит: «узкоспециализированный», «осуществлять», «в настоящий момент».

**Искать реже в `out/` по всему статику — слишком медленно** (7781 html, 633 МБ,
регулярки с matchAll не успевают). Быстрее и надёжнее: точечный `grep` по
`src/` + чтение видимого текста 6–8 ключевых страниц из `out/` скриптом,
который снимает теги и `<!-- -->`.

**Ловушка React.** В собранном HTML между текстом и выражением стоит
`<!-- -->`, поэтому наивная склейка даёт мусор: «Это 11 класс , предмет»,
«3 бесплатные генерации , без регистрации», «Актуальные темы по классам на .».
Перед выводом регексп обязательно удаляй `<!-- -->` — иначе половина
находок будет ложными.

### Плейсхолдер в юридическом документе — брак, а не мелочь

В согласии на обработку ПДн печаталось `ИП Лушников Иван (уточняется),
адрес: адрес регистрации (уточняется)` — дефолты из `src/lib/site.ts`.
Согласие с таким текстом неполно, а «(уточняется)» в документе читается как
черновик. Убрал: при незаданной переменной выводится только имя оператора,
без пустого «адрес: .». Полные реквизиты (ИНН, ОГРНИП, адрес) ставятся
через `NEXT_PUBLIC_OPERATOR_NAME` / `NEXT_PUBLIC_OPERATOR_ADDRESS`.

**Общее правило для этого репозитория:** любая строка со словом «уточняется»
в `src/app/legal/**` — это баг. Реквизиты либо проставлены, либо документ
не готов к публикации.

**Ложь о локализации.** В FAQ про фото стояло «Данные хранятся на серверах
в России», а политика конфиденциальности уже говорила честно «за пределами
РФ» (Cloudflare Workers + D1). Расхождение FAQ и оферты на одном сайте —
ровно то, за что суд спрашивает по фактическому соблюдению локализации.
Правь оба места от одного факта, а не по одному.

### Параллельные воркеры в одной репе стирают друг друга (05.10.2026, nameone)

Два воркера, которым я дал непересекающиеся участки ФАЙЛОВ, работают в одном
рабочем дереве. Один из них догадался проредить дерево и запустил `git clean` —
это удалило незакоммиченные файлы другого воркера. Дважды. Он же переключил ветку
и сломал другому всю сборку. Чужие правки пришлось восстанавливать вручную.

**Правило на будущее — три части:**

1. **Разделение по файлам недостаточно.** Оно решает конфликт правки, но не
   конфликт окружения. Нужен запрет на команды, меняющие дерево целиком:
   `git clean`, `git checkout`, `git reset`, `git restore`, `git stash`. В
   промпте воркеру писать это прямо, а не оставлять на волю разумения.
2. **Перед запуском воркеров — `git status`.** Если в дереве есть незакоммиченные
   правки, не мои, значит в репе работает кто-то ещё (другая сессия). Это надо
   назвать вслух пользователю и разнести по веткам, а не начинать работу поверх.
3. **Воркеры не коммитят и не пушат.** Иначе два индекса на одной ветке. Коммит
   делаю я после приёмки — так правки обоих собираются одним куском.

**Страховка, которая спасла всё:** первым делом `git add -A && git commit` в
ветку-«страховку». Всё, что было в дереве, включая чужие правки, оказалось в
git и не потерялось. Это дешёвая операция, делать её до любой параллельной
работы.
